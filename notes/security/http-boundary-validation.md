# 프록시와 앱이 공유해야 할 HTTP 해석 경계

## 사용자 요청의 Host를 서비스의 공식 주소로 믿으면 안 됩니다

비밀번호 재설정 메일의 링크를 `request.host + path`로 만든다고 합시다. Host가 공격자가 선택할 수 있는 요청 입력인데도 그대로 쓰면 공식 메일 안에 다른 사이트 주소가 들어갈 수 있습니다. TLS 인증서가 우리 서버의 것이라는 사실은 요청 헤더가 서비스의 신뢰된 설정이라는 뜻이 아닙니다.

공식 외부 링크는 등록된 origin에서 만듭니다. 여러 고객 도메인을 지원하면 검증된 테넌트·등록 도메인 매핑에서 선택하며, 현재 Host가 그 테넌트의 허용 도메인인지 확인합니다. 캐시 키·절대 redirect·OAuth callback에도 같은 신뢰 구분이 필요합니다.

## 전달 헤더는 프록시가 검증해서 작성할 때만 근거가 됩니다

| 값 | 신뢰할 조건 | 잘못된 가정 |
| --- | --- | --- |
| Host·`:authority` | 허용 가상 호스트와 프로토콜 일관성 검사 | 서버 공식 origin과 항상 같음 |
| X-Forwarded-Host | 신뢰 프록시가 외부값 제거 후 재작성 | 이름에 Forwarded가 있으니 안전함 |
| Forwarded의 client 주소 | 실제 hop·프록시 주소 정책에 맞게 해석 | 맨 앞 주소가 무조건 실제 사용자 |
| 등록 origin | 관리 경로에서 검증한 설정 | 임의 요청값으로 즉시 갱신 가능 |

프록시 앞에 프록시가 더 추가되거나 앱 직접 접근이 열리면 고정 hop 수만 세는 정책이 깨질 수 있습니다. 누가 헤더를 추가·제거하는지 실제 경로를 그린 뒤 신뢰할 peer를 제한합니다. backend 직접 경로는 막거나 같은 검증을 적용합니다. 여러 헤더에 상충한 host가 왔을 때 한쪽은 캐시 키, 다른 쪽은 라우팅에 사용하는 불일치를 피합니다.

## 요청 경계를 다르게 읽으면 다음 요청도 바뀝니다

HTTP 연결 재사용에서는 한 요청이 끝난 바이트 뒤에 다음 요청이 이어집니다. 프런트 프록시가 길이를 L1로 읽고 백엔드가 L2로 읽으면, 한쪽이 본문으로 본 바이트를 다른 쪽은 다음 요청으로 해석할 수 있습니다. request smuggling의 핵심은 이 **메시지 경계 불일치**입니다. 요청 본문 내용의 문자열 필터만으로 고칠 수 없습니다.

Content-Length·Transfer-Encoding의 충돌, 중복 길이값, 잘못된 헤더 문법과 줄바꿈, HTTP/2에서 HTTP/1.1로의 변환 등 각 제품의 파서 계약을 검토합니다. 모호한 요청을 한 계층만 관대하게 수락하지 않도록 안전한 거절·정규화 정책을 맞춥니다. 단순히 “HTTP/2를 켰다”는 것으로 뒤쪽 변환 경계까지 안전해지는 것은 아닙니다.

## 거절 뒤 연결 상태도 정리해야 합니다

파서가 오류를 발견했어도 남은 바이트 위치를 확정할 수 없는 연결을 풀에 돌려주면 다음 사용자의 요청에 영향을 줄 수 있습니다. 모호한 경계의 오류는 안전하게 연결을 폐기하고, 프런트·백엔드 모두 같은 정책을 적용합니다. timeout·본문 제한을 둬도 파서 의미의 불일치를 없애지는 못합니다.

라이브러리·프록시의 보안 업데이트와 권장 설정을 적용하고, 한 제품의 단독 파서 시험만으로 실제 전체 체인을 검증했다고 보지 않습니다. WAF가 보는 문법과 실제 앱이 보는 문법이 다르면 탐지 설정에도 사각지대가 생깁니다.

## 허가된 격리 경로에서 양쪽 관찰을 대조합니다

테스트용 프록시·backend 체인에서 등록되지 않은 Host, 상충하는 전달 헤더, 직접 접근을 검사합니다. 재설정 링크·redirect·캐시 항목이 신뢰된 origin만 사용하는지 확인합니다. 실사용자 메일 대신 로컬 수신함을 사용합니다.

경계 검증은 제품의 공식 회귀 테스트·안전한 합성 입력을 사용해 프런트와 백엔드가 같은 요청 수·대상·본문 길이를 관찰하는지 대조합니다. 오류 후 연결 재사용이 없는지도 확인합니다. 운영 공유 연결에 임의 공격 트래픽을 보내지 않습니다. 이 노트는 방어 설계이며 실제 프록시 체인에 대한 침투시험 결과가 아닙니다.
