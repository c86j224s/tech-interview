# TLS·QUIC 0-RTT의 재생과 업무 멱등성

## 암호화한 주문도 두 번 처리될 수 있습니다

이전 연결 정보를 사용해 핸드셰이크 완료 전에 요청을 보내면 재연결 지연을 줄일 수 있습니다. TLS 1.3 early data와 이를 사용하는 QUIC의 0-RTT가 제공하는 이점입니다. 그러나 early data에는 재생 가능성이라는 별도 조건이 있습니다. 기밀성과 무결성이 있다고 논리 요청이 한 번만 실행되는 것은 아닙니다.

같은 주문 변경이 두 서버에서 수락되면 암호문이 변조되지 않았어도 재고가 두 번 줄 수 있습니다. 클라이언트가 요청을 한 번 만들었다는 사실과 서버가 한 번만 적용했다는 보장은 서로 다릅니다.

## 허용 API를 실제 부수 효과로 분류합니다

| 작업 | 판단할 것 | 선택 예 |
| --- | --- | --- |
| 순수 공개 조회 | 반복해도 민감 효과가 없는가 | 정책 아래 early data 허용 |
| 최초 조회 보상 지급 | GET이지만 상태 변경이 있는가 | early data 거절 또는 효과 멱등화 |
| 주문·결제 생성 | 중복 변경·외부 결제가 가능한가 | 정상 handshake 뒤 처리 우선 |
| 같은 논리 변경 재시도 | 안정적 키·거래·결과 보관이 있는가 | 검증된 범위에서만 허용 |

GET이라는 메서드 이름만으로 안전하다고 보지 않습니다. 분석 카운터 같은 부수 효과도 반복에 대한 허용 범위를 따로 정합니다. PUT이 멱등 메서드로 분류된다고 해서 앱 내부의 알림 발송·차감까지 자동으로 한 번이 되는 것도 아닙니다.

## 전송의 재생 방지 상태가 어디까지 공유되는지 봅니다

`anti-replay` 상태는 같은 early data를 다시 받아들이지 않도록 재수락 여부를 기록하고 거절하는 데 쓰입니다. 그 상태가 한 프로세스 메모리에만 있으면 다른 지역 서버나 재시작한 서버가 같은 ticket을 다시 받을 수 있으므로, ticket을 어디까지 수락하는지, 상태를 어디와 얼마나 오래 공유하는지, 시계와 장애 시 정책이 무엇인지가 실제 보장 범위를 정합니다.

특정 TLS 라이브러리에 anti-replay 기능이 있어도 그 기능이 전체 다중 지역 서비스의 모든 실행 경계에 동일한 효과를 준다고 볼 수는 없습니다.

## Early data 거절 뒤에도 같은 논리 요청입니다

서버가 early data를 거절하면 클라이언트는 핸드셰이크 완료 뒤 정상 요청으로 재시도할 수 있습니다. HTTP의 425 Too Early를 사용하는 경로도 구현·프록시 지원과 함께 확인합니다. 거절 후 retry가 또 early data로 나가지 않도록 해야 하며 새 논리 주문을 생성해서는 안 됩니다.

일부 처리 여부가 불확실하면 안정된 요청 키와 결과 조회로 복구합니다. 전송 계층이 거절했다고 알려 주는 정확한 단계와 애플리케이션이 이미 처리했는지를 섞지 않습니다. 비멱등 변경은 처음부터 정상 handshake 뒤에만 처리하고 지연은 연결 재사용·다른 최적화로 줄이는 선택이 더 단순할 수 있습니다.

## 재생·재시작·거절 후 반복을 따로 시험합니다

관리하는 격리 환경에서 동일 요청의 반복 전달, 두 서버 수락, anti-replay 상태 재시작, early data 거절 후 일반 요청을 재현합니다. 최종 원장과 외부 부수 효과가 정책대로 한 번인지 확인합니다. 단순 HTTP 성공 응답 수와 논리 효과 수를 구분합니다.

허용 API 목록·전송 라이브러리·배포 토폴로지·멱등 기록 보관 범위를 문서화합니다. 이 노트는 보장 범위 설명이며 실제 QUIC 서버에 재생 트래픽을 실행한 결과는 아닙니다.
