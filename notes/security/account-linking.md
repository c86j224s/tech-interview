# 외부 신원과 계정 연결

## 이메일 일치 기반 계정 통합의 위험

우리 서비스의 계정 A가 이메일 하나를 가지고 있고, 새 소셜 로그인 응답에도 같은 이메일이 들어 있다고 합시다. 이 두 문자열의 일치는 공급자가 같은 사람을 같은 신뢰 수준으로 확인했다는 증거가 아닙니다. 이메일은 변경·재할당될 수 있고 공급자마다 검증 의미도 다릅니다.

외부 로그인 신원에서 `issuer`는 어떤 공급자가 발급했는지를 나타내는 식별자이고, `subject`는 그 공급자가 정한 범위에서 사용자를 가리키는 식별자입니다. 따라서 서버에는 검증한 **issuer와 subject의 쌍**을 저장하고, `subject`만 키로 쓰지 않아야 서로 다른 공급자의 같은 문자열이 충돌하지 않습니다.

공급자 URL을 임의로 정규화하거나 이메일을 소문자로 바꾸는 규칙은 프로토콜이 정의한 신원 비교를 대신할 수 없습니다. 공급자에 따라 `subject`가 client 또는 sector 범위별로 달라질 수 있으므로 client를 옮길 때도 이메일 자동 병합이 아니라 별도 신원 이전 절차를 거쳐야 합니다.

## 계정 연결을 구성하는 세 가지 증거

| 증거 | 확인할 질문 | 충분하지 않은 대체값 |
| --- | --- | --- |
| 기존 계정 접근 | 현재 계정 A의 사용자가 민감 변경을 승인했는가 | 오래된 세션이 존재함 |
| 새 로그인 수단 소유 | 공급자 P의 신원 S를 새로 증명했는가 | 같은 이메일을 주장함 |
| 연결 의도 | 그 증명을 A의 로그인 수단 추가에 쓰기로 했는가 | 일반 로그인 callback 도착 |

계정 연결은 일반 로그인과 다른 작업이므로 별도의 `purpose`로 기록합니다. 사용자가 A에서 연결을 시작하면 서버는 A, 그때의 현재 세션, 재인증 시각, 선택한 공급자, 만료 시각, 한 번만 사용할 `state`를 하나의 시도에 묶습니다. callback이 돌아왔을 때 브라우저의 현재 계정이 B라면 callback 자체만 보고 B에 연결하지 않고, 시작 시 저장한 A·세션과 맞는지 먼저 비교합니다. 값이 맞지 않으면 연결을 거절하고 사용자가 올바른 계정에서 다시 시작하게 해야 합니다.

## 유일성 제약과 저장 경계

두 계정이 동시에 같은 외부 신원을 연결하려고 할 수 있습니다. 둘 다 먼저 조회했을 때 연결이 없다는 결과를 얻더라도 최종 저장은 하나만 성공해야 합니다. 신원 테이블의 `(issuer, subject)`에 unique 제약을 두고 연결 시도 소비·연결 생성·계정 보안 버전 변경을 가능한 한 같은 거래로 처리합니다.

```text
begin transaction
  lock and validate attempt T:
      purpose=link, account=A, session=original, not expired, not consumed
  validate current account security state and required reauthentication
  insert external_identity(P, S, A) with unique(P, S)
  mark T consumed
  increment A.security_version
  append security notification to outbox
commit
```

이미 A에 연결되어 있으면 정책에 따라 기존 결과를 보여 줄 수 있습니다. 다른 계정 B에 연결되어 있으면 조용히 옮기거나 두 계정을 합치지 않습니다. 별도 계정 병합은 양쪽 소유권·데이터 충돌·복구·감사까지 필요한 더 큰 변경입니다. 사용자에게 B의 상세 정보를 노출하지 않고 충돌을 설명해야 합니다.

## 연결 이후 기존 세션의 재평가

새 로그인 수단을 추가하면 앞으로 계정에 들어올 경로가 늘어납니다. 이미 탈취된 세션이 공격자의 로그인 수단을 추가하는 지속 접근 경로가 되지 않도록 최근의 적절한 재인증을 요구하고 기존 채널에 알립니다. 알림 발송 자체는 소유권 증명이 아닙니다.

수단을 추가하거나 삭제한 뒤에는 현재 세션 ID를 교체하거나 인증 강도와 계정의 보안 버전을 갱신하고, 다른 기기 세션을 유지할지 회수할지를 정책으로 정합니다. 보안 버전을 올려도 각 API가 그 값을 확인하지 않으면 기존 access token은 즉시 막히지 않으므로, 버전 갱신과 실제 차단 지점을 함께 확인해야 합니다. 약한 복구로 돌아온 세션이라면 새 강한 자격 등록을 곧바로 허용하지 않을 수 있습니다.

연결 해제에서는 마지막 로그인 수단인지 확인합니다. 비밀번호도 없고 다른 수단도 없는 계정에서 마지막 공급자를 제거하면 정상 사용자를 잠글 수 있습니다. 대체 수단 등록·검증을 먼저 완료하거나 명시적인 계정 종료 흐름으로 나눕니다. 이 검사도 동시에 두 수단을 삭제하는 경쟁을 막도록 같은 계정의 변경을 직렬화해야 합니다.

## 순서 변경 시나리오 기반 확인

A에서 연결을 시작한 뒤 B로 로그인하고 callback을 보내는 경우, 두 계정이 같은 외부 신원을 동시에 연결하는 경우, 같은 callback 재전송을 시험합니다. 기대 결과는 시작 계정 바뀜 거절·유일한 연결·중복 소비 방지입니다.

기존 세션 탈취를 가정한 테스트에서는 재인증 없이 수단 추가가 되는지, 복구 직후 제한이 유지되는지, 알림·회수가 실패했을 때 기록과 재처리가 남는지 봅니다. 이메일 변경이나 공급자 client 이전에서 계정이 뜻하지 않게 합쳐지지 않는 것도 확인해야 합니다. 이 검증 목록은 실제 운영 계정이 아니라 테스트 계정으로 수행할 절차입니다.
