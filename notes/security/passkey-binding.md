# 패스키의 사이트 바인딩과 서버 검증

## 다른 사이트에 같은 비밀번호를 입력하는 구조를 바꿉니다

비밀번호는 사람이 어떤 입력 칸에든 복사할 수 있는 공유 비밀입니다. 패스키는 relying party에 묶인 공개키 자격을 사용해 서버가 낸 challenge에 대한 서명 증명을 만들게 합니다. 브라우저와 인증기가 사이트 범위를 함께 제한하므로, 가짜 사이트에 진짜 서비스 비밀번호를 입력하는 식의 피싱을 줄입니다.

하지만 프런트엔드가 `success=true`를 보냈다고 인증이 끝나는 것은 아닙니다. 서버는 실제 assertion의 서명과 요청 문맥을 검증하고, 그 공개키가 어느 계정에 등록된 것인지 확인해야 합니다.

## Origin과 RP ID는 다른 값입니다

| 값 | 예시 | 서버에서의 역할 |
| --- | --- | --- |
| origin | `https://login.example.com` | 허용된 웹 출처인지 정확히 확인 |
| RP ID | `example.com` | 자격이 속한 relying party 범위와 rpIdHash 검증 |
| challenge | 시도별 예측 불가능한 값 | 이번 요청에 대한 증명인지 확인 |
| credential ID | 등록된 공개키를 찾는 식별자 | 해당 계정·자격 상태에 연결 |

RP ID는 origin 전체 URL과 같지 않습니다. 일반 웹 문맥에서는 origin의 유효 도메인과 프로토콜이 허용하는 상위 도메인 관계를 따릅니다. 임의의 다른 사이트나 public suffix를 쓰는 규칙이 아닙니다. 정확한 플랫폼·교차 origin·네이티브 앱 프로파일은 검증된 WebAuthn 라이브러리와 해당 규칙을 따릅니다.

기대 origin을 요청의 임의 Host나 Origin 헤더에서 그대로 만들면 공격자가 기대값을 선택하게 됩니다. 배포된 서비스의 신뢰 설정에서 정하고, 개발 환경용 예외가 운영 허용 목록에 남지 않게 합니다.

## 서명은 요청 데이터와 인증기 데이터를 함께 묶습니다

일반적인 WebAuthn assertion에서 검증 서명 입력은 `authenticatorData || SHA256(clientDataJSON)`입니다. clientDataJSON에 요청 유형·challenge·origin 등이 있고, authenticatorData에는 RP ID 해시와 사용자 존재·확인 플래그 등 정보가 있습니다. JSON을 임의로 재직렬화한 바이트 대신 프로토콜이 정한 원문 바이트를 사용합니다.

challenge의 만료·미사용·로그인 또는 등록 용도를 확인하고 같은 challenge가 두 요청에서 세션 발급에 재사용되지 않도록 소비를 원자화합니다. 사용자 존재 UP와 사용자 확인 UV는 다른 플래그입니다. 민감 작업에 UV를 요구한다면 실제 검증 결과가 그 요구를 만족해야 합니다. UI에 지문 아이콘이 보였다는 관찰로 대신하지 않습니다.

## 등록은 기존 계정의 소유권 변경입니다

로그인은 이미 등록된 공개키로 증명하는 흐름이고, 등록은 새 공개키를 계정에 추가하는 흐름입니다. 등록 요청이 보낸 account ID를 그대로 믿거나 약한 세션에서 무제한 새 자격을 추가하면 강한 서명 검증도 도움이 되지 않습니다. 기존 계정의 적절한 재인증과 일회성 등록 시도를 결합합니다.

동기화된 패스키와 한 기기에 바인딩된 자격은 복구·백업 특성이 다릅니다. 서명 카운터도 모든 동기화 자격에서 엄격하게 증가한다고 가정하지 않습니다. 카운터와 백업 관련 신호의 처리 정책은 라이브러리·인증기 특성과 맞춰야 하며, 감소 하나만으로 모든 계정을 영구 차단하는 단순 정책은 오탐을 만들 수 있습니다.

## 세션 탈취와 약한 복구는 별도 문제입니다

패스키로 로그인했어도 발급된 세션 쿠키가 탈취되거나 이미 허용된 브라우저에서 악성 동작이 일어나면 자원 인가와 세션 회수가 필요합니다. 이메일 복구만으로 새 패스키 등록을 열어 주면 로그인 입구의 피싱 저항이 복구 입구에서 약해집니다. 자격 등록·삭제·분실·동기화 복구를 함께 설계합니다.

가상 인증기와 테스트 계정으로 다른 origin, 다른 RP ID, challenge 재사용·만료, 잘못된 공개키, UV 불충족, 사용자 취소를 시험합니다. 정상 등록 뒤 로그인뿐 아니라 다른 계정에 같은 자격을 잘못 연결하지 않는지도 검사합니다. 이 노트는 프로토콜 검증 설명이며 실제 인증기나 WebAuthn 브라우저 테스트를 실행한 결과는 아닙니다.
