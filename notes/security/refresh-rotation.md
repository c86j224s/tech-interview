# 갱신 토큰 회전의 원자성과 응답 유실

## 두 탭의 정상 요청도 옛 토큰 재사용으로 보입니다

브라우저의 탭 A와 B가 같은 refresh token R7을 보관하고 있다가 동시에 갱신한다고 합시다. A가 먼저 성공해 R8을 받으면 B의 R7은 이미 소비된 토큰입니다. 서버 입장에서는 이 요청이 정상 탭의 늦은 갱신인지, 탈취한 R7을 재생한 것인지 bearer만 보고 완벽히 구분할 수 없습니다.

**회전**은 갱신 성공 때 이전 토큰을 소비하고 후속 토큰으로 바꾸는 과정입니다. 재사용 탐지는 이 전환 이력을 이용하지만, 정상 동시성과 응답 유실의 복구 정책까지 자동으로 결정해 주지는 않습니다.

## 계열의 현재 상태는 한 번만 바뀌어야 합니다

서버에 family F, 기기 세션 S, 현재 버전 7, R7의 검증용 해시, 만료·회수 상태를 둔다고 합시다. 두 worker가 모두 먼저 검증에 성공할 수 있어도 최종 전환은 조건부 갱신으로 하나만 허용해야 합니다.

```text
begin transaction
  load and lock family F
  require active session S and active account version
  require current_version = 7 and hash_matches(R7)
  generate R8 and its verifier hash
  mark R7 consumed; set current_version = 8
  store hash(R8), expiry, predecessor relation
  optionally store encrypted short-lived retry result
commit
return access_token, R8
```

이 코드는 상태 전이를 보여 주는 슈도코드입니다. 실제 토큰 생성·비교에는 암호학적 난수와 검증된 구현을 사용하고, DB 실패 시 응답으로 미커밋 토큰을 성공 반환하지 않습니다. 서로 다른 서버 인스턴스도 같은 권위 상태에 조건부 전환을 적용해야 합니다. 한 프로세스의 mutex로는 충분하지 않습니다.

## 해시는 발급한 토큰 원문을 돌려주지 못합니다

전환을 커밋한 뒤 A로 가는 응답이 유실되면 A는 여전히 R7만 압니다. 서버가 R8의 해시만 저장했다면 R8을 역산해 재전달할 수 없습니다. 해시는 후보 검증을 위한 것이지 발급 결과의 백업이 아닙니다.

| 복구 선택 | 필요한 상태 | 받아들이는 비용 |
| --- | --- | --- |
| 재로그인 요구 | 소비 이력·회수 상태 | 정상 응답 유실에도 사용자 개입 |
| 제한적 동일 결과 재전달 | 암호화한 결과·요청 결합·짧은 TTL | 민감 원문 보관과 재생 창 |
| 옛 토큰 무제한 허용 | 사실상 회전 경계 없음 | 탈취 재생 탐지 약화로 부적절 |

재전달을 선택하면 원래 검증된 세션·계열·요청 ID·입력과 결과를 묶고 짧은 시간과 횟수로 제한합니다. 요청 ID와 IP·User-Agent는 복제될 수 있으므로 독립적인 기기 소유 증명이 아닙니다. 더 강한 sender binding이 필요한지는 프로토콜 지원과 위협 모델로 판단합니다. 암호화 결과 캐시는 키 접근 통제·폐기·로그 비노출까지 포함한 추가 비밀 저장소입니다.

## 클라이언트 조정은 충돌을 줄이고 서버가 최종 결정을 합니다

탭 하나에서 refresh를 맡고 다른 탭이 완료를 기다리도록 브라우저의 공유 조정 수단을 사용할 수 있습니다. 그러나 메모리 변수 하나는 탭마다 따로 존재하고, 리더 탭 종료·메시지 유실·오래된 응답 도착이 생깁니다. 조정자를 사용해도 서버의 원자 소비 검사를 제거하지 않습니다.

클라이언트는 늦은 R7 기반 결과가 더 최신인 R9 상태를 덮지 않도록 요청 세대와 갱신 순서를 관리합니다. bearer 원문을 탭 간 메시지로 무조건 방송하지 말고 보관 구조와 노출 경계를 정합니다. 각 기기는 별도 family로 나눌 수 있어 다른 기기의 정상 갱신까지 하나로 직렬화할 필요는 없습니다.

## 의심되는 재사용은 어떤 범위를 끊을지 결정합니다

유예 범위를 벗어난 옛 토큰 사용이나 계열 복제 신호가 보이면 해당 family를 회수하고 재인증을 요구할 수 있습니다. 계정 전체 침해 근거가 있으면 더 넓게 회수합니다. 정상 동시 갱신 하나를 무조건 계정 전체 침해로 단정하면 사용성이 나빠지고, 반대로 모든 재사용을 정상이라고 허용하면 회전 목적을 잃습니다.

refresh family 회수는 이미 발급한 access token을 자동으로 없애지 않습니다. 즉시 차단이 필요한 API는 세션·계정 버전을 현재 상태와 비교하고, 그렇지 않은 서비스는 짧은 access token의 잔여 수명만큼 허용 지연을 인정해야 합니다.

## 성공 응답이 없는 성공을 시험합니다

두 worker가 R7 검증을 동시에 끝내도록 한 뒤 커밋 성공이 하나인지 확인합니다. 이어서 커밋 직후 응답을 버리고 다른 서버로 같은 요청을 재전송합니다. 정책이 재전달이면 동일한 결과만 제한적으로 돌아와야 하고, 재로그인이면 새 후속 계열이 생기지 않아야 합니다.

유예 만료·계열 회수·암호화 결과 만료·탭 리더 종료·늦은 응답 덮어쓰기를 따로 검사합니다. 로그에는 family·버전·판정 사유를 남기되 토큰과 결과 원문은 제외합니다. 여기서의 경쟁 순서는 설계 예제이며 실제 브라우저 인증 제품을 실행한 검증 결과는 아닙니다.
