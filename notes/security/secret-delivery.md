# 비밀값 전달·재읽기·장애 시 유효 기간

## Base64는 Git에 올려도 되는 암호화가 아닙니다

Kubernetes Secret의 data 값을 base64로 바꾸면 사람이 바로 읽기 어려워 보이지만 누구나 되돌릴 수 있습니다. 비밀값을 그대로 인코딩해 Git에 넣으면 저장소·포크·캐시·로그를 통해 원문이 노출된 것과 다르지 않습니다. 나중 커밋에서 지워도 이미 복제된 값은 회수되지 않습니다.

GitOps에서는 암호화된 선언을 저장하고 복호화 권한을 배포 환경에만 주거나, 외부 비밀 저장소의 이름·버전을 참조하게 할 수 있습니다. 어느 방식이든 Git을 읽는 권한과 운영 비밀을 해독·조회하는 권한을 분리해야 합니다. base64 Secret을 API 서버가 받았다는 사실만으로 저장소 암호화·RBAC·노드 접근이 모두 안전해지는 것은 아닙니다.

## 전달 경로별로 누구에게 원문이 보이는지 추적합니다

| 경로 | 필요한 통제 | 자주 빠지는 노출 |
| --- | --- | --- |
| Git의 암호문 | KMS·복호화 주체 분리 | CI가 평문 diff 출력 |
| 외부 Secret 참조 | workload별 최소 조회 권한 | 모든 namespace 공용 자격 |
| 배포 프로세스 | 신뢰된 배포 코드·로그 마스킹 | 비신뢰 PR에서 운영 자격 사용 |
| 앱 런타임 | 필요한 프로세스만 접근 | crash dump·환경 출력·디버그 API |

비밀을 저장소에서 안전하게 꺼내도 빌드 이미지 레이어나 테스트 snapshot에 남기면 전달 경계가 다시 열립니다. 비신뢰 PR의 스크립트에 운영 비밀을 주지 않고 검증과 배포 실행 주체를 분리합니다. Secret 읽기 권한은 다른 서비스의 자격 획득 권한이 될 수 있으므로 이름만 보고 저위험 권한으로 취급하지 않습니다.

## 파일이 바뀐 시각과 실제 사용 키가 바뀐 시각은 다릅니다

환경 변수는 일반적으로 프로세스 시작 시 설정되므로 Secret 객체를 바꿨다고 기존 프로세스 환경이 자동으로 바뀌지 않습니다. 재시작·롤링 교체가 필요할 수 있습니다. 마운트 파일은 플랫폼이 갱신하더라도 앱이 처음 읽은 문자열이나 열린 핸들·기존 SDK client를 계속 사용하면 호출은 옛 키로 나갑니다.

Kubernetes의 Secret volume 갱신은 전파 지연이 있으며 subPath 마운트는 자동 갱신 대상이 아닌 제약이 있습니다. 원자적 파일 교체에서는 옛 파일 핸들이 이전 inode를 계속 가리킬 수 있습니다. 파일 변경 감지를 구현할 때 파일 한 번 읽기와 영구 핸들 유지의 차이를 확인해야 합니다.

## 저장소 장애가 새 신뢰를 만드는 이유는 아닙니다

마지막 정상값을 사용하는 정책은 이미 검증된 자격의 제한적 재사용입니다. 처음 시작한 인스턴스에 자격이 없거나 새로운 고권한 작업에 필요한 증명이 없으면 임의 기본값·평문 fallback으로 통과시키지 않습니다.

예를 들어 자격 원래 만료까지 10분이고 정책이 마지막 확인 후 최대 3분 stale을 허용한다면 실제 사용 기한은 둘 중 먼저 오는 때입니다. 이것은 예시 정책이며 적절한 시간은 자산·회수 요구로 정합니다. 이미 회수됐다는 신호가 있으면 저장소가 불안정하다는 이유로 옛 자격을 다시 살리지 않습니다. 저위험 기존 조회와 신규 관리자 작업을 같은 fail-open 정책으로 묶지 않습니다.

복구 시 모든 인스턴스가 동시에 조회하지 않도록 jitter·backoff·공유 갱신을 적용합니다. 최신 발급·회수 버전을 확인하고 원문 비밀을 로그나 임시 설정 파일에 복사해 장애를 우회하지 않습니다.

## 정상 교체와 소비자의 적용을 함께 시험합니다

새 키를 받아들이는 검증자를 먼저 준비한 뒤 소비자를 전환하고, 환경 변수 프로세스·파일 재읽기 프로세스·장기 SDK client 각각의 실제 호출 키 버전을 관찰합니다. 로그에는 키 원문 대신 버전과 사용 성공·실패만 남깁니다.

저장소 중단·파일 일부 오류·짝이 안 맞는 인증서·재시작·subPath·만료를 테스트 배포에서 재현합니다. 새 값을 읽었다는 로그만으로 완료하지 않고 구 키 폐기 뒤에도 모든 허용 경로가 정상이며 금지된 옛 자격은 실패하는지 확인합니다. 이 노트는 배포 설계 설명이며 실제 Kubernetes 클러스터에서 실행한 결과는 아닙니다.
