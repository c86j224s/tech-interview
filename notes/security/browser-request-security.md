# 쿠키 요청 위조와 스크립트 실행의 다른 경계

## 남의 사이트가 보낸 요청과 우리 사이트에서 실행된 코드는 다릅니다

사용자가 은행에 로그인한 상태에서 다른 사이트를 방문했다고 합시다. 그 사이트가 은행으로 상태 변경 요청을 보내고 브라우저가 은행 쿠키를 자동 첨부하면, 서버가 사용자 의도를 확인하지 않을 때 문제가 됩니다. 이것이 CSRF의 전형적인 경계입니다. 공격자가 응답을 읽을 수 있어야만 성립하는 것은 아닙니다.

반면 게시물의 비신뢰 입력이 우리 사이트의 스크립트로 실행되면 XSS입니다. 같은 origin에서 실행되는 코드는 사용자의 세션으로 요청하거나 화면을 바꿀 수 있습니다. HttpOnly 쿠키의 원문을 직접 읽지 못하더라도 피해가 남습니다. 따라서 CSRF와 XSS는 한 설정으로 함께 해결되는 문제가 아닙니다.

## Site와 origin을 구분해야 SameSite를 이해할 수 있습니다

origin은 scheme·host·port로 구분합니다. 현대 브라우저의 schemeful site 판단은 대체로 scheme과 등록 가능한 도메인을 기준으로 하므로 서로 다른 서브도메인이 cross-origin이면서 same-site일 수 있습니다. 허술한 형제 서브도메인을 신뢰할 수 없다면 SameSite만으로 모든 요청 위조를 막는다고 보지 않습니다.

| 설정 | 줄이는 범위 | 남는 조건 |
| --- | --- | --- |
| SameSite=Strict | cross-site 쿠키 첨부를 강하게 제한 | 외부 링크 로그인 UX·same-site 위협 |
| SameSite=Lax | 많은 cross-site 서브리소스·폼 요청에서 제한 | 안전 메서드의 최상위 탐색 등 허용 경로 |
| SameSite=None; Secure | cross-site 사용 허용 | 브라우저 추가 제한·별도 CSRF 방어 |
| HttpOnly | 스크립트의 쿠키 값 직접 읽기 | XSS의 인증된 요청 실행 |
| Secure | 일반적으로 HTTPS 전송에 한정 | 자원 인가·스크립트 안전성 |

속성을 생략한 브라우저 기본 동작과 명시적 Lax의 세부 예외를 같은 계약으로 단정하지 않습니다. 지원 브라우저에서 실제 navigation·form·fetch 경로를 확인합니다. host-only 쿠키나 적절한 `__Host-` 쿠키 제약은 서브도메인 범위를 줄이는 데 도움이 되지만 쿠키 Path는 강한 보안 격리 경계가 아닙니다.

## 상태 변경은 명시적인 의도를 확인합니다

세션에 결합된 CSRF 토큰을 발급하고 상태 변경 요청에서 검증할 수 있습니다. double-submit 방식도 단순히 두 입력이 같다는 비교만이 아니라 공격자가 쿠키를 주입할 가능성·서명·세션 결합을 고려한 검증된 구성을 사용합니다. Origin·Referer의 신뢰된 허용 목록 검사와 Fetch Metadata를 보조로 활용하되 없는 헤더·프록시 환경의 정책을 명시합니다.

CORS는 다른 origin의 스크립트가 응답을 읽거나 특정 요청을 보내는 브라우저 규칙이지 모든 서버 인가나 CSRF를 대체하지 않습니다. GET에 결제·포인트 지급 같은 부수 효과를 넣으면 링크 탐색·프리패치로도 변경이 일어날 수 있습니다. 상태 변경 메서드와 CSRF 방어를 함께 유지합니다.

## 출력할 위치에 맞는 방어를 사용합니다

단순 텍스트는 프레임워크의 기본 escaping이나 `textContent`로 넣습니다. HTML 본문·속성·URL·JavaScript 문자열은 다른 문법입니다. HTML용 escape를 한 값을 스크립트 문자열에 붙이는 것이 안전하다는 보장은 없습니다. 가능한 한 동적 script 문자열·`innerHTML`을 피하고 안전한 API로 구조와 데이터를 나눕니다.

사용자가 제한된 서식 HTML을 작성해야 한다면 유지보수되는 sanitizer의 요소·속성 허용 목록을 사용합니다. 정규식으로 script 태그만 지우는 것으로 충분하지 않습니다. 링크의 href는 속성 인코딩 외에 URL 해석 후 허용 스킴도 검사해야 합니다. 인코딩은 따옴표를 데이터로 만들 수 있어도 위험한 URL 의미를 안전한 탐색으로 바꾸지 않습니다. 상대 URL·base URL·정규화 규칙을 한 파서 계약으로 정합니다.

정화한 결과를 다른 라이브러리가 다시 조합하거나 위험한 속성을 추가하면 최종 DOM의 의미가 바뀔 수 있습니다. 저장 시 한 번 검사했다는 기록만 믿지 말고 실제 출력 경로와 sanitizer 버전 변경 때의 재처리를 고려합니다.

## CSP nonce는 신뢰한 코드 위치에만 붙입니다

CSP nonce는 응답마다 예측하기 어려운 값을 만들고 CSP 헤더와 허용 script 태그에 같은 값을 넣는 방식입니다. 템플릿이 사용자 HTML까지 포함한 모든 script에 nonce를 자동으로 붙이면 공격자 코드도 승인됩니다. nonce를 값의 비밀성만으로 이해하지 말고 누가 실행 허가를 받는지 통제해야 합니다.

캐시된 HTML의 nonce와 새 헤더의 nonce가 다르면 정상 코드가 막힙니다. 반대로 전체 HTML을 같은 nonce로 여러 응답에 장기간 재사용하면 응답별 새 값이라는 설계를 잃습니다. nonce 생성·헤더·본문을 같은 응답 단위로 만들거나, 고정된 정적 코드에 적합한 hash 기반 정책 등 다른 구조를 선택합니다. shared cache에서 사용자별 콘텐츠가 섞이는 문제도 별도로 막습니다.

`Report-Only`는 보고 모드이며 차단 모드가 아닙니다. 허용된 스크립트의 취약한 DOM 조작이나 지나치게 넓은 출처 허용은 여전히 문제가 됩니다. 정책 위반 보고의 원문·URL·트래픽도 개인정보와 비용을 고려해 제한합니다.

## 브라우저 경로별로 기대 차단을 확인합니다

테스트 origin 두 개와 형제 서브도메인을 두고 최상위 링크·폼·fetch·iframe 요청의 쿠키 첨부와 서버 거절을 따로 봅니다. 유효 세션으로 보낸 잘못된 CSRF 토큰, 누락 Origin 정책, 정상 외부 로그인 복귀도 포함합니다.

합성 HTML의 텍스트·속성·링크가 의도한 DOM으로 남는지, 미승인 script가 차단되는지, 승인 script는 실행되는지 검사합니다. 캐시 hit에서도 헤더와 본문 nonce가 맞아야 합니다. 이 노트는 방어 설계와 테스트 목록이며 이 보안 사례들을 실제 브라우저에서 실행했다고 주장하지 않습니다.
