# 위상 정렬과 순환 의존 진단

## 선행 작업을 먼저 해야 합니다

앱 배포 D는 빌드 B와 데이터 준비 C가 끝난 뒤 실행하고, B와 C는 설정 A가 준비된 뒤 시작한다고 합시다. 의존 관계를 `A→B, A→C, B→D, C→D`로 나타내면 모든 화살표의 출발점이 도착점보다 먼저 오는 순서를 찾을 수 있습니다. 이것이 **위상 정렬**입니다.

방향 비순환 그래프에는 이런 순서가 존재합니다. B와 C 사이에는 의존이 없으므로 `[A,B,C,D]`와 `[A,C,B,D]`는 둘 다 올바릅니다. 정답이 한 배열로 유일하다는 가정부터 버려야 합니다.

## 아직 남은 선행 조건을 셉니다

각 노드로 들어오는 간선 수를 진입 차수라고 합니다. 현재 남아 있는 그래프에서 차수가 0인 노드는 선행 조건이 없으므로 순서의 다음에 놓을 수 있습니다. 하나를 제거하면 그 노드의 후속 차수를 줄입니다. 이 방식이 Kahn 알고리즘입니다.

B를 제거한 것만으로 D를 넣으면 C 의존을 놓칩니다. 차수를 0으로 만드는 마지막 선행 간선이 제거됐을 때만 준비 상태가 됩니다.

## 정렬과 입력 검증의 슈도코드

```text
topologicalOrder(vertices, edges):
    require all edge endpoints belong to vertices
    edges = deduplicate(edges)              # 단순 의존 관계 정책
    outgoing = adjacency_list(vertices, edges)
    indegree[v] = 0 for all vertices
    for (u,v) in edges:
        indegree[v] += 1
    ready = FIFO(all vertices with indegree 0, stable initial order)
    order = []
    while ready not empty:
        u = ready.pop_front()
        order.append(u)
        for v in outgoing[u] in stable order:
            indegree[v] -= 1
            if indegree[v] == 0:
                ready.push_back(v)
    if length(order) != length(vertices):
        return cycle_blocked(order, vertices minus order)
    return order
```

중복 간선을 허용한다면 차수 계산과 제거에서 동일한 중복 개수를 처리해야 합니다. 여기서는 의존 관계를 집합으로 취급해 먼저 제거합니다. 자기 의존 `A→A`는 차수가 0이 되지 않으므로 오류로 드러납니다.

인접 리스트와 FIFO를 사용하면 O(V+E) 시간, O(V+E) 저장 공간입니다. 매번 준비된 노드 중 가장 작은 ID를 선택하려면 최소 힙을 사용할 수 있으며 O(E+V log V) 정도로 비용이 달라집니다. 안정적인 초기·이웃 순서의 FIFO는 재현 가능한 순서를 주지만 사전순 최소 결과까지 주지는 않습니다.

## 남은 모든 노드가 순환의 원인은 아닙니다

`A→B, B→A, B→C`를 보겠습니다. A와 B는 서로 기다리고 C는 B에 의존합니다. 처음 차수 0인 노드가 없으므로 세 노드가 모두 남습니다. 그러나 순환 자체는 A·B이고 C는 그 뒤에서 막힌 노드입니다.

실제 순환 경로를 보여 주려면 DFS의 미방문·진행 중·완료 색 상태를 사용해 진행 중 노드로 돌아가는 간선을 찾거나, 강한 연결 성분을 구합니다. 여러 노드를 가진 강한 연결 성분과 자기 간선이 있는 단일 노드가 순환 원인입니다. 남은 목록 전체를 “서로 순환하는 작업”이라고 표시하면 원인 진단이 틀립니다.

## 정렬 결과가 실행 성공을 대신하지 않습니다

정렬에서 B를 order에 넣은 것은 B 실행이 성공했다는 뜻이 아닙니다. 실제 배포 실행기는 B·C 완료를 관찰한 뒤 D를 시작해야 합니다. 실패·취소·재시도·부분 결과와 이미 실행된 외부 효과를 따로 관리합니다.

순환이 있는 그래프에서 독립 작업만 먼저 실행할 수도 있지만, 설정 오류를 발견한 뒤 일부 외부 효과가 생기는 비용을 고려해야 합니다. 전체 유효성 검사가 먼저 필요한 배포라면 순서를 완전히 검증한 뒤 실행합니다. 정렬 중에 바로 외부 명령을 실행하는 코드는 이 판단을 숨기기 쉽습니다.

## 검증은 화살표의 방향을 확인합니다

정렬 결과의 각 노드 위치를 맵으로 만들고 모든 `u→v`에 대해 `position[u] < position[v]`인지 검사합니다. 같은 간선 목록 하나와만 비교하지 않습니다. 고립 노드와 여러 연결 성분도 결과에 한 번씩 들어가야 합니다.

순환 입력에서는 A·B와 그에 막힌 C를 구분하고, 자기 간선·중복 간선·없는 끝점·빈 그래프를 시험합니다. 마지막으로 실제 실행 테스트에서 선행 작업이 실패했을 때 후속이 시작되지 않는지 확인해 그래프의 정합성과 실행 상태의 정합성을 따로 검증합니다.
