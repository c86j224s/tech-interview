# 해시 테이블의 충돌과 확장

## 해시는 후보를 찾습니다

해시 함수는 키를 숫자로 변환하고 테이블은 그 숫자로 후보 위치를 고릅니다. **해시가 같아도 키는 다를 수 있으므로 실제 동등 비교가 필요합니다.** 동등한 키가 같은 해시를 가져야 한다는 계약과 모든 해시가 서로 다르다는 주장은 다릅니다.

키를 넣은 뒤 동등성·해시 계산에 사용하는 필드를 바꾸면 항목이 남아 있어도 조회가 다른 버킷으로 가서 못 찾을 수 있습니다. 안정적인 불변 키를 쓰거나 변경 전에 삭제하고 재삽입합니다.

## 충돌 해결 두 방식

| 방식 | 저장 | 장점 | 비용 |
| --- | --- | --- | --- |
| Chaining | 버킷마다 목록·트리 등 | 버킷별 관리가 직관적 | 포인터·할당·긴 버킷 탐색 |
| Open addressing | 테이블의 다른 슬롯을 탐사 | 연속 메모리·지역성 | 높은 점유율·군집·삭제 처리 |

평균 O(1)에 가까운 비용은 좋은 분포와 적절한 부하율의 조건입니다. 모든 키가 충돌하면 최악에는 선형 탐색이 될 수 있습니다. 네트워크·문자열 해시·할당까지 포함한 전체 요청 지연이 상수라는 뜻도 아닙니다.

## 선형 탐사의 검색과 삭제

```text
find(key):
    start = hash(key) mod capacity
    for step = 0 .. capacity - 1:
        slot = table[(start + step) mod capacity]
        if slot is NEVER_USED: return not-found
        if slot is LIVE and slot.key == key: return slot.value
        // tombstone이면 멈추지 않음
    return not-found
```

중간 항목을 삭제하며 NEVER_USED로 바꾸면 뒤의 충돌 키를 찾기 전에 검색이 멈춥니다. tombstone은 삭제됐지만 탐사는 이어가야 한다는 표식입니다. 삽입 때 재사용할 수 있어도 같은 키가 뒤에 있는지 충분히 확인해 중복을 막아야 합니다.

실제 원소 수/용량과 tombstone을 포함한 탐사상 점유율을 나눠 봅니다. 삭제가 많으면 원소 수는 적어도 탐색이 느릴 수 있습니다.

## 확장과 점진 재해시

용량이 바뀌면 같은 해시의 슬롯 계산도 바뀌므로 원소를 새 테이블에 다시 배치해야 합니다. 한 번에 옮기면 O(n)의 지연과 옛·새 저장소 동시 보유가 생깁니다.

점진적 재해시는 일부씩 옮기며 양쪽을 조회합니다. 이때 반드시 정해야 하는 것은 다음과 같습니다.

1. 같은 키가 어느 세대에서 권위 있는가.
2. 갱신·삭제와 이동이 겹칠 때 옛 값이 되살아나지 않는가.
3. 이동 완료와 옛 배열의 독자 종료를 어떻게 구분하는가.
4. 읽기만 계속되어도 이동이 끝나는가.

버킷 하나에 충돌 키가 매우 많으면 ‘요청마다 한 버킷 이동’도 지연 상한이 아닙니다. 이동 원소 수·시간 예산을 별도로 제한할 수 있습니다.

## 동시성과 보안

일반 map과 concurrent map의 계약을 구분합니다. concurrent 구조도 `get → 계산 → put`의 복합 연산이나 value 객체 내부 변경까지 자동 원자화하지는 않습니다.

공개 입력에는 예측하기 어려운 해시 시드·키 길이·항목 수·실행 예산을 검토합니다. 보안용 무작위 해시를 서버 간 영구 샤드 배정 함수로 쓰면 같은 키가 다른 위치로 갈 수 있으므로 안정적인 분산 해시는 별도 계약으로 둡니다.

## 연습

충돌 키, 동일 키 갱신, 삭제 뒤 검색, 가득 찬 테이블, tombstone 재사용, 키 mutation을 테스트합니다. resize 중 삭제·재삽입을 기준 map과 대조하고 평균뿐 아니라 최대 탐사·재해시 p99·메모리 피크를 기록합니다.
