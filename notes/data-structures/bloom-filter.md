# 블룸 필터의 부재 판단과 갱신 경계

## 없는 상품을 매번 DB에서 찾을 필요가 있을까요

등록된 상품은 백만 개인데 존재하지 않는 상품 ID 요청이 계속 들어온다고 합시다. 모든 요청을 DB까지 보내기 전에 작은 자료구조로 “이 키는 저장된 집합에 없다”고 걸러낼 수 있다면 조회 비용을 줄일 수 있습니다.

**블룸 필터**는 원소 자체 대신 여러 해시 위치의 비트를 저장합니다. 올바르게 삽입된 집합에서는 없다는 답을 신뢰할 수 있지만, 있다는 답은 “있을 수 있다”는 뜻입니다. 양성 결과는 원본을 다시 확인해야 합니다. 원본 DB와 필터의 반영 시점이 다르다면 이 수학적 보장과 실제 서비스의 부재 응답도 구분해야 합니다.

## 비트 8개로 충돌을 직접 만듭니다

설명을 위해 키별 두 해시 위치를 아래처럼 정합니다. 실제 추천 해시 함수가 아니라 충돌을 보기 위한 작은 예입니다. 비트 번호는 0~7입니다.

| 키 | 해시 위치 | 삽입 여부 |
| --- | --- | --- |
| A | 1, 4 | 삽입 |
| B | 4, 6 | 삽입 |
| C | 1, 6 | 삽입 안 함 |
| D | 2, 4 | 삽입 안 함 |

A와 B를 넣으면 1·4·6번 비트가 켜집니다. C를 조회하면 두 위치가 모두 켜져 있으므로 필터는 양성이라고 답합니다. 하지만 C는 넣은 적이 없습니다. 여러 키가 켠 비트가 우연히 조합되어 생긴 **거짓 양성**입니다. D는 2번 비트가 꺼져 있어 부재로 판정할 수 있습니다.

## 삽입과 조회에는 비트를 지우는 동작이 없습니다

```text
insert(key):
    for position in hashPositions(key):
        bits[position] = 1

mayContain(key):
    for position in hashPositions(key):
        if bits[position] == 0:
            return false
    return true
```

동시 삽입에서는 서로 다른 비트라도 같은 기계어를 공유할 수 있습니다. 비원자적인 읽기·수정·저장으로 OR하면 한 스레드의 변경이 사라져 거짓 음성이 생길 수 있으므로 원자 OR나 잠금 등 실제 비트 저장의 동시성 계약이 필요합니다.

A를 삭제한다고 1·4번 비트를 끄면 B의 4번 비트도 사라집니다. B가 원본에 있는데 필터가 없다고 답하므로 잘못입니다. 삽입 전용 필터에서는 삭제된 키가 양성으로 남는 비용을 받아들이거나 새로 구축합니다. counting Bloom filter는 비트 대신 카운터를 사용하지만 정확한 삽입·삭제 횟수, 카운터 넘침·언더플로를 추가로 관리해야 합니다. 원본에 없는 키를 잘못 삭제하면 counting 방식도 안전하지 않습니다.

## 용량과 해시 수를 숫자로 정합니다

비트 수 `m`, 삽입 원소 수 `n`, 해시 수 `k`에 대해 독립·균등 해시를 가정한 거짓 양성률 근사는 다음과 같습니다.

```text
p ≈ (1 - exp(-k*n/m))^k
m ≈ -n*ln(p) / (ln(2)^2)
k ≈ (m/n)*ln(2)
```

원소 1,000개에 목표 거짓 양성률 1%라면 약 9,586비트, 약 1.2KB와 해시 7개가 출발점입니다. 실제 배열·객체·해시 상태의 부가 메모리는 포함하지 않은 계산입니다. 같은 필터에 2,000개를 넣으면 비트가 포화되어 위 근사에서 오류율이 약 15.7%로 커집니다.

해시 수를 무조건 늘리면 더 좋은 것은 아닙니다. 해시 계산이 늘고 비트도 더 빨리 켜집니다. 정수 반올림한 여러 k와 실제 키 분포를 비교하고, 원소 증가에 따라 필터를 교체할 시점을 정해야 합니다.

## DB에 있는데 필터에 없을 수 있는 이유

DB에 새 상품을 커밋하고 필터 갱신이 실패하면, 새 상품은 필터의 삽입 집합에 들어가지 않았습니다. 알고리즘의 “삽입된 키에는 거짓 음성이 없다”는 명제는 참이어도, 서비스는 실제 상품을 없다고 거를 수 있습니다.

필터가 원본의 어느 커밋 위치까지 반영했는지 추적하고, 그 이후 새 키의 조회는 원본으로 보내는 등 일관성 계약이 필요합니다. 필터를 먼저 갱신하고 DB가 실패하면 거짓 양성이 늘어나는 방향이지만, 갱신 중 오류·삭제·여러 writer까지 그 순서가 지켜지는지 확인해야 합니다. 필터는 권한 검사나 보안상의 존재 비공개를 대신하지 않습니다.

## 재구축은 snapshot과 이후 삽입을 함께 옮깁니다

원본의 기준 위치 S에서 snapshot을 읽어 새 필터를 만들었다고 해 보겠습니다. 구축 중 추가된 키 K가 증분 기록에만 있다면 snapshot만으로 새 필터를 활성화할 때 K를 놓칩니다.

1. snapshot의 기준 위치와 변경 로그 시작 위치를 일치시킵니다.
2. snapshot의 모든 키를 새 필터에 넣습니다.
3. S 이후의 신규 삽입을 재생하고 전환 경계까지 따라잡습니다.
4. 새 필터 활성화와 이후 쓰기의 갱신 대상 전환을 연결합니다.
5. 옛 필터를 읽는 작업이 끝난 뒤 회수합니다.

구축 중 두 필터 중 하나라도 양성이면 원본을 조회하는 보수적 방식은 도움이 됩니다. 하지만 둘 다 신규 키를 놓쳤다면 OR로도 복구되지 않습니다. 갱신이 불확실하면 음성 차단을 잠시 끄고 원본으로 보내되, 그때 늘어나는 DB 부하에도 상한이 필요합니다.

## 서로 다른 오류율을 구별해 검사합니다

| 지표 | 분모 | 뜻 |
| --- | --- | --- |
| 거짓 양성률 | 실제 부재 키 전체 | 없는 키 중 필터를 통과한 비율 |
| 양성 중 부재 비율 | 필터 양성 전체 | 원본 조회 중 낭비 비율, 요청 분포에 영향 |
| 잘못된 부재 응답 | 실제 존재 키 전체 | 반영 지연·잘못된 삭제·동시성 오류 가능성 |

작은 A·B·C·D 예에서 C 양성, D 음성, A·B 양성을 확인합니다. A 삭제 비트를 지운 잘못된 구현은 B를 놓쳐야 반례가 재현됩니다. 대규모 시험은 삽입 집합과 별도의 부재 집합을 보관해 오류율을 계산하고, 재구축 중 새 키·동시 비트 갱신·필터 복원 실패도 따로 시험합니다.
