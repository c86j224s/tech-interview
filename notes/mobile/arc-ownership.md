# ARC 참조 그래프와 비동기 완료 책임

## 화면 종료와 잔존 강한 참조

예를 들어 화면이 서비스를 강하게 보관하고, 서비스가 진행 중인 작업을 보관한다고 합시다. 작업이 끝날 때 실행할 완료 클로저가 다시 화면을 강하게 캡처하면 `화면 → 서비스 → 작업 → 클로저 → 화면` 고리가 생깁니다. 화면을 화면 계층에서 제거해도 이 고리의 강한 참조가 0이 되지 않으므로, ARC는 이런 순환을 추적 GC처럼 대신 끊어 주지 않습니다.

누수가 의심되면 모든 self를 weak로 바꾸기 전에 **누가 누구의 생존을 책임지는지** 그립니다. 화면이 사라져도 끝내야 하는 다운로드·결제 결과가 있다면 작업의 소유자를 화면 밖에 두어야 합니다.

작업이 끝나면 서비스의 핸들과 작업의 클로저를 정리해야 합니다. weak 캡처가 있어도 서비스가 완료 작업을 영원히 모으면 메모리가 증가할 수 있습니다. 반대로 모든 참조를 weak로 만들면 필요한 작업이 너무 일찍 사라질 수 있습니다.

## weak와 unowned의 실패 방식 차이

| 참조 | 강한 수명 연장 | 대상이 먼저 사라지면 |
| --- | --- | --- |
| strong | 예 | 소유자가 놓을 때까지 유지 가능 |
| weak | 아니오 | 자동 nil, 부재 처리 필요 |
| 일반적인 safe unowned | 아니오 | 사용 시 수명 계약 위반으로 런타임 오류 가능 |

`unowned`는 자동으로 `nil`이 되는 `weak`의 짧은 표기가 아닙니다. 외부 큐·타이머·네트워크가 호출 시점을 정하는 비동기 클로저에서 대상이 먼저 사라지면, `weak`는 `nil`이 되어 부재 처리를 할 수 있지만 `unowned`는 살아 있다는 전제가 깨져 런타임 오류가 날 수 있습니다.

그래서 클로저가 사용하는 전체 기간 동안 대상이 살아 있다는 불변식을 설명할 수 있을 때만 `unowned`를 선택하고, 그렇지 않으면 `weak` 뒤에서 `nil`을 처리해야 합니다. unsafe unowned 같은 별도 기능은 더 강한 위험을 가지며 여기서는 다루지 않습니다.

완료 클로저에서 `[weak self]`로 캡처한 뒤 `guard let self`를 실행하면, 그 `guard`가 만든 강한 지역 참조는 해당 사용 범위 동안 화면을 유지합니다. `await`를 포함한 작업의 시작부터 끝까지 이 참조를 유지하면 화면을 닫아도 완료를 기다리는 동안 화면 수명이 늘어날 수 있습니다. 따라서 코드에 `[weak self]`가 있다는 표지만 보고 완료 시점까지 참조가 약하다고 단정하지 말고, 강한 참조가 만들어지고 풀리는 범위를 확인해야 합니다.

## 취소·완료 경쟁과 단일 결과 전달권

weak는 객체 생존을 다루지만 콜백이 한 번만 실행되는지는 보장하지 않습니다. 취소와 정상 완료가 동시에 오면 actor 또는 lock으로 pending 상태에서 한 전이만 사용자 결과 전달권을 얻도록 합니다.

```text
finishUserResult(result):
    lock(state)
    if userResultState != pending:
        unlock(state)
        return
    userResultState = finished
    callback = completion
    completion = none
    unlock(state)
    dispatch_callback_on_required_executor(callback, result)
```

콜백은 잠금 밖에서 실행해 재진입과 교착을 줄입니다. 상태 검사와 변경 사이에 await를 두면 actor도 다른 작업이 끼어들 수 있으므로, 그 구간은 중단 없이 수행하거나 재검사해야 합니다. UI 변경은 해당 UI executor·MainActor 계약에 맞게 전달합니다.

## 사용자 결과와 외부 효과의 분리 기록

취소가 먼저 사용자 응답을 확정했어도 서버에서 주문 생성이 성공했을 수 있습니다. 늦은 성공을 무조건 버리면 사용자는 실패로 알고 다시 주문할 수 있습니다. 작업 서비스가 실제 결과·불확정 상태를 기록하고 UI는 현재 요청 세대에 맞는 것만 표시하도록 나눕니다.

I/O가 계속 참조하는 버퍼·작업 핸들은 실제 종료까지 유지해야 합니다. 화면 참조가 nil이라는 사실은 버퍼를 즉시 반환해도 된다는 뜻이 아닙니다. 타이머 취소·callback 제거·작업 완료의 정리 책임을 한 소유자에게 모으는 편이 검증하기 쉽습니다.

## 메모리 그래프와 실행 순서의 통합 시험

화면 열기·닫기를 반복하며 객체 ID와 deinit, 서비스의 진행 작업 수를 기록합니다. 완료 전 화면 해제, 완료 직전 취소, 취소 직전 완료, 작업이 취소를 무시하는 경우를 나누어 검사합니다. 사용자 콜백은 한 번만 전달되고 실제 결과는 필요한 저장소에 남아야 합니다.

Swift·iOS 런타임의 실제 메모리 그래프와 MainActor 전환은 대상 환경에서 확인해야 합니다. 이 노트는 소유권·상태 전이 모형이며 단순히 deinit이 빨리 호출된 것을 작업의 정확성까지 증명한 것으로 보지 않습니다.
