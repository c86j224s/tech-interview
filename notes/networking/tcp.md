# TCP 스트림에서 메시지 경계 복원하기

## 두 번 보냈는데 한 번 읽힐 수 있습니다

채팅 프로그램이 `HELLO`와 `OK`를 두 번의 쓰기 호출로 보냈다고 하겠습니다. 수신자가 반드시 두 번 읽는 것은 아닙니다. `HELLOOK`를 한 번에 받을 수도 있고, `HE`, `LLOO`, `K`로 나누어 받을 수도 있습니다. TCP는 연결 안에서 **바이트의 순서**를 제공하지만, 애플리케이션의 쓰기 호출 경계는 전달하지 않습니다.

따라서 “한 번 읽었으니 메시지 하나”라고 처리하면 네트워크 상태에 따라 같은 요청이 다르게 해석됩니다. 메시지의 시작과 끝을 정하는 규칙을 양쪽 애플리케이션이 합의해야 합니다. 이를 메시지 **프레이밍**(framing)이라고 부릅니다. 이 노트에서는 4바이트 길이 헤더 방식 하나를 끝까지 따라갑니다. 연결 수립, 혼잡 제어, TIME_WAIT는 별도 주제입니다.

## 길이 헤더의 뜻을 먼저 고정합니다

메시지는 `[4바이트 길이][본문]`으로 보냅니다. 길이는 부호 없는 32비트 정수이며 네트워크 바이트 순서인 big-endian으로 기록합니다. 여기서 길이는 **헤더를 제외한 본문 바이트 수**입니다. 문자열 글자 수가 아닙니다. UTF-8 한글은 글자 수와 바이트 수가 다를 수 있으므로 먼저 인코딩한 뒤 길이를 계산합니다.

| 항목 | 이 예제의 규칙 | 합의하지 않으면 생기는 문제 |
| --- | --- | --- |
| 길이에 포함되는 범위 | 본문만 | 헤더 4바이트만큼 다음 메시지가 밀림 |
| 길이의 단위 | 바이트 | 멀티바이트 문자가 잘림 |
| 바이트 순서 | big-endian | 작은 메시지를 거대한 길이로 오해 |
| 0 길이 | 빈 메시지로 허용 | 서로 다른 파서의 진행 규칙 |
| 최대 본문 | 예제에서는 1 MiB | 외부 입력이 메모리 할당을 지배 |

`HELLO`는 `00 00 00 05` 뒤에 5바이트, `OK`는 `00 00 00 02` 뒤에 2바이트를 붙입니다. 수신자는 TCP가 어떻게 나누어 주든 이 규칙으로 같은 두 메시지를 복원해야 합니다.

그림에서 소켓 읽기가 끝난 것은 파싱 완료가 아니고, 파싱 완료는 실제 요청 처리 완료가 아닙니다. 이 경계를 분리하면 버퍼가 부족한지, 처리 큐가 밀리는지, 요청 실행이 느린지를 따로 측정할 수 있습니다.

## 세 번의 읽기를 손으로 따라갑니다

아래 입력 조각은 예제를 위한 고정된 분할입니다. 실제 OS가 이 크기로 전달한다는 뜻은 아닙니다. `00` 같은 표기는 16진 바이트, 글자는 ASCII 바이트를 뜻합니다.

| 읽기 | 새로 도착한 바이트 | 파서의 행동 | 남겨 둘 바이트 |
| --- | --- | --- | --- |
| 1 | `00 00` | 헤더 4바이트가 안 모여 기다림 | `00 00` |
| 2 | `00 05 H E` | 길이 5 확인, 본문은 2바이트라 기다림 | 길이 헤더와 `H E` |
| 3 | `L L O 00 00 00 02 O K` | `HELLO` 복원 후 다시 반복해 `OK`도 복원 | 없음 |

세 번째 읽기에서 메시지 하나만 처리하고 반환하면 `OK`는 버퍼에 남습니다. 새로운 바이트가 더 오지 않을 수도 있으므로, **현재 버퍼에서 완성된 메시지를 모두 꺼내는 반복문**이 필요합니다. 반대로 본문이 아직 모이지 않았을 때 같은 버퍼를 계속 검사하면 진행 없는 무한 반복이 되므로 반환하고 다음 입력을 기다려야 합니다.

## 상태를 유지하는 증분 파서

다음은 원리를 보여 주는 슈도코드입니다. `append`는 연결별 상한 안에서만 수행하고, 입력 조각이 상한보다 크면 조각을 나누어 파싱하거나 일시 중지하는 정책이 필요합니다. 이 단순 예제에서는 초과 연결을 닫습니다.

```text
MAX_MESSAGE = 1 MiB
MAX_BUFFER = 2 MiB

on_bytes(data):
    if size(data) > MAX_BUFFER - available(buffer):
        reject_and_close("receive buffer limit")
        return
    append(buffer, data)

    while true:
        if available(buffer) < 4:
            return                         // 미완성 헤더
        length = decode_u32_big_endian(first_4_bytes(buffer))
        if length > MAX_MESSAGE:
            reject_and_close("message too large")
            return
        if available(buffer) - 4 < length:
            return                         // 미완성 본문
        if not processing_queue.has_capacity():
            pause_reading_and_resume_when_queue_drains()
            return                         // 이 프레임을 아직 소비하지 않음
        frame = copy_body(buffer, length)  // 독립된 소유 버퍼
        processing_queue.push(frame)
        consume_prefix(buffer, 4 + length)
```

길이를 검사할 때 `available >= 4 + length` 대신 헤더가 있는지 먼저 검사하고 뺄셈으로 비교하면, 제한되지 않은 길이 덧셈에서 생길 수 있는 정수 넘침을 피하기 쉽습니다. 실제 구현에서는 정수 타입과 변환도 확인해야 합니다.

이 슈도코드는 같은 연결의 파서와 큐 용량 확보가 직렬로 실행된다고 가정합니다. 여러 생산자가 같은 큐에 넣는 구조라면 “자리 확인”과 “삽입” 사이에 경쟁이 생기므로, 원자적 용량 예약이나 실패 가능한 삽입을 사용해야 합니다. 읽기를 멈췄다가 큐에 자리가 생기면 **기존 버퍼부터 다시 파싱**해야 합니다. 다음 소켓 이벤트만 기다리면 이미 완성된 메시지가 멈춰 있을 수 있습니다.

## 복사를 줄일 때는 수명이 더 중요해집니다

위 코드는 본문을 복사해 큐에 넘기므로 파서가 원래 수신 버퍼를 재사용해도 안전합니다. 복사 비용을 줄이려고 본문 위치를 가리키는 뷰만 넘길 수도 있지만, 처리기가 읽는 동안 그 메모리를 덮어쓰거나 확장해 주소를 바꾸면 안 됩니다.

## 연결이 끝날 때 남은 바이트를 해석합니다

읽기 API가 정상 EOF를 알렸는데 버퍼에 헤더 일부나 본문 일부가 남아 있다면 이 프로토콜에서는 잘린 메시지입니다. TCP 연결 종료를 본문 완료로 대신 해석하면 안 됩니다. 버퍼가 비어 있는 정상 종료와, 완성되지 않은 요청이 있는 종료를 로그와 복구 정책에서 구분합니다.

송신도 한 번의 호출로 모든 바이트를 넘겼다고 가정하지 않습니다. API가 일부만 처리했다고 보고하면 나머지 범위를 이어 보내고, 같은 연결에 쓰는 여러 작업은 프레임 바이트가 섞이지 않도록 직렬화합니다. 로컬 송신 완료나 TCP ACK는 상대 **애플리케이션의 처리 커밋**을 뜻하지 않습니다. 처리 성공을 알아야 하는 프로토콜에는 요청 ID와 애플리케이션 응답이 필요합니다.

## 분할 모양이 달라도 같은 결과인지 검사합니다

검사의 기준은 읽기 횟수가 아니라 복원한 메시지 목록입니다. `HELLO`, `OK`를 인코딩한 같은 바이트열을 한 번에, 한 바이트씩, 가능한 각 경계에서 두 조각으로 나누어 입력합니다. 모두 정확히 `[HELLO, OK]`가 나와야 합니다.

| 입력 조건 | 기대 결과 |
| --- | --- |
| 빈 본문 두 개 연속 | 빈 메시지 두 개, 무한 반복 없음 |
| 헤더 3바이트 뒤 EOF | 잘린 헤더 오류 |
| 본문 길이 5인데 4바이트 뒤 EOF | 잘린 본문 오류 |
| 최대 길이를 넘는 헤더만 입력 | 본문 할당 전에 거절 |
| 처리 큐가 꽉 찼다가 비워짐 | 같은 프레임을 한 번만 전달하고 진행 재개 |

실제 네트워크 부하 시험에 앞서 파서를 순수 바이트 입력 함수로 시험하면 오류를 재현하기 쉽습니다. 큰 정상 메시지도 연결별 상한과 전체 연결 수를 곱하면 메모리 부담이 되므로, 최대 메시지 크기뿐 아니라 전체 수신 버퍼와 처리 큐의 한도를 함께 정해야 합니다.
