# 실행 수와 대기열을 함께 제한하기

## 기다릴 자리를 늘려도 DB는 빨라지지 않습니다

DB 작업을 동시에 4개 실행하고 나머지는 큐에서 기다리는 서버를 생각해 보겠습니다. 작업 하나가 정확히 100ms 걸린다는 단순한 모형에서는 초당 약 40개를 끝냅니다. 초당 60개가 계속 들어오면 매초 20개씩 쌓입니다. 대기열을 100에서 1,000으로 늘려도 완료율은 그대로이고, 거절하기까지 기다리는 시간만 길어집니다.

실행 수는 하위 자원을 동시에 얼마나 사용하게 할지, 대기열은 아직 시작하지 않은 작업을 얼마나 보관할지 정합니다. 과부하에서 받을 요청을 고르는 **진입 제어**(admission control)와, 생산자에게 감속·대기를 전달하는 **백프레셔**(backpressure)는 함께 설계해야 합니다.

## 작은 시간표로 대기 비용을 계산합니다

시각 0에 네 작업이 막 시작했고, 큐에 여덟 작업이 있다고 합시다. 모든 작업이 100ms이고 FIFO이며 다른 지연이 없다는 가정입니다.

| 시각 | 실행을 시작하는 작업 | 새 요청의 상태 |
| --- | --- | --- |
| 0ms | 기존 실행 4개 | 큐의 아홉 번째로 들어감 |
| 100ms | 기존 대기 1~4 | 계속 기다림 |
| 200ms | 기존 대기 5~8 | 계속 기다림 |
| 300ms | 새 요청 | 실행 시작 |
| 400ms | 새 요청 완료 | 결과 반환 가능 |

남은 기한이 250ms라면 이 요청은 받아도 제때 끝날 수 없습니다. 실제 작업 시간은 고정이 아니므로 표의 계산은 하한·추정의 재료이지 지연 보장이 아닙니다. 긴 집계가 섞이면 같은 대기 개수에서도 결과가 크게 달라집니다.

안정 상태에서 평균 체류 개수 `L = λW`라는 리틀의 법칙을 사용할 수 있습니다. 초당 완료 40개, 대기와 실행을 합친 평균 체류 0.3초라면 평균 시스템 내 요청은 12개입니다. 이 값을 워커 12개라는 설정으로 바로 바꾸면 안 됩니다. 평균 관계는 p99를 보장하지 않고, 무한히 적체되는 비정상 상태에는 정상 상태 계산을 그대로 적용할 수 없습니다.

## 수락과 허가 반환은 원자적으로 관리합니다

다음 슈도코드는 하나의 소유 실행기가 큐와 실행 카운터를 직렬로 관리한다고 가정합니다. 멀티스레드 구현이면 같은 전이를 잠금 또는 원자 상태 변경으로 보호해야 합니다.

```text
onRequest(job):
    if stopping or job.deadline <= monotonicNow():
        return rejected
    if queuedCount == MAX_QUEUED or job.bytes > MAX_BYTES - queuedBytes:
        return overloaded
    queue.push(job)
    queuedCount += 1
    queuedBytes += job.bytes
    dispatch()

dispatch():
    while active < MAX_ACTIVE and queue not empty:
        job = queue.pop()
        queuedCount -= 1
        queuedBytes -= job.bytes
        if job.deadline <= monotonicNow():
            finishWithoutExecution(job, expired)
            continue
        active += 1
        try:
            submit(job, onActualTermination)
        catch definitelyNotSubmitted:
            active -= 1
            finishWithoutExecution(job, submissionFailed)

onActualTermination(job, result):
    assert job.executionCompletionNotYetConsumed
    job.executionCompletionNotYetConsumed = false
    active -= 1
    recordActualResult(job, result)
    dispatch()
```

`submit`이 콜백을 반환 전에 호출할 수 있는 API라면 완료 이벤트를 소유 실행기의 큐로 전달하거나 재진입을 허용하는 상태 전이를 먼저 준비해야 합니다. 제출 실패와 나중 완료가 둘 다 허가를 반환하면 카운터가 틀어집니다. “확실히 제출되지 않음”과 “실행 여부 불확정”을 API 계약에 맞게 구분합니다.

대기 중 만료 항목은 실행 자리가 날 때만 제거하지 않고 타이머나 취소 이벤트로도 회수해야 합니다. 그렇지 않으면 DB가 멈춘 동안 이미 끝난 요청의 본문이 큐를 차지합니다. 실행 중인 작업은 사용자의 대기 시간이 끝나도 실제 종료 전까지 허가를 유지합니다. 응답 종료와 실행 종료는 별도의 상태입니다.

## 요청 비용이 다르면 개수만 세지 않습니다

작은 조회 하나와 큰 보고서 하나가 같은 DB 비용을 쓰지는 않습니다. 작업 종류에 따라 허가 비용을 1·5처럼 정하고, 사용 중 가중치 합이 예산을 넘지 않게 할 수 있습니다. 가중치는 측정값에 기초한 근사이며 실제 메모리나 I/O 상한을 자동 보장하지 않습니다.

무거운 작업이 예산 전체를 기다리는 동안 작은 작업만 계속 들어오면 기아가 생길 수 있습니다. 최대 작업 비용이 전체 예산 이하인지 검사하고, 오래 기다린 작업에 예약 용량을 주거나 무거운 작업을 별도 풀로 분리하는 정책이 필요합니다. 순서대로 막으면 반대로 앞의 큰 작업 때문에 작은 작업이 지연되는 비용도 있습니다.

| 제한 | 보호하는 것 | 혼자서는 못 막는 것 |
| --- | --- | --- |
| 요청률 | 초당 유입·호출 과금 | 느려진 요청의 동시 점유 |
| 실행 수 또는 가중치 | 동시에 쓰는 하위 자원 | 무한 대기자·재시도 폭주 |
| 큐 개수·바이트 | 대기 메모리 | 기다려도 기한을 못 지키는 요청 |
| 전체 기한 | 무의미한 오래된 작업 | 실제 취소 불가능한 외부 실행 |

## 인스턴스 수와 재시도도 예산에 들어갑니다

인스턴스 하나에 실행 허가 20개를 주고 10개를 띄우면 DB에는 최대 200개가 들어갑니다. 자동 확장이 DB 용량을 늘리는 것은 아닙니다. 서비스별 예약 용량과 전체 하위 예산을 맞추어야 합니다.

거절된 클라이언트가 즉시 재시도하면 입구에서 더 큰 폭주가 생깁니다. 재시도 간격·지터·횟수·전체 기한을 안내하고, 클라이언트가 지키지 않아도 서버 내부 상한은 유지해야 합니다. 과부하 응답이 빨라졌다고 평균 지연만 보고 개선됐다고 판단하지 않습니다.

## 부하가 내려간 뒤까지 시험합니다

정상 부하, 한 번의 버스트, 하위 작업이 10배 느려지는 상황을 각각 재현합니다. 입력률·수락률·실제 성공률·거절률·가장 오래된 대기 시간·활성 작업 수를 함께 기록합니다. 순간 `active <= MAX_ACTIVE`, `queuedBytes <= MAX_BYTES`가 유지되는지와 제출 실패·취소 뒤 카운터가 원래로 돌아오는지 검사합니다.

마지막에는 유입을 정상 수준으로 되돌립니다. 과부하 동안 쌓인 오래된 작업을 정리하고 지연이 회복되는지 확인해야 합니다. 유효한 요청을 더 많이 제때 끝내는 것이 목적이지, 거절을 없애거나 큐를 가득 채우는 것이 목적은 아닙니다.
