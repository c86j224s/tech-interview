# 검증 가능한 위임과 동시 편집의 통합

## 세 역할을 만든다고 세 가지 증거가 생기지는 않습니다

작은 함수 수정에 설계자·작성자·검토자를 붙이면 문맥 전달과 통합이 구현보다 비쌀 수 있습니다. 독립된 공식 계약 조사·분리 모듈 검토처럼 결과를 합칠 기준이 명확한 작업을 먼저 나눕니다. 각 branch가 최종 판단을 바꿀 수 있는지, 다른 결과를 기다리는 의존성이 있는지 봅니다.

독립 조사 3개가 각 2분이고 통합 1분이면 이상적 wall time은 약 3분이나 작업 비용은 6분+통합입니다. 서로 같은 자료를 읽으면 오류도 상관될 수 있습니다. 단일 host 기준선과 성공·누락·중복 조사·통합 비용을 비교합니다.

## 위임에는 질문뿐 아니라 하지 않을 일도 포함합니다

| 계약 | 구체 내용 |
| --- | --- |
| 역할·목표 | 특정 API의 retry 계약 확인 |
| 범위·제외 | 해당 module 읽기, 구현·게시 금지 |
| 확정 조건 | 고정 interface·현재 version·사용자 제약 |
| 권한·예산 | 읽을 자료·전송 범위·시간·호출 상한 |
| 반환 | 결론·근거 위치·재현 입력·실행 결과·미확인 |
| 중단 | 필요한 사실 확보·권한 차단·새 결정 발견 |

“테스트 통과”에는 명령·환경·결과가 필요하고 “위험한 경계”보다 “n=0에서 X:42 인덱스 오류, Y로 재현”이 통합 가능성이 높습니다. 의심과 확정 결함·제안과 실행을 나눕니다. 하위 작업이 새로운 설계 결정을 만나면 범위를 넓히지 말고 host에 돌려줍니다.

## 구현의 공유 불변식은 한 통합자가 정합니다

읽기 조사와 여러 writer의 코드는 다릅니다. 변경을 분할한다면 disjoint 소유권·고정 인터페이스·독립 worktree를 사용합니다. 한 branch가 함수 인자를 바꾸고 다른 branch가 옛 인자의 호출자를 추가하면 텍스트 충돌 없이 의미 충돌이 생깁니다. 파일 이름이 다르다고 독립적인 변경은 아닙니다.

## 읽은 버전과 현재 버전이 다르면 다시 합칩니다

파일 해시 H1을 읽었는데 현재 H2면 좁은 patch가 우연히 적용돼도 의미를 다시 봅니다. 정확한 old string·base hash·version 조건으로 덮어쓰기를 막고 현재 내용을 재조회해 의도를 합칩니다. 원격 문서 저장도 같은 원칙입니다. 충돌을 피하려 force overwrite하는 것은 사용자 변경을 버리는 별도 결정입니다.

rename·삭제·공통 타입 변경·사용자 미커밋 변경을 확인하고 한 통합 지점에서 반영합니다. worktree는 동시 파일 덮어쓰기를 줄이지만 최종 merge 정확성을 보장하지 않습니다. 각각 통과한 테스트도 합친 tree에서 다시 실행합니다.

## 결과 알림은 수용 심사의 시작입니다

완료 알림이 가리키는 commit·산출물 version을 읽고 요구 충족·누락·모순·실제 실행을 대조합니다. 하위 보고의 “검증 생략 가능”은 상위 정책을 바꾸지 않습니다. 실패 branch가 필수 증거면 전체를 차단하고, 아니라면 제한된 결론에 누락을 표시합니다. 아직 실행 중인 결과를 예측해 완료라고 하지 않습니다.

근거가 충분하면 불필요한 새 branch를 만들지 않고 필요 없는 실행은 수명 계약에 따라 취소합니다. 이 노트는 위임·통합 설계이며 여러 에이전트를 실행해 속도 개선을 측정한 결과는 아닙니다.
