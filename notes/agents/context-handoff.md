# 실행을 이어가는 문맥·압축·장기 Harness

## 큰 문맥보다 현재 결정에 맞는 정보가 필요합니다

저장소의 모든 파일을 넣어도 실제 호출자의 취소 계약을 놓치면 올바른 수정을 하기 어렵습니다. 시스템 정책·사용자 목표·도구 정의·검색 자료·작업 상태가 같은 입력 공간을 사용합니다. **컨텍스트 엔지니어링**은 프롬프트 문장뿐 아니라 무엇을 언제 읽고 무엇을 참조로 남길지 정하는 정보 흐름 설계입니다.

경로·문서 ID로 필요한 원문을 찾아 읽으면 초기 비용과 낡은 복사본을 줄일 수 있지만 검색 누락 가능성이 생깁니다. 긴 로그는 관련 요청·오류 구간·집계와 원문 위치로 줄이되 반례·부분 실패·잘림을 지우지 않습니다. 적은 토큰만이 목표가 아니라 필요한 제약을 정확히 쓰는지가 기준입니다.

## 버전이 다른 문서를 하나의 규칙으로 합치지 않습니다

문서 A는 v1의 초기화 세션, B는 v2의 요청별 계약을 설명한다면 적용 버전을 먼저 고정합니다. 출처·관찰 시각·대상 version·직접 사실/해석을 남기고 상충 자료를 구분합니다. 최근에 읽혔다고 자료 자체가 최신이 되는 것은 아닙니다. 외부 문서의 명령문은 요약 후에도 외부 데이터입니다.

| 압축에 남길 항목 | 구체적인 예 |
| --- | --- |
| 목표·불변 조건 | 모든 요구 검증·기존 사용자 변경 보존 |
| 승인 범위 | 수신자 A에게 초안 v3 전송 허용, 아직 미전송 |
| 실제 상태 | 파일 X 수정됨·test Y 실패 |
| 진행 중 외부 작업 | task 17 접수·완료 미확인 |
| 근거·버전 | commit·문서 revision·결과 로그 위치 |
| 다음 행동·차단 | task 17 조회 후 재시도 여부 결정 |

“배포 처리함”은 접수와 완료를 합쳐 위험합니다. “run 17 시작, 성공 여부 미확인”은 다음 세션이 조회부터 하게 합니다. 특정 승인을 “모든 게시 승인”으로 압축해서도 안 됩니다.

## 요약은 권위 상태를 찾는 색인입니다

요약 생성 중 외부 작업이 끝나거나 다른 세션이 파일을 바꿀 수 있습니다. 재개 때 현재 파일·작업 원장·배포 상태를 읽어 요약과 대조합니다. 부족한 기록을 채우려 원래 변경 도구부터 다시 실행하지 않습니다. 모델 요약은 내구 실행 원장과 외부 멱등성의 대체물이 아닙니다.

## Harness는 모델 바깥의 실행 환경입니다

harness에는 도구·정책·자격·상태 저장·환경 시작·검증 절차가 포함됩니다. 초기 세션은 실행 방법·요구 목록·기준선을 만들고 후속 세션은 현재 작업 트리·진행 기록·미완료와 환경을 확인합니다. 작은 항목을 구현하고 검증한 뒤 상태를 바꾸면 실패 위치와 재개 지점을 찾기 쉽습니다.

요구를 JSON으로 저장해도 모델이 완료 boolean만 바꾸면 거짓 완료가 가능합니다. 요구 변경 권한과 검증 상태 갱신 경로를 분리하고 외부 테스트 증거로 판정합니다. 버튼 생성과 클릭 후 저장 성공은 다른 완료 조건입니다. 커밋·게시·배포도 각각 현재 승인 범위를 유지합니다.

## 압축 경계에서 회귀를 시험합니다

도구 접수 직후·파일 수정 후 테스트 전·승인 대기·외부 효과 확인 전에서 강제로 세션을 끊어 재개합니다. 중복 실행·승인 확대·미완료 오인·테스트 누락·불필요한 재탐색을 측정합니다. 긴 무관 자료·문맥 중간의 중요한 조건·상충 버전을 섞어 입력 선택의 강건성도 봅니다.

이 노트는 재개 계약을 설명합니다. 특정 압축 방식이 모든 장기 작업에 최적이라는 실험 결과는 아니며 문맥 절약과 최종 성공·재개 비용을 함께 평가해야 합니다.
