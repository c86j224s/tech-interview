# WAL 커밋·Group Commit·시점 복구의 내구 경계

## 커밋된 행의 페이지가 아직 메모리에 있어도 복구할 수 있습니다

DB가 모든 변경 페이지를 매 커밋마다 최종 위치에 쓰면 많은 랜덤 I/O가 필요할 수 있습니다. WAL은 변경을 복구할 로그를 먼저 내구 기록하고 데이터 페이지는 나중에 반영할 수 있게 합니다. 변경 페이지가 저장되기 전에 그 페이지 복구에 필요한 로그가 먼저 안전한 지점에 있어야 하는 write-ahead 순서를 지킵니다.

커밋 성공의 정확한 내구 지점은 DB 설정과 OS·파일시스템·장치의 flush 계약에 달렸습니다. 로그가 DB 메모리나 OS cache에만 있는데 성공을 반환하는 비동기 정책은 전원 손실에서 최근 쓰기를 잃을 수 있습니다. write 시스템 호출 성공과 장치 내구화를 같은 것으로 보지 않습니다.

## 로그·페이지·응답을 다른 사건으로 기록합니다

| 사건 | 의미 | 남는 조건 |
| --- | --- | --- |
| 로그 레코드 생성 | 복구 정보가 준비됨 | 메모리만일 수 있음 |
| 약속한 WAL flush | 로그 내구 조건 충족 | 장치·설정 보장 |
| commit 응답 | 해당 정책상 성공 통지 | 클라이언트 도달 여부 |
| 데이터 페이지 기록 | 최종 페이지 반영 | 모든 커밋과 같은 시각 아님 |
| replica 확인 | 특정 복제 단계 확인 | 수신·flush·replay·승격 범위 |

PostgreSQL WAL·InnoDB redo/binlog·SQL Server transaction log는 설정·복구·동기화 범위가 다릅니다. 모든 엔진이 WAL에서 같은 방식으로 undo한다고 가정하지 않습니다. 복구는 redo·undo·MVCC 가시성 등 해당 엔진의 절차로 미완료 변경이 정상 커밋처럼 보이지 않게 해야 합니다.

## Group Commit은 여러 거래의 Flush 비용을 나눕니다

여러 커밋의 로그를 한 flush에 포함하면 디스크 왕복 비용을 분담할 수 있습니다. 각 거래는 자신의 로그가 약속한 지점까지 포함된 뒤 응답해야 같은 내구 계약을 유지합니다. 묶이기를 기다리는 시간과 부하가 낮을 때의 지연·throughput을 함께 봅니다. group commit 자체가 데이터를 일부 잃는 기능인 것은 아니며 flush 지연 정책과 구분합니다.

checkpoint는 더티 페이지·복구 시작 범위와 로그 재생량에 영향을 줍니다. 너무 잦으면 정상 I/O·추가 로그 비용이 늘 수 있고 너무 드물면 재시작 복구량·로그 공간이 커질 수 있습니다. checkpoint가 모든 커밋을 한꺼번에 만드는 거래도 아니고 백업과 동일한 것도 아닙니다. 백업·replica·CDC 보존 때문에 checkpoint 이전 로그도 더 오래 필요할 수 있습니다.

## 특정 시점 복구에는 기준 백업 뒤 연속된 로그가 필요합니다

오전 1시 백업 뒤 10시 5분의 잘못된 DELETE 직전으로 돌아가려면 해당 기준 백업과 이후 목표 지점까지의 연속 로그·필요 키·설정이 있어야 합니다. 중간 로그 하나가 없으면 그 뒤로 재생할 수 없을 수 있습니다. DB별 recovery model·archive·binlog·log backup 절차를 확인합니다.

벽시계 시각만으로 목표를 모호하게 정하지 말고 문제 transaction·로그 위치·엔진의 inclusive/exclusive target 의미를 확인합니다. 먼저 외부 효과가 차단된 별도 환경에 복원해 데이터를 검사합니다. 운영 DB를 급히 덮으면 삭제 이후 정상 변경도 잃을 수 있습니다.

## 복원된 Outbox가 외부 결제를 다시 보내지 않게 합니다

복원 DB에는 과거 미발행 outbox·미완료 작업·이미 외부에서 성공한 결제가 남을 수 있습니다. 복원 환경의 네트워크·자격·worker 실행을 제한하고 외부 원장과 대사합니다. 데이터 복원 성공을 이유로 예전 작업을 무조건 재실행하지 않습니다.

일부 삭제 행만 운영에 가져올 때는 현재 version·키·외래키·후속 변경·개인정보 상태와 충돌을 확인합니다. 같은 이름의 신규 계정에 옛 자료를 잘못 연결하지 않습니다. 기준 복원과 선택적 병합은 다른 승인·검증 범위입니다.

## 응답을 받은 쓰기와 불확실한 쓰기를 나눠 확인합니다

정해진 내구 정책에서 성공 응답을 받은 커밋은 해당 장애 모형의 복구 뒤 존재해야 합니다. 응답을 못 받은 요청은 커밋되었거나 아닐 수 있으므로 논리 ID로 결과를 조회해 한 번의 효과로 수렴시켜야 합니다. 비동기 replica 승격에서 dedupe 기록까지 손실될 수 있는 한계는 별도입니다.

정상 종료만 시험하지 말고 승인된 격리 환경에서 프로세스 중단·호스트 손실·로그 연속성 누락·실제 restore를 확인합니다. 최신 유효 복구 위치와 서비스 쓰기 재개 시각으로 RPO·RTO를 측정합니다. 현재 작업에서는 DB 전원·flush·PITR 실험을 실행하지 않았으며 본문은 내구와 복구 계약 설명입니다.
