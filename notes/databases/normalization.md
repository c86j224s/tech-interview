# 정규화의 사실 분리와 모든 후보키 검사

## 한 행에 수강과 강좌를 묶으면 수명이 엉킵니다

수강 신청 행마다 학생 이름·강좌명·교수명을 복사하면 강좌명 하나를 바꿀 때 그 강좌를 신청한 모든 행을 찾아 고쳐야 하고, 한 행을 빠뜨리면 서로 다른 이름이 남습니다. 이렇게 한 사실을 수정할 때 여러 행을 함께 고쳐야 하는 문제가 수정 이상입니다. 수강생이 없으면 강좌만 등록할 수 없거나 마지막 신청을 삭제했을 때 강좌 정보까지 사라지는 것도 각각 삽입 이상과 삭제 이상입니다. 따라서 문제는 같은 값의 반복 자체가 아니라 서로 다른 사실과 수명이 한 행에 묶인 데 있으며, 여러 신청에 같은 강좌 ID를 두는 관계 표현까지 없애면 연결 정보가 사라집니다.

## 학생·강좌·신청의 사실을 나눕니다

| 테이블 | 결정 관계의 예 | 남길 사실 |
| --- | --- | --- |
| Student | student_id → name | 학생 자체 정보 |
| Offering | offering_id → course·term·teacher | 학기별 개설 정보 |
| Enrollment | (student_id, offering_id) → enrolled_at·grade | 관계 자체 정보 |

같은 학생이 같은 개설 강좌에 한 번만 신청한다는 전제라면 복합 UNIQUE로 중복을 막고 양쪽 외래키로 존재를 강제할 수 있습니다. 재수강·취소 후 재신청 이력을 여러 행으로 남긴다면 attempt 또는 별도 관계 ID와 현재 활성 제약이 필요합니다. 관계의 성적을 학생 테이블에 옮기면 어떤 강좌의 성적인지 잃습니다.

## 주문 예제로 부분 종속과 이행 종속을 추적합니다

R(주문번호, 상품번호, 상품명, 수량, 고객번호, 고객명)에서 한 주문의 동일 상품은 한 행이고 상품명·고객명은 현재 정보라고 하겠습니다. `(주문번호, 상품번호)`가 그 상세 행을 식별하는 후보키이며 상품번호→상품명, 주문번호→고객번호, 고객번호→고객명이 성립합니다.

1NF는 한 칸에 선택한 도메인의 하나의 원자값을 두는 상태이므로 상품 목록을 문자열이나 JSON 하나에 숨긴다고 관계 제약이 자동으로 생기지 않습니다. 2NF에서는 어떤 후보키의 진부분에만 종속되는 비주요 속성이 없어야 합니다. 비주요 속성은 어느 후보키에도 속하지 않는 속성입니다. 이 예에서 상품명은 상품 테이블로, 고객번호는 주문 테이블로 분리하고 상세에는 두 ID와 수량을 남깁니다. 주문번호→고객번호→고객명처럼 중간 속성을 거쳐 고객명이 결정되는 이행 종속도 남으므로 고객명을 고객 테이블로 옮기며, 다른 저장 모델을 택하면 그 모델의 질의·검증 규칙을 별도로 설계합니다.

## 3NF는 Primary Key 하나만 검사하지 않습니다

정확한 3NF 조건은 모든 비자명 함수 종속 X→A에서 X가 superkey이거나 A가 어떤 후보키에 속하는 prime attribute인 것입니다. “비키는 키에만 의존한다”는 요약은 여러 후보키가 있을 때 예외를 놓칠 수 있습니다. 2NF 역시 선택한 기본키뿐 아니라 모든 후보키의 부분 종속을 봅니다.

예를 들어 R(A,B,C,D)에 A→BC, BC→AD, B→D가 있으면 A와 BC가 후보키일 수 있습니다. 단일 열 A를 PK로 골라도 비주요 D가 다른 후보키 BC의 일부 B에 종속되는 문제를 놓치면 안 됩니다. surrogate ID 추가가 원래 업무 종속을 지우지 않는 이유입니다. 실제 후보키·prime 속성은 폐포와 최소성으로 확인합니다.

## 현재 사실과 당시 Snapshot을 혼동하지 않습니다

주문 당시 상품명·가격을 보존해야 한다면 현재 Product의 이름을 JOIN하는 것으로 대체하면 역사적 의미가 바뀝니다. 당시 사실은 주문 항목에 독립 snapshot으로 남을 수 있습니다. 같은 문자열이 반복된다고 항상 제거할 중복은 아닙니다.

반면 현재 이름의 조회 최적화를 위해 복사한 것은 파생 읽기 모델입니다. 원본·변경 전파·버전·재구축·불일치 탐지 책임을 정해야 합니다. 정규형을 높이기 위해 역사 의미를 바꾸거나 테이블 수를 늘리는 것 자체를 목표로 하지 않습니다.

## 외래키는 삭제 권한과 보관 수명을 정하지 않습니다

외래키는 자식 행이 참조하는 부모 행의 존재 관계를 지키는 장치이지, 부모를 지울 권한이나 두 행의 보존 기간을 정하지 않습니다. `CASCADE`는 부모 삭제를 자식 삭제로 연쇄하고, `RESTRICT`·`NO ACTION`은 참조가 남아 있으면 삭제를 막는 정책이며, `SET NULL`은 nullable(NULL을 허용하는) 자식 키를 NULL로 바꿀 수 있습니다.

각 정책의 검사 시점과 deferred(제약 검사를 거래 끝으로 미루는 기능) 지원은 엔진별로 다릅니다. 주문·결제·성적 같은 이력은 계정 삭제와 같은 수명을 가져야 하는지, 익명화·개인정보 분리·접근 제한을 어떻게 할지는 업무 규칙으로 정해야 합니다.

대량 cascade는 한 부모 삭제도 많은 자식·인덱스·로그·잠금을 만들 수 있습니다. 배치로 나눌 때는 중간 상태·재개 키·동시 삽입 차단을 설계하고, ORM 옵션과 실제 DB FK가 같은지와 마지막 신청 삭제가 강좌 자체를 지우지 않는지도 시험합니다.

## 분해 뒤에도 의미와 비용을 같이 확인합니다

이름 변경·신청 없는 강좌 생성·마지막 신청 삭제·동시 중복 신청·재수강을 합성 데이터로 검사합니다. 모든 후보키의 폐포와 부분 종속을 검산하고 조회의 JOIN 행 수·인덱스·반환 바이트를 비교합니다. 이 노트는 모델 설계이며 특정 DB에서 정규화 migration과 삭제 실험을 실행한 결과는 아닙니다.
