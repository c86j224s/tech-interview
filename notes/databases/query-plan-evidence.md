# 실행 계획 회귀의 추정·메모리·대기 근거

## SQL이 같아도 데이터와 계획과 자원은 달라집니다

한 고객의 주문이 10개일 때 선택한 seek+lookup 계획이 주문 10만 개인 고객에게도 재사용되면 많은 추가 읽기가 생길 수 있습니다. 코드 배포가 없어도 데이터 분포·통계·parameter·계획 캐시·메모리·잠금이 바뀝니다. 먼저 실제로 계획이 바뀐 것인지 같은 계획이 다른 자원 상태에서 느려진 것인지 구분합니다.

질의 fingerprint·정확한 환경·바인드 타입과 안전한 분포 정보·실행 시각·plan ID를 모아 이전 정상 사례와 비교합니다. 추정 cost 숫자를 실제 밀리초로 해석하지 않습니다.

## 추정과 실제가 처음 크게 갈리는 연산을 찾습니다

| 관측 | 가능한 원인 | 후속 확인 |
| --- | --- | --- |
| 추정 1, 실제 10만 | 분포·상관·parameter plan | join 반복·lookup·spill |
| 추정 과다, 실제 소수 | 부정확한 선택도 | 큰 grant·불필요 scan |
| 계획 같고 I/O 증가 | cache·스토리지·동시 작업 | 논리/물리 읽기·대기 |
| 계획 같고 lock 대기 증가 | 긴 transaction·충돌 | blocker·보유 시간 |
| 컴파일 증가 | 캐시·재컴파일·쿼리 변형 | 컴파일 CPU·계획 수 |

최종 반환 행만 보지 말고 인덱스에서 읽은 후보·필터 후 행·각 join의 반복 횟수를 봅니다. 실제 plan 수집이 쿼리를 실행하는 옵션이라면 운영 변경문에 무심코 적용하지 말고 승인된 사본·읽기 범위에서 사용합니다.

## 단일 컬럼 통계가 최신이어도 상관을 놓칠 수 있습니다

100만 행 중 도시 A가 10%, 우편번호 Z가 1%이고 Z가 모두 A에 속한다고 합시다. 독립 선택도 가정이면 둘의 결합을 0.1×0.01=0.001, 즉 1천 행으로 예상할 수 있지만 실제는 1만 행입니다. 이것은 단순 모델의 예이며 모든 옵티마이저가 항상 독립 곱만 사용한다는 뜻은 아닙니다.

지원되는 다중 컬럼·확장 통계의 dependency·distinct·빈도 정보가 부족한 근거를 보완할 수 있습니다. 그러나 엔진마다 표현 범위와 join 추론·parameter 지원이 다릅니다. 새 인덱스와 통계 보강은 다른 처방이며 통계를 무조건 늘리는 것도 분석·유지 비용을 만듭니다.

## 부족한 메모리와 과다 예약은 다른 증상입니다

sort·hash의 실제 데이터가 메모리에 들어가지 않으면 임시 디스크로 spill할 수 있습니다. 반대로 추정이 너무 커서 큰 메모리를 예약하면 자신의 실행은 빠르더라도 다른 쿼리가 메모리 허가를 기다릴 수 있습니다. 요청·grant·실사용·spill·대기와 실제 행 수를 같이 봅니다.

SQL Server의 query memory grant·feedback, PostgreSQL의 work_mem 및 연산자·parallel worker별 사용, MySQL의 해당 버퍼·임시 테이블은 같은 전역 예약 모델이 아닙니다. 설정 하나를 “쿼리당 절대 메모리”로 일반화하지 않습니다. 연산자 수·병렬도·동시 쿼리가 곱해져 총 사용량이 커질 수 있습니다.

메모리를 늘리기 전에 불필요한 행·넓은 컬럼·잘못된 join·통계·index 순서를 검토합니다. 단일 쿼리 개선이 전체 workload의 처리량·OOM·p99를 악화시키지 않는지 확인합니다.

## Plan 강제와 재컴파일은 수명이 있는 완화책입니다

좋았던 plan 고정·힌트·재컴파일·통계 갱신은 상황에 따라 도움되지만 다른 parameter나 미래 분포에서 나빠질 수 있습니다. SQL Server Query Store·PostgreSQL 계획 관측·MySQL optimizer 도구의 지원 범위를 구분합니다. 적용 대상·기대 효과·회귀 경보·해제 기준을 기록합니다.

통계 갱신 직후에도 최적 계획이 자동 보장되지는 않습니다. 작은 고객·큰 고객·희귀 조합·없는 조합·cold/warm·동시 쓰기·복제/백업 부하를 비교합니다. 평균 한 값보다 입력 분포별 tail과 자원 사용을 봅니다.

## 이력은 재현에 충분하고 보관은 제한적으로 둡니다

query ID·plan ID·시각·엔진 버전·통계 변경·parameter의 안전한 크기/분포 특징·실제 행·읽기·대기를 연결합니다. 모든 실행의 전체 plan과 민감 parameter를 무제한 저장하지 않습니다. 느린 사례·계획 변경·오류·대표 입력을 선별하고 드문 큰 tenant가 표본에서 사라지지 않게 별도 범주를 둡니다.

수집 오버헤드·보관 기간·접근권한·원문 마스킹을 정합니다. 과거 parameter를 저장했다면 테스트 데이터로 안전하게 재현하고 타인의 실제 자료를 외부에 보내지 않습니다. 현재 작업에서는 제품별 plan·grant·JFR 같은 실행 관측을 수행하지 않았으며 본문은 진단 절차와 산술 예제입니다.
