# 합의 구성 변경의 공동 쿼럼과 노드 재가입

## 서버 목록을 동시에 배포해도 실제 적용은 동시에 되지 않습니다

old={A,B,C}, new={C,D,E}로 바꾸려 합니다. A·B는 old의 과반이고 D·E는 new의 과반인데 서로 공유 노드가 없습니다. 각자가 다른 목록으로 결정을 확정하면 같은 위치에 충돌한 값을 만들 수 있습니다. 합의 구성은 단순 주소 설정이 아니라 누가 결정 권한을 갖는지 나타내는 프로토콜 상태입니다.

구성 변경은 현재 이력에 연결되어야 합니다. 각 서버의 파일을 새 목록으로 덮는 것이 그 이력을 만들지는 않습니다.

## 공동 단계에서는 전체 다섯 중 아무 셋이 아닙니다

joint consensus를 지원하는 모형은 전환 중 old 과반과 new 과반을 모두 요구합니다. old 2개, new 2개의 조건을 동시에 만족해야 합니다.

| 응답 집합 | old 안 수 | new 안 수 | 공동 조건 |
| --- | --- | --- | --- |
| A,B,D | 2 | 1 | 불충족 |
| A,C,D | 2 | 2 | 충족 |
| C,D,E | 1 | 3 | 불충족 |
| A,B,D,E | 2 | 2 | 충족 |

C가 두 집합에 들어간다고 모든 성공 응답에 C가 꼭 있어야 하는 것은 아닙니다. 두 과반의 조건을 각각 만족시키는 규칙이 핵심입니다. 구체 구현이 joint가 아니라 검증된 단일 멤버 변경 절차를 쓴다면 그 프로토콜을 따라야 하며 두 설명을 임의로 섞지 않습니다.

## Learner의 데이터 준비와 투표 권한은 다릅니다

뒤처진 새 노드를 바로 투표자로 넣으면 quorum의 필요한 응답 수는 늘지만 그 노드가 로그를 처리하지 못해 가용성이 떨어질 수 있습니다. 비투표 learner로 snapshot·log를 따라잡게 하고 저장 안정성·replication lag·apply·실제 성능을 확인한 뒤 승격합니다.

네트워크 연결·프로세스 Ready·로그 끝 숫자 하나만으로 모든 준비를 판단하지 않습니다. 구성 변경 중 leader가 죽으면 joint·최종 구성 항목의 저장·commit·적용 상태를 프로토콜대로 복구해야 합니다. 미커밋 구성 처리를 임의 파일 상태로 대체하지 않습니다.

## 제거한 노드는 주소가 보인다고 자동 투표자로 돌아오지 않습니다

오래된 노드가 예전 로그와 높은 term을 가지고 재등장할 수 있습니다. 현재 구성·cluster ID·노드 자격·term·로그를 검증하고 지원되는 재등록·learner·승격 경로로만 참여시킵니다. 제거 노드의 메시지와 term 영향을 제한하는 규칙·pre-vote 지원은 구현별로 확인합니다.

삭제한 node ID를 다른 새 프로세스에 재사용하면서 옛 디스크·메시지를 섞으면 정체성이 모호해질 수 있습니다. identity·generation·자격 폐기·저장소 fencing을 관리합니다. 서비스 발견 목록에 주소가 있다는 것과 합의 투표자로 등록되었다는 것은 별개입니다.

## 변경 중 필요한 과반이 없으면 정상 전환을 멈춥니다

old 또는 new 조건을 만족하지 못하면 안전한 공동 단계 확정을 할 수 없습니다. 구성 숫자를 강제로 줄이는 것은 장애에서 벗어난 것처럼 보여도 과거 확정 기록을 버릴 수 있는 재해 복구입니다. 정상 변경과 별도 승인·손실 범위·옛 클러스터 차단·원장 대사가 필요합니다.

한 번에 여러 장애 영역의 투표자를 바꾸지 말고 현재 quorum 여유와 대체 node 준비를 확인합니다. node 수뿐 아니라 같은 rack·zone 손실 후 어떤 집합이 통신 가능한지 계산합니다.

## 각 전환 단계에서 리더 손실을 시험합니다

learner 전송 중, 공동 구성 저장·commit 전후, new 확정 전후에 중단을 넣고 같은 로그 위치의 단일 결정과 구성 회복을 확인합니다. 제거 node 복귀·늦은 메시지·자격 오류도 포함합니다. 현재 작업에서는 합의 구성 변경을 실행하지 않았습니다. 본문은 전환 규칙과 검증 설계입니다.
