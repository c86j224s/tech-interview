# C++ RAII 정리와 강한 예외 보장의 차이

## 잠금을 풀어도 이미 차감한 잔액은 돌아오지 않습니다

잠금 안에서 계정 A를 차감하고 B에 입금하려던 중 메모리 할당 예외가 났다고 합시다. lock_guard가 스코프를 벗어나 잠금을 풀어도 A의 차감은 그대로 남을 수 있습니다. RAII는 소유 객체의 수명에 자원 정리를 연결하는 관용구이지 모든 업무 변경의 자동 롤백이 아닙니다.

파일 핸들 닫기, 임시 메모리 해제, 잠금 해제와 관찰 가능한 데이터 상태 복원은 다른 계약입니다. 예외 안전성을 말할 때 무엇이 보장되는지 구분해야 합니다.

## 기본·강한·무예외 보장을 구분합니다

| 보장 | 실패 뒤 약속 | 비용·조건 |
| --- | --- | --- |
| 기본 보장 | 자원 누수 없이 유효한 불변식 유지 | 값은 바뀔 수 있음 |
| 강한 보장 | 관찰 가능한 상태가 변경 전과 같음 | 임시 상태·추가 메모리·커밋 설계 |
| 무예외 보장 | 예외가 밖으로 나오지 않음 | 실제 구현이 던지지 않아야 함 |

소멸자를 noexcept로 선언해도 내부 작업의 실패가 성공으로 바뀌는 것은 아닙니다. 예외가 빠져나오면 terminate될 수 있습니다. 다른 예외로 스택을 푸는 동안 소멸자에서 또 예외를 전파하는 구조는 특히 피해야 합니다.

## 모든 새 상태를 준비한 뒤 하나의 경계로 게시합니다

기존 설정의 routes와 index가 서로 맞아야 한다면 routes만 먼저 바꾼 뒤 index를 만들지 않습니다. 임시 State에 둘 다 완성하고 검증한 다음, 해당 타입·allocator 조건에서 실제로 던지지 않는 교체로 게시합니다.

```text
replacement = build_complete_state(input)   # 실패해도 current는 그대로
validate_invariant(replacement)
with lock protecting current:
    check expected version if derived from old current
    swap_without_throw(current, replacement)
# replacement가 이제 옛 상태를 소유하며 정리
```

routes와 index를 독립 객체로 둔 상태에서 첫 번째 swap 뒤 두 번째 swap이 예외를 던지면, 잠금 없는 독자는 한쪽만 새 상태인 조합을 볼 수 있습니다. 비교자·allocator·외부 핸들처럼 함께 바뀌는 조건까지 새 불변식에 넣어 하나의 State로 준비하고, 그 State를 한 번에 게시해야 합니다.

잠금 없이 여러 필드를 읽는 독자에게는 swap이 원자 snapshot을 주지 않으므로 같은 잠금이나 올바른 snapshot 게시 경계를 사용합니다. 새 상태를 옛 상태에서 계산했다면 다른 writer의 변경을 덮지 않도록 게시 전에 기대 버전을 재검사하거나 재계산·직렬화합니다.

## 생성 중 실패에도 자원 소유자가 있어야 합니다

생성자에서 raw 파일 핸들을 얻은 뒤 다른 멤버 초기화가 던지면 생성에 실패한 객체 자체의 소멸자를 기대할 수 없습니다. 이미 완전히 생성된 멤버는 정리되므로 획득한 자원을 즉시 RAII 멤버에 소유시키는 구조가 안전합니다. “소멸자에서 마지막에 닫는다”만으로 부분 생성 실패를 보호할 수 없습니다.

스택 풀기가 일어나는 예외·정상 반환과 `abort`·프로세스 강제 종료도 다릅니다. 모든 종료에서 소멸자가 실행된다고 가정하지 않습니다. 외부 파일의 일관성은 임시 파일·원자 게시·복구 절차 등 별도 내구 설계가 필요합니다.

## 중요한 실패는 명시적인 commit에서 전달합니다

파일 저장 결과를 호출자가 알아야 한다면 명시적인 `commit`·`flush`·`close`에서 오류를 반환하거나 적절히 전파합니다. 소멸자는 남은 자원의 안전한 정리를 담당하고 중요 저장의 성공을 암묵적으로 결정하지 않게 합니다.

`write`가 성공해도 사용자 공간 버퍼 flush, OS 버퍼 반영, 디스크 내구화, 이름 교체의 내구성은 각각 다른 단계로 남습니다. 따라서 API는 이 중 어느 단계까지 완료되면 성공이라고 볼지 약속해야 합니다. `commit`이 실패했을 때 객체가 재시도 가능한지 폐기만 가능한지를 상태로 표현하고, 외부에 이미 적용됐는지 모르는 실패는 같은 변경을 무조건 재시도하지 않습니다. 첫 시도가 실제로 반영된 뒤 두 번째 시도가 실행되면 중복 효과가 생길 수 있기 때문입니다.

원래 예외와 cleanup 오류가 함께 나면 원래 실패를 잃지 않게 보존하고 정리 오류를 별도로 보고합니다. 비밀 데이터·파일 원문을 진단 로그에 남기지 않습니다. 보상 작업이 유용하더라도 보상 실패와 중간 관찰이 가능한 경우 강한 예외 보장과 같다고 부르지 않습니다.

## 실패 지점을 하나씩 이동하며 확인합니다

임시 상태의 첫 할당·중간 원소 복사·검증·커밋 전 단계에 실패를 주입하고 원본 값과 불변식·열린 핸들 수를 대조합니다. 게시 뒤 옛 상태 정리 비용이 민감한 스레드의 지연을 만들지 않는지도 봅니다.

파일 실험은 일시적인 테스트 디렉터리에서 저장 실패·close 실패·중단을 구분합니다. 이 노트는 보장 설계와 시험 절차이며 아직 C++ 예제를 컴파일하거나 실제 저장 장애를 주입한 결과는 아닙니다.
