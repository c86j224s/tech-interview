# PyPy Trace JIT의 예열과 실행 경계

## 반복 경로의 JIT 예열 비용

PyPy는 Python 프로그램을 실행하는 런타임으로, trace JIT가 자주 반복되는 경로를 기록한 뒤 그 경로에 맞춘 기계어를 만들 수 있습니다. 타입과 분기가 안정적인 긴 순수 Python 루프라면 매 반복마다 인터프리터가 처리하는 비용을 줄일 여지가 있지만, 짧은 CLI에서는 추적·컴파일 비용을 지불한 뒤 회수하기 전에 프로세스가 끝나 더 빠르지 않을 수 있습니다.

Python 언어 의미와 PyPy의 최적화 전략은 다릅니다. 런타임을 바꿨다는 사실만으로 모든 라이브러리가 같은 성능·호환성을 제공하지 않습니다.

## Trace 가정과 Guard 검증

정수만 들어오는 반복 경로를 관찰해 특화 코드를 만들면, 실행할 때도 각 값이 그 가정을 지키는지 guard가 확인합니다. 다른 타입이나 분기가 나타나면 guard에서 side exit로 빠져 interpreter를 다시 타거나 bridge trace를 붙이는 대응이 일어날 수 있으며, 입력 한 번의 변화가 모든 최적화 코드를 무조건 폐기한다는 뜻은 아닙니다.

## C 확장 지원 방식과 내부 계산 비중

| 경로 | PyPy에서 기대할 여지 | 확인할 비용 |
| --- | --- | --- |
| 긴 순수 Python 반복 | trace 최적화 | 예열·guard·메모리 |
| 짧은 프로세스 | 제한적일 수 있음 | 시작·컴파일 준비 |
| 대부분 native 수치 계산 | Python 부분 이득이 작을 수 있음 | ABI·호환 계층·내부 thread |
| DB·네트워크 중심 | CPU 부분만 개선 | 외부 대기·연결 상한 |

CPython C API 확장이 PyPy에서도 같은 객체 표현·ABI·성능으로 동작한다고 전제하지 말고, cpyext·CFFI 중 어떤 경로를 쓰는지와 패키지 버전·wheel·플랫폼을 맞춰 확인합니다. 설치가 끝나도 기능·예외·자원 정리·성능을 따로 시험해야 하며, JIT와 GIL·스레드 병렬성은 별개라 CPU 코드가 빨라졌다고 여러 코어를 자동으로 쓰는 것은 아닙니다.

## 전체 서비스의 개선 가능 비율

요청 시간의 20%만 Python 계산이고 그 부분이 두 배 빨라졌다면 이상적인 전체 시간은 `0.8 + 0.2/2 = 0.9`배입니다. 약 1.11배 처리 속도 개선에 해당하는 단순 산술이며 실제 경합·메모리·동시성 변화는 추가로 봐야 합니다. hot loop의 큰 배수를 서비스 전체 배수로 보고하면 안 됩니다.

CPython과 PyPy 비교는 같은 입력·패키지 의미·CPU·메모리 한도에서 cold start·예열 곡선·steady state·입력 타입 변화 구간을 나눕니다. 평균뿐 아니라 p95·p99·메모리 피크·오류·프로세스 재시작을 기록합니다. 배포 이미지·관측 도구·지원 패키지 유지 비용도 선택에 포함합니다.

## JIT 로그와 프로파일의 시간축 대조

사용 버전이 지원하는 JIT 로그·profiler로 어느 loop가 trace되었는지, guard에서 얼마나 벗어나는지, bridge와 컴파일 비용이 언제 생겼는지 확인합니다. 로그 옵션은 버전별 문서에 맞추고 과도한 로깅이 측정 결과를 바꾸는지도 비교합니다.

정상 타입·혼합 타입·예외·C 호출 빈도를 바꾸되 기능 결과가 같은지 먼저 검사합니다. 현재 작업에서 PyPy를 실행하지 않았으므로 실제 trace 생성·guard 실패·성능 향상을 측정했다고 주장하지 않습니다. 이 노트는 런타임 선택을 위한 검증 절차입니다.
