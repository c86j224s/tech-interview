# Go Slice의 기반 배열과 보관 수명

## 변수 두 개가 원소 두 벌을 뜻하지는 않습니다

슬라이스는 기반 배열을 가리키는 정보와 len·cap을 가진 값으로 이해할 수 있습니다. `b := a`는 이 헤더 정보를 복사하므로 길이를 각각 갖지만 원소 저장소는 공유합니다. Go가 값 전달이라는 사실과 원소까지 독립이라는 주장은 다릅니다.

```go
a := []int{10, 20, 30}
b := a
b[0] = 99
fmt.Println(a) // [99 20 30]
```

원소가 정수라면 새 배열을 할당해 copy하면 독립적으로 수정할 수 있습니다. 원소가 포인터·map·slice라면 바깥 원소를 복사해도 그 안의 참조 대상은 공유합니다. 깊은 복사의 범위는 도메인 소유 모델로 정합니다.

## Append는 남는 용량을 사용할 수 있습니다

| 연산 | 기반 배열 | 헤더 |
| --- | --- | --- |
| `b := a` | 공유 | 복사 |
| `b[0] = x` | 공유 원소 수정 | 길이 유지 |
| 여유 cap 안 append | 기존 배열 재사용 | 반환된 slice의 len 증가 |
| cap 초과 append | 새 배열에 원소 이전 | 새 배열·len·cap 반환 |
| make 후 copy | 새 바깥 배열 | 독립 헤더 |

```go
a := []int{10, 20, 30}
b := a[:1]
b = append(b, 99)
fmt.Println(a, b) // [10 99 30] [10 99]
```

b의 len은 1이지만 cap은 3이므로 append가 a의 두 번째 원소를 덮습니다. a의 len이 2로 바뀌는 것은 아닙니다. 함수 안 append가 반환한 새 헤더를 호출자에게 전달하지 않으면 원소 일부는 바뀌고 길이는 그대로인 상태나, 새 배열이 생겨 추가 원소가 전혀 보이지 않는 상태가 될 수 있습니다. 확장을 지원하는 API는 반환 slice를 명시합니다.

## Cap 제한은 기존 원소를 복제하지 않습니다


`a[:1:1]`을 만든 뒤 b[0]을 바꾸면 공유가 남고, b에 한 원소를 append하면 cap을 넘으므로 새 저장소를 사용합니다. 이미 존재하는 원소의 수정 격리와 여유 용량의 append 격리는 다른 조건입니다. cap을 줄여도 원래 큰 할당이 작은 할당으로 바뀌지 않습니다.

## 작은 Slice가 큰 배열을 오래 붙잡을 수 있습니다

100 MiB 수신 버퍼에서 필요한 20바이트만 잘라 장기 캐시에 보관하면 작은 slice가 큰 기반 배열의 수명을 유지할 수 있습니다. 보관 경계에서 필요한 부분을 작은 새 slice로 copy하면 수명을 분리할 수 있습니다. 짧게 빌리는 경로는 복사를 아끼고 오래 남기는 경로는 적은 복사 비용으로 큰 보유량을 줄일 수 있습니다.

포인터 원소가 있는 slice의 논리 삭제 후 뒤쪽 슬롯에 불필요한 참조가 남는지도 확인합니다. 그 배열이 계속 살아 있으면 지운 것처럼 보이는 객체를 붙잡을 수 있습니다. 더 이상 필요 없는 슬롯을 clear하는 방식은 다른 별칭이 그 슬롯을 필요로 하지 않는 소유 조건 아래 적용합니다. 특정 라이브러리 삭제 함수의 tail 정리 동작은 Go 버전에 따라 확인합니다.

heap profile은 주로 할당 위치와 표본 보유량을 보여 주며 모든 객체의 root 경로를 자동으로 제공하는 도구는 아닙니다. 큰 버퍼를 만드는 호출 위치와 장기 보관 코드·수명 추적을 함께 조사하고, 필요하면 더 구체적인 덤프·계측을 사용합니다. in-use 감소와 RSS 반환 시점도 다릅니다.

## 비동기 전달 뒤 풀에 돌려줄 때를 정합니다

수신 버퍼의 slice를 worker에 보내고 즉시 pool에 반환하면 worker가 읽기 전에 다른 요청이 같은 배열을 덮을 수 있습니다. 채널로 slice 헤더를 전송했다고 데이터 소유권이 자동 복제되지 않습니다. 완료까지 원본 버퍼를 유지하거나 필요한 영역을 복사하거나 명시적으로 소유권을 이전합니다.

copy는 겹치는 slice 사이 복사를 지원하지만 다른 goroutine이 동시에 수정하는 배열에 동기화 없이 써도 된다는 뜻은 아닙니다. nil slice와 길이 0의 non-nil slice도 len·range는 비슷해도 nil 검사·일부 JSON 표현에서 다를 수 있으므로 외부 계약을 정합니다. 용량 성장 배율은 런타임 구현 세부로 취급합니다.

## 헤더·원소·보유량을 각각 확인합니다

대입, cap 안 append, cap 초과 append, full slice 직접 수정, make+copy, 중첩 포인터를 작은 예제로 검사합니다. 큰 배열 보유는 동일 부하와 보관 기간에서 필요한 부분 복사 전후 in-use·할당률·RSS를 따로 봅니다. 버퍼 반환과 worker 읽기 경쟁은 race detector와 순서를 제어한 테스트로 확인합니다. 이 노트는 기대 동작과 측정 절차이며 실제 서버 메모리 프로파일을 측정한 결과는 아닙니다.
