# C++ 저장 공간과 객체·반복자의 유효성

## 주소가 읽혀도 올바른 객체를 읽는 것은 아닙니다

수신 버퍼의 네 바이트를 uint32_t 포인터로 캐스팅해 읽는 코드를 생각해 보겠습니다. 길이가 네 바이트 이상이라는 검사만으로 충분하지 않습니다. 주소 정렬·객체 수명·타입 접근 규칙·byte order가 맞아야 합니다. 운 좋게 한 CPU에서 값이 나왔다고 언어 계약이 유효한 것은 아닙니다.

vector에서 원소 주소를 보관한 경우도 비슷합니다. 주소가 여전히 매핑되어 있다고 그 주소의 객체가 계속 같은 논리 원소라고 보장할 수 없습니다. 저장 공간의 존재와 객체의 정체성·수명을 나누어야 합니다.

## 외부 바이트와 로컬 객체 표현은 다른 형식입니다

| 조건 | 질문 | 크기 검사만으로 알 수 있나 |
| --- | --- | --- |
| 정렬 | 이 타입 접근에 맞는 주소인가 | 아니오 |
| 수명 | 해당 타입 객체가 이 위치에서 살아 있는가 | 아니오 |
| 타입 접근 | 이 glvalue 타입으로 접근할 수 있는가 | 아니오 |
| 표현 | endian·padding·필드 폭이 맞는가 | 아니오 |
| 값 의미 | 길이·enum·범위가 도메인에 맞는가 | 아니오 |

`reinterpret_cast`로 버퍼 주소를 `T*`로 바꿔도 그 위치에서 임의의 `T` 객체 수명이 시작되지는 않습니다. 일부 implicit-lifetime 타입과 `memcpy` 같은 메모리 연산의 적용 규칙은 표준 버전에 따라 정해지므로, `memcpy`만 하면 모든 타입이 생성된다고 일반화하지 않습니다. packed 구조체는 구현 기능으로 padding과 정렬의 일부만 바꿀 뿐, aliasing·객체 수명·외부 포인터의 유효성은 대신 보장하지 않습니다.

## 정해진 필드를 바이트 단위로 해석합니다

8비트 바이트와 uint32_t를 제공하는 구현에서, big-endian 4바이트를 읽는 예제입니다. 필요한 헤더는 `<cstdint>`, `<span>`, `<stdexcept>`입니다.

```cpp
std::uint32_t read_be32(std::span<const std::uint8_t> input) {
    if (input.size() < 4) throw std::runtime_error("truncated length");
    return (std::uint32_t(input[0]) << 24)
         | (std::uint32_t(input[1]) << 16)
         | (std::uint32_t(input[2]) << 8)
         |  std::uint32_t(input[3]);
}
```

각 바이트를 unsigned 32비트로 변환한 뒤 shift해 부호 있는 좁은 정수 승격의 함정을 피합니다. 결과를 얻은 뒤에도 최대 허용 길이와 남은 입력 바이트를 검사해야 합니다. 구조체 포인터를 복원하거나 외부 값을 로컬 포인터로 사용하는 방식은 피합니다.

trivially copyable 객체의 표현 복사에 memcpy·bit_cast를 사용할 수 있지만 크기·타입·유효 표현 등 조건이 있습니다. 특히 bit_cast는 크기가 같은 trivially copyable 타입이라는 전제를 요구하며 의미 있는 유효 값을 임의 입력에서 보장해 주는 범용 디코더가 아닙니다. enum·bool·포인터처럼 외부 비트를 그대로 신뢰하기 어려운 값은 명시적으로 검증합니다.

## Vector 연산별 무효화 범위가 다릅니다

| 연산 | 재할당 여부 | 원소 포인터·참조·iterator |
| --- | --- | --- |
| push_back | 재할당 발생 | 기존 것 모두 무효화 |
| push_back | 재할당 없음 | 기존 원소는 유지, 옛 end는 무효화 |
| 중간 insert | 재할당 없음 | 삽입 위치와 그 뒤는 무효화 |
| erase | 일반적으로 용량 유지 | 삭제 위치와 그 뒤는 무효화 |
| reserve | 기존 capacity 초과로 재할당 | 모두 무효화 |

reserve는 정해진 크기 안에서 재할당을 줄일 뿐 영구 안정성을 만들지 않습니다. erase 뒤 같은 인덱스에는 다른 원소가 올 수 있습니다. 무효화된 iterator를 역참조해 값이 그럴듯한지 확인하는 방식 자체가 잘못된 검사입니다.

## 비동기 참조는 저장소의 모든 변경과 함께 설계합니다

callback이 끝날 때까지 구조 변경을 금지하거나, 객체를 독립 할당해 안정적인 소유 참조를 전달하거나, ID·세대를 통해 현재 객체를 다시 찾는 방식을 선택할 수 있습니다. `vector<unique_ptr<T>>`에서는 vector가 이동해도 소유된 T의 주소는 유지될 수 있지만 해당 원소 삭제가 T를 파괴한다는 조건은 남습니다.

list·deque도 모든 iterator·참조가 모든 연산에서 유지되는 것은 아닙니다. 필요한 연산의 표준 계약을 확인해야 합니다. 객체 풀의 같은 주소 재사용도 옛 포인터를 영구 유효하게 만들지 않으며 이전 소멸과 새 수명 시작·별칭 사용 규칙을 지켜야 합니다.

## 정의된 동작의 결과와 진단용 실패를 구분합니다

디코더는 잘린 입력·주소 offset·최댓값·허용 범위를 시험하고 알려진 바이트 벡터와 결과를 대조합니다. vector는 capacity를 의도적으로 넘기고 새 유효 iterator를 다시 얻어 결과를 검사합니다. 무효 참조 진단이 필요하면 별도 격리 테스트와 sanitizer·디버그 iterator 모드를 사용하고 결과를 정상 프로그램의 기대 동작으로 기록하지 않습니다.

sanitizer가 모든 aliasing·수명 UB를 찾지는 못합니다. `scripts/verify-cpp-study.cpp`를 Apple Clang 21.0.0, C++20, ASan·UBSan으로 실행해 offset이 있는 바이트 입력·잘린 입력 거절과 재할당 없는 append·erase 뒤 새 원소 조회를 확인했습니다. 무효화된 포인터를 일부러 역참조하지 않았으며, 이 통과를 모든 아키텍처·객체 수명 규칙의 증명으로 보지 않습니다.
