# 여러 스레드가 같은 설정 데이터를 읽고 한 항목만 바꿔 공유하려 합니다. 불변 데이터가 안전성과 비용에 미치는 영향은 무엇인가요?

## 구두 답변

불변 데이터는 만든 뒤 그 객체 자체를 바꾸지 않는 값입니다. 여러 실행 흐름이 같은 인스턴스를 읽을 때 누가 언제 필드를 바꿨는지 조정할 필요가 줄어들어, 잠금 누락이나 관찰 중간 상태를 예방하기 쉽습니다. 변경이 필요하면 새 값을 만들고 참조를 교체하므로 이전 버전을 읽던 코드와 새 버전을 읽는 코드가 서로의 객체를 훼손하지 않습니다.

하지만 `final`이나 읽기 전용 참조 하나만으로 깊은 불변이 되지는 않습니다. 불변 객체가 내부의 가변 목록을 그대로 노출하거나, 목록 원소가 변경 가능하면 외부에서 내부 상태를 바꿀 수 있습니다. 설정 스냅샷이라면 필드뿐 아니라 중첩된 목록·맵·원소까지 변경 경로를 닫고, 외부 입력을 받을 때 복사하거나 불변 값으로 변환하겠습니다. 읽기 전용 뷰는 호출자가 뷰를 통해 수정하지 못하게 할 뿐, 원본을 가진 다른 코드의 변경까지 막지는 않습니다.

매번 큰 트리를 통째로 복사하면 메모리와 CPU 비용이 커질 수 있습니다. 그래서 바뀌지 않은 하위 구조를 재사용하는 구조적 공유와 경로 복사를 사용할 수 있지만, 공유된 원소가 정말 불변이어야 안전합니다. 작은 설정은 전체 복사가 단순하고, 큰 문서나 빈번한 갱신은 공유 구조가 유리할 수 있습니다. 여러 스레드가 최신 스냅샷을 교체할 때는 참조 교체의 원자성뿐 아니라 새 객체의 초기화가 독자에게 보이는 안전한 공개와 이전 객체의 수명도 보장하고, 불변 객체가 여러 데이터를 저장하는 트랜잭션의 원자적 커밋까지 보장한다고 과장하지 않겠습니다.

## 득점 포인트

- 얕은 읽기 전용과 중첩 객체까지 보호하는 깊은 불변을 구분한다.
- 새 버전 생성의 안전성뿐 아니라 전체 복사 비용과 구조적 공유의 전제를 설명한다.
- 공유 스냅샷 교체와 외부 저장의 원자성을 별개의 보장으로 판단한다.

## 감점 포인트

- 참조를 재할당할 수 없으면 내부 객체도 불변이라고 말한다. 가변 목록과 원소가 남을 수 있다.
- 불변 데이터면 동기화가 전혀 필요 없다고 한다. 참조 교체와 외부 자원 커밋에는 별도 원자성이 필요하다.
- 변경 때마다 전체 복사하면 항상 안전하고 좋은 선택이라고 한다. 큰 구조에서는 비용과 지연이 커진다.

## 더 파고들 거리

- 구조적 공유 자료구조에서 한 하위 노드를 바꿀 때 복사해야 하는 경로의 범위는 어떻게 정할까요?
- 불변 스냅샷을 읽는 동안 메모리 회수와 객체 수명을 어떤 방식으로 보장할까요?
- 가변 캐시를 불변 스냅샷으로 바꿀 때 갱신 빈도와 읽기 지연을 어떻게 측정할까요?
