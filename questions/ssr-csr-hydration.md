# 서버가 보낸 HTML은 바로 보이는데 버튼은 잠시 반응하지 않고 hydration 경고도 납니다. SSR·CSR·hydration은 각각 언제 실행되며 무엇을 확인해야 하나요?

## 구두 답변

SSR은 서버가 요청 시점의 데이터를 반영한 HTML을 만들어 보내는 방식이고, CSR은 브라우저가 자바스크립트를 실행해 화면을 구성하는 방식입니다. 실제 애플리케이션은 서버가 첫 HTML을 보내고 브라우저가 번들을 내려받아 상호작용을 연결하는 혼합 형태를 자주 사용합니다. 이때 hydration은 빈 화면에 HTML을 다시 그리는 것이 아니라, 이미 있는 서버 HTML을 클라이언트 렌더 트리와 연결해 이벤트 처리와 상태 로직을 활성화하는 과정입니다.

hydration의 전제는 클라이언트의 최초 렌더 결과가 서버 HTML과 일치해야 한다는 것입니다. 서버와 브라우저가 서로 다른 현재 시각·난수·로케일·데이터를 사용하거나, 렌더 중 `window` 같은 브라우저 전용 API로 분기하면 텍스트나 속성이 달라질 수 있습니다. 개발 환경에서는 경고가 보일 수 있고, 프레임워크가 일부를 복구하더라도 이벤트가 잘못된 요소에 연결되거나 추가 렌더 비용이 생길 수 있으므로 단순히 경고를 숨길 문제로 보지 않겠습니다.

브라우저에서만 알 수 있는 값이 필요하면 최초 렌더에서는 서버와 같은 placeholder를 사용하고 hydration 뒤 effect나 명시적인 클라이언트 상태 전환으로 바꾸겠습니다. 정말 의도적인 단일 텍스트 차이만 예외 옵션으로 억제할 수 있지만 범위를 좁히고 남용하지 않아야 합니다. 서버 HTML의 장점은 빠른 첫 콘텐츠와 검색·공유 가능한 문서이고, CSR은 이후 화면 전환과 사용자별 상호작용에 유리하지만 초기 자바스크립트와 hydration 비용이 있습니다.

선택은 SSR이 항상 우월하다는 식이 아니라 콘텐츠 신선도, 개인화, 자바스크립트 용량, 상호작용 시작 시간으로 정하겠습니다. 검증할 때는 서버 HTML과 클라이언트 최초 출력의 차이, hydration 경고, 실제 상호작용 가능 시점, effect 이후의 의도된 전환을 각각 측정하겠습니다.

## 득점 포인트

- SSR·CSR·hydration을 HTML 생성과 상호작용 연결의 단계로 구분한다.
- 서버와 클라이언트 최초 렌더 불일치의 원인과 비용을 설명한다.
- 브라우저 전용 값의 지연 반영과 예외 억제의 한계를 제시한다.

## 감점 포인트

- hydration이 서버 HTML을 무조건 다시 완전히 그리는 과정이라고 말한다.
- 서버와 클라이언트의 최초 출력이 달라도 프레임워크가 항상 안전하게 고친다고 단정한다.
- SSR이면 자바스크립트와 hydration 비용이 없다고 말한다.

## 더 파고들 거리

- 스트리밍 SSR과 부분 hydration이 첫 콘텐츠와 상호작용 시점에 미치는 영향을 비교해 보세요.
- 서버·클라이언트 데이터 버전이 다를 때 일치성을 어떻게 확보할까요?
- 개인화된 화면에서 캐시와 SSR HTML의 사용자 데이터 노출을 어떻게 막을까요?
