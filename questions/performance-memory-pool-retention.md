# 할당을 줄이려고 객체 풀을 넣었는데 RSS가 줄지 않고 오래된 값이 보입니다. 풀의 비용과 초기화는 어떻게 관리하나요?

## 구두 답변

풀은 할당·해제 비용을 재사용으로 바꾸지만 객체와 버퍼를 오래 보관해 메모리 상주량을 높일 수 있습니다. 반환 시 논리 상태·참조·비밀 데이터와 다음 대여의 초기화 계약을 명확히 해야 합니다.

### 동작 원리와 전제

큰 요청 한 번이 대형 버퍼를 풀에 남기면 이후 작은 요청만 있어도 메모리가 유지될 수 있습니다. 크기 등급·최대 보관량·유휴 회수 정책을 둡니다. 이전 사용자 데이터가 남은 버퍼를 새 응답에 노출하지 않게 길이·초기화·출력 범위를 검사합니다.

### 선택과 실패 처리

비동기 I/O가 끝나기 전에 풀로 반환하면 새 작업이 같은 메모리를 덮을 수 있습니다. 실제 참조 수명과 완료 조건을 확인하고 double return·use-after-return을 방지합니다. 풀 락이 병목이면 할당 감소 이점이 사라질 수 있습니다.

### 구체적인 사례와 검증

I/O 완료 callback이 아직 buffer를 읽는데 timeout 응답 때문에 풀에 반환하면 새 요청이 같은 메모리를 덮을 수 있습니다. 이 오류는 pool 자체의 lock이 있어도 실제 대여 수명이 잘못된 문제입니다. 논리 취소와 물리 I/O 종료를 분리해 완료 후 한 번만 반환합니다. 큰 버퍼가 풀에 오래 남는 경우에는 크기별 상한이나 큰 항목 비보관 정책을 둘 수 있습니다. 재사용 객체의 참조를 reset하지 않으면 다른 큰 객체도 함께 살아 있을 수 있어 retained heap을 확인합니다. 할당 횟수 감소와 메모리 상주량·안전성 개선을 같은 지표로 보지 않겠습니다.

burst·큰 객체·취소·중복 반환·동시 대여를 시험합니다. 할당 횟수뿐 아니라 p99·RSS·대기·메모리 오염을 측정합니다. 풀은 만능 최적화가 아니며 런타임 allocator와 GC가 이미 잘 처리하는 경우 단순 코드가 더 나을 수 있습니다.

## 득점 포인트

- 핵심 구분: 풀은 할당·해제 비용을 재사용으로 바꾸지만 객체와 버퍼를 오래 보관해 메모리 상주량을 높일 수 있습니다.
- 선택 조건: 비동기 I/O가 끝나기 전에 풀로 반환하면 새 작업이 같은 메모리를 덮을 수 있습니다.
- 검증 기준: burst·큰 객체·취소·중복 반환·동시 대여를 시험합니다.

## 감점 포인트

- timeout 응답을 보냈으면 비동기 버퍼를 즉시 풀에 반환해도 된다고 한다.
