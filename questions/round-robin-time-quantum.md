# 긴 계산과 짧은 대화형 작업을 함께 실행합니다. Round Robin의 time quantum을 줄이면 응답성과 문맥 교환 비용이 어떻게 달라지나요?

## 구두 답변

실행 시간을 작게 나누면 다른 작업이 기회를 얻기까지 기다리는 시간이 줄 수 있지만, 너무 작으면 컨텍스트 스위치와 스케줄링 비용이 커집니다. 캐시가 식거나 실제 작업보다 전환에 많은 시간을 쓰면 응답도 악화될 수 있습니다.

반대로 quantum이 매우 크면 먼저 실행된 긴 작업이 오랫동안 CPU를 차지해 FCFS와 비슷한 반응성을 보일 수 있습니다. I/O 대기가 많은 작업은 quantum을 모두 쓰기 전에 자발적으로 멈출 수 있으므로 CPU 계산 작업과 같은 패턴으로 보지 않겠습니다.

저는 시스템 호출과 전환 비용, 작업 길이 분포를 기준으로 첫 응답과 완료 시간의 균형을 보겠습니다. 평균 CPU 사용률만으로 적절한 값을 판단하지 않고 대기열 길이와 짧은 작업의 꼬리 지연을 확인합니다. 실제 OS에서는 임의 조정이 가능한 단일 값이 아닐 수 있으므로 사용 중 스케줄러의 정책 범위를 먼저 확인해야 합니다. 숫자를 줄이는 것보다 사용자가 기다리는 원인을 줄이는 것이 목적입니다.

## 득점 포인트

- 시간 분할과 전환 오버헤드의 교환을 설명한다.
- CPU 작업과 I/O 작업을 구분한다.
- 응답·완료·꼬리 지연을 함께 본다.

## 감점 포인트

- quantum은 작을수록 무조건 좋다고 말한다.
- 모든 작업이 매번 시간을 끝까지 사용한다고 말한다.
- 현재 OS에 교과서 RR 값 하나만 있다고 가정한다.

## 더 파고들 거리

- 실행 가능한 작업 수가 늘면 한 바퀴 대기는 어떻게 바뀔까요?
- 우선순위가 다른 큐에 서로 다른 quantum을 줄 수 있을까요?
- 전환 비용을 실제 프로파일에서 어떻게 측정할까요?
