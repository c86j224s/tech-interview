01

구두 답변

정의를 외우기보다, 원리와 조건을 연결해 설명해 보세요.

가능합니다. 캐시가 없으면 데이터베이스에서 읽어 캐시를 채우는 방식을 캐시 어사이드라고 하는데, 읽기와 쓰기가 겹치면 데이터베이스 갱신 후 캐시를 삭제해도 예전 값이 다시 저장될 수 있습니다. 데이터베이스와 캐시의 변경이 하나의 원자적인 작업으로 묶이지 않기 때문입니다.

예를 들어 캐시가 비어 있는 상태에서 읽기 요청이 데이터베이스의 예전 값을 가져왔다고 하겠습니다. 아직 캐시에는 넣지 않은 사이에 다른 요청이 데이터베이스를 새 값으로 바꾸고 캐시를 삭제합니다. 그 후 처음 읽기 요청이 예전 값을 캐시에 저장하면, 데이터베이스는 새 값인데 캐시는 예전 값을 가지게 됩니다. 모든 명령이 성공해도 실행 순서만으로 불일치가 생기는 것입니다.

따라서 먼저 어느 정도의 오래된 값을 허용할지 정해야 합니다. 짧은 지연을 허용하는 조회라면 TTL로 오래된 값이 계속 남지 않게 하고, 캐시 삭제 실패에 대한 재시도나 변경 이벤트 기반 무효화를 함께 사용할 수 있습니다. 다만 TTL은 개별 캐시 항목의 수명을 제한하는 것이지 전체 시스템의 엄격한 최신성 보장은 아닙니다. 지연된 조회나 읽기 복제본에서 낡은 값을 다시 채우면 문제가 이어질 수 있습니다.

더 강한 제어가 필요하면 데이터 버전과 함께 값을 저장하고 오래된 버전의 쓰기를 거절하는 구조를 고려할 수 있습니다. 이때 버전 비교와 캐시 변경이 원자적이어야 하고, 캐시를 삭제했을 때 비교 기준까지 사라지지 않도록 설계해야 합니다. 모든 갱신 경로를 직렬화하는 방법도 있지만 처리량과 장애 복구 비용이 생깁니다.

재고 차감이나 권한 판정처럼 최신성이 중요한 결정은 캐시 값만 믿지 않고 권위 있는 저장소에서 조건을 검증하는 편이 안전할 수 있습니다. 결국 캐시 삭제 한 줄로 정합성이 해결된다고 보기보다, 경쟁 순서와 실패 경로를 확인하고 허용 가능한 불일치 범위에 맞는 방식을 선택해야 합니다.

02

득점 포인트

이해가 드러나는 지점을 확인해 보세요.

  • 오래된 값이 다시 들어가는 실행 순서를 설명한다. 삭제 실패 없이도 진행 중인 읽기 요청이 예전 값을 재삽입할 수 있음을 짚는다.
  • 정합성 요구부터 확인한다. 잠깐의 오래된 조회를 허용하는 경우와 정확한 상태 판정이 필요한 경우를 구분한다.
  • TTL의 보장 범위를 제한해서 설명한다. 캐시 항목의 만료와 시스템 전체의 최신성 보장을 혼동하지 않는다.
  • 개선책의 전제까지 다룬다. 버전 검사의 원자성, 삭제 이후 비교 기준, 우회하는 갱신 경로 등을 고려한다.
03

감점 포인트

놓치기 쉬운 조건과 오해를 짚어 보세요.

  • “DB를 먼저 갱신하고 캐시를 삭제하면 경쟁 상태가 없다”고 말한다. 진행 중인 읽기 요청이 예전 값을 뒤늦게 저장할 수 있다.
  • “캐시를 두 번 삭제하면 항상 해결된다”고 말한다. 지연 시간을 둔 재삭제는 일부 경쟁을 줄일 수 있지만 모든 요청 지연과 실패를 포괄하는 보장은 아니다.
  • “TTL만 설정하면 최대 그 시간 안에 반드시 최신 값이 보인다”고 단정한다. 오래된 데이터의 재삽입이나 복제 지연까지 고려해야 한다.
  • “버전을 넣기만 하면 안전하다”고 말한다. 비교와 저장을 따로 수행하거나 비교 기준이 사라지면 오래된 쓰기를 막지 못할 수 있다.
04

더 파고들 거리

하나 더 질문하며 이해의 범위를 넓혀 보세요.

  • 캐시 삭제에 실패했는데 데이터베이스 변경은 완료됐다면, 무효화 작업을 어떻게 유실 없이 이어 갈까요?
  • 읽기 복제본의 지연이 캐시와 결합되면 오래된 값이 얼마나 오래 유지될 수 있을까요?
  • 인기 키의 캐시가 만료될 때 많은 요청이 동시에 DB를 조회하는 현상은 어떻게 줄일까요?
  • 캐시에서 권한 정보를 읽는다면 권한 회수의 반영 시간을 어떻게 정의하고 보장해야 할까요?

득점·감점 포인트는 학습용 자기 점검 기준이며, 특정 회사의 실제 채점표가 아닙니다.
