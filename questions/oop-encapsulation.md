# 주문 객체의 필드를 private으로 바꿨지만 setter로 음수 금액이나 잘못된 상태를 넣을 수 있습니다. 캡슐화가 보호해야 할 규칙은 무엇이며 API를 어떻게 바꾸나요?

## 구두 답변

캡슐화는 필드를 private으로 바꾸는 데서 끝나지 않고, 객체가 항상 지켜야 하는 규칙인 불변식을 외부의 임의 변경으로부터 보호하는 설계입니다. 따라서 주문의 상태나 금액을 감추고, 아무 값이나 넣는 setter 대신 결제 승인이나 취소처럼 규칙을 검사하는 동작을 객체가 제공하게 하겠습니다.

예를 들어 주문 금액은 0보다 커야 하고 결제된 주문은 다시 대기 상태가 될 수 없다고 합시다. 필드를 숨겼더라도 public setter가 -1을 그대로 넣도록 허용하면 상태의 유효성은 보호되지 않습니다. `changeAmount(newAmount)`에서 미결제 상태와 양수 조건을 함께 검사하거나, 생성 시 검증하고 이후 금액을 바꾸지 않는 값 객체로 만들면 객체가 관찰되는 모든 시점에 규칙을 유지할 수 있습니다.

다만 모든 데이터를 무조건 숨기고 getter와 setter를 늘리는 것이 좋은 캡슐화는 아닙니다. 호출자가 여러 필드를 읽어 조합해 규칙을 판단하면 불변식이 서비스 곳곳으로 흩어지고, 내부 표현을 바꾸기 어려워집니다. 반대로 단순한 전송용 데이터처럼 규칙이 없는 구조는 공개 필드나 접근자를 써도 비용이 작습니다. 핵심은 정보 은닉을 목적이 아니라 변경 권한과 규칙의 소유권을 정하는 수단으로 선택하는 것입니다.

## 득점 포인트

- 필드 접근 제한과 불변식 보호를 구분하고, 유효성 검사를 변경 동작의 경계에 둔다.
- setter 나열 대신 객체가 상태 전이를 책임지게 하여 규칙의 중복을 줄인다.
- 규칙이 없는 전송 객체까지 과도하게 감싸지 않고 캡슐화 비용을 판단한다.

## 감점 포인트

- private 필드만 만들면 어떤 값이든 안전하다고 말한다. 접근 제한만으로 불변식은 보장되지 않는다.
- getter로 여러 값을 꺼낸 뒤 외부 서비스가 상태 규칙을 조합해도 캡슐화라고 한다. 규칙이 외부로 새어 나간다.
- 모든 객체에 setter를 제공한다. 생성 후 바뀌면 안 되는 상태까지 변경 가능하게 만든다.

## 더 파고들 거리

- 컬렉션을 반환할 때 내부 목록을 직접 노출하지 않으려면 어떤 복사 또는 읽기 전용 뷰가 필요한가요?
- 서로 연관된 두 객체의 불변식을 한 객체가 함께 보장해야 할 때 경계를 어떻게 정할까요?
- 캡슐화로 내부 표현을 바꿔도 클라이언트가 깨지지 않는지 어떤 테스트로 확인할까요?
