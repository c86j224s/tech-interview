Go에서 nil처럼 보이는 인터페이스가 nil과 같지 않은 이유는 무엇인가요?

01

구두 답변

정의를 외우기보다, 원리와 조건을 연결해 설명해 보세요.

인터페이스는 동적 타입과 값 정보를 함께 갖기 때문입니다. 인터페이스 자체가 nil이려면 타입 정보도 값도 없어야 합니다. 구체적인 포인터 타입은 들어 있지만 포인터 값만 nil인 경우는 nil 인터페이스와 다릅니다.

예를 들어 어떤 함수가 구체적인 오류 포인터를 만들고, 오류가 없을 때 그 nil 포인터를 error 인터페이스로 반환한다고 하겠습니다. 호출자는 err가 nil이 아니라고 판단할 수 있습니다. 이때 저는 포인터가 nil인지 출력만 보고 판단하지 않고 반환 타입과 인터페이스로 변환되는 지점을 보겠습니다. 오류가 없으면 명시적으로 nil 인터페이스를 반환하는 식으로 계약을 분명히 하겠습니다.

nil 수신자를 허용하는 메서드도 있을 수 있어서 nil 포인터의 메서드 호출이 무조건 즉시 실패하는 것은 아닙니다. 그러나 메서드가 필드에 접근하면 문제가 생길 수 있습니다. 저는 모든 인터페이스 입력을 리플렉션으로 검사하기보다, 생성자와 반환 경계에서 유효한 구현체 또는 nil 중 하나만 반환하도록 설계하겠습니다. 테스트도 구현체가 정상인 경우뿐 아니라 타입 있는 nil이 넘어오는 경로를 포함하겠습니다. 핵심은 언어의 nil 규칙을 호출자마다 보정하기보다 API 경계에서 혼동을 줄이는 것입니다.

02

득점 포인트

이해가 드러나는 지점을 확인해 보세요.

  • 타입과 값을 구분한다. nil 인터페이스와 타입 있는 nil 포인터의 차이를 설명한다.
  • 실제 오류 반환 사례를 든다. 변환 경계에서 문제를 찾는다.
  • API 계약으로 해결한다. 생성·반환 시 명확한 nil을 사용한다.
03

감점 포인트

놓치기 쉬운 조건과 오해를 짚어 보세요.

  • 포인터가 nil이면 인터페이스도 nil이라고 말한다. 동적 타입이 남을 수 있다.
  • 모든 nil 수신자 메서드가 항상 패닉이라고 말한다. 구현이 nil을 처리할 수 있다.
  • 호출자마다 리플렉션을 넣자고 한다. 원인인 API 계약을 먼저 정리해야 한다.
04

더 파고들 거리

하나 더 질문하며 이해의 범위를 넓혀 보세요.

  • error wrapping을 사용할 때 nil 오류는 어떻게 처리해야 할까요?
  • 인터페이스 비교가 패닉을 일으킬 수 있는 동적 값은 무엇인가요?
  • 선택적 의존성을 인터페이스 nil 대신 명시적 타입으로 표현하면 어떤 장점이 있나요?
