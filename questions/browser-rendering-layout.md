# DOM을 여러 번 바꾸는 화면에서 layout이 반복되어 느려집니다. 브라우저 렌더링 단계와 레이아웃 스래싱을 설명해 보세요.

## 구두 답변

브라우저는 HTML을 파싱해 DOM을 만들고 CSS를 파싱해 CSSOM을 만든 뒤, 두 트리에서 실제로 화면에 그릴 대상을 구성합니다. 그 다음 layout에서 각 상자의 위치와 크기를 계산하고, paint에서 픽셀을 그릴 명령을 만들며, 필요하면 합성 단계에서 레이어를 조합합니다. DOM에 존재해도 `display: none`인 요소처럼 렌더링 대상에서 제외되는 것은 layout에 참여하지 않을 수 있습니다. 반대로 색상만 바꾸는 변경과 크기·위치를 바꾸는 변경은 비용의 범위가 다릅니다.

레이아웃 스래싱은 layout을 유발하는 쓰기와, 최신 기하 정보를 요구하는 읽기를 반복해 브라우저가 중간 계산을 강제로 수행하는 현상입니다. 예를 들면 루프 안에서 `element.style.width = ...`를 바꾼 직후 `element.offsetWidth`를 읽고 다시 스타일을 바꾸는 패턴이 문제를 만들 수 있습니다. 브라우저가 변경을 모아 다음 프레임에 처리할 기회를 잃고, 매 읽기마다 이전 변경을 반영하기 위한 layout을 수행할 수 있기 때문입니다.

수정은 읽기와 쓰기를 분리하고, 여러 DOM 변경을 한 번에 적용하며, 애니메이션은 가능한 경우 `transform`과 `opacity`로 처리하는 순서로 진행하겠습니다. 반복적으로 요소를 만들면 문서 조각이나 프레임워크의 일괄 갱신을 사용하고, 스크롤 이벤트처럼 빈번한 입력은 `requestAnimationFrame`이나 측정 주기 제한으로 묶겠습니다. 다만 transform도 무조건 비용이 없는 것은 아니며 레이어 메모리와 합성 비용을 늘릴 수 있습니다.

개발자 도구의 Performance 기록에서 Recalculate Style, Layout, Paint 시간을 확인하고, 긴 작업·프레임 드롭·강제 layout 경고를 변경 전후로 비교하겠습니다. DOM 노드 수를 무조건 줄이는 것이 목표가 아니라, 실제로 어떤 읽기와 쓰기가 같은 프레임에 섞였는지 찾아 적용 범위와 사용자 지연을 줄이는 것이 핵심입니다.

## 득점 포인트

- DOM·CSSOM·layout·paint·합성의 역할을 순서대로 구분한다.
- 크기를 바꾸는 쓰기 뒤 최신 기하 정보를 읽을 때 강제 layout이 반복되는 이유를 설명한다.
- 배치 갱신과 측정 도구 및 transform의 비용까지 판단한다.

## 감점 포인트

- DOM 트리와 렌더링 트리가 항상 같은 노드라고 말한다.
- 모든 스타일 변경이 같은 비용의 layout을 유발한다고 단정한다.
- transform을 사용하면 어떤 상황에서도 성능 문제가 사라진다고 말한다.
