# iOS 멀티 씬 앱에서 화면이 백그라운드로 갈 때 무엇을 저장해야 하나요? 앱 종료 알림만 기다려도 될까요?

## 구두 답변

iOS 13 이후의 UIKit 앱은 프로세스 하나 안에 여러 개의 UI 윈도우 세션을 둘 수 있고, 각 세션을 관리하는 단위가 씬(scene)입니다. 따라서 앱 전체의 시작·종료와 각 씬의 화면 표시·숨김을 같은 사건으로 보면 안 됩니다. 한 씬이 활성 상태여도 다른 씬은 백그라운드에 있을 수 있으므로, 화면·작업·임시 상태는 씬별로 관리하고 공용 데이터만 앱 수준 저장소에서 조정하는 편이 안전합니다.

사용자가 홈으로 나가거나 다른 앱을 전면에 두면 씬은 활성 상태에서 비활성·백그라운드로 이동합니다. 이때 `sceneDidEnterBackground` 같은 씬 생명주기 지점에서 문서 편집 내용, 결제 초안, 현재 선택 상태처럼 다시 계산할 수 없는 데이터를 먼저 영속화합니다. 네트워크 동기화나 정리 작업은 백그라운드 실행 시간이 제한될 수 있으므로 무한히 끝날 것이라고 가정하지 말고, 중단돼도 다음 실행에서 이어갈 수 있는 작은 단위와 재시도 상태를 저장해야 합니다.

반대로 사용자가 앱을 스와이프해 종료하거나 시스템이 메모리 압박으로 프로세스를 종료하는 경우에는 종료 콜백이 호출된다는 보장이 없습니다. `applicationWillTerminate` 또는 유사한 종료 알림을 마지막 저장 지점으로 삼으면 데이터가 유실됩니다. 마지막 순간에만 저장하는 대신 값이 변경될 때 원자적으로 기록하고, 백그라운드 진입 때 한 번 더 flush하는 전략을 사용합니다. 키체인·파일·데이터베이스처럼 목적에 맞는 저장소와 버전이 있는 복구 형식을 선택하는 것도 중요합니다.

실무에서는 앱 델리게이트에서 모든 창을 한꺼번에 숨기는 식보다 씬 델리게이트와 `UIScene` 상태를 기준으로 전환을 처리합니다. 여러 씬이 동일한 계정을 수정한다면 마지막으로 저장한 씬이 무조건 이긴다고 정하지 말고 변경 버전, 충돌 해결, 저장 실패 복구를 정의해야 합니다. 즉 백그라운드는 저장을 시작할 신호이지 저장 완료를 보장하는 시간이 아니며, 종료 알림은 최후의 보조 기회일 뿐 필수 계약이 아닙니다.

## 득점 포인트

- 프로세스 생명주기와 씬 생명주기를 구분하고, 여러 씬이 서로 다른 상태일 수 있음을 설명한다.
- 백그라운드 진입 시 복구 가능한 영속화를 시작하되 실행 시간이 제한된다는 조건을 연결한다.
- 종료 콜백의 비보장성을 근거로 변경 시점 저장과 재실행 가능한 복구 상태를 선택한다.

## 감점 포인트

- 앱이 종료될 때 항상 `applicationWillTerminate`가 호출되므로 그때 저장하면 된다고 단정한다.
- 모든 씬이 동시에 foreground 또는 background가 된다고 가정해 씬별 상태를 덮어쓴다.
- 백그라운드 작업이 시작됐다는 사실을 작업이 끝까지 실행된다는 보장으로 오해한다.

## 더 파고들 거리

- SceneDelegate 콜백과 SwiftUI `scenePhase`를 혼합할 때 중복 저장을 어떻게 멱등적으로 만들지 설명해 보세요.
- 여러 씬이 같은 문서를 수정할 때 버전 벡터나 충돌 해결 정책을 어떻게 설계할지 비교해 보세요.
- 백그라운드 작업 만료 시 저장 중간 파일을 손상 없이 교체하는 원자적 파일 쓰기를 검증해 보세요.
