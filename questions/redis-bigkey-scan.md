# Redis 운영 환경에서 KEYS와 큰 키 삭제가 지연을 만드는 이유와 안전한 조사·삭제 방법은 무엇인가요?

## 구두 답변

Redis의 주 명령 실행 경로는 한 번에 한 명령을 처리하므로, 전체 키를 훑거나 큰 자료구조를 한 번에 반환·삭제하면 다른 클라이언트의 짧은 명령도 기다릴 수 있습니다. `KEYS`는 많은 키를 한 번에 찾아 결과와 서버 처리 비용을 만들고, 큰 컬렉션 삭제는 메모리 해제 자체가 오래 걸릴 수 있습니다. 응답 바이트가 커지면 클라이언트 출력 버퍼도 압박받습니다.

운영 조사에서는 `SCAN`으로 커서를 이어 받아 작은 배치로 나눕니다. `COUNT`는 목표 힌트이지 정확한 반환 개수나 전체 스냅샷을 보장하지 않습니다. 순회 중 키가 추가·삭제되면 결과가 달라지고 중복이 나올 수 있으므로, 정리 작업은 같은 키를 여러 번 만나도 안전한 조건부 삭제로 만들겠습니다. 패턴이 맞는지 확인한 뒤 타입과 소유권을 검증하고 삭제해야 합니다.

큰 키를 삭제할 때 `UNLINK`는 해제 일부를 백그라운드로 넘겨 주 실행 경로의 지연을 줄일 수 있지만, 메모리가 즉시 모두 반환되거나 RSS가 즉시 내려간다는 뜻은 아닙니다. 큰 키는 조회·복제·RDB/AOF 작업에도 부담이므로, 장기적으로는 시간·사용자·버킷 단위로 데이터를 쪼갤지 검토합니다. 배치 사이에는 정상 트래픽이 처리될 여유를 두고 작업률을 제한하겠습니다.

확인은 Redis slow log와 latency 이벤트, 명령별 호출·시간, 응답 크기, 큰 키 크기, lazy free 대기와 RSS를 함께 봅니다. `KEYS`를 `SCAN`으로 바꾸는 것만이 아니라 작업의 단위와 속도를 운영 예산 안에 두는 것이 핵심입니다.

## 득점 포인트

- 주 실행 경로·응답 버퍼·메모리 해제 비용을 연결한다.
- `SCAN`의 비스냅샷·중복·COUNT 힌트 계약을 설명한다.
- `UNLINK`의 비동기 해제와 실제 RSS를 구분한다.

## 감점 포인트

- 운영 전체 키 조사를 반복해서 `KEYS`로 수행한다.
- `SCAN COUNT 100`이 항상 정확히 100개를 반환한다고 말한다.
- `UNLINK` 응답 즉시 모든 메모리가 반환된다고 말한다.
