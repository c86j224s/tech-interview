# 반복 계산이 많은 Python 서비스를 PyPy로 옮기려 합니다. trace JIT가 유리한 코드와 예열·C 확장 때문에 불리할 수 있는 경우를 어떻게 검증하나요?

## 구두 답변

PyPy가 모든 Python 프로그램을 CPython보다 빠르게 실행하는 것은 아닙니다. PyPy는 Python 언어를 실행하는 인터프리터에 trace JIT(Just-In-Time) 컴파일을 적용해, 실행 중 자주 반복되는 경로를 관찰하고 그 경로에 특화된 기계어를 만들어 인터프리터 호출 비용을 줄입니다. 타입과 분기 패턴이 안정적인 긴 루프에서 특히 이득이 생길 수 있습니다.

대신 처음 몇 번의 실행에는 추적·컴파일·최적화 비용이 들어가므로 짧은 CLI나 한 번만 실행되는 작업은 예열 비용 때문에 이득이 없을 수 있습니다. JIT가 가정한 경로에서 벗어나면 deoptimization으로 인터프리터 경로로 돌아갈 수도 있습니다. 따라서 마이크로벤치마크의 첫 실행값이 아니라 실제 요청 수명, steady state 처리량, p95 지연, 메모리 사용량을 CPython과 동일한 조건에서 비교해야 합니다.

또 하나의 경계는 C 확장입니다. PyPy는 CPython의 C ABI를 그대로 실행하는 방식이 아니므로 일부 확장은 호환 계층이나 별도 지원에 의존하고, 내부 객체 표현을 직접 다루는 확장은 성능·호환성 제약을 받을 수 있습니다. 순수 Python 계산이 병목인지, NumPy 같은 확장이 이미 대부분의 시간을 쓰는지에 따라 결과가 달라집니다. 런타임만 바꾸기보다 의존 패키지 지원, 배포 이미지, 프로파일 결과를 먼저 확인하고 반복되는 순수 Python 경로가 길면 PyPy를 선택하겠습니다.

## 득점 포인트

- trace JIT가 자주 실행되는 안정적인 경로를 전문화한다는 원리를 설명한다.
- 예열·deoptimization 때문에 짧은 실행과 steady state 벤치마크를 구분한다.
- CPython C 확장 호환성과 실제 병목의 위치를 런타임 선택 조건에 포함한다.

## 감점 포인트

- PyPy가 Python 코드를 실행하므로 항상 CPython보다 빠르다고 단정한다.
- JIT 컴파일 비용이 첫 요청의 지연에 영향을 주지 않는다고 말한다.
- CPython용 모든 C 확장이 PyPy에서 동일한 ABI와 성능으로 동작한다고 주장한다.
