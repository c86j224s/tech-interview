# Kafka 소비자가 메시지를 처리하는 동안 리밸런싱으로 파티션을 잃으면, 작업과 offset을 어떤 순서로 정리해야 하나요?

## 구두 답변

리밸런싱은 파티션 소유자가 바뀌는 사건이므로, 이전 소비자가 처리 중인 외부 작업과 새 소유자의 작업이 겹칠 수 있습니다. 먼저 해당 partition에 새 작업을 배정하지 않고, 이미 시작한 작업을 완료·취소·재시도 중 어떤 상태로 만들지 정합니다. offset은 읽은 마지막 위치가 아니라 외부 효과가 성공한 레코드들의 가장 긴 연속 구간까지만 커밋해야 합니다.

예를 들어 10번과 11번을 처리 중인데 11번이 먼저 끝나면 12번을 커밋해 10번을 건너뛰면 안 됩니다. 반납 단계에서 워커를 중지하고 완료 결과를 회수한 뒤 10번부터 연속 완료 위치를 계산하겠습니다. 소비자 세대가 바뀐 뒤 이전 세대의 늦은 커밋은 거절될 수 있으므로 오류를 무시하지 않고, 늦게 끝난 외부 쓰기가 새 소유자의 상태를 덮지 않도록 소유권·버전·멱등성을 둡니다.

처리가 `max.poll.interval.ms`를 넘으면 heartbeat와 작업 완료가 어긋나 반복 리밸런싱이 생길 수 있습니다. poll과 워커 큐 크기, 처리 시간을 조정하고, cooperative rebalance(소유권을 조금씩 넘기는 재분배)와 static membership(재시작한 소비자의 기존 신원을 유지하는 방식)을 선택할 때의 효과를 비교하겠습니다. 전자는 전체 중단을 줄일 수 있고 후자는 짧은 재시작에서 불필요한 재분배를 줄일 수 있지만, 처리 중 작업을 대신 완료해 주지는 않습니다. 느린 처리 중 scale-out·scale-in을 반복해 중복, 누락, 지연, 늦은 쓰기 거절이 모두 예상대로인지 검증합니다.

## 득점 포인트

- 파티션 반납과 외부 작업 완료를 연결한다.
- 연속 완료 offset의 예시로 잘못된 커밋을 드러낸다.
- 세대·버전·멱등성으로 늦은 작업의 영향을 제한한다.

## 감점 포인트

- 반납 시 마지막으로 읽은 offset을 무조건 커밋한다.
- heartbeat가 정상이면 메시지 처리가 안전하다고 말한다.
- 옛 소비자의 늦은 외부 쓰기를 성공으로 그대로 받아들인다.

## 더 파고들 거리

- cooperative rebalance가 처리 중 partition 정지 범위를 어떻게 줄이나요?
- static membership은 재시작 중 리밸런싱을 줄이는 대신 어떤 지연을 만들까요?
- partition별 워커 큐를 폐기할 때 완료·취소·재처리 상태를 어떻게 내구화할까요?
