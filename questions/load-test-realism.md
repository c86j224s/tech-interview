# 부하 테스트의 TPS와 지연 결과가 운영 성능을 예측하려면 요청·데이터·캐시·부하 생성 조건을 무엇까지 맞춰야 하나요?

## 구두 답변

요청 수만 운영과 맞추면 충분하지 않습니다. 요청 종류와 읽기·쓰기 비율, payload 크기, 키의 인기 분포, 도착 패턴, 캐시 상태, 데이터베이스의 실제 크기와 인덱스 상태가 결과를 크게 바꿉니다. 같은 키만 반복하는 테스트는 캐시 적중률을 과도하게 높여 다양한 사용자 키를 읽는 운영보다 원본 부하를 낮출 수 있습니다.

시나리오는 steady state(부하가 일정한 안정 구간), 단계적 증가, 버스트, 재시작 직후 빈 cache, 캐시 장애를 분리해 구성하겠습니다. 부하 생성기가 앞선 응답을 받은 뒤 다음 요청을 보내는 closed-loop(응답 대기형)인지, 정해진 도착률을 계속 보내는 open-loop(도착률 고정형)인지도 기록해야 합니다. 응답 대기형은 생성기 자체가 느려져 서버 적체를 숨길 수 있습니다. 생성기 CPU·네트워크가 먼저 포화되면 발송률이 목표보다 낮아져 서버의 한계를 숨길 수 있습니다. 중간값(p50) 하나가 아니라 느린 요청의 95·99번째 백분위수(p95/p99), 오류율, 큐 대기와 회복 시간을 보겠습니다. 일부 느린 사용자가 겪는 장애를 평균값이 숨길 수 있기 때문입니다.

부하를 내린 뒤 연결·고루틴·메모리·큐가 회복되는지 soak 구간을 포함하고, 테스트 데이터·서버 설정·생성기 자원·캐시 예열 절차를 함께 저장해 재현성을 확보합니다. 운영 트래픽을 재생할 때는 개인정보를 제거하고 쓰기·결제 같은 부수 효과를 격리합니다. 단일 최고 TPS(초당 처리 요청 수)가 아니라 SLO(사용자 지연·오류에 대한 목표)를 지키는 지속 처리율과 비용을 용량 기준으로 삼겠습니다.

## 득점 포인트

- 요청·키·캐시 분포와 도착 모델을 운영 예측의 조건으로 제시한다.
- 생성기 병목과 대상 시스템 병목을 분리한다.
- 회복·재현성·개인정보·부수 효과를 테스트 설계에 포함한다.

## 감점 포인트

- 같은 키 반복 결과로 전체 용량을 주장한다.
- 생성기 발송률을 확인하지 않고 서버 한계로 해석한다.
- 짧은 최고 TPS만 보고 지속 운영 용량을 정한다.

## 더 파고들 거리

- 운영 트래픽을 재생하면서 개인정보와 쓰기 부수 효과를 어떤 방식으로 제거할까요?
- 장시간 soak test에서 파일 디스크립터·메모리·연결·큐의 어떤 추세를 볼까요?
- 비용이 다른 요청을 하나의 처리량 수치로 비교할 때 가중 기준을 어떻게 정할까요?
