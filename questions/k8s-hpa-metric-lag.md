# HPA가 반응할 때 이미 큐 지연이 커져 있습니다. 지표 지연과 안정화 정책은 어떻게 해석하나요?

## 구두 답변

지표 수집·집계·제어 주기·Pod 시작·준비까지 시간이 걸리므로 부하 변화와 실제 용량 증가는 동시에 일어나지 않습니다. HPA 목표값만 바꾸기보다 전체 제어 경로와 지표 의미를 확인해야 합니다.

### 동작 원리와 전제

CPU 평균은 I/O 대기나 특정 핫 파티션의 병목을 잘 못 나타낼 수 있습니다. 큐 길이·처리 지연·동시성 같은 지표가 맞는지 보고, per-Pod인지 전체 값인지 수학적 의미를 확인합니다. 누락 지표와 새 Pod의 상태도 동작에 영향을 줄 수 있습니다.

### 선택과 실패 처리

빠른 확장과 느린 축소·stabilization은 진동을 줄이지만 비용과 회복 시간을 바꿉니다. 최소 여유 용량과 사전 확장, 수락 제한을 조합합니다. scale-out이 DB·파티션 한도 때문에 처리량을 늘리지 못하면 근본 병목을 고쳐야 합니다.

### 구체적인 사례와 검증

부하가 증가한 뒤 metrics pipeline에 30초, 제어와 시작에 추가 시간이 걸리면 확장된 replica가 준비되기 전에 큐가 커질 수 있습니다. 이 기간을 흡수할 여유 용량과 bounded queue·빠른 거절을 설계합니다. desired replicas가 늘었는데 scheduler 용량이 없거나 startup이 실패하면 실제 처리량은 그대로입니다. 새 Pod의 CPU 평균이 낮아졌다고 전체 workload가 해결됐다고 보지 않고 완료율·가장 오래된 작업을 확인합니다. 축소가 진행 중인 작업을 끊지 않게 drain과 재처리를 준비합니다. 제어기의 수학과 실제 서비스의 상태·수명은 함께 검증해야 합니다.

급격한 burst·지속 증가·지표 누락·느린 초기화·축소를 시험합니다. desired·scheduled·ready replica와 실제 완료율을 나눠 봅니다. 제어 신호가 좋아 보이는 것보다 사용자 지연이 허용 범위에 있는지가 기준입니다.

## 득점 포인트

- 핵심 구분: 지표 수집·집계·제어 주기·Pod 시작·준비까지 시간이 걸리므로 부하 변화와 실제 용량 증가는 동시에 일어나지 않습니다.
- 선택 조건: 빠른 확장과 느린 축소·stabilization은 진동을 줄이지만 비용과 회복 시간을 바꿉니다.
- 검증 기준: 급격한 burst·지속 증가·지표 누락·느린 초기화·축소를 시험합니다.

## 감점 포인트

- HPA 목표 replica 증가가 즉시 준비된 처리 용량 증가를 뜻한다고 한다.
