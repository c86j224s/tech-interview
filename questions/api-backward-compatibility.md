# API에 필드를 추가하는 것도 호환성을 깨뜨릴 수 있나요?

## 구두 답변

필드를 추가하면 대체로 안전해 보이지만 소비자가 모르는 필드를 거절하거나, 서명·캐시 키·직렬화 순서에 의존하면 문제가 될 수 있습니다. 구조의 추가뿐 아니라 의미와 기본값이 기존 클라이언트에게 어떻게 보이는지를 확인해야 합니다.

응답에 새로운 상태 값을 추가했다고 하겠습니다. 문자열 필드 자체는 그대로여도 클라이언트가 기존 세 값만 처리하면 예외가 나거나 잘못된 기본 동작을 할 수 있습니다. 저는 알 수 없는 값의 처리 정책과 기존 값의 의미를 유지하는지 확인하겠습니다. 요청의 선택 필드를 필수로 바꾸거나 기본 동작을 바꾸는 것도 명백한 호환 변화입니다.

배포는 공급자와 소비자가 같은 순간에 바뀐다고 가정하지 않겠습니다. 오래된 모바일 앱과 배치 작업을 포함한 소비자 목록을 확인하고, 계약 테스트와 실제 사용 지표로 구버전이 남아 있는지 보겠습니다. 큰 의미 변경은 명시적인 버전이나 새 필드로 나누고, 폐기 일정과 관측을 둡니다. 테스트에서는 새 서버에 구클라이언트, 구서버에 신클라이언트가 각각 어떻게 동작하는지 확인하겠습니다. JSON 파싱이 성공했다는 것보다 같은 업무 의도가 유지되는지가 호환성의 기준입니다.

## 득점 포인트

- **구조와 의미의 호환성을 구분한다.** enum·기본값·필수화 영향을 설명한다.
- **혼합 버전 배포를 검증한다.** 양방향 조합을 테스트한다.
- **실제 소비자를 관측한다.** 구버전 제거 근거를 확보한다.

## 감점 포인트

- **필드 추가는 항상 안전하다고 말한다.** 엄격한 파서와 의미 변화가 있다.
- **파싱 성공이면 호환이라고 말한다.** 업무 동작이 바뀔 수 있다.
- **서버와 앱을 동시에 배포하면 된다고 말한다.** 오래된 소비자가 남는다.

## 더 파고들 거리

- 필드의 null과 생략을 다르게 해석하는 API는 어떻게 문서화할까요?
- 프로토콜 버퍼의 필드 번호 재사용은 왜 위험할까요?
- API 폐기를 지표로 판단할 때 드문 배치 소비자는 어떻게 발견할까요?
