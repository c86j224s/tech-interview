# 현재 회원 데이터에서는 이메일이 모두 달라 이메일을 키로 쓰자는 제안이 나왔습니다. 후보키를 정할 때 관찰한 데이터와 반드시 지켜야 할 제약을 어떻게 구분하나요?

## 구두 답변

함수 종속은 어떤 속성 집합의 값이 다른 속성 집합의 값을 하나로 결정한다는 제약입니다. ‘학생번호가 학생이름을 결정한다’는 말은 같은 학생번호를 가진 두 행의 학생이름이 달라서는 안 된다는 뜻이지, 현재 샘플 데이터에서 우연히 값이 하나였다는 뜻이 아닙니다. 이 제약은 도메인의 업무 규칙에서 나와야 합니다. 예를 들어 이메일이 현재 유일하더라도 업무상 중복 가입을 허용한다면 이메일에서 회원을 결정하는 함수 종속으로 설계하면 안 됩니다.

슈퍼키는 행을 유일하게 식별하는 속성 집합이고, 후보키는 그중 어느 속성도 빼면 더 이상 유일하지 않은 최소 슈퍼키입니다. 기본키는 후보키 하나를 대표로 선택한 것이며 후보키가 하나뿐이라는 뜻은 아닙니다. 후보키를 찾을 때는 주어진 함수 종속을 적용해 속성 집합으로부터 결정되는 속성을 반복해서 넓혀 보는 방식으로 폐포를 계산합니다. 폐포에 모든 속성이 들어오면 슈퍼키이고, 각 속성을 하나씩 제거해도 전체를 결정하는지 확인해 최소성을 검사합니다.

예를 들어 수강 테이블에서 (학생번호, 강좌번호)가 신청 행을 식별하고, 학생번호가 학생이름을 결정한다면 두 속성의 조합은 키가 될 수 있지만 학생번호만으로는 강좌별 행을 구분하지 못합니다. 다만 수강생이 한 강좌를 한 번만 신청한다는 제약이 실제로 존재해야 합니다. 함수 종속을 잘못 추정하면 키와 정규형 판단이 모두 흔들리므로 샘플을 보고 추측하지 말고 유일성의 범위, 시간에 따른 변경, 테넌트 같은 업무 조건을 확인해야 합니다.

후보키가 정해지면 기본키와 대체 후보키에 각각 제약을 두고, 외래키가 참조할 식별자도 명확해집니다. 반대로 시스템이 생성한 ID는 행을 식별할 뿐 학생번호나 이메일과의 업무 관계를 대신 설명하지 않으므로 필요한 업무 고유 제약을 별도로 선언해야 합니다.

## 득점 포인트

- 함수 종속을 현재 데이터의 우연한 유일성이 아닌 업무 제약으로 설명한다.
- 슈퍼키·후보키·기본키의 포함 관계와 후보키의 최소성을 구분한다.
- 폐포와 속성 제거 검사를 이용해 식별 가능성과 최소성을 확인한다.

## 감점 포인트

- 현재 중복이 없다는 이유만으로 모든 속성에서 단일 속성 함수 종속을 만든다.
- 기본키가 선택되면 다른 후보키의 업무 고유성 제약은 필요 없다고 말한다.
- 함수 종속의 결정자가 행을 식별하는지 확인하지 않고 정규형을 판정한다.

## 더 파고들 거리

- 테넌트별로만 이메일이 유일한 경우 후보키와 고유 제약을 어떻게 표현할지 정해 보세요.
- 부분 함수 종속이 복합키 테이블의 설계에 어떤 분해를 요구하는지 연결해 보세요.
- 시간에 따라 바뀌는 이메일과 변경 이력을 함께 저장할 때 어떤 함수 종속이 유지되는지 검토해 보세요.
