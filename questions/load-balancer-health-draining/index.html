01

구두 답변

정의를 외우기보다, 원리와 조건을 연결해 설명해 보세요.

헬스 체크는 특정 시점의 특정 검사가 성공했다는 뜻이지, 다음 실제 요청의 성공 보장은 아닙니다. 검사 경로가 너무 단순하면 DB 장애나 작업 큐 포화를 놓칠 수 있고, 반대로 모든 외부 의존성을 검사하면 하나의 공통 장애로 모든 서버가 동시에 제외될 수도 있습니다.

저는 프로세스가 살아 있는지와 새 요청을 받을 준비가 됐는지를 구분하겠습니다. 아직 초기화 중이거나 종료 중인 서버는 살아 있어도 준비 상태는 실패해야 합니다. 다만 하위 기능 하나의 장애 때문에 모든 기능을 제외할지, 일부 기능만 실패로 돌릴지는 서비스 계약에 따라 정해야 합니다. 헬스 체크에 의존성 검사를 더하는 것이 항상 더 정확한 운영은 아닙니다.

배포 때는 먼저 새 요청 유입을 막고 기존 요청을 끝낼 시간을 주겠습니다. 로드밸런서의 상태 반영 지연과 이미 유지 중인 연결도 있어, 준비 상태를 바꾸고 즉시 프로세스를 죽이면 실패가 생길 수 있습니다. 진행 중 요청과 연결 수를 보며 제한 시간까지 배출하고, 끝나지 않은 작업은 재시도나 복구가 가능하도록 설계하겠습니다. 성공 기준은 체크 응답이 아니라 배포 중 실제 오류율과 장기 요청의 처리 결과입니다.

02

득점 포인트

이해가 드러나는 지점을 확인해 보세요.

  • 검사의 범위를 구분한다. 생존·준비·업무 성공을 나눈다.
  • 공통 장애의 영향을 생각한다. 과한 검사로 모든 서버를 제외하지 않는다.
  • 종료 순서를 설계한다. 유입 차단·반영 지연·기존 요청 배출을 포함한다.
03

감점 포인트

놓치기 쉬운 조건과 오해를 짚어 보세요.

  • 헬스 체크 성공이면 모든 요청이 성공한다고 말한다. 검사 범위가 제한된다.
  • 종료 전에 체크만 실패시키면 즉시 안전하다고 말한다. 전파와 연결 지연이 남는다.
  • 모든 외부 장애를 생존 실패로 처리한다. 불필요한 재시작이 연쇄될 수 있다.
04

더 파고들 거리

하나 더 질문하며 이해의 범위를 넓혀 보세요.

  • 긴 스트리밍 연결을 가진 서비스의 드레이닝은 어떻게 다를까요?
  • 준비 상태가 자주 바뀌는 서버의 트래픽 출렁임을 어떻게 줄일까요?
  • 종료 제한 시간을 넘긴 요청은 어떤 계약으로 재시도해야 할까요?

득점·감점 포인트는 학습용 자기 점검 기준이며, 특정 회사의 실제 채점표가 아닙니다.
