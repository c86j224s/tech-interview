# 메시지 소비자가 같은 이벤트를 두 번 받으면 어떻게 처리하나요?

## 구두 답변

중복 전달을 예외 상황이 아니라 정상적인 재시도 경로로 보겠습니다. 소비자가 데이터를 저장한 뒤 확인 응답을 보내기 전에 죽으면 브로커는 처리 여부를 몰라 다시 전달할 수 있습니다. 따라서 이벤트를 받은 횟수와 업무 효과가 반영된 횟수를 분리해야 합니다.

포인트 지급 이벤트라면 이벤트 ID에 고유 제약을 둔 처리 기록과 포인트 변경을 같은 트랜잭션으로 저장하겠습니다. 커밋 뒤 확인 응답을 보내면 다시 와도 이미 처리한 ID를 보고 효과를 반복하지 않습니다. 처리 기록을 먼저 따로 커밋하면 기록만 있고 포인트는 없는 상태가 생길 수 있고, 확인을 먼저 보내면 작업이 유실될 수 있습니다.

외부 API를 호출하는 소비자는 로컬 처리 기록만으로 원자성을 만들 수 없으므로 외부 멱등성 키나 상태 대사가 필요합니다. 처리 기록도 언제까지 보관할지 재전달 가능 기간과 맞춰야 합니다. 기록을 지운 뒤 오래된 메시지를 재생하면 효과가 다시 발생할 수 있기 때문입니다. 테스트에서는 커밋 후 확인 유실, 여러 소비자의 동시 중복, 오래된 재생을 확인하겠습니다. 중복 메시지를 버린 비율만 보는 것이 아니라 실제 업무 결과가 한 번만 적용되는지가 검증 기준입니다.

## 득점 포인트

- **중복 전달의 원인을 설명한다.** 커밋과 확인 응답 사이를 구분한다.
- **처리 기록과 효과를 묶는다.** 동일 트랜잭션과 확인 순서를 정한다.
- **보관 기간과 외부 효과를 다룬다.** 재생 및 원자성 한계를 설명한다.

## 감점 포인트

- **ACK를 먼저 보내면 중복이 없어 안전하다고 말한다.** 작업 유실이 생길 수 있다.
- **이벤트 ID만 메모리에 저장한다.** 재시작 뒤 중복 방지가 사라진다.
- **처리 기록을 아무 때나 지워도 된다고 말한다.** 늦은 재전달이 다시 반영될 수 있다.

## 더 파고들 거리

- 이벤트 ID 대신 업무 고유 키로 멱등성을 만들 수 있는 조건은 무엇인가요?
- 같은 이벤트가 다른 payload로 재전달되면 어떻게 처리할까요?
- 이벤트 버전이 건너뛰거나 역전되면 멱등성과 별도로 무엇이 필요한가요?
