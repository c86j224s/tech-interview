01

구두 답변

정의를 외우기보다, 원리와 조건을 연결해 설명해 보세요.

플래그는 이후 코드 경로를 바꾸는 장치이지 이미 저장된 데이터나 발행된 이벤트를 되돌리는 장치는 아닙니다. 새 경로가 기존 형식으로 읽을 수 없는 데이터를 만들었다면 플래그를 꺼도 이전 코드가 실패할 수 있습니다. 저는 코드 전환과 데이터 복구를 구분하겠습니다.

작은 사용자 집단부터 새 기능을 켠다면 같은 사용자가 요청마다 다른 경로로 흔들리지 않도록 안정적인 배정 키를 쓰겠습니다. 집단별 성공률과 지연, 업무 결과를 비교하고 중단 기준을 미리 정하겠습니다. 전체 평균은 작은 집단의 오류를 가릴 수 있으므로 플래그 노출 여부를 관측에 연결해야 합니다.

플래그 설정도 모든 인스턴스에 즉시 전파되지 않을 수 있습니다. 서로 다른 경로가 동시에 실행돼도 프로토콜과 상태가 호환돼야 합니다. 장애 대응용 플래그는 의존 시스템이 아플 때도 작동하는지 확인하겠습니다. 도입이 끝난 플래그는 제거해 조합 폭증과 테스트 부담을 줄입니다. 테스트에서는 켜짐·꺼짐뿐 아니라 진행 중 변경과 설정 조회 실패를 확인하겠습니다. 되돌릴 수 있는 범위를 명확히 해 두는 것이 빠르게 끄는 버튼보다 중요합니다.

02

득점 포인트

이해가 드러나는 지점을 확인해 보세요.

  • 코드 경로와 부수 효과를 구분한다. 데이터·이벤트 복구는 별도임을 설명한다.
  • 안정적인 집단과 지표를 연결한다. 작은 오류 집단을 놓치지 않는다.
  • 혼합 상태와 제거를 계획한다. 전파 지연·설정 장애·플래그 수명을 다룬다.
03

감점 포인트

놓치기 쉬운 조건과 오해를 짚어 보세요.

  • 끄면 모든 영향이 사라진다고 말한다. 이미 저장된 변경이 남는다.
  • 요청마다 무작위 배정한다. 상태가 섞여 사용자 경험이 흔들릴 수 있다.
  • 완료된 플래그를 계속 남긴다. 조합과 유지 비용이 커진다.
04

더 파고들 거리

하나 더 질문하며 이해의 범위를 넓혀 보세요.

  • 사용자별 배정과 조직별 배정은 실험 결과와 정합성에 어떤 영향을 주나요?
  • 새 기능이 이벤트를 발행한 뒤 롤백하면 소비자는 어떻게 처리해야 할까요?
  • 킬 스위치가 설정 서비스 장애에도 동작하려면 어떤 기본값이 필요할까요?
