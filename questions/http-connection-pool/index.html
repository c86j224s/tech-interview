01

구두 답변

정의를 외우기보다, 원리와 조건을 연결해 설명해 보세요.

연결을 기다리는 것이 병목이고 하위 서버에 여유가 있다면 도움이 될 수 있습니다. 하지만 하위가 이미 포화라면 연결만 늘어 요청이 더 많이 쌓일 수 있습니다. 저는 연결을 얻는 대기 시간과 실제 요청 시간을 나눠 보겠습니다.

연결 획득은 오래 걸리는데 요청 자체는 빠르고 하위 자원도 여유가 있다면 풀 상한을 조금씩 늘려 비교하겠습니다. 반대로 요청 시간이 함께 늘고 오류가 증가한다면 연결 수를 줄여 하위 부하를 제한하는 편이 낫습니다. 서비스 전체의 연결 수는 인스턴스 수와 함께 늘므로 인스턴스당 설정만 봐서는 안 됩니다. HTTP/2라면 연결 수와 동시 스트림 수가 같지 않다는 점도 고려해야 합니다.

유휴 연결을 무한히 유지하는 것도 피하겠습니다. 로드밸런서가 먼저 끊은 연결을 다시 쓰면 첫 요청이 실패할 수 있고, 오래된 연결만 유지하면 새 서버로 부하가 잘 이동하지 않을 수 있습니다. 최대 수명과 유휴 시간을 정하되 모든 인스턴스가 동시에 재연결하지 않게 분산하겠습니다. 테스트는 정상 처리량뿐 아니라 하위 서버 교체와 유휴 후 재사용을 포함하고, 풀 대기·새 연결률·실패율로 적절한 범위를 찾겠습니다.

02

득점 포인트

이해가 드러나는 지점을 확인해 보세요.

  • 풀 대기와 서버 지연을 구분한다. 하위 여유에 따라 증설 여부를 결정한다.
  • 전체 연결 예산을 본다. 인스턴스와 프로토콜의 동시성 차이를 고려한다.
  • 재사용 실패를 다룬다. 유휴 종료·최대 수명·재연결을 검증한다.
03

감점 포인트

놓치기 쉬운 조건과 오해를 짚어 보세요.

  • 연결 수가 많을수록 좋다고 말한다. 하위 포화를 악화시킬 수 있다.
  • HTTP/2 스트림과 연결을 동일시한다. 한 연결에서 여러 요청이 진행된다.
  • idle 연결은 항상 유효하다고 본다. 중간 장치가 먼저 닫을 수 있다.
04

더 파고들 거리

하나 더 질문하며 이해의 범위를 넓혀 보세요.

  • 연결 획득 타임아웃과 요청 데드라인을 어떻게 묶을까요?
  • DNS 변경이 기존 연결 풀에 반영되지 않는 문제는 어떻게 다룰까요?
  • 연결별 실패가 반복될 때 즉시 재시도가 안전한 요청은 무엇일까요?
