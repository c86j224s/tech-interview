# 비동기 API를 사용하면 호출한 스레드는 블로킹되지 않나요?

## 구두 답변

반드시 그렇지는 않습니다. 비동기는 작업을 요청한 시점과 결과를 받는 시점을 분리하는 방식입니다. 그런데 결과를 받는 코드에서 다시 기다리면, 요청은 비동기로 했어도 그 스레드는 멈출 수 있습니다. 그래서 저는 API 이름보다 **결과가 아직 없을 때 코드가 어떻게 동작하는지**를 먼저 보겠습니다.

예를 들어 DB 조회를 비동기로 보내고 future를 받았는데, 바로 get을 호출해 결과를 기다린다고 하겠습니다. 별도의 작업 스레드라면 그 스레드가 기다리는 것으로 끝날 수 있지만, 여러 연결을 담당하는 이벤트 루프라면 다른 요청 처리까지 함께 밀립니다. 특히 모든 워커가 같은 스레드 풀에 넣어 둔 하위 작업을 기다린다면, 하위 작업을 실행할 스레드가 없어 진행이 막힐 수도 있습니다. 이런 것이 스레드 풀 고갈이 교착으로 이어지는 경우입니다.

이 상황에서는 워커 수부터 늘리기보다 대기가 필요한 위치를 바꾸겠습니다. 완료 콜백이나 코루틴의 중단을 이용해 결과가 올 때까지 실행 자원을 내주고, 완료된 뒤 이어서 처리하도록 합니다. 다만 await 같은 문법만 썼다고 되는 것은 아닙니다. 그 안에서 동기 I/O를 호출한다면 여전히 스레드를 잡고 있으므로, 실제 호출 경로를 확인해야 합니다.

또 이렇게 바꿔도 DB의 처리 용량은 그대로입니다. 저는 DB 연결을 기다린 시간과 실제 쿼리 시간을 나눠 보겠습니다. 쿼리 시간은 비슷한데 연결 대기만 늘어난다면 요청을 더 병렬로 보내기보다 DB로 들어가는 작업 수를 제한하겠습니다. 대기열에도 상한을 두고, 남은 시간 안에 처리하기 어려운 요청은 오래 붙잡아 두지 않고 거절하는 편을 택하겠습니다. 이런 식으로 하위 시스템의 처리 한계를 상위에 반영하는 것이 백프레셔입니다.

결국 **비동기는 기다림을 없애는 기술이 아니라, 기다리는 동안 실행 자원을 다르게 쓰는 방식**이라고 보겠습니다. 스레드가 풀렸다는 것만 확인하지 않고, 그 대기가 요청 큐와 메모리로 옮겨간 것은 아닌지까지 확인해야 합니다.

## 득점 포인트

- **대기 위치와 영향 범위를 연결한다.** future의 동기 대기가 전용 워커와 이벤트 루프에서 왜 다른 영향을 주는지 설명한다.
- **실행 자원을 내주는 방법을 설명한다.** 콜백·코루틴을 제안하면서 실제 I/O 경로가 블로킹인지 확인한다.
- **관측 결과에 따라 행동을 선택한다.** 쿼리 시간과 연결 대기 시간을 나눠 보고, 대기가 병목이면 작업 수와 대기열을 제한한다.
- **최적화 뒤의 병목 이동을 확인한다.** 스레드 대기가 줄어도 요청과 메모리가 쌓일 수 있음을 설명한다.

## 감점 포인트

- **“비동기 API니까 스레드는 절대 멈추지 않는다”고 말한다.** 결과를 동기적으로 기다리는 호출과 내부 동기 I/O가 있을 수 있다.
- **“await를 붙이면 별도 스레드에서 실행된다”고 말한다.** 중단·재개와 실행 위치는 런타임 및 대기 대상 구현에 달려 있다.
- **“스레드 풀을 키우면 해결된다”고 단정한다.** 동일 풀에 대한 의존 사이클과 하위 시스템 용량 제한은 남는다.
- **“백프레셔를 고려한다”로 끝낸다.** 어떤 대기를 보고 어디에서 작업을 제한할지 설명하지 않으면 실제 판단이 빠진다.
