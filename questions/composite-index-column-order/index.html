01

구두 답변

정의를 외우기보다, 원리와 조건을 연결해 설명해 보세요.

B-tree 계열 복합 인덱스는 키를 **사전식 순서(lexicographic order)**로 정렬합니다. (고객ID, 주문시각)이면 고객별로 모인 안에서 시각순으로 정렬되므로 특정 고객의 기간 조회와 최신 주문 검색에 유리합니다. 컬럼 순서는 선택도만이 아니라 쿼리가 어떤 연속 범위를 탐색하고 어떤 정렬을 피할 수 있는지의 문제입니다.

일반적으로 동등 조건으로 앞부분을 고정하고 다음 컬럼의 범위를 탐색하는 구성이 좋습니다. 하지만 동등 조건이 여러 개라면 가장 선택적인 컬럼을 무조건 앞에 두기보다, 어떤 조건이 자주 생략되는지와 주요 쿼리의 ORDER BY·LIMIT까지 봐야 합니다. 선두 컬럼에 범위가 걸리면 뒤 조건은 탐색 경계를 좁히기보다 **잔여 조건(residual predicate)**으로 평가될 수 있습니다. 인덱스를 탔다고 읽는 양이 작다는 뜻은 아닙니다.

또 조건 자체가 인덱스 탐색에 적합한 SARGable 조건인지 확인하겠습니다. 인덱스 컬럼에 함수를 적용하거나 암시적 형 변환이 생기면 효율적인 seek가 어려워질 수 있습니다. 옵티마이저가 변환하거나 표현식 인덱스를 활용할 수 있는 예외도 있어 실제 계획을 확인해야 합니다.

반환할 컬럼까지 담는 커버링 인덱스는 테이블 접근이나 key lookup을 줄일 수 있습니다. SQL Server라면 탐색·정렬에 필요한 키와 반환용 INCLUDE 컬럼을 구분할 수 있습니다. 대신 인덱스가 넓어지면 페이지 수, 버퍼 캐시 점유, 갱신 시 로그와 페이지 분할 같은 쓰기 증폭이 커집니다. 조회 하나의 개선이 전체 쓰기 부하를 악화시키지 않는지 봐야 합니다.

최종적으로 실제 실행 계획에서 seek 조건과 residual 조건, 읽은 행과 반환한 행, lookup 횟수, 정렬 spill을 확인하겠습니다. 추정·실제 카디널리티가 크게 다르면 통계의 노후화나 데이터 편중, 파라미터 민감도를 의심합니다. 인덱스 사용 여부가 아니라 대표 파라미터별 logical reads, CPU, 지연과 쓰기 비용이 개선되는지로 결정하겠습니다.

02

득점 포인트

이해가 드러나는 지점을 확인해 보세요.

  • 정렬 구조와 접근 경로를 연결한다. 동등·범위·정렬 조건이 연속 탐색 범위를 어떻게 만드는지 설명한다.
  • seek와 residual 평가를 구분한다. 인덱스 사용 여부를 넘어 실제 읽기 증폭과 SARGability를 점검한다.
  • 커버링의 읽기 이득과 쓰기 비용을 비교한다. 키·포함 컬럼, lookup 감소, 캐시 점유와 인덱스 유지 비용을 함께 다룬다.
  • 옵티마이저의 추정을 검증한다. 카디널리티 오차와 파라미터 편중을 실제 계획·논리 읽기·spill에 연결한다.
03

감점 포인트

놓치기 쉬운 조건과 오해를 짚어 보세요.

  • “선택도가 가장 높은 컬럼을 항상 앞에 둔다”고 말한다. 복합 조건과 정렬, 선두 조건이 없는 다른 쿼리를 고려하지 않은 규칙이다.
  • “인덱스 seek면 효율적이고 scan이면 비효율적이다”라고 말한다. 넓은 seek와 많은 lookup이 scan보다 비쌀 수 있다.
  • “INCLUDE 컬럼은 비용 없이 조회를 빠르게 한다”고 말한다. 리프 크기, 캐시 사용량, 갱신·로그 비용이 증가할 수 있다.
  • “추정 실행 계획의 비용이 줄었으니 튜닝이 끝났다”고 말한다. 실제 행 수·분포·실행 통계와 쓰기 워크로드를 검증해야 한다.
04

더 파고들 거리

하나 더 질문하며 이해의 범위를 넓혀 보세요.

  • 정렬을 피하는 인덱스와 필터 선택도가 높은 인덱스 중 LIMIT 크기에 따라 어느 쪽이 유리해질까요?
  • 파라미터 스니핑으로 특정 값에 최적화된 계획이 재사용될 때 통계 갱신, 재컴파일, 계획 분리를 어떻게 선택할까요?
  • 키셋 페이지네이션에서 정렬 키가 유일하지 않다면 보조 키와 복합 조건을 어떻게 설계해야 할까요?
  • 클러스터링 키의 폭과 삽입 패턴이 비클러스터 인덱스 크기 및 페이지 분할에 어떤 영향을 줄까요?

득점·감점 포인트는 학습용 자기 점검 기준이며, 특정 회사의 실제 채점표가 아닙니다.
