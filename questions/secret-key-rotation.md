# 서비스 중단 없이 서명키나 API 비밀키를 교체하려면 어떻게 하나요?

## 구두 답변

새 키를 발급하는 것보다 이전 키를 사용하는 생산자와 소비자가 함께 있는 기간을 설계하는 것이 중요합니다. 서명키라면 새 키로 서명하기 전에 검증자들이 새 공개키를 알 수 있어야 하고, 이전 토큰이 유효한 동안은 이전 검증키도 유지할 수 있습니다. 키 ID로 어떤 키인지 명확히 구분하겠습니다.

API 비밀키도 상대가 두 키를 잠시 허용할 수 있다면 새 키 배포와 사용 전환을 확인한 뒤 이전 키를 폐기하겠습니다. 모든 서버가 동시에 바뀐다고 가정하지 않고, 오래 실행되는 작업과 캐시된 키도 추적해야 합니다. 유출 대응이라면 정상 교체와 달리 이전 자격을 빨리 거절해야 하므로 사용자 재인증이나 일시 오류를 받아들여야 할 수도 있습니다.

저는 키 원문을 설정 파일과 로그에 복제하지 않고 비밀 저장소에서 권한을 제한해 전달하겠습니다. 교체 여부는 키 값이 아니라 키 버전과 성공·실패 지표로 확인합니다. 롤백할 때 이미 유출된 키를 되살리는 선택은 하지 않겠습니다. 테스트에서는 일부 검증자가 새 키를 아직 모르는 상황과 이전 자격 만료, 저장소 장애를 재현하겠습니다. 목적은 단순한 자동 교체가 아니라 어떤 시점에 어떤 자격이 허용되는지 설명 가능한 상태를 만드는 것입니다.

## 득점 포인트

- **배포 순서와 중첩 기간을 정한다.** 검증 준비 후 새 발급으로 전환한다.
- **정상 교체와 유출 대응을 구분한다.** 회수 속도와 가용성 비용을 나눈다.
- **원문 없이 관측한다.** 키 ID·버전·검증 결과로 확인한다.

## 감점 포인트

- **모든 인스턴스가 즉시 새 키를 안다고 가정한다.** 캐시와 배포 지연이 있다.
- **이전 키를 무기한 허용한다.** 교체의 보안 효과가 약해진다.
- **장애가 나면 유출된 키로 롤백한다.** 이미 깨진 신뢰를 복구하지 못한다.

## 더 파고들 거리

- 검증키 캐시의 갱신과 키 ID 미발견 처리에는 어떤 제한이 필요할까요?
- 짧은 토큰 수명과 긴 작업 수명이 충돌하면 인증을 어떻게 갱신할까요?
- 비밀 저장소 장애 때 기존 키의 사용 기간을 어디까지 허용할까요?
