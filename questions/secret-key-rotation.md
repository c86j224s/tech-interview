# 서비스를 중단하지 않고 JWT 서명키나 API 비밀키를 교체할 때 배포 순서와 유출 대응을 어떻게 나누나요?

## 구두 답변

키 교체의 핵심은 새 키를 만드는 일이 아니라 생산자와 검증자가 서로 다른 버전을 보는 중첩 기간을 안전하게 관리하는 것입니다. JWT 서명키라면 먼저 검증자들이 새 공개키를 키 ID와 함께 알게 한 뒤, 새 키로 서명을 발급합니다. 이전 토큰의 유효 기간 동안은 이전 공개키도 검증에 남겨 두고, 그 기간이 지나거나 정책상 회수할 때 제거합니다.

API 비밀키에서 상대가 두 키를 잠시 허용할 수 있다면 새 키를 배포하고 실제 호출 성공을 확인한 뒤 생산자의 사용 키를 전환하고, 캐시·장기 실행 작업·배치까지 새 키를 쓰는 것을 확인한 다음 이전 키를 폐기합니다. 모든 인스턴스가 동시에 바뀐다고 가정하지 않고, 키 ID 미발견·캐시 지연·부분 배포를 정상 전환의 실패 조건으로 다룹니다.

유출 대응은 정상 교체와 다릅니다. 이전 키가 이미 공격자에게 알려졌다면 가용성을 위해 그 키로 롤백하지 않고 즉시 폐기하며, 토큰 계열 회수나 사용자 재인증을 받아들여야 할 수 있습니다. 키 원문은 비밀 저장소와 제한된 권한으로 전달하고 로그에는 값 대신 버전·키 ID·검증 성공률만 남기겠습니다.

검증은 일부 검증자가 새 공개키를 아직 받지 않은 상태, 이전 토큰 만료, 저장소 장애, 키 ID 캐시 불일치를 재현합니다. 롤백도 키 값을 되살리는 것이 아니라 안전한 이전 버전 또는 새로 발급한 키로 돌아가는 절차여야 합니다.

## 득점 포인트

- 검증 준비→새 발급→중첩 기간→이전 키 폐기의 순서를 설명한다.
- 정상 교체와 유출 시 즉시 회수의 가용성 비용을 구분한다.
- 원문 노출 없이 버전·ID·검증 결과로 운영을 확인한다.

## 감점 포인트

- 모든 인스턴스가 즉시 새 키를 안다고 가정한다.
- 이전 키를 무기한 허용한다.
- 장애 때 유출된 키를 다시 활성화해 롤백한다.

## 더 파고들 거리

- 공개키 캐시에서 새 키 ID를 모를 때 재시도를 어떻게 제한하나요?
- 짧은 토큰 수명과 긴 작업 수명이 충돌할 때 인증을 어떻게 갱신하나요?
- 비밀 저장소 장애 동안 기존 키를 언제까지 허용할까요?
