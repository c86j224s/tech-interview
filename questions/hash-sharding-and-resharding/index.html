01

구두 답변

정의를 외우기보다, 원리와 조건을 연결해 설명해 보세요.

키를 잘 분산시키는 해시 함수를 사용하면 키 개수를 비교적 고르게 나누는 데 도움이 됩니다. 하지만 키 개수가 고르다고 실제 부하도 고른 것은 아닙니다. 특정 키에 요청이 몰리거나 키마다 데이터 크기와 처리 비용이 다르면 일부 샤드가 더 바쁠 수 있습니다.

예를 들어 계정 ID의 해시값을 샤드 수 N으로 나눈 나머지를 목적지로 사용한다고 하겠습니다. 구현이 단순하고 같은 키는 같은 샤드로 보내기 쉽습니다. 하지만 매우 활발한 계정 하나가 대부분의 요청을 만들면 그 계정이 속한 샤드에 부하가 집중됩니다. 이런 핫키는 해시 함수를 바꾸는 것만으로 해결되지 않습니다. 데이터를 더 잘게 나눌 수 있는지, 읽기를 복제하거나 캐시할 수 있는지, 같은 키의 쓰기를 분리해도 규칙을 지킬 수 있는지 검토해야 합니다.

샤드 수를 바꾸는 문제도 있습니다. 나머지 연산의 N이 바뀌면 많은 키의 목적지가 달라질 수 있어 대규모 데이터 이동이 필요합니다. 일관된 해싱이나 랑데부 해싱은 노드 변경 시 이동해야 하는 키의 비율을 줄이는 방법입니다. 고정된 논리 파티션을 먼저 만들고 물리 샤드와의 매핑만 조정하는 방식도 있습니다. 다만 어떤 방식도 실제 데이터 복사와 변경 반영을 자동으로 해결해 주지는 않습니다.

운영 중에 데이터를 옮긴다면 복사 중 발생한 쓰기를 어떻게 따라잡을지, 어느 시점에 새 샤드로 요청을 보낼지 정해야 합니다. 라우팅 정보를 다르게 알고 있는 서버들이 동시에 쓰더라도 변경이 유실되지 않도록 버전이나 소유권 전환 규칙이 필요합니다. 검증과 실패 시 복구 절차도 있어야 합니다.

따라서 샤딩 키는 분산도뿐 아니라 주요 조회와 트랜잭션이 한 샤드 안에서 끝나는지도 고려해 고르겠습니다. 운영에서는 키 개수보다 요청량, 지연, 데이터 크기와 핫키를 함께 관찰하고, 샤드 증설을 데이터 이동과 라우팅 전환을 포함한 작업으로 다뤄야 합니다.

02

득점 포인트

이해가 드러나는 지점을 확인해 보세요.

  • 키 분포와 부하 분포를 구분한다. 접근 빈도와 데이터 크기, 처리 비용이 다르면 편중이 남는다고 설명한다.
  • 나머지 기반 샤딩의 증설 비용을 설명한다. 샤드 수 변경이 많은 키의 재배치로 이어질 수 있다고 짚는다.
  • 해싱 알고리즘과 마이그레이션 절차를 구분한다. 이동량을 줄이는 알고리즘만으로 쓰기 정합성과 전환이 해결되지는 않는다고 설명한다.
  • 데이터 접근 패턴을 함께 고려한다. 조회 범위와 트랜잭션 경계, 핫키 대응을 샤딩 키 선정에 반영한다.
03

감점 포인트

놓치기 쉬운 조건과 오해를 짚어 보세요.

  • “좋은 해시 함수면 부하는 항상 균등하다”고 말한다. 키의 요청 빈도와 처리 비용은 해시가 균등하게 만들지 못한다.
  • “샤드를 추가한 뒤 나머지 연산의 숫자만 바꾸면 된다”고 말한다. 기존 데이터 위치와 새로운 라우팅의 불일치를 해결해야 한다.
  • “일관된 해싱이면 데이터 이동이 없다”고 말한다. 이동을 없애는 것이 아니라 변경에 따른 이동 범위를 줄이는 방식이다.
  • “복사만 끝나면 즉시 이전 샤드를 지워도 된다”고 말한다. 복사 중 변경과 진행 중인 요청, 라우팅 전환, 복구 가능성을 확인해야 한다.
04

더 파고들 거리

하나 더 질문하며 이해의 범위를 넓혀 보세요.

  • 가상 노드나 논리 파티션 수를 늘리면 재배치 단위와 관리 비용은 어떻게 달라질까요?
  • 하나의 핫키에 쓰기가 집중될 때 키를 쪼개면 어떤 정합성 문제가 생길까요?
  • 다른 샤드에 있는 두 계정의 상태를 함께 변경해야 한다면 어떤 선택지가 있을까요?
  • 샤드 이동 중 오래된 라우팅 정보를 가진 요청이 도착하면 거절, 전달, 재시도 중 어떤 방식을 선택할까요?

득점·감점 포인트는 학습용 자기 점검 기준이며, 특정 회사의 실제 채점표가 아닙니다.
