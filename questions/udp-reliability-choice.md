# 실시간 게임 메시지의 최신성·순서·손실 요구에 따라 TCP와 UDP 또는 검증된 전송 계층을 어떻게 선택하나요?

## 구두 답변

UDP를 선택하면 TCP가 제공하는 연결·순서·재전송·혼잡 제어의 일부를 애플리케이션이 직접 선택할 수 있습니다. 그러나 프로토콜을 UDP로 바꾼다고 지연이 자동으로 줄지는 않습니다. 모든 패킷을 순서대로 재전송하고 확인 응답까지 기다리면 TCP와 비슷한 대기와 더 큰 구현·운영 비용이 생깁니다.

먼저 메시지 종류별 계약을 나눕니다. 실시간 위치 스냅샷은 오래된 값이 늦게 도착하는 것보다 최신 값만 유지하는 것이 중요할 수 있습니다. 순서 번호를 붙여 이미 처리한 번호나 오래된 번호를 버리고, 최신 스냅샷을 주기적으로 보내면 손실을 기다리지 않을 수 있습니다. 반면 결제·계정 변경·입력 명령처럼 유실되면 안 되는 메시지는 확인, 재전송, 중복 방지, 최종 상태 조회가 필요하며 TCP나 신뢰성 있는 검증 라이브러리가 더 적합할 수 있습니다.

UDP를 사용하더라도 전송률 제한과 혼잡 제어를 직접 또는 라이브러리로 제공해야 합니다. 경로 MTU를 넘는 큰 데이터그램은 조각 손실의 영향이 커질 수 있으므로 크기를 제한하거나 애플리케이션 분할·재조립 상태와 제한을 둡니다. NAT·방화벽의 유휴 매핑, 재정렬, 중복, 스푸핑, 서버별 증폭 위험도 고려합니다.

선택은 손실·재정렬·지연을 주는 실제 경로에서 사용자 경험, 대역폭, CPU, 재전송량을 비교해 정합니다. 이미 요구를 충족하는 검증된 QUIC 같은 계층이 있다면 직접 신뢰성 프로토콜을 만드는 것보다 먼저 검토하겠습니다.

## 득점 포인트

- 최신 상태와 반드시 실행할 명령의 전달 계약을 구분한다.
- UDP에서 직접 책임질 순서·중복·혼잡·크기 문제를 설명한다.
- 실제 손실·NAT 환경과 검증된 라이브러리를 선택 기준에 포함한다.

## 감점 포인트

- UDP가 항상 더 빠르고 가볍다고 말한다.
- UDP에는 혼잡 제어가 필요 없다고 말한다.
- 모든 메시지를 동일하게 재전송한다.

## 더 파고들 거리

- 스냅샷과 입력 명령을 다른 전달 정책으로 나누는 장점은 무엇인가요?
- MTU를 넘는 메시지를 분할할 때 어떤 수명·상한 상태가 필요한가요?
- 순서 번호가 순환할 때 최신 패킷을 어떻게 비교하나요?
