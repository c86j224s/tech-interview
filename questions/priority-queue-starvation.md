# 우선순위가 높은 작업이 계속 들어와 낮은 작업은 오래 기다립니다. 중요한 작업을 먼저 처리하면서도 기아를 막으려면 큐와 실행 자원을 어떻게 조정하나요?

## 구두 답변

우선순위 큐는 높은 중요도의 작업을 먼저 선택하지만, 높은 작업이 계속 유입되면 낮은 작업이 무기한 대기하는 starvation이 생길 수 있습니다. “낮은 우선순위”가 “언제 처리되지 않아도 된다”는 뜻은 아니므로, 높은 요청의 응답 목표와 낮은 요청의 최대 대기·폐기 조건을 함께 정하겠습니다.

해법으로 클래스별 최소 실행 예산, 가중 라운드 로빈, 일정 비율의 low-priority 슬롯, 대기 시간에 따라 우선순위를 올리는 aging을 사용할 수 있습니다. 다만 deadline을 이미 넘긴 작업을 무조건 승격하면 유용하지 않은 작업이 자원을 차지할 수 있어 만료·취소를 먼저 확인합니다. 요청 개수가 아니라 실행 시간·메모리·외부 연결 점유가 다른 경우 긴 작업을 별도 큐와 시간 예산으로 분리합니다.

비선점 작업이 길면 높은 우선순위도 현재 작업이 끝날 때까지 기다릴 수 있으므로 chunking·취소 지점·worker pool 격리를 검토합니다. 고우선순위 부하를 지속 주입해 저우선순위의 p99 대기(느린 대기의 99번째 백분위수), 완료율, 만료율과 핵심 요청의 SLO(사용자 지연·오류 목표)를 함께 측정합니다. 고우선순위만 정상이고 낮은 요청이 계속 만료되면 공정성 정책이 실패한 것입니다. 우선순위는 과부하에서 손실을 어디에 배분할지 정하는 정책이지 전체 용량을 늘리는 방법은 아닙니다.

## 득점 포인트

- 우선순위 선택과 최소 진행 보장을 분리한다.
- 가중 예산·aging·deadline·취소를 조건부 정책으로 제시한다.
- 요청 수가 아닌 실행 자원과 비선점 비용을 반영한다.

## 감점 포인트

- 우선순위 큐만 두면 낮은 요청도 자동 공정하다고 말한다.
- 오래된 요청은 유용성·deadline과 무관하게 무조건 실행한다.
- 요청 수 비율이 CPU·메모리 자원 비율과 같다고 말한다.

## 더 파고들 거리

- 비선점 작업이 실행 중이면 높은 우선순위 요청도 왜 즉시 실행되지 않나요?
- 우선순위 역전과 일반적인 queue starvation을 어떤 관측으로 구분할까요?
- 테넌트별 공정성과 기능별 중요도를 계층 스케줄러에서 어떻게 결합할까요?
