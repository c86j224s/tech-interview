# 브라우저 주소창에 HTTPS 상품 페이지 주소를 입력했습니다. 이름 조회와 서버 연결부터 화면 표시까지 어떤 과정을 거치며, 캐시가 있으면 무엇이 생략될 수 있나요?

## 구두 답변

여기서는 HTTP/1.1 또는 HTTP/2를 TCP 위에서 사용하는 HTTPS 탐색을 전제로 합니다. HTTP/3는 QUIC을 사용하므로 연결 단계가 다릅니다. 브라우저 탐색은 URL을 해석하는 단계, 이름을 주소로 바꾸는 단계, 전송 연결을 준비하는 단계, HTTP 요청을 주고받는 단계, 응답을 화면으로 바꾸는 단계로 나누어 설명하는 것이 정확합니다. 먼저 브라우저는 입력 문자열을 URL로 파싱해 스킴, 호스트, 포트, 경로, 쿼리와 프래그먼트를 구분합니다. 프래그먼트는 일반적으로 서버에 전송되지 않고 문서 안의 위치 이동에 사용되므로 요청 대상과 구별해야 합니다.

호스트 이름이 있으면 브라우저·운영체제·리졸버의 캐시를 확인하고 필요하면 DNS 질의로 IP 주소를 얻습니다. DNS 결과를 얻었다고 HTTP가 바로 시작되는 것은 아닙니다. 브라우저는 목적지 포트로 연결을 만들고, 일반적인 HTTPS에서는 TCP 연결을 만든 뒤 TLS 핸드셰이크에서 암호화 키와 서버 인증서를 검증합니다. 각 경계가 별도이므로 DNS는 맞지만 TCP가 막히거나, TCP는 연결됐지만 인증서 이름이 맞지 않아 TLS에서 실패할 수 있습니다.

그 다음 브라우저가 HTTP 요청을 보내고 서버·프록시·캐시가 응답을 돌려줍니다. 리다이렉트나 인증, 캐시 검증이 있으면 이 흐름이 여러 번 반복될 수 있습니다. 응답의 HTML을 파싱해 DOM을 만들고 CSS를 읽어 CSSOM을 만든 뒤, 필요한 리소스를 추가로 요청합니다. DOM과 CSSOM으로 렌더링 대상을 정하고 layout으로 크기와 위치를 계산하며 paint·합성 단계를 거쳐 화면을 갱신합니다. 자바스크립트는 파싱과 렌더링을 막거나 DOM을 바꿔 이 순서를 다시 일으킬 수 있습니다.

문제 분석에서는 ‘페이지가 느리다’고 묶지 않고 DNS 시간, 연결 시간, TLS 시간, 요청 대기, 응답 수신, 렌더링·스크립트 시간을 나눠 측정하겠습니다. 캐시 적중이나 기존 연결 재사용이 있으면 일부 단계가 생략될 수 있으므로 첫 탐색과 재탐색도 구분하겠습니다.

## 득점 포인트

- URL 파싱부터 렌더링까지를 독립된 경계와 실패 지점으로 나눈다.
- DNS·TCP·TLS가 각각 다른 역할과 지연을 가진다고 설명한다.
- 네트워크 완료와 DOM·layout·paint 완료를 구분해 측정한다.

## 감점 포인트

- DNS가 끝나면 곧바로 HTML이 화면에 보인다고 말한다.
- HTTPS의 TLS 검증을 TCP 연결 자체의 기능으로 설명한다.
- 브라우저 캐시·연결 재사용·리다이렉트를 무시하고 항상 같은 순서를 단정한다.
