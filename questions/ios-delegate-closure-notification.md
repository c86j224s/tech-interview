# iOS 앱에서 다운로드 결과는 요청한 화면에 돌려주고, 로그인 상태 변경은 여러 화면에 알려야 합니다. delegate·완료 클로저·Notification을 어떤 기준으로 나누나요?

## 구두 답변

세 방식의 핵심 차이는 문법보다 관계와 수명입니다. delegate는 한 객체가 특정 협력자에게 여러 이벤트를 순서 있게 전달하거나, 협력자의 결정을 다시 받아야 할 때 쓰는 1 대 1 계약입니다. 프로토콜로 메서드와 필수 조건을 드러내기 때문에 테이블 뷰처럼 이벤트 종류가 많고 재사용되는 컴포넌트에 적합합니다. 대신 delegate를 누가 소유하는지 명확히 하고, 보통 순환을 피하기 위해 약한 참조로 둡니다.

완료 클로저는 한 번의 비동기 작업이 성공·실패 결과를 호출자에게 돌려주는 데 간결합니다. 예를 들어 이미지 한 장을 받아 화면에 적용하는 요청이라면 호출 시점의 문맥과 결과 처리를 가까이 둘 수 있습니다. 하지만 클로저를 작업 객체가 오래 보관하고 클로저가 작업 객체나 뷰 컨트롤러를 강하게 캡처하면 순환 참조가 생길 수 있습니다. 반복 이벤트에 같은 클로저를 계속 호출하거나 여러 소비자가 필요해지면, 취소·중복·호출 횟수 계약이 불명확해지므로 delegate나 별도 스트림으로 관계를 다시 설계합니다.

Notification은 발신자가 수신자를 직접 알지 못한 채 여러 관찰자에게 방송하는 방식입니다. 앱 전역 설정 변경이나 서로 독립적인 화면의 상태 무효화처럼 여러 객체가 같은 사건에 반응해야 할 때 유용하지만, 누가 듣고 있는지와 호출 순서를 코드만 보고 파악하기 어렵습니다. 알림은 과거 사건을 자동으로 재생하지 않으므로 늦게 등록한 화면이 현재 상태를 얻어야 한다면 저장된 상태를 별도로 조회해야 합니다. 관찰자 수명, 객체 해제 후 토큰 정리, 사용자 정보가 포함된 payload의 범위도 관리해야 합니다.

따라서 한 명의 명확한 협력자와 양방향 계약이면 delegate, 단발성 결과면 완료 클로저, 다수의 독립 수신자가 현재 사건에 반응하면 Notification을 우선 검토합니다. 여러 방식을 섞을 때도 같은 이벤트를 세 경로로 중복 전달하지 말고, 취소·실패·호출 시점·수신자 해제 후 동작을 문서화해야 합니다. 선택 기준은 구독자 수만이 아니라 결합도, 타입 안전성, 수명, 이벤트를 놓쳤을 때의 복구 가능성까지 포함해야 합니다.

## 득점 포인트

- delegate의 1 대 1 양방향 계약, 클로저의 단발성 결과, Notification의 다수 방송을 구분한다.
- 오래 사는 클로저와 delegate가 강하게 소유될 때 생길 수 있는 수명·순환 문제를 설명한다.
- Notification은 과거 상태를 보장하지 않으므로 현재 상태 조회나 저장 모델이 필요하다는 조건을 말한다.

## 감점 포인트

- Notification이 항상 delegate보다 성능이 좋거나 모든 이벤트에 적합하다고 단정한다.
- 완료 클로저가 한 번만 호출된다는 계약 없이 재호출·취소·실패 경로를 구현한다.
- delegate를 강한 참조로 연결해 양방향 객체가 서로 해제되지 않는 문제를 만든다.
