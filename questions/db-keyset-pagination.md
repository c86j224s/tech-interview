# 주문 목록에서 OFFSET으로 뒤 페이지를 열수록 느려집니다. 마지막 주문의 시각과 ID를 커서로 쓰면 어떻게 달라지나요?

## 구두 답변

OFFSET으로 앞의 행을 건너뛰는 방식이라면 뒤 페이지일수록 많은 행을 읽고 버릴 수 있습니다. 저는 실제 읽은 행 수와 정렬 비용을 확인하겠습니다. 반환은 20개여도 수십만 행을 지나야 한다면 페이지 크기보다 접근 방식이 문제입니다.

순서대로 더 보기를 제공하는 화면이라면 마지막으로 읽은 정렬 키 다음부터 찾는 키셋 페이지네이션을 선택하겠습니다. 키셋 방식은 페이지 번호 대신 직전 페이지의 마지막 정렬 키를 커서로 전달합니다. 다음은 `:last_created_at`, `:last_id`, `:page_size`를 각각 직전 페이지 마지막 주문의 시각, 주문 ID, 요청한 페이지 크기로 둔 PostgreSQL용 SQL 템플릿입니다. 콜론 이름은 설명용 바인딩 자리이며 실제 드라이버의 파라미터 문법으로 바꿔 실행합니다. 정렬 컬럼은 NULL이 없다고 가정합니다.

```sql
SELECT id, created_at, customer_id, total_amount
FROM orders
WHERE (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT :page_size;
```

주문 시각과 주문 ID를 함께 정렬 키로 두면 같은 시각의 주문도 순서를 정할 수 있습니다. 시각만 비교하면 같은 시각의 행을 빠뜨릴 수 있어 유일한 보조 키가 필요합니다. PostgreSQL이 아닌 DB에서 행 비교식을 지원하지 않으면 `created_at < :last_created_at OR (created_at = :last_created_at AND id < :last_id)`와 같은 조건으로 표현할 수 있습니다.

대신 임의의 300번째 페이지로 바로 이동하거나 정확한 전체 페이지 수를 보여 주는 요구는 구현 방식이 달라집니다. 데이터가 중간에 삽입·수정되는 동안 어떤 목록 일관성을 기대하는지도 정해야 합니다. 저는 대량 목록의 연속 탐색은 커서를 쓰고, 작은 관리 목록의 페이지 번호 요구는 비용을 확인해 별도로 허용하겠습니다. 테스트에서는 같은 정렬 값, 새 행 삽입, 정렬 키 변경을 섞어 누락과 중복이 계약 범위 안인지 확인하겠습니다.

## 득점 포인트

- OFFSET의 반환 건수와 실제 건너뛴 읽기 비용을 구분한다.
- 유일한 보조 키를 정렬·커서·인덱스에 함께 사용한다.
- 연속 탐색과 임의 페이지 요구의 차이를 설명한다.

## 감점 포인트

- 인덱스가 있으면 OFFSET 비용이 일정하다고 말한다.
- 시각 하나만 커서로 써 같은 시각 행을 누락한다.
- 키셋이 모든 동시 변경에서 완전한 스냅샷이라고 말한다.
