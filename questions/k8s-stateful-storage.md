# StatefulSet의 Pod가 재시작할 때 PVC가 다시 붙는다면 데이터의 복제·일관성·가용성도 보장되나요?

## 구두 답변

PVC는 Pod가 요청한 저장 볼륨을 연결하고 수명과 접근 모드를 표현하지만, 애플리케이션 데이터의 복제·트랜잭션 일관성·재해 복구를 자동으로 보장하지는 않습니다. `Bound`는 클레임과 볼륨이 연결됐다는 뜻이지 데이터가 여러 노드나 영역에 복제됐다는 뜻이 아닙니다. `ReadWriteOnce` 같은 접근 모드도 저장소 접근 조건이지, 애플리케이션 수준의 중복 쓰기나 fencing(오래된 노드의 쓰기를 차단하는 장치)을 대신하는 애플리케이션의 쓰기 잠금이 아닙니다. 옛 노드와 새 Pod가 동시에 쓰는 사례에서는 이 차단이 없으면 데이터가 갈라질 수 있습니다.

노드 장애 뒤 새 Pod를 스케줄링하려면 기존 노드에서 안전하게 detach하고 새 노드에 attach해야 합니다. 옛 노드가 아직 쓰는 상황에서 새 Pod가 동시에 쓰면 split-brain(두 실행 주체가 자신이 주인이라고 믿는 상태)과 데이터 손상이 생길 수 있습니다. 따라서 오래된 노드의 쓰기를 차단하는 fencing이 실제로 동작하는지, 스토리지 provisioner(볼륨을 만들고 연결하는 구성요소)의 노드 장애 처리, 영역 제약, 볼륨 attach(노드에 연결) 지연을 확인하겠습니다. 차단이 확인되지 않으면 새 Pod를 띄우는 것보다 먼저 옛 실행 주체를 격리해야 합니다. StatefulSet의 안정적인 이름과 PVC(Pod가 사용할 저장 볼륨 요청) 유지 역시 저장소 자체의 장애 내구성을 의미하지 않습니다. Pod 이름이 그대로 돌아와도 볼륨이 손상됐거나 다른 영역에서 접근할 수 없으면 서비스가 복구되지 않습니다.

DB나 로그 기반 애플리케이션은 자체 복제와 WAL·재생·복구 절차가 필요합니다. 볼륨 스냅샷은 파일 시점 복사일 수 있어 애플리케이션이 일관된 시점인지, 복원 뒤 로그를 재생해야 하는지 검증해야 합니다. 테스트는 Pod 재시작뿐 아니라 노드·영역 장애, detach 실패, 스냅샷 복원, reclaim 정책에 따른 삭제를 포함하고, 목표 RPO/RTO와 실제 읽기·쓰기 결과로 가용성을 판단하겠습니다.

## 득점 포인트

- PVC 연결 상태와 데이터 복제·일관성을 분리한다.
- detach·fencing·영역 제약을 장애 순서에 넣는다.
- 스냅샷과 DB 일관된 백업 및 RPO/RTO를 구분한다.

## 감점 포인트

- PVC만 있으면 다중 영역 복제가 된다고 말한다.
- 접근 모드가 애플리케이션의 중복 쓰기를 모두 막는다고 말한다.
- Pod 재시작만으로 스토리지 복구를 검증했다고 결론 낸다.
