01

구두 답변

정의를 외우기보다, 원리와 조건을 연결해 설명해 보세요.

처리량은 단위 시간에 완료한 작업 수이고, 응답 시간은 개별 요청을 보낸 뒤 결과를 받기까지 걸린 시간입니다. 많은 요청을 처리하는 능력과 한 요청에 빠르게 응답하는 능력은 관련돼 있지만 같은 지표는 아닙니다. 동시에 더 많은 작업을 실행하면 처리량은 늘어도 각 요청의 대기 시간이 길어질 수 있습니다.

특히 시스템이 포화에 가까워지면 처리량은 더 이상 크게 늘지 않는데 응답 시간은 급격히 나빠질 수 있습니다. 새 요청이 도착하는 속도를 따라가지 못해 큐가 길어지기 때문입니다. 그래서 서버 내부의 실제 처리 시간만 측정하면 안 되고, 큐나 연결 풀에서 기다린 시간까지 포함한 응답 시간을 봐야 합니다.

평균만으로는 일부 사용자가 겪는 긴 지연을 놓칠 수 있습니다. 대부분의 요청이 빠르고 일부가 매우 느린 시스템은 평균이 괜찮아도 사용자 경험이 불안정합니다. p95가 200밀리초라는 것은 측정한 요청의 약 95%가 200밀리초 이내에 끝났다는 뜻입니다. p99 같은 꼬리 지연과 오류율, 타임아웃 비율도 함께 봐야 합니다. 백분위수는 최대 지연을 보장하는 수치는 아닙니다.

비교 조건도 중요합니다. 요청 종류, 데이터 크기, 캐시 상태, 동시 요청 수가 다르면 수치만 놓고 개선이라고 말하기 어렵습니다. 빠르게 실패한 요청을 성공 요청과 섞으면 응답 시간이 좋아 보일 수도 있습니다. 또 부하 도구가 응답을 기다린 뒤 다음 요청을 보내는 방식이라면 서버가 느려질수록 부하도 줄어들어, 실제 도착률이 유지되는 환경의 적체를 충분히 재현하지 못할 수 있습니다.

따라서 동일한 조건에서 부하를 단계적으로 높이며 성공 처리량, 전체 응답 시간 분포, 오류율, 자원 사용량을 함께 확인하겠습니다. 목표 응답 시간을 지키면서 처리할 수 있는 양을 찾는 것이 중요합니다. 단순히 최대 TPS 하나를 높이는 것과 운영에 쓸 수 있는 처리 용량을 늘리는 것은 다릅니다.

02

득점 포인트

이해가 드러나는 지점을 확인해 보세요.

  • 처리량과 개별 요청의 지연을 구분한다. 동시성을 늘릴 때 두 지표가 항상 함께 좋아지지는 않는다고 설명한다.
  • 포화와 대기열을 연결한다. 처리량이 정체돼도 대기 시간은 계속 늘 수 있음을 짚는다.
  • 백분위수를 정확히 해석한다. 평균, p95, p99, 최대값이 서로 다른 정보를 제공한다고 설명한다.
  • 측정 조건과 실패 요청을 고려한다. 성공 처리량과 오류율을 분리하고 부하 생성 방식까지 확인한다.
03

감점 포인트

놓치기 쉬운 조건과 오해를 짚어 보세요.

  • “처리량은 응답 시간의 역수다”라고 일반화한다. 동시 요청 수와 대기열이 존재하는 시스템에서는 단순한 역수 관계가 아니다.
  • “p99가 1초면 모든 요청이 1초 안에 끝난다”고 말한다. 나머지 꼬리 구간에는 더 느린 요청이 있을 수 있다.
  • “평균이 줄었으므로 모든 사용자가 빨라졌다”고 말한다. 일부 구간의 지연은 악화됐을 수 있다.
  • “최대 TPS가 높은 서버가 언제나 더 좋다”고 판단한다. 응답 시간 목표와 오류율, 비용 조건을 만족하는지 함께 봐야 한다.
04

더 파고들 거리

하나 더 질문하며 이해의 범위를 넓혀 보세요.

  • 안정적인 시스템에서 평균 진행 중 요청 수, 처리량, 평균 응답 시간은 리틀의 법칙으로 어떻게 연결될까요?
  • 여러 서버의 p99를 평균 내면 전체 요청의 p99가 될까요? 어떤 집계 정보가 필요할까요?
  • 캐시가 예열된 상태와 재시작 직후를 부하 테스트에서 어떻게 구분해야 할까요?
  • 요청을 일정한 속도로 보내는 테스트와 일정한 동시 사용자 수를 유지하는 테스트는 어떤 장애를 다르게 드러낼까요?
