# 하나의 에이전트가 할 일을 여러 전문 에이전트로 나누려 합니다. 어떤 작업을 나눠야 실제 이득이 생기나요?

## 구두 답변

독립적으로 조사·검증할 수 있고 결과를 합치는 기준이 명확한 작업부터 나누겠습니다. 역할 이름을 여러 개 붙이는 것만으로 전문성이 생기거나 품질이 올라가지는 않습니다. 하위 작업을 시작할 때마다 문맥 전달·모델 호출·결과 검토 비용이 들고 서로 의존하는 작업은 병렬 실행해도 기다림과 재작업이 생깁니다. 단일 에이전트 기준선과 비교해 실제 이득을 확인해야 합니다.

### 독립성과 소유권을 기준으로 분해합니다

서로 다른 공식 문서의 계약을 조사하거나 변경 파일의 별도 모듈을 검토하는 일은 분리하기 좋습니다. 반면 하나의 작은 함수 수정에 설계자·작성자·검토자를 무조건 붙이면 설명과 조정 비용이 구현보다 커질 수 있습니다. 각 하위 작업에 질문, 읽을 범위, 반환 형식, 종료 조건을 주고 공유 정책·최종 통합 판단은 상위 조정자가 유지합니다. 하위 작업이 결정하면 안 되는 선택도 명시합니다.

조사와 실제 코드 변경은 위험이 다릅니다. 읽기 전용 조사 결과는 호스트가 대조해 통합할 수 있지만 여러 작업자가 같은 파일을 수정하면 덮어쓰기와 상충된 전제가 생깁니다. 변경을 위임한다면 파일·모듈 소유권을 겹치지 않게 하거나 독립 작업 트리를 사용하고, 최종 diff를 한곳에서 검토합니다. 하위 에이전트가 성공했다고 보고해도 실제 파일과 테스트 결과를 확인하기 전에는 완료로 인정하지 않습니다.

### 분해 비용을 결과에 포함합니다

총 지연은 가장 느린 하위 작업과 통합 시간에 영향을 받고, 총 비용은 모든 호출·재시도·문맥 중복을 합산합니다. 여러 답을 모았다고 오류가 독립적이라는 보장도 없습니다. 같은 모델·자료·문제를 공유하면 같은 오해를 반복할 수 있으므로 역할을 단순히 바꾸기보다 다른 증거와 검증 방법을 사용하는 것이 중요합니다. 결론이 충돌하면 투표만으로 결정하지 않고 근거를 대조합니다.

평가에서는 단일 구조와 분해 구조를 같은 과제·예산에서 비교하고 성공률·누락·중복 조사·통합 오류·비용을 봅니다. 먼저 소수의 가치 있는 하위 작업을 사용하고, 추가 분기가 어떤 불확실성을 줄이는지 설명할 수 있을 때만 늘립니다. 멀티 에이전트는 협업 구조이지 자동 품질 보증이 아니며, 책임 없는 합의보다 최종 통합자가 근거를 검증하는 구조가 필요합니다.

### 실행 사례로 확인합니다

독립 조사 세 개가 각각 2분이고 통합에 1분이 걸리면 이상적으로 약 3분에 끝낼 수 있지만, 총 작업 비용은 여전히 세 조사와 통합을 모두 합한 값입니다. 하나의 조사가 다른 조사의 결과를 필요로 하면 이 지연 이점은 줄어듭니다. 분해 전에 의존 그래프를 그리고 각 분기가 최종 결정을 바꿀 수 있는지 확인하겠습니다. 결과가 이미 충분하면 불필요해진 하위 작업은 취소하거나 더 이상 시작하지 않습니다. 오류가 난 분기의 증거가 필수인지에 따라 전체를 차단할지 제한된 결론을 낼지도 정합니다. 모든 분기 실패를 숨기고 성공한 보고만 합치는 것은 실제 검토 범위를 과장하는 결과가 됩니다.

## 득점 포인트

- 독립 작업과 의존 작업, 읽기 조사와 변경 소유권을 나눈다.
- 하위 작업의 범위·계약·종료와 최종 통합 책임을 명시한다.
- 상관 오류와 문맥·통합 비용을 단일 기준선과 비교한다.

## 감점 포인트

- 역할 이름이나 에이전트 수가 많으면 전문성이 생긴다고 한다.
- 여러 작업자가 같은 파일을 무통제 수정한다.
- 하위 완료 보고를 실제 결과 확인 없이 수용한다.
