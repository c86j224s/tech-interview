# Kubernetes에 Deployment 복제본 수를 바꾸는 요청은 성공했는데 Pod가 아직 준비되지 않았습니다. 선언은 어떤 과정을 거쳐 실제 상태가 되나요?

## 구두 답변

Kubernetes는 한 번 명령을 실행하고 끝내기보다 원하는 상태와 관찰한 상태의 차이를 반복해서 줄이는 컨트롤 루프를 사용합니다. Deployment에 replica 수를 적으면 컨트롤러가 현재 Pod 상태를 보고 부족한 것을 만들거나 넘치는 것을 줄입니다. API 요청 성공은 실제 워크로드 준비 완료와 같지 않습니다.

Deployment는 같은 애플리케이션의 실행 복제본을 유지하는 리소스입니다. API는 원하는 개수를 저장하고, 관련 컨트롤러와 스케줄러·노드 구성요소가 Pod 생성·배치·컨테이너 시작을 이어 갑니다. API 응답이 모든 컨테이너의 준비 완료를 기다려 주는 것은 아닙니다. 이 차이를 줄이기 위해 반복해서 관찰하고 조정하는 과정을 reconciliation이라고 합니다.

클러스터에 노드 자동 공급기가 있다면 노드 준비가 추가될 수 있고, 이미지 다운로드와 컨테이너 시작도 시간이 걸리고 실패할 수 있습니다. 저는 적용 명령의 종료 코드만 보지 않고 리소스의 status와 condition, 이벤트를 확인하겠습니다. 같은 조정을 반복해도 안전해야 하므로 컨트롤러의 작업은 멱등적으로 설계하는 것이 중요합니다. 외부 API에 영향을 주는 커스텀 컨트롤러라면 중복 생성과 삭제 복구도 별도로 관리해야 합니다.

관찰에는 지연이 있고 컨트롤러가 잠깐 멈출 수도 있으므로 즉각적인 일치를 가정하지 않겠습니다. 원하는 상태를 바꾸면서 실제 준비 여부를 기다리는 배포 절차가 필요합니다. 테스트는 Pod 삭제와 컨트롤러 재시작을 재현해 목표로 다시 수렴하는지 확인합니다. 선언형이라는 것은 실패가 없다는 뜻이 아니라 반복적으로 복구할 기준을 시스템에 남긴다는 뜻입니다.

## 득점 포인트

- 원하는 상태와 관찰 상태를 구분한다.
- API 성공과 준비 완료를 나눈다.
- 반복 조정의 멱등성을 설명한다.

## 감점 포인트

- apply 성공이면 서비스도 즉시 준비됐다고 말한다.
- 컨트롤러는 처음 한 번만 실행한다고 말한다.
- 선언형이면 외부 부수 효과도 자동 안전하다고 말한다.
