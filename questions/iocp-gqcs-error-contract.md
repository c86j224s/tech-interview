# GetQueuedCompletionStatus가 FALSE를 반환했습니다. 실패한 I/O 완료를 받은 것인지, 타임아웃으로 아무 패킷도 못 받은 것인지 어떻게 구분하나요?

## 구두 답변

반드시 그렇지는 않습니다. FALSE와 함께 유효한 OVERLAPPED가 반환됐다면 실패한 I/O 작업의 완료를 받은 경우일 수 있습니다. 반대로 OVERLAPPED가 null이면 타임아웃이나 완료 포트 관련 오류처럼 작업 패킷을 얻지 못한 경우를 구분해야 합니다. 반환값만으로 작업 컨텍스트를 버려서는 안 됩니다.

GetQueuedCompletionStatus는 완료 큐에서 결과를 꺼내는 함수이며 아래에서는 GQCS라고 줄여 부르겠습니다. ok는 반환 성공 여부, ov는 출력 OVERLAPPED 포인터입니다. FALSE일 때도 ov가 있으면 정리해야 할 완료 작업이 있을 수 있습니다.

| 반환 조합 | 의미 | 처리 |
|---|---|---|
| FALSE, ov 있음 | 실패한 I/O 완료 패킷을 받음 | GetLastError로 오류를 얻고 해당 작업의 완료 처리 |
| FALSE, ov 없음 | 패킷 없이 대기가 끝남 | 타임아웃·포트 오류 구분, bytes와 key는 사용하지 않음 |
| TRUE | 패킷을 받음 | 성공 I/O 또는 자체 게시한 패킷인지 프로그램 규약으로 구분 |

PostQueuedCompletionStatus로 직접 넣은 패킷은 OVERLAPPED가 null일 수도 있습니다. 그러므로 ‘ov가 없으면 언제나 타임아웃’이라는 분기는 잘못입니다.

수신이 연결 종료나 취소로 실패해도 그 작업은 완료 처리와 자원 반환이 필요합니다. 저는 반환값과 OVERLAPPED 유무를 먼저 나누고, 실패 코드와 작업 종류를 함께 해석하겠습니다. 사용자 정의 패킷을 넣는 구조라면 null OVERLAPPED를 사용하는 규약도 따로 정해 종료 신호와 일반 완료를 구별해야 합니다. 결과가 없는 경로에서 key나 바이트 수가 유효하다고 가정하지 않겠습니다.

타임아웃은 작업 실패가 아니라 워커의 대기 결과일 수 있어 특정 작업을 정리하는 근거로 사용하지 않겠습니다. 포트 종료는 모든 제출 작업의 수명 관리가 끝났는지와 연결해야 합니다. 테스트는 정상 완료, 실패한 I/O, 큐 대기 타임아웃과 포트 종료를 각각 재현하겠습니다. 같은 FALSE라도 정리할 작업이 있는지 없는지가 다르다는 점이 핵심입니다.

## 득점 포인트

- **반환값과 포인터를 함께 해석한다.** 실패한 완료와 패킷 없음의 차이를 설명한다.
- **작업 실패도 정리한다.** 취소·오류의 완료 수명을 유지한다.
- **사용자 패킷 규약을 정한다.** 종료 신호와 실제 작업을 구분한다.

## 감점 포인트

- **FALSE면 무조건 continue한다.** 실패 완료의 자원이 남을 수 있다.
- **대기 타임아웃이면 I/O도 취소됐다고 말한다.** 별개의 상태다.
- **모든 출력값이 항상 유효하다고 가정한다.** 반환 계약을 확인해야 한다.
