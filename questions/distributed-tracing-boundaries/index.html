01

구두 답변

정의를 외우기보다, 원리와 조건을 연결해 설명해 보세요.

전체 요청 시간이 길다는 사실만으로 어느 서비스가 원인인지 알 수는 없습니다. 저는 호출·대기·실행 구간을 나눠 기록하고 실제 응답을 결정하는 경로를 보겠습니다. 병렬로 실행된 하위 호출 시간을 단순 합산하면 전체 지연을 잘못 해석할 수 있습니다.

DB 호출 span이 길다면 그 안에 연결 풀 대기가 포함돼 있는지 확인하겠습니다. 쿼리 자체는 빠른데 연결을 기다린 것이라면 SQL 튜닝보다 진입 제어가 먼저일 수 있습니다. 비동기 큐를 거치는 작업은 발행 시점과 소비 시작 사이의 대기를 별도로 남겨야 합니다. HTTP 호출만 이어 놓으면 실제로 오래 머문 큐 구간을 놓칠 수 있습니다.

추적 ID는 로그와 연결하되 사용자 정보나 토큰을 태그로 넣지 않겠습니다. 샘플링 때문에 느린 요청이 빠질 수 있어 오류와 긴 지연을 보존하는 정책도 검토하겠습니다. 다만 모든 요청을 무조건 저장하면 비용과 민감정보 위험이 커집니다. 저는 먼저 사용자 영향이 큰 경로와 의존성 경계를 계측하고, 추적으로 만든 가설을 지표·프로파일로 확인하겠습니다. 예쁜 호출 그림이 아니라 무엇을 줄이면 실제 응답이 빨라지는지 알아내는 것이 목적입니다.

02

득점 포인트

이해가 드러나는 지점을 확인해 보세요.

  • 경계와 병렬성을 구분한다. 단순 시간 합산을 피한다.
  • 숨은 대기를 계측한다. 풀·큐·실행 시간을 분리한다.
  • 비용과 보안도 관리한다. 샘플링과 태그 정책을 정한다.
03

감점 포인트

놓치기 쉬운 조건과 오해를 짚어 보세요.

  • 가장 긴 span이 항상 계산 병목이라고 말한다. 대기가 포함될 수 있다.
  • 비동기 경계의 문맥 전달을 생략한다. 추적이 끊어진다.
  • 모든 입력을 태그로 넣는다. 비용과 정보 노출이 커진다.
04

더 파고들 거리

하나 더 질문하며 이해의 범위를 넓혀 보세요.

  • tail sampling은 느린 요청 보존과 수집 비용에서 어떤 장단점이 있나요?
  • 메시지 배치가 여러 원인 요청에서 왔다면 추적 문맥은 어떻게 연결할까요?
  • 서버 간 시계 오차가 span 해석에 어떤 영향을 줄까요?

득점·감점 포인트는 학습용 자기 점검 기준이며, 특정 회사의 실제 채점표가 아닙니다.
