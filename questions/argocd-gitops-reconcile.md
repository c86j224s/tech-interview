# Argo CD로 관리하는 Deployment를 운영자가 kubectl로 직접 수정했습니다. Git과 실제 설정이 달라지면 어떻게 감지되며, 어느 쪽 상태가 유지되나요?

## 구두 답변

Argo CD는 Git 등에 선언된 원하는 리소스와 클러스터의 실제 리소스를 비교하고 동기화 상태를 보여 줍니다. 자동 동기화와 self-heal 정책을 켰는지에 따라 실제 변경을 다시 맞추는 동작이 달라집니다. Git에 기록됐다는 것과 즉시 실행됐다는 것은 다릅니다.

운영자가 kubectl로 긴급 수정했는데 self-heal이 켜져 있으면 원래 선언으로 돌아갈 수 있습니다. 저는 긴급 변경도 가능한 빨리 선언된 원본에 반영하거나, 동기화 제어를 명확히 멈추는 절차를 두겠습니다. 누가 어떤 필드를 소유하는지 불명확하면 HPA나 다른 컨트롤러와 서로 값을 되돌릴 수 있습니다.

Sync 상태가 맞아도 애플리케이션의 기능이 정상 동작하는 것은 아닙니다. Health와 실제 사용자 지표를 함께 확인해야 합니다. Git 저장소 접근·템플릿 렌더링·클러스터 권한 실패도 단계별로 구분하겠습니다. 테스트는 수동 drift와 잘못된 선언을 넣고, 자동화가 예상대로 수정하거나 멈추는지 확인합니다. GitOps의 장점은 변경 근거와 재현성을 남기는 것이지 잘못된 선언을 안전하게 만들어 주는 것은 아닙니다.

## 득점 포인트

- 비교·동기화·self-heal을 구분한다.
- 긴급 수정과 원본 반영을 연결한다.
- Sync와 실제 기능의 정상 동작 여부를 나눈다.

## 감점 포인트

- Git 커밋이면 배포가 무조건 끝났다고 말한다.
- 수동 변경이 영구 유지된다고 가정한다.
- 모든 필드의 소유권 충돌을 무시한다.
