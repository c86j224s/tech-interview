# 여러 쿼리를 트랜잭션으로 묶으면 동시 요청으로 인한 데이터 충돌도 막을 수 있나요?

## 구두 답변

트랜잭션으로 묶는 것만으로 모든 동시성 문제가 해결되지는 않습니다. 트랜잭션의 원자성은 여러 변경을 전부 반영하거나 전부 취소하는 성질입니다. 동시에 실행되는 다른 트랜잭션의 영향을 얼마나 차단할지는 격리 수준과 실제 쿼리 방식에 따라 달라집니다.

예를 들어 카운터 값이 10일 때 두 요청이 각각 값을 읽고, 애플리케이션에서 1을 더한 뒤 11로 저장한다고 하겠습니다. 두 트랜잭션이 모두 10을 읽고, 먼저 완료된 변경을 나중 요청이 덮어쓸 수 있는 조건이라면 두 번 증가시켰는데도 최종 값은 11이 됩니다. 이런 문제를 갱신 손실이라고 합니다. 읽기와 쓰기를 각각 트랜잭션 안에서 수행했더라도, 읽은 값에 근거한 변경을 보호하지 않으면 발생할 수 있습니다.

단순한 증가라면 값을 읽어 계산한 결과를 저장하는 대신, 데이터베이스에서 `SET count = count + 1`처럼 갱신하도록 만드는 것이 우선적인 방법입니다. 재고 차감이라면 재고가 충분한지 확인하는 조건까지 UPDATE에 포함하고, 영향받은 행 수로 성공 여부를 확인할 수 있습니다. 조회와 변경 사이의 틈을 하나의 문장으로 줄이는 것입니다.

읽은 내용을 바탕으로 복잡한 판단을 해야 한다면 다른 방법이 필요합니다. 비관적 동시성 제어는 데이터베이스에 맞는 잠금 구문으로 대상 데이터를 보호한 상태에서 판단하고 변경하는 방식입니다. 낙관적 동시성 제어는 버전 값을 함께 읽고, 갱신 시 그 버전이 그대로인지 조건으로 확인합니다. 버전이 바뀌었다면 충돌로 처리하고 새 값을 읽어 다시 판단해야 합니다.

직렬화 가능 격리 수준을 사용하는 방법도 있지만, 대기나 트랜잭션 실패가 생길 수 있어 재시도 처리가 필요합니다. 결국 트랜잭션을 사용했는지만 볼 것이 아니라, 어떤 데이터 규칙을 지켜야 하는지 정하고 데이터베이스의 격리 동작과 갱신 방식이 그 규칙을 보장하는지 확인해야 합니다.

## 득점 포인트

- **원자성과 격리성을 구분한다.** 변경을 전부 반영하거나 취소한다는 보장과, 동시 실행의 간섭을 제어한다는 보장은 다르다고 설명한다.
- **갱신 손실을 실행 순서로 설명한다.** 두 요청이 같은 값을 읽고 계산한 결과를 덮어쓰는 과정을 구체적으로 제시한다.
- **문제에 맞는 해결책을 고른다.** 단순 갱신은 조건부 UPDATE나 데이터베이스 내 연산으로 처리하고, 복잡한 판단에는 잠금이나 버전 검사를 고려한다.
- **충돌 이후의 처리까지 언급한다.** 영향받은 행 수 확인, 롤백, 최신 상태에서의 재판단과 재시도가 필요함을 설명한다.

## 감점 포인트

- **“트랜잭션 안의 쿼리는 다른 트랜잭션과 섞이지 않는다”고 말한다.** 실제 간섭과 관찰 가능한 결과는 격리 수준 및 데이터베이스 구현에 따라 다르다.
- **“UPDATE가 행을 잠그므로 이전 SELECT 결과도 안전하다”고 설명한다.** 쓰기 시점의 잠금만으로 그 전에 읽은 값이 여전히 유효하다는 보장이 생기지는 않는다.
- **“낙관적 동시성 제어는 조회할 때 버전만 확인하면 된다”고 말한다.** 버전 조건 확인과 변경이 하나의 원자적인 갱신으로 이루어져야 한다.
- **“격리 수준을 높이면 실패 처리가 필요 없다”고 말한다.** 교착 상태나 직렬화 실패 등으로 트랜잭션이 중단될 수 있다.

## 더 파고들 거리

- 갱신 손실과 쓰기 편향은 어떻게 다르며, 서로 다른 행을 수정하는 트랜잭션도 데이터 규칙을 깨뜨릴 수 있을까요?
- 낙관적 동시성 제어에서 충돌이 자주 발생하면 어떤 비용이 커지고, 언제 비관적 방식이 더 적합할까요?
- 여러 행을 잠그는 작업에서 교착 상태를 줄이려면 잠금 순서와 트랜잭션 범위를 어떻게 정해야 할까요?
- 트랜잭션을 재시도할 때 이메일 발송이나 외부 API 호출까지 중복 실행되지 않게 하려면 어떻게 해야 할까요?
