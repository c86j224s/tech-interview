# 여러 쿼리를 트랜잭션으로 묶으면 동시 요청으로 인한 데이터 충돌도 막을 수 있나요?

## 구두 답변

트랜잭션을 사용했다는 사실만으로는 부족합니다. **원자성은 전부 반영하거나 취소한다는 보장이고, 격리성은 동시 실행의 간섭을 제어하는 보장**입니다. 먼저 지켜야 할 업무 불변식을 정하고, 읽기와 갱신이 그 불변식을 어떤 격리 수준에서 보장하는지 확인해야 합니다.

예를 들어 두 요청이 카운터 10을 읽고 각각 11로 저장하면, 읽은 값을 보호하지 않는 실행에서는 나중 쓰기가 먼저 한 증가를 덮어씁니다. 이것이 **갱신 손실(lost update)**입니다. 단순 증가라면 `SET count = count + 1`, 재고 차감이라면 `WHERE stock >= 수량`을 포함한 조건부 UPDATE로 판단과 변경을 DB 안에서 원자화하고 영향받은 행 수를 확인하겠습니다.

복잡한 read-modify-write라면 비관적 잠금이나 **낙관적 동시성 제어(OCC)**를 고려합니다. OCC는 `WHERE version = 읽은버전` 조건으로 변경과 버전 증가를 함께 수행하는 compare-and-swap 형태입니다. 충돌하면 이전 계산값을 그대로 재사용하지 않고 최신 상태에서 다시 판단해야 합니다. 충돌이 빈번하면 재시도 비용 때문에 잠금이 더 유리할 수 있고, 잠금은 긴 트랜잭션에서 대기와 교착 비용이 커집니다.

같은 행의 충돌만 막는 것으로 충분하지 않을 수도 있습니다. **MVCC나 스냅샷 격리**에서 두 트랜잭션이 같은 조건을 읽고 서로 다른 행을 수정하면, 직접적인 쓰기 충돌 없이 전체 규칙을 깨는 write skew가 가능할 수 있습니다. 이런 경우 SERIALIZABLE, 공통 조정 행의 잠금, 제약조건 등으로 조건 전체를 보호해야 합니다. 격리 수준의 이름만 보지 않고 DB별 실제 동작을 확인해야 합니다.

검증할 때는 두 세션의 실행 순서를 의도적으로 맞춰 불변식이 깨지는지 재현하겠습니다. 락 대기, 교착 그래프, OCC 충돌률과 재시도 횟수를 측정하고, 실패 시 재시도 범위도 정해야 합니다. **트랜잭션 밖의 이메일 발송이나 외부 API는 롤백되지 않으므로**, 외부 효과까지 포함하면 outbox나 멱등성 설계가 추가로 필요합니다.

## 득점 포인트

- **원자성·격리성을 업무 불변식과 연결한다.** 트랜잭션 사용 여부보다 어떤 실행 순서가 금지돼야 하는지를 설명한다.
- **갱신 방식을 구체적으로 제시한다.** 조건부 UPDATE의 영향 행 수와 버전 기반 CAS를 통해 검사·변경을 원자화한다.
- **행 충돌과 조건 충돌을 구분한다.** lost update와 write skew의 차이, MVCC의 보장 한계를 설명한다.
- **충돌 비용과 복구 범위를 고려한다.** OCC 재시도와 잠금 대기를 비교하고 외부 부수 효과의 멱등성까지 다룬다.

## 감점 포인트

- **“MVCC는 락을 쓰지 않으므로 동시성 문제가 없다”고 말한다.** 버전 기반 읽기는 쓰기 충돌과 다중 행 불변식을 자동으로 해결하지 않는다.
- **“UPDATE의 배타 락이 앞선 SELECT 결과도 보호한다”고 말한다.** 쓰기 직렬화와 이전 읽기의 유효성은 별개다.
- **“충돌하면 실패한 UPDATE만 그대로 재시도한다”고 말한다.** 판단의 근거가 바뀌었다면 읽기부터 포함한 업무 단위 재실행이 필요하다.
- **“SERIALIZABLE이면 요청이 실패하지 않는다”고 말한다.** 직렬화 가능한 결과를 위해 충돌 트랜잭션이 중단될 수 있으며 재시도 처리가 필요하다.

## 더 파고들 거리

- 서로 다른 행을 수정하는 당직자 변경 사례에서 write skew를 어떻게 재현하고 어떤 잠금 범위로 막을까요?
- SQL Server의 READ COMMITTED SNAPSHOT과 SNAPSHOT은 읽기 시점과 갱신 충돌 처리에서 어떻게 다를까요?
- 버전 컬럼을 사용하는 OCC에서 일부 갱신 경로가 버전을 올리지 않으면 어떤 보장이 깨질까요?
- 재시도 가능한 트랜잭션과 외부 이벤트 발행을 묶을 때 outbox가 해결하는 실패 구간과 남기는 중복은 무엇일까요?
