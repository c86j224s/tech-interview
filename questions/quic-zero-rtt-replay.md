# 재연결 지연을 줄이려고 TLS·QUIC 0-RTT로 주문 요청을 보내려 합니다. 재생 공격과 멱등성을 왜 확인하나요?

## 구두 답변

0-RTT early data는 이전 연결 정보를 이용해 초기 왕복을 줄일 수 있지만 재생 가능성이라는 별도 보안 조건이 있습니다. 일반적인 암호화 연결의 기밀성과 요청이 한 번만 실행되는 보장은 다릅니다.

### 동작 원리와 전제

같은 early data가 다시 전달되어 서버가 주문을 두 번 적용하면 암호화가 정상이어도 문제가 됩니다. 서버의 anti-replay 동작·분산 배치·재시작 범위를 확인하고 비멱등 변경은 early data로 허용하지 않거나 안정적인 요청 키로 보호합니다.

### 선택과 실패 처리

GET이라는 이름만으로 안전하다고 판단하지 않습니다. 실제 조회가 보상 지급이나 상태 변경을 수행하면 재생에 취약합니다. 서버가 early data를 거절했을 때 정상 핸드셰이크 뒤 재시도하는 경로도 논리 요청을 유지해야 합니다.

### 구체적인 사례와 검증

early data를 허용한 endpoint가 포인트를 조회하면서 최초 조회 보상을 지급한다면 GET처럼 보이더라도 반복 실행에 안전하지 않습니다. 전송 프로토콜의 안전 메서드 분류와 실제 구현의 부수 효과를 대조해야 합니다. 여러 지역 서버가 replay 방지 상태를 공유하는지, 재시작 뒤 상태가 유지되는지에 따라 보장 범위가 달라질 수 있습니다. 비멱등 작업은 일반 handshake 뒤 처리하고 사용자 응답 시간을 다른 방식으로 개선하는 선택도 가능합니다. 지연을 줄이기 위해 재생 가능성을 숨기지 않고 서버·클라이언트 양쪽의 거절 후 재시도 계약을 유지하겠습니다.

반복 early data·여러 지역 서버·재시작·거절 후 재시도를 격리 환경에서 시험합니다. 얻는 지연 이점과 제한할 API 범위를 명시합니다. 전송의 빠른 시작과 업무 변경의 정확히 한 번 효과를 별도 계층에서 설계하겠습니다.

## 득점 포인트

- 핵심 구분: 0-RTT early data는 이전 연결 정보를 이용해 초기 왕복을 줄일 수 있지만 재생 가능성이라는 별도 보안 조건이 있습니다.
- 선택 조건: GET이라는 이름만으로 안전하다고 판단하지 않습니다.
- 검증 기준: 반복 early data·여러 지역 서버·재시작·거절 후 재시도를 격리 환경에서 시험합니다.
