# Redis 키가 설정한 TTL보다 일찍 사라졌습니다. 만료와 maxmemory eviction의 차이를 어떻게 확인하고 어떤 데이터를 제거해도 되는지 정책을 정하나요?

## 구두 답변

TTL 만료는 키에 설정한 수명이 끝났다는 시간 조건이고, eviction은 메모리 한도에 도달했을 때 정책에 따라 키를 내보내는 용량 조건입니다. TTL이 남아 있는 키도 메모리 압박으로 eviction될 수 있으며, TTL 시각이 지났다고 그 순간 모든 메모리가 반환되는 것도 아닙니다. Redis는 접근 시 만료를 확인하고 주기적으로 만료 키를 정리할 수 있습니다.

`maxmemory-policy`는 모든 키를 대상으로 할지, TTL이 있는 키만 대상으로 할지, 메모리가 부족할 때 쓰기를 거절할지를 정합니다. 캐시처럼 없어져도 원본에서 재생성할 데이터와 반드시 보존해야 하는 원본 데이터를 같은 인스턴스에 두면 eviction이 원본 데이터를 없애는 사고가 될 수 있으므로, 데이터 분리나 정책별 인스턴스를 우선 검토하겠습니다. `volatile-*` 정책에서 제거할 TTL 키가 부족하면 새 쓰기가 거절될 수 있습니다.

큰 키를 제거하는 비용, 복제 버퍼·AOF/RDB·메모리 할당기 여유까지 고려해야 합니다. `maxmemory`를 호스트 RAM과 같게 두면 프로세스 외 메모리와 순간 버퍼 때문에 압박이 생길 수 있습니다. 지표는 `expired_keys`와 `evicted_keys`, 거절된 쓰기, RSS와 lazy freeing 대기를 분리해 봅니다.

테스트에서는 만료 집중과 메모리 압력을 따로 발생시키고, 만료 시점의 실제 조회 결과와 eviction 정책의 대상을 확인하겠습니다. TTL은 데이터 보존 보장이 아니라 수명 상한이며, eviction은 그보다 별도의 손실 정책입니다.

## 득점 포인트

- 시간 만료와 용량 제거를 원인·대상별로 구분한다.
- eviction 정책과 쓰기 거절 조건을 설명한다.
- 키 외 버퍼·RSS·해제 비용을 운영 지표에 포함한다.

## 감점 포인트

- TTL 전에는 키가 반드시 남는다고 말한다.
- 만료와 eviction 지표를 같은 현상으로 본다.
- `maxmemory`가 프로세스 전체 RSS의 절대 상한이라고 말한다.

## 더 파고들 거리

- volatile 정책에서 대상 TTL 키가 부족할 때 어떤 쓰기 결과가 나오나요?
- lazy freeing이 명령 지연과 RSS 하락 시점에 미치는 영향은 무엇인가요?
- 정확한 작업 스케줄러를 TTL 만료 이벤트로 대체하면 어떤 문제가 있나요?
