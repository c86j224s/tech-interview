# 서로 다른 소셜 로그인으로 받은 이메일 주소가 같습니다. 기존 서비스 계정에 새 로그인 수단을 자동으로 연결해도 되나요?

## 구두 답변

이메일이 같다는 이유만으로 자동 연결하는 것은 위험합니다. 공급자가 이메일 소유를 어떤 방식으로 검증했는지 다르고, 이메일이 변경되거나 재할당될 수도 있습니다. 같은 표시 문자열과 두 계정의 소유권 증명은 구분해야 합니다.

여기서 연결은 새 로그인 수단으로도 기존 계정에 접근할 수 있게 한다는 뜻입니다. 이메일 문자열이 같다는 이유로 연결하면, 두 인증 공급자가 같은 수준으로 이메일 소유를 확인하지 않는 경우 다른 사람에게 기존 계정 접근권을 줄 수 있습니다. 그래서 현재 계정의 소유와 새 로그인 수단의 소유를 각각 확인해야 합니다.

저는 이미 로그인한 사용자가 새 로그인 수단을 추가하는 명시적인 연결 흐름을 우선하겠습니다. 현재 계정의 최근 인증을 확인하고 새 공급자에서도 인증을 완료한 뒤 두 결과를 같은 연결 요청에 묶습니다. 공급자의 안정적인 사용자 식별자와 발급자를 키로 저장하고, 이메일만 영구 신원으로 사용하지 않겠습니다.

이미 다른 계정에 연결된 자격이라면 조용히 옮기지 않고 충돌로 처리해야 합니다. 계정 연결은 로그인 수단 추가이고 데이터 병합은 별도 업무일 수 있습니다. 연결 해제 때도 마지막 로그인 수단을 없애 잠기지 않도록 복구 경로를 확인하겠습니다. 테스트에서는 이메일이 같은 다른 공급자 사용자, 오래된 세션, 중복 연결 요청을 재현하겠습니다. 사용자가 편하게 로그인하도록 만드는 기능이 기존 계정의 소유권 경계를 우회하지 않게 하는 것이 핵심입니다.

## 득점 포인트

- 이메일 속성과 소유권 증명을 구분한다.
- 현재 계정·새 공급자 인증을 하나의 요청에 바인딩한다.
- issuer·안정 ID·충돌·해제 규칙을 제시한다.

## 감점 포인트

- 이메일이 같으면 동일인이라고 단정한다.
- 이미 연결된 자격을 자동 이동한다.
- 연결과 데이터 병합을 동일시한다.

## 더 파고들 거리

- 연결 중 세션이나 브라우저 계정이 바뀌면 요청을 어떻게 무효화할까요?
- 공급자 ID 재사용을 어떤 키로 방지할까요?
- 마지막 로그인 수단 해제에 어떤 대체 수단이 필요할까요?
