01

구두 답변

정의를 외우기보다, 원리와 조건을 연결해 설명해 보세요.

먼저 기존 호출을 새 구현으로 조금씩 돌릴 수 있는 경계를 만들겠습니다. 모든 기능과 데이터를 동시에 바꾸기보다 기능이나 사용자 집단 단위로 전환하고, 같은 외부 계약을 유지하며 결과를 비교하는 방식입니다. 보통 이런 점진적 대체를 strangler 방식이라고 부릅니다.

계정 조회부터 새 서비스로 옮긴다면 진입 라우터에서 일부 요청을 선택하고, 원본과 새 응답의 차이를 관찰할 수 있습니다. 쓰기는 더 조심해야 합니다. 두 시스템이 동시에 권위 있는 상태를 바꾸면 충돌이 생기므로 어떤 단계에서 누가 쓰기 소유자인지 정해야 합니다. 읽기 복제나 결과 비교와 실제 이중 쓰기를 같은 위험도로 취급하지 않겠습니다.

저는 새 경로의 오류와 지연이 기준 안에 있는 집단부터 확대하고, 되돌릴 때 필요한 데이터 호환을 유지하겠습니다. 새 기능이 이전 형식으로 표현되지 않는 데이터를 만들었다면 라우팅만 되돌려서는 안 됩니다. 전환율과 함께 남은 레거시 호출, 오래된 프로토콜 사용, 데이터 차이를 추적하겠습니다. 최종 제거도 계획해야 합니다. 새 시스템이 생겼는데 이전 시스템이 계속 남으면 복잡성이 두 배가 될 수 있으므로, 사용 경로가 없다는 증거와 보관·복구 요구를 확인한 뒤 종료하겠습니다.

02

득점 포인트

이해가 드러나는 지점을 확인해 보세요.

  • 전환 단위를 작게 정한다. 외부 계약과 관측을 유지한다.
  • 쓰기 소유권을 명확히 한다. 이중 읽기와 이중 쓰기를 구분한다.
  • 롤백과 제거를 계획한다. 데이터 호환과 남은 의존성을 확인한다.
03

감점 포인트

놓치기 쉬운 조건과 오해를 짚어 보세요.

  • 라우팅만 되돌리면 항상 롤백된다고 말한다. 새 데이터가 이전 형식과 다를 수 있다.
  • 두 시스템을 동시에 쓰면 안전하다고 말한다. 부분 성공과 충돌이 생긴다.
  • 신규 구축 완료를 전환 완료로 본다. 레거시 의존성 제거가 남는다.
04

더 파고들 거리

하나 더 질문하며 이해의 범위를 넓혀 보세요.

  • shadow traffic으로 쓰기 경로를 비교할 때 실제 부수 효과를 어떻게 막을까요?
  • 사용자 단위 전환과 기능 단위 전환은 어떤 위험이 다를까요?
  • 장기간 병행 운영의 정책 차이를 어떻게 추적할까요?

득점·감점 포인트는 학습용 자기 점검 기준이며, 특정 회사의 실제 채점표가 아닙니다.
