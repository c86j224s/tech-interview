01

구두 답변

정의를 외우기보다, 원리와 조건을 연결해 설명해 보세요.

N+1은 목록을 한 번 읽은 뒤 각 항목의 관련 데이터를 별도로 읽어 요청 수가 항목 수에 따라 늘어나는 패턴입니다. 각 쿼리가 빨라도 네트워크 왕복과 연결 사용이 누적됩니다. 저는 느린 쿼리 하나만 찾기보다 한 사용자 요청이 몇 번 DB를 호출하는지 보겠습니다.

주문 목록 50개에 고객 정보를 하나씩 붙인다면 고객 키를 모아 한 번에 읽고 매핑하는 방식으로 왕복을 줄일 수 있습니다. JOIN도 좋은 방법이지만 여러 일대다 관계를 동시에 붙이면 행이 곱으로 늘어 중복 데이터와 정렬 비용이 커질 수 있습니다. ORM의 eager loading 옵션 하나로 해결됐다고 보지 않고 실제 생성 SQL과 반환 행 수를 확인하겠습니다.

저는 관계의 크기에 따라 단일 JOIN과 제한된 배치 조회를 선택하겠습니다. 페이지 대상 주문을 먼저 확정한 뒤 그 주문들의 세부 데이터를 읽는 방식도 가능합니다. 배치 크기를 무한히 키우면 큰 IN 조건과 메모리 문제가 생기므로 상한을 두겠습니다. 테스트는 목록 크기를 늘리면서 쿼리 수, 읽은 행, 응답 크기와 지연을 비교합니다. 목표는 쿼리 개수만 최소화하는 것이 아니라 같은 업무 데이터를 적은 왕복과 과하지 않은 읽기로 가져오는 것입니다.

02

득점 포인트

이해가 드러나는 지점을 확인해 보세요.

  • 요청 단위 호출 수를 본다. 개별 쿼리 지연만으로 판단하지 않는다.
  • JOIN의 행 증폭을 고려한다. 여러 일대다 관계를 무작정 합치지 않는다.
  • 배치 크기와 페이지 범위를 제한한다. 실제 읽기와 메모리를 함께 본다.
03

감점 포인트

놓치기 쉬운 조건과 오해를 짚어 보세요.

  • 모든 조회를 하나의 JOIN으로 합친다. 중복 행 폭증이 가능하다.
  • 각 쿼리가 빠르면 문제없다고 말한다. 왕복이 누적된다.
  • ORM 옵션만 보고 완료라고 한다. 실제 SQL을 확인해야 한다.
04

더 파고들 거리

하나 더 질문하며 이해의 범위를 넓혀 보세요.

  • 캐시가 N+1을 숨기는 경우 콜드 상태에서 어떻게 검증할까요?
  • 배치 로더의 요청별 캐시와 전역 캐시는 어떤 정합성 차이가 있나요?
  • 일대다 JOIN에서 LIMIT을 적용할 때 부모 페이지가 깨지는 이유는 무엇인가요?
