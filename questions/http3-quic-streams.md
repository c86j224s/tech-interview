# HTTP/3는 TCP의 head-of-line blocking을 줄인다고 합니다. 패킷 유실이 다른 요청에 전혀 영향을 주지 않나요?

## 구두 답변

QUIC은 스트림별 순서 복구를 제공해 한 스트림의 누락 바이트가 다른 스트림의 전달을 TCP처럼 직접 막는 문제를 줄입니다. 하지만 연결의 혼잡 제어·대역폭·CPU를 공유하므로 유실 영향이 완전히 사라지는 것은 아닙니다.

### 동작 원리와 전제

한 QUIC 패킷에 여러 스트림 데이터가 들어갈 수 있고 유실되면 해당 데이터는 재전송해야 합니다. 다른 스트림에 전달 가능한 데이터는 계속 처리할 수 있지만 혼잡 창 감소는 연결 전체 처리량에 영향을 줍니다. HTTP/3와 QUIC의 역할도 구분합니다.

### 선택과 실패 처리

UDP 기반이라고 애플리케이션이 직접 신뢰성을 모두 구현하는 것은 아닙니다. QUIC이 암호화·흐름·혼잡·스트림을 제공합니다. 네트워크의 UDP 차단, fallback, MTU·CPU 비용과 기존 프록시 지원을 확인합니다.

### 구체적인 사례와 검증

요청 A의 데이터 일부가 유실돼도 B의 필요한 바이트가 도착했다면 B를 애플리케이션에 전달할 수 있습니다. 그러나 동일 연결의 congestion window가 줄면 이후 B의 새 데이터 전송도 느려질 수 있습니다. 이 두 현상을 구분해야 'HOL 제거'를 '손실 영향 0'으로 과장하지 않습니다. HTTP 헤더 압축과 애플리케이션의 요청 의존도 추가 대기를 만들 수 있습니다. 실제 모바일 네트워크에서 재연결·연결 이동·fallback을 함께 시험하고, UDP가 차단된 환경에서 사용자가 연결 자체를 잃지 않게 검증합니다. 프로토콜 이름보다 실제 성공률·지연 분포·CPU 비용을 비교하겠습니다.

손실·지터·이동 네트워크·동시 스트림에서 HTTP/2와 전체 지연을 비교합니다. 스트림 개수와 서버 예산도 제한합니다. 전송 계층 개선이 느린 DB나 애플리케이션의 순차 의존을 해결하지는 않으므로 병목을 분리하겠습니다.

## 득점 포인트

- 핵심 구분: QUIC은 스트림별 순서 복구를 제공해 한 스트림의 누락 바이트가 다른 스트림의 전달을 TCP처럼 직접 막는 문제를 줄입니다.
- 선택 조건: UDP 기반이라고 애플리케이션이 직접 신뢰성을 모두 구현하는 것은 아닙니다.
- 검증 기준: 손실·지터·이동 네트워크·동시 스트림에서 HTTP/2와 전체 지연을 비교합니다.
