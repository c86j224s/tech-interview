01

구두 답변

정의를 외우기보다, 원리와 조건을 연결해 설명해 보세요.

바로 이동한다고 보장할 수 없습니다. DNS 응답은 리졸버와 운영체제, 런타임에서 캐시될 수 있고 이미 맺은 연결은 DNS를 다시 조회하지 않고 계속 사용할 수 있습니다. 주소 변경은 새 조회의 결과를 바꾸는 것이지 기존 연결을 옮기는 명령은 아닙니다.

서버 교체를 계획한다면 TTL을 미리 낮추고 이전 TTL의 캐시가 줄어들 시간을 확보하겠습니다. 그래도 모든 클라이언트가 같은 규칙과 시간을 따르는 것은 아니므로 이전 서버를 바로 제거하지 않겠습니다. 기존 연결을 점진적으로 배출하고 새 연결이 어느 서버로 가는지 관찰하는 기간이 필요합니다. 존재하지 않는 이름의 실패 응답도 캐시될 수 있어, 잘못된 등록을 수정해도 일부 클라이언트가 계속 실패하는 경우를 봐야 합니다.

장애 전환에서는 DNS만으로 원하는 복구 시간을 맞출 수 있는지 따져 보겠습니다. 연결 풀이 오래된 주소를 붙잡는다면 연결 최대 수명이나 실패 후 재조회 정책이 필요합니다. 저는 리졸버 결과, 실제 원격 연결 주소, 클라이언트 오류를 함께 확인하겠습니다. 전환 속도를 위해 TTL을 과하게 낮추면 조회 부하와 DNS 의존성도 커집니다. 즉시 전환이 중요한 서비스는 DNS 외에 로드밸런싱과 연결 재수립 경로를 함께 설계하겠습니다.

02

득점 포인트

이해가 드러나는 지점을 확인해 보세요.

  • 조회와 기존 연결을 구분한다. DNS 변경이 연결 이동은 아님을 설명한다.
  • 전환 순서를 정한다. 사전 TTL 조정·관찰·이전 서버 배출을 포함한다.
  • 실제 접속 주소를 확인한다. 캐시 결과와 연결 상태를 함께 본다.
03

감점 포인트

놓치기 쉬운 조건과 오해를 짚어 보세요.

  • TTL이 지나면 모든 연결이 바뀐다고 말한다. 기존 연결은 계속될 수 있다.
  • 주소 변경 직후 이전 서버를 없앤다. 캐시된 클라이언트가 실패할 수 있다.
  • 낮은 TTL에는 비용이 없다고 말한다. 조회량과 의존성이 늘어난다.
04

더 파고들 거리

  • 가중 DNS로 부하를 나눌 때 요청 비율이 정확히 맞지 않는 이유는 무엇인가요?
