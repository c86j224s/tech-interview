Redis Cluster에서 hash tag로 관련 키를 같은 슬롯에 배치할 때 원자성·분산·재시도에 어떤 제약이 생기나요?

01

구두 답변

정의를 외우기보다, 원리와 조건을 연결해 설명해 보세요.

Redis Cluster는 키를 슬롯으로 나누므로 다중 키 명령이나 여러 키를 사용하는 Lua 스크립트는 일반적으로 같은 슬롯의 키를 요구합니다. 키 이름에 {...}가 있으면 그 중괄호 안의 부분을 해시 대상으로 삼는 hash tag를 사용할 수 있습니다. 예를 들어 {acct:42}:balance와 {acct:42}:ledger는 같은 계정 태그를 사용해 함께 배치할 수 있습니다.

이 배치는 한 계정의 잔액과 원장을 짧은 원자적 연산으로 갱신하는 데 도움이 됩니다. 그러나 모든 계정에 {all} 같은 태그를 쓰면 한 슬롯에 부하와 메모리가 몰려 샤딩의 이점이 사라집니다. 함께 변경되어야 하는 최소 업무 단위만 묶고, 두 계정 간 이체처럼 서로 다른 태그를 함께 바꿔야 하는 업무는 애초에 단일 슬롯 연산으로 표현할 수 있는지 또는 별도의 조정·보상 흐름이 필요한지 설계하겠습니다.

hash tag가 제공하는 것은 슬롯 배치와 그 범위 안의 다중 키 제약을 만족시키는 도움이지 여러 슬롯을 가로지르는 전역 트랜잭션이 아닙니다. 슬롯 이동 중 클라이언트가 MOVED와 ASK를 처리하고 라우팅 정보를 갱신해야 하며, 타임아웃 뒤 재시도하면 업무 효과가 중복될 수 있어 요청 ID나 멱등 처리를 둡니다. 실제 검증에서는 핫 계정과 큰 태그 그룹, 슬롯 재배치, 재연결을 재현하겠습니다.

02

득점 포인트

이해가 드러나는 지점을 확인해 보세요.

  • 슬롯 계산과 다중 키·스크립트의 같은 슬롯 조건을 연결한다.
  • 업무 결합 범위와 핫 슬롯의 분산 비용을 비교한다.
  • 슬롯 이동 응답과 타임아웃 재시도의 위험을 포함한다.
03

감점 포인트

놓치기 쉬운 조건과 오해를 짚어 보세요.

  • 모든 키에 같은 태그를 사용해도 분산이 유지된다고 말한다.
  • hash tag가 여러 슬롯의 원자성을 제공한다고 말한다.
  • 키 파싱 규칙과 이동 응답을 추측해 구현한다.
04

더 파고들 거리

하나 더 질문하며 이해의 범위를 넓혀 보세요.

  • 서로 다른 태그의 두 계정 이체를 어떤 업무 흐름으로 바꿀까요?
  • ASK와 MOVED는 클라이언트 라우팅에서 어떻게 다르게 처리되나요?
  • 핫 슬롯을 탐지하고 태그 설계를 바꾸는 기준은 무엇인가요?

득점·감점 포인트는 학습용 자기 점검 기준이며, 특정 회사의 실제 채점표가 아닙니다.
