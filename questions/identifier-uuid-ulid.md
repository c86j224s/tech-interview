# UUID나 ULID를 쓰면 ID 충돌과 시간순 정렬, 중복 요청 처리가 모두 해결되나요?

## 구두 답변

ID 형식마다 무작위성·시간 성분·정렬·노출 특성이 다르며 용도를 나눠 선택해야 합니다. 충분한 무작위 ID는 충돌 확률을 낮추지만 같은 논리 요청이 새 ID를 두 번 생성하는 문제는 별도입니다.

### 동작 원리와 전제

시간 정렬형 ID는 인덱스 locality에 유리할 수 있지만 같은 시각의 순서와 여러 노드 시계 차이를 보장하지 않습니다. 생성 시각이나 부하 정보가 일부 드러날 수 있습니다. 사용하는 UUID 버전·ULID 구현의 엔트로피·단조 생성 범위를 확인합니다.

### 선택과 실패 처리

DB 고유 제약과 충돌 처리, API 문자열 표현과 비교 규칙을 유지합니다. URL에 추측 어려운 ID가 있어도 자원 인가는 필요합니다. 멱등 요청에는 사용자 의도에서 발급한 안정적인 키를 재사용합니다.

### 구체적인 사례와 검증

같은 사용자가 네트워크 오류로 가입 요청을 다시 보내면서 매번 새 UUID를 만들면 서로 다른 두 레코드가 생길 수 있습니다. 이는 ID 충돌이 아니라 논리 요청 중복입니다. DB의 이메일 유일성이나 요청 멱등 키가 별도로 필요합니다. 시간 정렬형 키가 순차 삽입의 locality를 개선할 수 있어도 고동시성 마지막 페이지 경합을 만들 수 있으므로 실제 엔진에서 측정합니다. 문자열 표현의 대소문자·길이·정렬 규칙을 API와 DB에서 맞춥니다. URL에서 ID를 추측하기 어렵게 만들더라도 해당 사용자에게 그 자원 권한이 있는지 반드시 검사해야 합니다.

대량 생성·재시작·시계 역행·다국어 직렬화·인덱스 크기를 시험합니다. 충돌이 드물다는 통계와 절대 불변식은 다릅니다. ID 선택은 저장·정렬·보안·호환 요구를 함께 만족하는 표현 결정입니다.

## 득점 포인트

- 핵심 구분: ID 형식마다 무작위성·시간 성분·정렬·노출 특성이 다르며 용도를 나눠 선택해야 합니다.
- 선택 조건: DB 고유 제약과 충돌 처리, API 문자열 표현과 비교 규칙을 유지합니다.
- 검증 기준: 대량 생성·재시작·시계 역행·다국어 직렬화·인덱스 크기를 시험합니다.

## 감점 포인트

- UUID를 생성하면 같은 논리 요청의 중복 생성까지 자동 제거된다고 한다.
