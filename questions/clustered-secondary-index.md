# 주문 테이블에 기본키와 고객 ID 인덱스가 있는데 고객별 주문 조회 비용이 예상보다 큽니다. DB의 실제 행 배치와 보조 인덱스가 행을 찾는 방식을 어떻게 확인하나요?

## 구두 답변

기본키는 행을 논리적으로 유일하게 식별하는 제약이고, 클러스터링은 그 키의 순서나 저장 구조가 데이터 페이지 배치에 영향을 주는 물리적 선택입니다. 둘은 같은 개념이 아닙니다. 어떤 엔진은 기본키를 클러스터드 구조의 기준으로 사용하지만, 어떤 엔진은 테이블을 별도 힙에 두고 기본키 인덱스를 보조 구조로 관리합니다. 따라서 ‘기본키는 항상 클러스터드 인덱스’라고 일반화하면 제품 차이를 놓칩니다. 한 테이블에서 물리적 행 배치 기준은 보통 하나만 효율적으로 유지할 수 있으므로, 자주 함께 읽는 순서와 삽입 패턴을 보고 정해야 합니다.

보조 인덱스는 검색 키와 실제 행을 찾을 수 있는 위치 정보를 저장합니다. 클러스터드 테이블에서는 그 위치가 직접적인 물리 주소가 아니라 클러스터링 키일 수 있어, 보조 인덱스에서 키를 찾은 뒤 클러스터드 구조를 다시 탐색하는 lookup이 생깁니다. 결과 컬럼이 보조 인덱스에 모두 들어 있으면 추가 접근을 피하는 covering 형태가 될 수 있지만, 인덱스가 넓어져 저장·쓰기 비용이 커집니다. 힙 기반 엔진에서는 행 위치가 바뀌면 보조 인덱스 포인터를 유지하는 방식 등 다른 비용 모델을 가질 수 있습니다.

클러스터링 키를 바꾸면 데이터 행의 위치나 관련 인덱스의 참조가 바뀔 수 있고, 넓은 키는 보조 인덱스에도 반복되어 크기와 캐시 효율에 영향을 줍니다. 순차적으로 증가하는 키는 임의 위치 삽입에 따른 분할과 단편화를 줄이는 데 유리할 수 있지만, 많은 쓰기가 마지막 페이지에 몰리면 삽입 경합이 커질 수 있습니다. 시간과 상관관계가 있는 키라도 실제 시간 조건을 효율적으로 탐색할 인덱스가 있는지는 별도로 확인해야 합니다. 반대로 임의 키는 분산 삽입의 이점이 있어도 페이지 분할과 조각화를 만들 수 있습니다.

선택 순서는 논리 기본키를 먼저 주문이나 고객을 식별하는 키로 정하고, 그다음 대표 조회의 정렬·범위·lookup 비율과 엔진의 실제 저장 방식을 확인하는 것입니다. 클러스터링을 바꾼 뒤에는 인덱스 크기, 페이지 읽기, lookup 횟수, 쓰기 지연을 측정해야 하며 용어만 보고 성능을 추정하지 않겠습니다.

## 득점 포인트

- 논리적 기본키 제약과 물리적 클러스터링을 분리해 설명한다.
- 보조 인덱스의 키 탐색 뒤 lookup이 생기는 이유와 covering의 비용을 말한다.
- 엔진별 구현 차이와 클러스터링 키 폭·삽입 패턴의 영향을 함께 고려한다.

## 감점 포인트

- 모든 DBMS가 기본키를 자동으로 클러스터드 인덱스로 만든다고 단정한다.
- 보조 인덱스는 항상 물리 주소를 저장하며 클러스터링 키를 거치지 않는다고 말한다.
- 클러스터드 인덱스가 하나뿐이면 어떤 조회에도 최적인 저장 순서라고 설명한다.

## 더 파고들 거리

- 클러스터링 키를 넓게 바꿀 때 보조 인덱스 크기와 쓰기량이 어떻게 변하는지 계산해 보세요.
- 힙 테이블과 클러스터드 테이블에서 같은 보조 인덱스 질의의 실행 계획을 비교해 보세요.
- 순차 키와 임의 키의 페이지 분할·경합·범위 조회 결과를 부하 조건별로 측정해 보세요.
