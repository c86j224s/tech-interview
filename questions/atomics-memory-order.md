# 원자적 변수를 쓰면 주변 데이터도 안전하게 공유되나요?

## 구두 답변

원자적이라는 것은 해당 연산이 찢어지지 않는다는 보장이지, 주변 데이터의 접근 순서까지 언제나 안전하다는 뜻은 아닙니다. 특히 C++에서는 어떤 메모리 순서를 사용하고 어떤 연산과 연결되는지 봐야 합니다. 하나의 카운터를 늘리는 문제와 완성된 객체를 다른 스레드에 공개하는 문제는 다릅니다.

예를 들어 생산자가 일반 메모리에 결과를 채운 뒤 준비 플래그를 원자적으로 켠다고 하겠습니다. 소비자가 플래그를 보고 결과를 읽으려면, 결과 쓰기가 플래그 확인 이후 읽기에 보이도록 동기화 관계가 필요합니다. 생산자의 release 저장과 그 값을 읽는 소비자의 acquire 읽기를 연결하는 것이 한 방법입니다. 단순 relaxed 플래그만으로는 그 관계가 생기지 않습니다. 또 공개한 뒤 생산자가 객체를 계속 바꾸면 최초 공개를 안전하게 했더라도 이후 접근은 별도로 보호해야 합니다.

저는 공유 객체를 불변으로 만든 뒤 공개하거나, 변경이 필요하면 뮤텍스로 보호하는 방식을 먼저 선택하겠습니다. 원자 연산만으로 구현하면 객체 수명과 복합 불변식까지 직접 증명해야 하기 때문입니다. 성능상 근거가 있을 때만 더 약한 순서를 쓰고, 작은 동시성 테스트와 레이스 탐지로 오류를 찾겠습니다. 테스트가 통과한 것만으로 모든 실행 순서가 안전하다는 증명은 아니므로, 어떤 읽기가 어떤 쓰기와 동기화되는지 코드 검토에서 명시하겠습니다.

## 득점 포인트

- **원자성과 가시성을 구분한다.** 단일 연산과 주변 데이터 공개는 다른 보장임을 설명한다.
- **공개 관계를 구체화한다.** release·acquire가 어떤 값을 통해 연결되는지 짚는다.
- **단순한 대안을 우선한다.** 불변 객체나 락과 비교해 복잡성을 정당화한다.

## 감점 포인트

- **atomic이면 모든 접근이 안전하다고 말한다.** 복합 연산과 수명은 따로 보호해야 한다.
- **relaxed도 순서를 보장한다고 말한다.** 필요한 동기화 관계가 없을 수 있다.
- **테스트 통과를 완전한 증명으로 본다.** 관찰하지 못한 실행 순서가 남는다.

## 더 파고들 거리

- 서로 다른 atomic 변수 두 개로 복합 상태를 표현할 때 어떤 중간 상태가 보일까요?
