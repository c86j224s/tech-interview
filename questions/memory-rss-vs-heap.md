# 힙 사용량은 줄었는데 프로세스의 메모리는 왜 줄지 않을 수 있나요?

## 구두 답변

애플리케이션에서 객체를 해제하는 것과 운영체제에 메모리를 돌려주는 것은 다릅니다. 할당자는 다음 요청에 재사용하려고 확보한 영역을 유지할 수 있고, 프로세스에는 힙 외에도 스택·파일 매핑·네이티브 라이브러리 메모리가 있습니다. 그래서 힙 지표 하나가 줄었다고 RSS도 바로 줄어야 하는 것은 아닙니다.

먼저 부하를 내린 뒤 살아 있는 객체 크기와 RSS의 추세를 나눠 보겠습니다. 살아 있는 객체는 일정한데 요청량이 한 번 늘어난 뒤 RSS가 높은 수준에서 안정된다면 할당자의 재사용 공간이나 단편화일 수 있습니다. 큰 객체를 해제했더라도 같은 페이지에 작은 객체가 남으면 그 페이지 전체를 반환하기 어렵습니다. 반면 부하를 반복할 때 살아 있는 객체도 계속 늘어난다면 참조가 남는 경로를 찾아야 합니다.

저는 증가한 영역을 프로세스 메모리 맵과 힙 프로파일로 먼저 좁히겠습니다. 네이티브 할당이 원인인데 GC 설정만 바꾸는 식의 대응은 피하겠습니다. 재사용 때문에 남은 메모리라면 무조건 즉시 반환하게 하기보다 호스트의 실제 압력과 재할당 비용을 비교하겠습니다. 메모리 한도가 가까워지는 서비스는 캐시·동시성·할당 패턴부터 줄이고, 반환 정책 변경은 처리량과 지연을 함께 측정해서 적용하겠습니다.

## 득점 포인트

- **객체 수명과 페이지 반환을 구분한다.** 해제된 공간도 재사용이나 단편화 때문에 남을 수 있다고 설명한다.
- **추세로 누수를 구분한다.** 부하 회복 후 안정되는 경우와 반복 증가하는 경우를 비교한다.
- **증가 영역부터 찾는다.** 힙·스택·매핑·네이티브 할당을 나눠 대응한다.

## 감점 포인트

- **RSS가 안 줄면 무조건 누수라고 말한다.** 할당자 보유 공간과 단편화일 수 있다.
- **GC만 실행하면 모든 메모리가 반환된다고 말한다.** 관리 힙 밖의 할당과 반환 정책은 별개다.
- **반환을 자주 할수록 좋다고 말한다.** 재할당과 페이지 폴트 비용이 늘 수 있다.

- 컨테이너 메모리 한도에서 파일 캐시와 프로세스 힙을 어떻게 관찰할까요?
