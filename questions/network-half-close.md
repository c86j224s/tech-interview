# TCP에서 상대가 FIN을 보냈습니다. 우리 쪽도 즉시 모든 송신을 중단해야 하나요?

## 구두 답변

TCP는 양방향 바이트 흐름이므로 한쪽의 FIN은 그 방향으로 더 보낼 데이터가 없다는 의미입니다. 반대 방향의 송신이 즉시 불가능해진다는 뜻은 아닙니다. 애플리케이션 프로토콜이 허용하는 half-close 의미를 확인해야 합니다.

### 동작 원리와 전제

상대의 송신 종료를 읽기 EOF로 관찰해도 아직 응답을 보낼 수 있습니다. 반대로 RST는 연결의 비정상 종료로 다른 처리가 필요합니다. 입력 EOF를 빈 메시지나 일시적 데이터 부재와 혼동하지 않습니다.

### 선택과 실패 처리

서버는 남은 응답을 보낸 뒤 적절한 방향을 shutdown하고 close할 수 있지만 무한히 기다리지 않습니다. TLS와 HTTP 같은 상위 프로토콜은 자체 종료·길이 규칙이 있어 TCP FIN만으로 메시지 완전성을 확정하지 않습니다.

### 구체적인 사례와 검증

파일 처리 프로토콜에서 클라이언트가 모든 입력을 보내고 write 방향을 닫은 뒤 서버의 계산 결과를 기다리는 흐름은 half-close를 활용할 수 있습니다. 서버가 FIN을 받자마자 소켓 전체를 닫으면 정상 응답을 보낼 기회를 잃습니다. 반대로 HTTP에서는 body 길이와 chunk 종료 등 상위 규칙이 있어 EOF를 무조건 정상 메시지 종료로 해석하면 잘린 요청을 성공 처리할 수 있습니다. 송신 완료도 로컬 버퍼 처리와 상대 애플리케이션의 수신·처리를 구분해야 합니다. 종료 중에 업무 효과가 이미 발생했다면 재접속한 client가 같은 논리 ID로 결과를 확인할 수 있어야 합니다.

요청 전송 뒤 half-close, 응답 중 단절, FIN 재전송·RST·부분 메시지를 시험합니다. 버퍼와 진행 중 I/O 수명은 실제 완료까지 유지합니다. 연결 종료 상태와 업무 요청 성공 여부는 별도로 기록하고 불확정 변경은 멱등 조회로 처리합니다.

## 득점 포인트

- 핵심 구분: TCP는 양방향 바이트 흐름이므로 한쪽의 FIN은 그 방향으로 더 보낼 데이터가 없다는 의미입니다.
- 선택 조건: 서버는 남은 응답을 보낸 뒤 적절한 방향을 shutdown하고 close할 수 있지만 무한히 기다리지 않습니다.
- 검증 기준: 요청 전송 뒤 half-close, 응답 중 단절, FIN 재전송·RST·부분 메시지를 시험합니다.

## 감점 포인트

- 상대의 FIN이 양방향 송수신과 업무 요청의 즉시 종료를 뜻한다고 한다.
