# 비밀번호를 복호화 가능한 암호로 저장하지 않고 비밀번호 전용 해시로 검증해야 하는 이유와 운영상 선택 기준은 무엇인가요?

## 구두 답변

로그인에서는 입력한 비밀번호가 맞는지 확인하면 되지, 저장한 값을 원래 비밀번호로 되돌릴 필요는 없습니다. 그래서 보통 복호화 가능한 암호화 대신 **비밀번호 후보를 검증하는 데 의도적으로 비용이 들도록 만든 해시·키 유도 함수**를 사용합니다.

여기서 “SHA-256도 해시인데 왜 쓰면 안 되나요?”라는 질문이 생길 수 있습니다. **SHA-256 자체가 깨졌다는 뜻이 아니라, 비밀번호 저장에 한 번만 적용하면 너무 빠르다는 뜻**입니다. 비밀번호 DB를 얻은 공격자는 해시를 수학적으로 역산할 필요 없이 사람들이 자주 쓰는 비밀번호를 대입해 결과가 같은지 비교할 수 있습니다.

다음은 실제 구현 코드가 아니라 방식을 비교하기 위한 표입니다.

| 방식 | 비밀번호 저장에서의 의미 |
|---|---|
| `SHA-256(password)` | 계산이 빨라 많은 후보를 빠르게 시험할 수 있음 |
| `SHA-256(salt + password)` | 사용자별 salt로 사전 계산의 재사용은 줄이지만, 개별 후보 계산은 여전히 빠름 |
| `PBKDF2-HMAC-SHA-256` | SHA-256을 내부 구성 요소로 사용하되, 반복 횟수로 후보 하나를 검증하는 계산 비용을 높임 |
| `Argon2id`·`scrypt` | 계산 시간뿐 아니라 메모리 사용 비용도 파라미터로 조정할 수 있음 |
| `bcrypt` | work factor로 계산 반복량을 조정함. Argon2id처럼 별도의 메모리 크기 파라미터를 조정하는 방식은 아님 |

따라서 어떤 시스템이 “SHA-256을 쓴다”고 하면 **단순 해시인지 PBKDF2-HMAC-SHA-256인지 먼저 확인**하겠습니다. 비밀번호 전용 구현에는 사용자별 무작위 salt와 알고리즘·비용 파라미터를 함께 저장합니다. salt는 같은 비밀번호의 결과가 같아지는 것을 막고 사전 계산의 재사용을 어렵게 하지만, 숨겨야 하는 비밀키는 아닙니다. DB가 유출된 뒤의 대입 속도를 충분히 늦추려면 비용 설정도 필요합니다.

새 시스템에서는 환경에서 지원하는 Argon2id를 우선 검토하겠습니다. FIPS 같은 제약이 있다면 요구에 맞게 검증된 모듈과 구성의 PBKDF2-HMAC-SHA-256을 검토할 수 있습니다. 알고리즘 이름만 골랐다고 FIPS 요구가 충족되는 것은 아닙니다. 기존 bcrypt도 사용했다는 이유만으로 잘못된 것은 아니며, work factor와 라이브러리의 입력 길이 처리 등을 확인해야 합니다.

비용을 무조건 높이지는 않겠습니다. 실제 장비에서 로그인 지연과 동시 인증 부하를 재고, 메모리 예산과 요청 제한을 함께 정하겠습니다. 온라인 요청 제한은 서비스 남용을 줄이고, 비밀번호 해시 비용은 DB 유출 후 오프라인 대입을 어렵게 하는 서로 다른 방어입니다.

기존 단순 SHA-256 저장을 옮긴다면 **이전 방식으로 로그인을 검증한 뒤, 성공한 요청의 비밀번호를 새 방식으로 다시 해시**할 수 있습니다. 장기 미접속 계정에는 재설정 같은 별도 전환 정책이 필요합니다. 비밀번호 원문은 이 과정의 로그나 오류에도 남기지 않겠습니다.

## 득점 포인트

- **빠른 일반 해시와 비밀번호 전용 처리를 구분한다.** SHA-256의 역산이 아니라 후보 대입 속도가 문제이며, PBKDF2-HMAC-SHA-256은 단순 SHA-256과 다르다고 설명한다.
- **salt와 알고리즘별 비용의 역할을 나눈다.** salt의 고유성과 Argon2id·scrypt의 메모리 비용, bcrypt·PBKDF2의 계산 비용을 혼동하지 않는다.
- **운영 조건과 전환을 구체화한다.** 인증 부하에서 비용을 측정하고, 저장된 이전 알고리즘을 식별해 로그인 성공 시 재해시하는 절차를 설명한다.

## 감점 포인트

- **“SHA-256은 취약하므로 어떤 방식으로도 비밀번호에 사용하면 안 된다”고 말한다.** 단순 SHA-256 저장과 PBKDF2-HMAC-SHA-256을 혼동한 설명이다.
- **“salt만 붙이면 빠른 대입을 막는다”고 말한다.** salt를 아는 공격자는 특정 계정의 후보를 계속 시험할 수 있어 충분한 검증 비용이 필요하다.
- **“bcrypt의 cost를 올리면 Argon2id처럼 메모리 크기도 조절된다”고 말한다.** bcrypt의 work factor는 주로 계산 반복량을 조절한다.
- **비용을 무조건 최대로 설정하거나 원문 비밀번호를 로그에 남긴다.** 정상 인증의 자원 고갈과 비밀 노출을 방지해야 한다.
