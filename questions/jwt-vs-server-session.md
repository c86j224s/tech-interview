# JWT와 서버 세션은 어떤 기준으로 선택하나요?

## 구두 답변

JWT는 검증에 필요한 정보를 토큰에 담아 여러 서비스가 서명으로 확인할 수 있고, 서버 세션은 식별자로 서버의 현재 상태를 조회하는 방식입니다. 저는 무상태라는 표현보다 권한과 세션을 얼마나 빨리 회수해야 하는지, 검증 서비스를 어디까지 의존할 수 있는지로 선택하겠습니다.

짧은 수명의 접근 토큰을 여러 서비스가 검증해야 한다면 JWT가 조회 부담을 줄일 수 있습니다. 다만 발급 뒤 권한이 바뀌어도 만료 전까지 기존 내용이 남습니다. 즉시 로그아웃이나 강제 차단이 중요하다면 세션 상태나 토큰 버전을 다시 확인해야 하며, 그러면 완전한 무상태의 이점은 줄어듭니다. 서버 세션은 회수가 명확한 대신 저장소 조회와 장애 영향을 관리해야 합니다.

JWT를 고르더라도 서명만 보지 않고 허용 알고리즘·발급자·대상·만료를 검증하겠습니다. 토큰에 민감한 원문을 넣지 않고, 재발급 수단의 수명과 회수도 따로 설계해야 합니다. 세션을 고르면 저장소 장애 시 어떤 기능을 거절할지와 캐시된 상태의 최신성을 정하겠습니다. 두 방식 모두 탈취된 자격을 그대로 사용하면 문제가 생길 수 있어 전송·보관 보호는 필요합니다. 검증은 정상 로그인뿐 아니라 회수 직후, 키 교체, 저장소 장애에서 약속한 동작이 나오는지 확인하겠습니다.

## 득점 포인트

- **회수와 의존성으로 선택한다.** 토큰 형식보다 운영 계약을 본다.
- **JWT의 검증 범위를 설명한다.** 서명 외 대상·발급자·시간을 확인한다.
- **수명 전체를 설계한다.** 발급·재발급·회수·장애를 다룬다.

## 감점 포인트

- **JWT는 저장소가 절대 필요 없다고 말한다.** 회수·재발급 상태가 필요할 수 있다.
- **JWT 내용은 암호화돼 숨겨진다고 말한다.** 일반 서명 토큰은 읽을 수 있다.
- **세션이면 탈취에 안전하다고 말한다.** 보유 자격 보호가 필요하다.

## 더 파고들 거리

- 짧은 접근 토큰과 긴 갱신 토큰을 나누면 어떤 위험이 이동할까요?
- 서명키를 교체하면서 기존 토큰을 얼마 동안 허용할까요?
- 세션 상태 캐시가 즉시 회수 보장을 약하게 만드는 이유는 무엇인가요?
