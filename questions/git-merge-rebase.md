# 두 브랜치의 변경을 합칠 때 merge와 rebase는 이력을 어떻게 다르게 만들며, 공유 브랜치에서는 무엇을 조심해야 하나요?

## 구두 답변

merge는 두 브랜치의 기존 커밋을 보존하고 필요하면 두 부모를 가진 merge 커밋을 추가해 분기를 합칩니다. rebase는 한 브랜치의 커밋을 다른 기준점 위에 새 커밋으로 다시 만들어 직선에 가까운 이력을 만듭니다. 내용상 같은 변경을 합칠 수 있어도 커밋 ID와 조상 관계가 달라지므로, 둘은 단순히 보기 좋은 이력과 나쁜 이력의 차이가 아닙니다.

개인 작업 브랜치가 `main`에서 오래 갈라졌다면 rebase로 최신 기준 위에 다시 올린 뒤 테스트하고 fast-forward로 합치는 방식을 선택할 수 있습니다. 충돌을 커밋 단위로 해결하며 각 커밋의 의미를 정리하기 쉽다는 장점이 있지만, rebase 중에는 같은 변경을 새로 재생성하므로 결과를 반드시 검토해야 합니다. 이미 여러 사람이 기준으로 가져간 브랜치의 커밋을 rebase하고 강제 push하면 그들의 조상 관계가 사라져 pull과 복구가 어려워집니다.

공유 브랜치나 공개 이력은 merge 또는 별도의 통합 커밋으로 보존하고, 개인 브랜치처럼 아직 다른 사람이 기준으로 삼지 않은 이력만 rebase하겠습니다. 강제 push가 필요하다면 일반 `--force`보다 원격의 새 변경을 덮어쓰지 않는 `--force-with-lease`를 사용하더라도 정책과 리뷰를 먼저 확인해야 합니다. 어떤 방식을 쓰든 충돌 해결 뒤 테스트와 diff를 확인하고, 이력 재작성 여부와 원격 보호 규칙을 팀에 맞춰 명시하는 것이 핵심입니다.

## 득점 포인트

- merge의 기존 이력 보존과 rebase의 커밋 재작성·새 ID 생성을 구분한다.
- 개인 브랜치와 공유 이력의 위험을 나누어 선택 기준을 제시한다.
- 충돌 해결 후 diff·테스트·강제 push 보호까지 실제 작업 순서로 설명한다.

## 감점 포인트

- rebase는 파일 내용을 절대 바꾸지 않는다고 단정한다. 충돌 해결 과정에서 내용이 달라질 수 있다.
- merge는 항상 지저분하고 rebase는 항상 옳다고 말한다. 추적 가능성과 공유 이력 안정성도 기준이다.
- force-with-lease면 어떤 강제 push도 안전하다고 한다. 원격 정책과 다른 사람의 작업을 먼저 확인해야 한다.

## 더 파고들 거리

- rebase로 커밋 ID와 부모가 바뀌는 과정과 reflog를 이용한 복구는 어떻게 연결되나요?
- merge conflict를 해결한 뒤 원래 변경과 상대 변경이 모두 보존됐는지 어떤 diff로 검증할까요?
- 공유 브랜치에서 선형 이력을 강제하고 싶을 때 squash merge와 보호 규칙은 어떤 비용을 만드나요?
