01

구두 답변

정의를 외우기보다, 원리와 조건을 연결해 설명해 보세요.

그대로 재시도해도 안전한지는 요청의 성격에 따라 다릅니다. 타임아웃은 호출자가 정해진 시간 안에 결과를 받지 못했다는 뜻이지, 서버가 작업을 수행하지 않았다는 뜻은 아닙니다. 서버가 요청을 받기 전일 수도 있고, 처리 중일 수도 있고, 처리를 끝냈지만 응답만 전달되지 않았을 수도 있습니다.

예를 들어 잔액을 차감하는 요청이 서버에서 완료된 뒤 응답이 유실됐다면, 같은 요청을 새 작업처럼 재시도할 때 잔액이 두 번 줄어들 수 있습니다. 이런 상황을 다루기 위해 멱등성이 필요합니다. 같은 논리적 요청을 여러 번 실행해도 의도한 상태 변화가 한 번 실행했을 때와 같도록 만드는 성질입니다. 응답 내용이 매번 완전히 같아야 한다는 뜻은 아닙니다.

중복 실행이 위험한 API에는 멱등성 키를 사용할 수 있습니다. 클라이언트가 한 작업에 대해 키를 만들고 재시도에도 같은 키를 보냅니다. 서버는 그 키를 이미 처리했는지 확인하고, 완료했다면 기존 결과를 반환하거나 처리 상태를 알려 줍니다. 같은 키가 서로 다른 요청 내용에 재사용되면 오류로 처리해야 하고, 사용자나 작업 종류별로 키의 범위도 명확히 해야 합니다.

중요한 것은 키를 조회하고 작업을 실행하는 과정의 경쟁 상태입니다. 두 요청이 동시에 키가 없다고 판단하면 둘 다 실행할 수 있습니다. 그래서 고유 제약과 트랜잭션 같은 수단으로 키 등록과 실제 상태 변경을 함께 보호해야 합니다. 외부 서비스 호출까지 포함되면 로컬 트랜잭션만으로 묶을 수 없으므로, 외부 시스템의 중복 방지 기능이나 별도의 복구 절차가 필요합니다.

재시도 자체도 횟수와 전체 시간 예산을 제한하고, 지수 백오프와 무작위 지연으로 요청이 한꺼번에 몰리지 않게 해야 합니다. 따라서 재시도 가능 여부를 정할 때는 오류 종류뿐 아니라 중복 처리의 영향, 처리 상태 확인 방법, 멱등성 기록의 보관 기간까지 함께 확인하겠습니다.

02

득점 포인트

이해가 드러나는 지점을 확인해 보세요.

  • 타임아웃과 실행 실패를 구분한다. 호출자가 결과를 모르는 상황일 수 있다고 설명한다.
  • 멱등성을 상태 변화 기준으로 정의한다. 반복 호출 횟수와 무관하게 같은 논리적 작업의 효과가 중복되지 않도록 한다고 설명한다.
  • 동시에 도착한 중복 요청을 고려한다. 키의 단순 사전 조회가 아니라 원자적인 등록과 상태 변경 보호가 필요함을 짚는다.
  • 재시도의 운영 비용을 고려한다. 횟수, 전체 시간 예산, 백오프, 무작위 지연을 통해 부하 증폭을 제한한다.
03

감점 포인트

놓치기 쉬운 조건과 오해를 짚어 보세요.

  • “타임아웃이면 서버도 작업을 취소했다”고 말한다. 호출자의 대기 종료가 서버 작업 중단을 자동으로 의미하지는 않는다.
  • “재시도할 때마다 새로운 멱등성 키를 만들면 된다”고 말한다. 같은 논리적 작업의 재시도에는 같은 키를 사용해야 중복을 인식할 수 있다.
  • “키가 있는지 조회했으니 중복 실행은 없다”고 말한다. 조회와 등록 사이에 다른 요청이 끼어들 수 있다.
  • “POST는 항상 재시도 불가능하고 PUT은 항상 안전하다”고 단정한다. HTTP의 의도된 의미와 실제 구현이 일치하는지, 부수 효과와 API 계약은 무엇인지 확인해야 한다.
04

더 파고들 거리

하나 더 질문하며 이해의 범위를 넓혀 보세요.

  • 같은 멱등성 키의 첫 요청이 아직 처리 중이라면 두 번째 요청에는 어떤 응답을 주는 것이 좋을까요?
  • 멱등성 기록을 삭제한 뒤 아주 늦은 재시도가 도착하면 어떤 문제가 생길까요?
  • 여러 서비스가 각자 재시도하면 전체 호출 횟수가 어떻게 늘어나며, 재시도 책임은 어디에 두어야 할까요?
  • 작업이 외부 결제나 메시지 발행까지 포함할 때 중복 실행 방지와 장애 복구를 어떻게 연결할까요?

득점·감점 포인트는 학습용 자기 점검 기준이며, 특정 회사의 실제 채점표가 아닙니다.
