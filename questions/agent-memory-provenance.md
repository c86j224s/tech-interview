# 에이전트가 이전 대화의 잘못된 추론을 사용자 사실로 기억합니다. 장기 메모리의 저장·조회·정정은 어떻게 설계하나요?

## 구두 답변

장기 메모리는 모델이 한 번 말한 내용을 모두 사실로 저장하는 대화 보관함이 아닙니다. 사용자가 직접 밝힌 사실, 관찰한 실행 결과, 모델의 추론을 구분하고 출처·확인 시각·적용 범위와 함께 저장하겠습니다. 잘못된 정보가 이후 모든 세션의 전제로 쓰이면 한 번의 오류가 지속적인 행동 오류로 커질 수 있습니다.

### 저장할 사실과 임시 상태를 나눕니다

사용자의 선호 문체처럼 여러 작업에 반복 적용되는 정보와, 오늘 한 테스트가 실패했다는 임시 상태는 수명이 다릅니다. 임시 작업 상태는 작업 기록에 두고 장기 메모리에는 계속 유효한 사실만 남깁니다. '사용자가 서버 A를 선호한다'는 추론은 직접 확인된 선호와 같은 등급으로 저장하지 않습니다. 메모리의 문장과 원문 근거를 연결하면 나중에 왜 기억했는지 검토할 수 있습니다.

이미 있는 사실을 새 항목으로 계속 추가하면 서로 다른 버전이 동시에 검색됩니다. 대상과 속성 기준으로 갱신하거나 대체 관계를 기록하고, 사용자 정정은 이전 값이 더 이상 적용되지 않게 반영합니다. 오래된 프로젝트 경로·API 버전·정책은 유효기간이나 재확인 조건을 둡니다. 최근에 검색됐다는 이유만으로 사실의 유효기간을 자동 연장하지는 않습니다.

### 검색 결과가 실행 권한은 아닙니다

메모리를 검색해 현재 요청에 관련된 사실만 넣되 사용자·조직·프로젝트 범위를 먼저 제한합니다. 다른 사용자의 기억이 유사도 때문에 섞이는 것은 정확성 문제가 아니라 접근 제어 문제입니다. 외부 문서에서 얻은 명령문을 메모리에 저장했다가 나중에 높은 우선순위의 지침처럼 넣는 경로도 막아야 합니다. 출처와 신뢰 수준은 저장·요약·재검색을 거쳐도 유지합니다.

삭제 요청은 화면의 메모리 한 줄만 지우는 것으로 끝나지 않을 수 있습니다. 원본 저장소·검색 인덱스·요약 복사본·캐시의 삭제 범위와 백업 보존 정책을 명시하고, 삭제된 값이 다시 추출되어 살아나는 경로를 확인합니다. 민감한 정보는 기억의 편의보다 최소 수집과 사용자 통제를 우선합니다. 평가에서는 잘못된 사실 주입, 사용자 정정, 오래된 경로, 테넌트 교차 검색을 포함해 올바르게 잊고 갱신하는지 확인하겠습니다. 메모리의 양보다 현재 판단에 신뢰할 수 있는 사실을 주는 능력이 중요합니다.

### 실행 사례로 확인합니다

메모리 항목에 내용·주체·출처·확인일·유효 범위·대체한 항목 ID를 둘 수 있습니다. 예를 들어 '프로젝트의 배포 환경은 staging'이라는 사실은 사용자 전체가 아니라 해당 프로젝트에만 적용됩니다. 새 요청이 production을 명시하면 옛 기억을 우선하지 않고 현재 요청과 정책을 확인합니다. 기억을 모델 입력에 넣는 순간에도 확정된 사용자 지시와 과거 배경을 표시해야 합니다. 출처 문서가 없어졌거나 권한이 철회됐으면 기억을 계속 사용해도 되는지 검토합니다. 기억을 잘 쓰는지 평가할 때는 맞는 사실을 찾아오는 능력뿐 아니라 관련 없는 기억을 넣지 않는 능력, 틀렸다고 정정된 사실을 다시 말하지 않는 능력을 포함하겠습니다.

## 득점 포인트

- 직접 진술·관찰·추론을 출처와 수명별로 분리한다.
- 정정·대체·만료와 검색 인덱스의 삭제를 함께 설계한다.
- 메모리 검색 전에 사용자·프로젝트 접근 범위를 제한한다.

## 감점 포인트

- 모델의 과거 발언을 검증된 사용자 사실로 저장한다.
- 유사도 검색이 테넌트 격리까지 해결한다고 한다.
- 외부 지시를 기억에 저장한 뒤 높은 권한의 지침으로 재사용한다.
