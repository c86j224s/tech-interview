# 요청 하나에서 여러 하위 API를 호출하는데 하나가 실패하거나 사용자가 연결을 끊었습니다. 꼭 필요한 결과와 선택 결과를 나누고 남은 작업의 수명을 어떻게 관리하나요?

## 구두 답변

정책은 먼저 응답 계약으로부터 정합니다. 모든 하위 결과가 있어야 유효한 요청인지, 일부 결과가 없어도 기본 응답을 만들 수 있는지에 따라 한 실패 뒤 나머지를 취소할지 끝까지 기다릴지가 달라집니다. 첫 오류를 반환하는 것 자체는 자식 작업이 끝났다는 뜻이 아니므로, 연결·버퍼·늦은 쓰기가 남지 않게 자식의 취소와 종료를 부모 범위에서 관리해야 합니다.

필수 프로필·권한·재고 조회 중 하나가 실패하면 부모가 deadline을 전파하고 다른 자식에 취소를 알린 뒤, 자식들이 실제로 종료됐는지 기다리고 대표 오류를 반환하겠습니다. 취소 신호를 무시하는 하위 라이브러리라면 호출을 제한 시간 안에 격리하되, 백그라운드에서 계속 실행되는 작업의 소유자와 결과 폐기 규칙을 별도로 관리해야 합니다. 구조화된 동시성은 생성한 작업의 수명이 부모 작업의 범위 밖으로 새지 않게 하는 원칙입니다.

추천 목록처럼 없어도 기본 응답이 유효하면 deadline 안에 도착한 결과만 사용하고 누락을 명시할 수 있습니다. 이때 전체 API는 성공이어도 선택 하위 호출 실패율을 별도 지표로 기록해야 품질 저하를 숨기지 않습니다. 팬아웃 수에는 부모별 동시성 제한과 서비스 전체 예산을 함께 둬 하위 장애가 연결 폭주로 번지지 않게 합니다.

테스트는 첫 오류, 동시 오류, 부모 취소, 응답 직후 완료, 취소 무시 작업을 주입합니다. 반환 후에도 자식이 남아 있지 않은지와 선택 실패가 관측되는지를 확인하겠습니다.

## 득점 포인트

- 결과 계약으로 전부 취소·부분 성공 정책을 정한다.
- 부모 취소 전파와 자식 종료 확인을 작업 수명과 연결한다.
- 선택 작업 실패와 팬아웃 자원 한도를 별도 관측한다.

## 감점 포인트

- 첫 오류를 반환하면 자식 정리도 끝났다고 말한다.
- 모든 작업을 항상 끝까지 기다리는 것이 안전하다고 말한다.
- 선택 작업 실패를 완전히 숨긴다.

## 더 파고들 거리

- 여러 오류 중 대표 오류와 나머지 진단을 어떻게 구성하나요?
- 취소 불가능한 작업의 완료 추적 책임은 어디에 두나요?
- 팬아웃 제한을 부모별·서비스 전체 중 어떻게 조합하나요?
