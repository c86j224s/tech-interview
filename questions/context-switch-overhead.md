# 컨텍스트 스위치가 많으면 반드시 성능 문제가 있는 건가요?

## 구두 답변

횟수만으로 문제라고 보기는 어렵습니다. I/O를 기다리며 실행 기회를 넘기는 서버는 정상적으로도 컨텍스트 스위치가 많을 수 있습니다. 중요한 것은 전환이 유용한 작업을 이어 주는지, 아니면 깨웠다가 다시 재우는 비용만 늘리는지입니다. 같은 요청량에서 CPU 시간과 응답 지연이 함께 나빠졌는지 보겠습니다.

예를 들어 짧은 작업 하나를 처리할 때마다 여러 스레드 사이로 넘기면, 실제 계산보다 큐 등록과 깨우기 비용이 더 커질 수 있습니다. 스레드 덤프와 스케줄링 추적을 보고 같은 락 앞에서 잠들고 깨어나는 흐름이 반복되는지 확인하겠습니다. 실행 가능한 스레드가 CPU 수보다 지나치게 많다면 타임슬라이스 경쟁과 캐시 지역성 손실도 의심할 수 있습니다.

원인이 작은 작업의 과도한 전달이라면 작업을 조금씩 묶어 처리하거나 불필요한 실행기 전환을 줄이겠습니다. 락 경합이라면 스레드 수보다 잠금 범위와 공유 상태를 먼저 바꾸겠습니다. 다만 배치를 키우면 먼저 도착한 작업이 모일 때까지 기다릴 수 있으므로 처리량만 보지 않고 p99도 확인해야 합니다. 정상적인 I/O 대기까지 없애려고 바쁜 대기로 바꾸는 것은 CPU와 전력만 소모할 수 있어, 전환을 줄이는 것 자체를 목표로 삼지는 않겠습니다.

## 득점 포인트

- **횟수와 비용을 구분한다.** 동일 부하에서 유용한 일과 전환 비용을 비교한다.
- **전환 이유를 찾는다.** I/O 대기·락 경합·과도한 실행 흐름을 구분한다.
- **개선과 지연의 교환을 설명한다.** 배치와 실행기 전환 감소가 꼬리 지연에 주는 영향을 확인한다.

## 감점 포인트

- **전환 횟수가 높으면 무조건 문제라고 말한다.** 정상 I/O 대기에서도 많을 수 있다.
- **바쁜 대기로 모두 바꾸자고 한다.** CPU 비용과 다른 작업의 실행 기회를 무시한다.
- **작업자를 계속 늘리면 된다고 말한다.** 경합과 스케줄링 비용이 커질 수 있다.
