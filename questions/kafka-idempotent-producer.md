# Kafka 멱등 프로듀서를 켜면 생산 재시도·소비 재처리·같은 업무의 두 번 생성이 각각 어떻게 달라지나요?

## 구두 답변

Kafka의 멱등 프로듀서는 한 프로듀서 세션이 재시도하는 동일한 생산 요청을 producer ID와 파티션별 sequence로 식별해 브로커 로그에 중복 append되는 일을 줄입니다. 예를 들어 브로커가 레코드를 저장했지만 응답이 네트워크에서 유실되면 프로듀서는 재전송할 수 있고, 브로커는 이미 받은 sequence를 중복으로 기록하지 않도록 처리합니다. 이것은 Kafka 로그에 대한 생산 경계의 기능입니다.

소비자가 외부 DB를 갱신한 뒤 ACK나 offset 커밋 전에 죽으면 같은 레코드를 다시 읽을 수 있습니다. 멱등 프로듀서는 이 소비 재처리를 막지 않으며, 클라이언트가 같은 주문 API를 두 번 호출해 서로 다른 producer sequence를 만든 경우도 같은 업무로 자동 판별하지 않습니다. 따라서 업무 ID에 고유 제약을 두거나 외부 시스템이 제공하는 멱등 키를 사용해야 합니다.

`enable.idempotence`, `acks`, 동시에 보내는 요청 수, 재시도와 `transactional.id`(트랜잭션 프로듀서를 식별하는 이름)의 지원 조건은 Kafka와 클라이언트 버전에 따라 확인하고 의도를 명시하겠습니다. 이 설정을 맞추지 않으면 재시도 중 순서나 트랜잭션 소유권이 기대와 달라질 수 있습니다. 생산 응답 유실과 소비자 재시작을 따로 재현해 Kafka 로그의 중복, 외부 DB(업무 데이터를 저장하는 데이터베이스)의 효과, 중복 이벤트를 각각 세겠습니다. “한 번 처리”라고 말할 때는 브로커 기록인지, Kafka 내부 처리인지, 최종 업무 효과인지 범위를 반드시 붙이겠습니다.

## 득점 포인트

- producer retry dedup과 consumer retry를 서로 다른 실패 구간으로 설명한다.
- producer sequence와 업무 고유 ID의 수명을 구분한다.
- exactly-once 표현의 경계를 검증 가능한 관찰 항목으로 바꾼다.

## 감점 포인트

- 멱등 프로듀서가 외부 DB 변경을 한 번으로 만든다고 말한다.
- payload가 같은 새 메시지도 자동으로 제거된다고 말한다.
- 클라이언트 버전과 함께 쓰는 설정의 조건을 확인하지 않는다.

- 브로커 sequence와 업무 멱등 키의 보관 기간은 왜 달라질 수 있나요?
