# Kubernetes Secret의 base64 값을 Git에 넣어 배포하려 합니다. 이 값은 비밀로 보호되며 어떻게 안전하게 전달·교체해야 하나요?

## 구두 답변

Kubernetes Secret의 기본 표현이 base64라는 것은 암호화됐다는 뜻이 아닙니다. 원문과 비슷하게 다뤄야 하고 Git 이력에 들어가면 나중에 지워도 이전 커밋에 남을 수 있습니다. GitOps의 변경 추적과 비밀값 보관은 분리하는 것이 좋습니다.

base64는 바이트를 텍스트로 표현하는 인코딩이지 키가 있어야 풀 수 있는 암호화가 아닙니다. 예를 들어 `aGVsbG8=`는 누구나 `hello`로 되돌릴 수 있는 설명용 값입니다. 실제 비밀번호를 같은 방식으로 Git에 넣으면 저장소를 읽는 사람이 원문을 얻을 수 있습니다.

저는 외부 비밀 저장소에서 참조해 전달하거나 암호화된 선언을 안전한 키 관리와 함께 사용하는 방식을 검토하겠습니다. 복호화 키를 같은 저장소에 두면 분리의 의미가 약해집니다. Argo CD나 외부 secret controller가 어떤 권한으로 어느 namespace에 값을 만들 수 있는지도 제한해야 합니다.

값을 바꿨다고 모든 애플리케이션이 즉시 새 비밀을 읽는 것은 아닙니다. 환경 변수 주입과 파일 마운트, 앱의 재로딩 동작이 다릅니다. 저는 새 값 전달과 실제 사용 전환을 구분해 검증하고 오래된 자격을 폐기하겠습니다. 로그와 diff에서도 비밀 원문이 노출되지 않게 합니다. 이미 커밋된 비밀은 파일 삭제보다 우선 회수·교체해야 합니다.

## 득점 포인트

- 인코딩과 암호화를 구분한다.
- 저장소·키·권한의 경계를 정한다.
- 전달과 앱 적용 시점을 확인한다.

## 감점 포인트

- base64면 안전하다고 말한다.
- 비밀과 복호화 키를 같은 접근 범위에 둔다.
- Git에서 지우면 유출이 해결됐다고 말한다.
