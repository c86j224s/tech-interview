# DB가 커밋 성공을 응답한 직후 서버 전원이 꺼졌습니다. 데이터 페이지가 아직 디스크에 쓰이지 않았어도 복구할 수 있는 이유와 필요한 설정은 무엇인가요?

## 구두 답변

커밋 성공은 보통 모든 데이터 페이지가 최종 위치에 기록됐다는 뜻은 아닙니다. 먼저 변경을 재현할 로그를 안전하게 기록하고 나중에 데이터 페이지를 반영하는 방식이 흔합니다. 쓰기 전 로그, 즉 WAL은 장애 뒤 미반영 변경을 복구할 근거를 남기는 역할입니다.

예를 들어 커밋된 변경의 데이터 페이지는 메모리에만 있어도 필요한 로그가 내구성 있게 남았다면 재시작 시 복구할 수 있습니다. 반대로 로그를 메모리나 운영체제 버퍼에만 두고 응답하는 설정이라면 전원 장애에서 최근 커밋을 잃을 수 있습니다. 저는 DB 이름만으로 보장을 가정하지 않고 동기화 설정과 저장 장치가 실제로 어떤 완료를 보장하는지 확인하겠습니다.

성능을 위해 동기화를 늦추거나 여러 커밋을 묶을 수 있지만, 허용할 유실과 지연을 서비스의 요구에 맞춰야 합니다. 계정 잔액 같은 데이터는 빠른 응답보다 약속한 내구성이 우선일 수 있습니다. 복제본이 있다고 원본 로그 유실이 자동 해결되는 것도 아닙니다. 복제가 어디까지 확인된 뒤 응답하는지 별개입니다. 테스트에서는 정상 종료가 아닌 프로세스 중단과 저장 장애를 재현하고, 응답한 커밋이 복구 후 존재하는지 확인하겠습니다.

## 득점 포인트

- **로그와 데이터 페이지를 구분한다.** 커밋 응답의 근거를 설명한다.
- **설정과 저장 계층을 확인한다.** 버퍼 기록과 내구 기록을 구분한다.
- **서비스가 허용할 데이터 유실 범위를 정한다.** 성능 변경의 대가를 명시한다.

## 감점 포인트

- **커밋이면 모든 페이지가 최종 기록됐다고 말한다.** 로그 기반 복구가 가능하다.
- **복제만 있으면 내구성이 무조건 보장된다고 말한다.** 확인 시점과 복제 방식이 다르다.
- **정상 종료 테스트로 장애 복구를 검증한다.** 실제 실패 구간을 재현해야 한다.

- 커밋 응답 유실 뒤 클라이언트는 결과를 어떻게 확인해야 할까요?
