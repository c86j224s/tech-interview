01

구두 답변

정의를 외우기보다, 원리와 조건을 연결해 설명해 보세요.

보통 모든 데이터 페이지가 최종 위치에 기록됐다는 뜻은 아닙니다. 먼저 변경을 재현할 로그를 안전하게 기록하고 나중에 데이터 페이지를 반영하는 방식이 흔합니다. 쓰기 전 로그, 즉 WAL은 장애 뒤 미반영 변경을 복구할 근거를 남기는 역할입니다.

예를 들어 커밋된 변경의 데이터 페이지는 메모리에만 있어도 필요한 로그가 내구성 있게 남았다면 재시작 시 복구할 수 있습니다. 반대로 로그를 메모리나 운영체제 버퍼에만 두고 응답하는 설정이라면 전원 장애에서 최근 커밋을 잃을 수 있습니다. 저는 DB 이름만으로 보장을 가정하지 않고 동기화 설정과 저장 장치가 실제로 어떤 완료를 보장하는지 확인하겠습니다.

성능을 위해 동기화를 늦추거나 여러 커밋을 묶을 수 있지만, 허용할 유실과 지연을 업무와 맞춰야 합니다. 계정 잔액 같은 데이터는 빠른 응답보다 약속한 내구성이 우선일 수 있습니다. 복제본이 있다고 원본 로그 유실이 자동 해결되는 것도 아닙니다. 복제가 어디까지 확인된 뒤 응답하는지 별개입니다. 테스트에서는 정상 종료가 아닌 프로세스 중단과 저장 장애를 재현하고, 응답한 커밋이 복구 후 존재하는지 확인하겠습니다.

02

득점 포인트

이해가 드러나는 지점을 확인해 보세요.

  • 로그와 데이터 페이지를 구분한다. 커밋 응답의 근거를 설명한다.
  • 설정과 저장 계층을 확인한다. 버퍼 기록과 내구 기록을 구분한다.
  • 업무상 유실 허용을 정한다. 성능 변경의 대가를 명시한다.
03

감점 포인트

놓치기 쉬운 조건과 오해를 짚어 보세요.

  • 커밋이면 모든 페이지가 최종 기록됐다고 말한다. 로그 기반 복구가 가능하다.
  • 복제만 있으면 내구성이 무조건 보장된다고 말한다. 확인 시점과 복제 방식이 다르다.
  • 정상 종료 테스트로 장애 복구를 검증한다. 실제 실패 구간을 재현해야 한다.
04

더 파고들 거리

하나 더 질문하며 이해의 범위를 넓혀 보세요.

  • group commit은 내구성을 유지하면서 어떤 비용을 줄이나요?
  • 체크포인트가 잦거나 드물 때 복구 시간과 쓰기 비용은 어떻게 달라지나요?
  • 커밋 응답 유실 뒤 클라이언트는 결과를 어떻게 확인해야 할까요?

득점·감점 포인트는 학습용 자기 점검 기준이며, 특정 회사의 실제 채점표가 아닙니다.
