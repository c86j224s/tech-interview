# Kubernetes HPA의 목표 replica 수는 늘었는데 응답 지연이 그대로입니다. 새 Pod의 준비 상태와 실제 병목을 어떻게 확인하나요?

## 구두 답변

확장 신호가 실제 병목을 잘 나타내는지부터 보겠습니다. CPU 기반 HPA는 CPU와 처리 용량이 관련된 워크로드에 도움이 되지만 DB 대기나 단일 핫키가 병목이면 Pod만 늘려도 개선되지 않을 수 있습니다. 목표 replica 수가 늘었다는 것과 실제 준비된 용량이 늘어난 것도 다릅니다.

HPA는 메트릭을 보고 실행 복제본의 목표 수를 조절하는 컨트롤러입니다. Pod는 애플리케이션 컨테이너가 실행되는 단위이며 목표에 맞춰 생성돼도 실행할 노드를 기다리거나 초기화 중일 수 있습니다. 예를 들어 목표 10개 중 준비된 Pod가 3개뿐이면 실제 요청 처리 용량은 아직 10개가 아닙니다.

새 Pod가 스케줄되지 않거나 이미지 다운로드·예열이 오래 걸리면 확장 반응이 늦습니다. 저는 desired·current·ready replica와 pending 이유를 나눠 확인하겠습니다. CPU utilization이 request 대비 비율이라면 request 값 변경이 확장 판단을 바꿀 수 있습니다. 여러 지표를 사용하면 그 선택 규칙과 지표 누락 때 동작도 확인해야 합니다.

부하가 잠깐 출렁일 때 scale down이 너무 빠르면 준비 비용을 반복합니다. 안정화 구간과 최소 용량을 두되 비용과 응답 목표를 비교하겠습니다. 테스트는 부하 증가 속도와 새 Pod 준비 시간을 함께 재현합니다. HPA는 무한 용량이 아니라 측정·계산·스케줄·준비를 거치는 제어 루프이므로 그 지연 동안 보호할 대기열 상한도 필요합니다.

## 득점 포인트

- 지표와 실제 병목을 연결한다.
- 목표·실행·준비된 용량을 나눈다.
- 제어 지연과 안정화 정책을 고려한다.

## 감점 포인트

- CPU가 낮으니 더 확장할 필요가 없다고 단정한다.
- desired replica가 늘면 즉시 용량이 생긴다고 말한다.
- scale down을 가장 빠르게만 설정한다.

## 더 파고들 거리

- 외부 지표가 실패하면 HPA는 어떻게 동작하는지 어디서 확인할까요?
- 예열 중 Pod의 CPU가 확장 신호를 왜곡하면 어떻게 할까요?
- HPA와 수동 replica 변경이 충돌하면 어떤 결과가 생길까요?
