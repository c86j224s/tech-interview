# 행 몇 개를 수정하는데 다른 요청까지 크게 막히면 무엇을 의심하나요?

## 구두 답변

실제로 잡는 잠금 범위가 수정한 행 수보다 넓은지 확인하겠습니다. 조건에 맞는 행은 적어도 찾기 위해 많은 행을 읽거나, 여러 잠금이 더 큰 단위로 승격되면 다른 요청이 영향을 받을 수 있습니다. SQL Server의 락 에스컬레이션처럼 구현에 따라 잠금 단위가 바뀌는 경우도 있습니다.

예를 들어 상태가 오래된 작업 일부를 갱신하는 쿼리가 적절한 인덱스 없이 넓게 스캔한다고 하겠습니다. 먼저 블로킹 체인에서 누가 기다리고 누가 잠금을 보유하는지 찾고, 실제 실행 계획과 잠금 리소스를 보겠습니다. 수정 건수가 작다는 애플리케이션 로그만으로 범위가 좁다고 판단하지 않겠습니다. 트랜잭션 안에서 외부 호출을 기다리고 있다면 쿼리 자체가 짧아도 잠금 보유 시간은 길어질 수 있습니다.

원인이 탐색 범위라면 인덱스와 조건을 개선하고, 대량 작업이라면 작은 배치로 나눠 잠금 시간을 줄이겠습니다. 단, 배치 사이에 다른 변경이 들어와도 전체 규칙이 유지되는지 확인해야 합니다. 잠금 힌트로 무조건 행 잠금을 강제하거나 격리를 낮추는 것은 첫 선택으로 삼지 않겠습니다. 대기 시간과 처리량을 측정하면서 메모리 비용과 데이터 정확성까지 유지되는 개선인지 검증하겠습니다.

## 득점 포인트

- **수정량과 잠금 범위를 구분한다.** 넓은 탐색과 승격 가능성을 확인한다.
- **블로킹 소유자를 추적한다.** 실행 계획과 트랜잭션 시간을 함께 본다.
- **배치 분할의 정확성을 확인한다.** 대기 감소와 중간 상태를 비교한다.

## 감점 포인트

- **몇 행만 바꾸니 잠금도 작다고 말한다.** 탐색과 승격 범위가 다를 수 있다.
- **잠금 힌트로 항상 해결된다고 말한다.** 비용과 보장 조건을 봐야 한다.
- **격리를 낮춰 막힘만 없앤다.** 잘못된 읽기나 불변식 위반이 생길 수 있다.
