# Kafka consumer lag가 큰 파티션이 보일 때 소비자 수를 늘리기 전에 어떤 원인을 어떻게 구분하나요?

## 구두 답변

Consumer lag는 소비자 위치와 파티션의 최신 위치 사이에 남은 레코드 수를 보여 주는 단서이지 원인이나 메시지 처리 완료를 직접 뜻하지는 않습니다. 같은 1,000개 lag라도 레코드 크기, 처리 비용, 재시도 횟수와 입력률이 다르면 회복 시간이 달라집니다. 따라서 파티션별 lag, 가장 오래된 레코드의 나이, 입력률, 완료 처리율, 오류·재시도율을 함께 보겠습니다.

한 파티션만 밀리면 핫키, 비싼 레코드, 독성 메시지 또는 순서 제약을 의심합니다. 모든 파티션이 밀리면서 DB 연결 풀이나 저장소가 포화라면, 소비자를 늘려 하위 데이터베이스의 대기열과 오류를 더 키울 수 있습니다. 반대로 파티션이 충분하고 소비자 CPU·I/O가 포화이며 하위 시스템에 여유가 있다면 소비자 증가가 도움이 됩니다. 읽기는 빨라도 처리 완료 뒤 offset 커밋이 늦는 구조라면 표시 lag가 크게 남을 수 있으므로, lag와 실제 처리 상태를 구분해야 합니다.

확장은 입력률보다 처리율이 높아져야 lag가 줄어드는 조건부 해법입니다. 목표는 lag 0 하나가 아니라 허용된 메시지 나이와 회복 시간입니다. 입력 증가와 하위 지연을 분리해 실험하고, DLQ(처리하지 못해 별도 보관하는 대기열)로 넘긴 이벤트를 성공 처리와 별도 지표로 남기며, scale-out 뒤 재할당 중복과 비용까지 확인하겠습니다. DLQ 이동을 정상 메시지 처리 완료로 세면 lag가 줄어도 실패가 숨겨집니다.

## 득점 포인트

- lag 개수·메시지 나이·처리율을 함께 해석한다.
- 파티션 편중과 하위 시스템 포화를 구분하는 순서를 준다.
- 확장 성공 기준을 회복 시간과 메시지 처리 완료로 구체화한다.

## 감점 포인트

- lag가 크면 항상 소비자를 늘린다.
- lag 0이면 모든 외부 효과가 확정됐다고 말한다.
- 입력률보다 처리율이 낮아도 scale-out이 계속 해결한다고 말한다.
