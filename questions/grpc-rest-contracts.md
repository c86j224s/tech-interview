# 여러 언어의 내부 서비스가 REST API로 통신합니다. gRPC로 바꾸면 계약 관리와 실행 비용에서 무엇이 달라지나요?

## 구두 답변

gRPC는 스키마 기반 코드 생성과 스트리밍, 데드라인 같은 기능을 일관되게 쓰기 좋습니다. 하지만 프로토콜을 바꾸는 것만으로 느린 DB나 과도한 호출 구조가 해결되지는 않습니다. 저는 실제 병목과 팀이 원하는 계약 관리 방식을 먼저 확인하겠습니다.

gRPC는 서비스 메서드와 메시지 형태를 스키마에 정의하고 클라이언트·서버 코드를 생성하는 RPC 프레임워크입니다. REST API의 JSON을 각 팀이 수동으로 해석하는 대신 같은 정의를 공유하는 이점이 있습니다. 그러나 생성 코드가 같아도 상태 값의 의미나 재시도 가능한 오류는 팀 간 계약으로 정해야 합니다.

여러 언어의 내부 서비스가 같은 메시지와 오류 계약을 사용한다면 스키마에서 클라이언트를 생성하는 것이 실수를 줄일 수 있습니다. 다만 필드 추가·삭제와 enum 처리 규칙을 지켜야 하고, 생성 코드 버전이 서비스들의 배포를 강하게 묶지 않게 해야 합니다. REST는 브라우저·운영 도구·외부 소비자와의 접근성이 좋을 수 있어 모든 경계를 같은 방식으로 통일할 필요는 없습니다.

저는 대표 요청의 직렬화 비용과 메시지 크기, 연결 재사용 상태를 비교하고, 데드라인과 취소가 실제 하위 처리까지 전파되는지 확인하겠습니다. 오류 코드가 업무 실패와 일시 장애를 구분하는지도 중요합니다. 로드밸런서가 스트림과 연결을 어떻게 분산하는지, 운영자가 요청을 추적하기 쉬운지도 함께 봐야 합니다. 선택 기준은 최신 기술이라는 인상보다 계약 일관성·성능 이득·관측과 배포 비용의 합입니다.

## 득점 포인트

- **요구와 병목을 먼저 본다.** 프로토콜 교체의 범위를 제한한다.
- **스키마의 운영 비용을 설명한다.** 혼합 버전과 생성 코드 의존성을 다룬다.
- **실제 호출 계약을 검증한다.** 오류·취소·연결·추적을 확인한다.

## 감점 포인트

- **gRPC면 언제나 빠르다고 말한다.** 실제 병목과 페이로드에 달려 있다.
- **스키마가 있으면 호환성 문제가 없다고 말한다.** 변경 규칙이 필요하다.
- **내부 통신이니 오류 계약이 중요하지 않다고 말한다.** 재시도와 복구가 의존한다.

## 더 파고들 거리

- 클라이언트 스트리밍에서 백프레셔는 업무 큐까지 어떻게 이어져야 할까요?
- HTTP/2 연결 재사용이 인스턴스별 부하 편중을 만드는 경우는 무엇인가요?
- 업무 오류를 전송 오류로 표현하면 어떤 재시도 문제가 생길까요?
