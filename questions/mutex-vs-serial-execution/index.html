뮤텍스로 보호하는 것과 작업을 큐에 넣어 순서대로 실행하는 것은 어떤 차이가 있나요?

01

구두 답변

정의를 외우기보다, 원리와 조건을 연결해 설명해 보세요.

둘 다 동시 접근을 제어할 수 있지만, 상태를 다루는 방식이 다릅니다. 뮤텍스는 여러 스레드가 공유 상태를 번갈아 잠그고 사용하게 합니다. 직렬 실행 큐는 그 상태를 변경하는 작업을 한곳으로 보내 하나씩 실행하게 합니다. 저는 짧은 공유 연산을 보호하려는지, 업무의 처리 순서와 소유권을 정하려는지부터 구분하겠습니다.

예를 들어 계정 잔액을 메모리에서 읽고 바로 변경하는 짧은 작업이라면 뮤텍스가 단순합니다. 같은 뮤텍스로 모든 접근을 보호하면 동시에 변경하지 못하게 할 뿐 아니라, 앞선 쓰기를 다음 스레드가 볼 수 있도록 메모리 가시성도 보장합니다. 반면 계정별로 여러 요청을 정해진 순서에 따라 처리해야 한다면, 계정 키별 큐로 보내는 구조가 이해하기 쉬울 수 있습니다. 일반적인 뮤텍스는 먼저 온 요청이 먼저 락을 얻는다는 보장은 없기 때문입니다.

다만 큐에 넣는 것만으로 업무 전체가 원자적이 되지는 않습니다. 첫 작업이 잔액을 읽고 비동기 DB 요청을 보낸 뒤 반환했다고 하겠습니다. 그사이에 다음 작업이 잔액을 바꾸면, 첫 작업의 완료 콜백은 이미 달라진 상태를 보게 됩니다. 시작과 콜백을 각각 직렬로 실행해도 둘 사이에 다른 작업이 끼어들 수 있는 것입니다.

요청 순서를 끝까지 지켜야 한다면 첫 업무가 완료될 때까지 같은 계정의 다음 업무를 보류하겠습니다. 대신 느린 DB 요청 하나가 뒤의 요청을 모두 막는 비용을 받아들여야 합니다. 그 지연이 허용되지 않는다면 업무를 중간 상태로 나누고 완료 시 버전이 바뀌었는지 확인하는 방법이 있지만, 취소와 실패 처리가 더 복잡해집니다. 저는 먼저 단순한 쪽으로 정확성을 확보하고, 계정별 큐 대기 시간이 실제 문제가 될 때 구조를 확장하겠습니다.

따라서 락과 큐 중 무엇이 빠르다고 정하기보다 어디까지 한 작업으로 보호해야 하는지를 먼저 정하겠습니다. 락 보유 시간과 큐 대기 시간을 재서 병목을 찾고, 서로 독립적인 계정만 병렬화하겠습니다. 두 계정을 함께 바꾸는 업무는 계정별 큐만으로 보호되지 않으므로 별도 조정이 필요합니다.

02

득점 포인트

이해가 드러나는 지점을 확인해 보세요.

  • 작업 성격에 따라 방식을 고른다. 짧은 공유 연산과 계정별 업무 순서 관리에 각각 적합한 이유를 설명한다.
  • 상호 배제와 가시성을 함께 이해한다. 모든 접근이 같은 동기화 규칙을 따라야 한다는 전제를 짚는다.
  • 비동기 경계에서 생기는 인터리빙을 설명한다. 콜백을 직렬화해도 업무 전체가 원자적이지 않은 사례를 든다.
  • 선택의 비용과 변경 시점을 말한다. 완료까지 보류하는 단순한 설계와 재진입 가능한 설계의 복잡성을 비교한다.
03

감점 포인트

놓치기 쉬운 조건과 오해를 짚어 보세요.

  • “큐에서 하나씩 실행하니 모든 업무가 원자적이다”라고 말한다. 비동기 중단 사이에 다른 작업이 들어갈 수 있다.
  • “뮤텍스는 요청 도착 순서도 보장한다”고 말한다. 일반적인 뮤텍스의 상호 배제와 FIFO 순서는 다르다.
  • “큐는 락이 없어서 항상 빠르다”고 말한다. 큐 내부 동기화와 스케줄링 비용, 작업 본문의 대기는 남을 수 있다.
  • “키별 직렬화면 두 키의 동시 변경도 안전하다”고 말한다. 여러 키에 걸친 불변식은 별도의 원자성 경계가 필요하다.
04

더 파고들 거리

하나 더 질문하며 이해의 범위를 넓혀 보세요.

  • 두 계정 사이의 이체를 처리할 때 잠금 순서, 상위 조정자, 버전 검사 중 무엇을 선택할까요?
  • 직렬 실행기가 매번 다른 OS 스레드에서 작업을 실행해도 메모리 가시성을 보장하려면 무엇이 필요할까요?
  • 느린 작업을 여러 단계로 나눌 때 재진입과 취소에 안전한 상태 머신은 어떻게 만들까요?
  • FIFO 큐의 등록 순서와 외부에서 정의한 업무 순서가 다를 때 순서 번호는 어디에서 부여해야 할까요?

득점·감점 포인트는 학습용 자기 점검 기준이며, 특정 회사의 실제 채점표가 아닙니다.
