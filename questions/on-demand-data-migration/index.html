사용자가 접속할 때 데이터를 옮기는 온디맨드 마이그레이션은 어떻게 안전하게 만드나요?

01

구두 답변

정의를 외우기보다, 원리와 조건을 연결해 설명해 보세요.

접속 시 옮기면 실제 사용하는 데이터부터 전환할 수 있지만, 로그인 같은 사용자 경로에 복사 비용과 실패가 들어옵니다. 저는 미이관·진행 중·완료·복구 필요 상태를 구분하고, 여러 접속이 같은 데이터를 동시에 옮기지 않게 하겠습니다.

첫 요청이 복사를 시작한 뒤 멈추고 두 번째 요청이 들어올 수 있습니다. 단순한 완료 플래그만으로는 복사가 일부 진행됐는지 알기 어렵습니다. 작업 ID와 원본 버전, 반영 단계를 저장하고 단계별 재시도를 멱등적으로 만들겠습니다. 완료는 데이터 복사뿐 아니라 필요한 연관 데이터와 권한, 라우팅까지 검증된 뒤 표시해야 합니다. 진행 중인 요청이 기다릴 수 있는 시간을 넘으면 명시적인 재시도 상태를 돌려주는 편이 무한 대기보다 낫습니다.

복사 중 원본에 새 쓰기가 허용되는지도 정해야 합니다. 짧게 쓰기를 보류할 수 있으면 전환을 단순화할 수 있고, 허용해야 한다면 변경 추적과 소유권 전환이 필요합니다. 오래 접속하지 않는 사용자는 영원히 남을 수 있어 잔여 데이터 일괄 이관이나 보관 정책도 있어야 합니다. 검증은 첫 접속 지연, 동시 접속, 단계별 중단과 오래된 워커의 재개를 포함하겠습니다. 빠르게 옮기는 것보다 완료 상태를 믿을 수 있고 실패 후 다시 진행할 수 있는 것이 핵심입니다.

02

득점 포인트

이해가 드러나는 지점을 확인해 보세요.

  • 진행 상태를 내구화한다. 완료 플래그만으로 처리하지 않는다.
  • 사용자 지연과 복구를 함께 설계한다. 대기 상한과 재시도 계약을 둔다.
  • 원본 변경과 잔여 데이터를 다룬다. 소유권과 종료 계획을 정한다.
03

감점 포인트

놓치기 쉬운 조건과 오해를 짚어 보세요.

  • 복사가 끝나면 즉시 완료라고 말한다. 관련 데이터와 라우팅 확인이 필요하다.
  • 접속마다 처음부터 다시 복사한다. 중복 효과와 부하가 생긴다.
  • 미접속 사용자는 무시한다. 레거시 종료와 보관 요구가 남는다.
04

더 파고들 거리

하나 더 질문하며 이해의 범위를 넓혀 보세요.

  • 마이그레이션 진행 중 자격 변경 요청이 들어오면 어디에서 처리할까요?
  • 작업 lease가 만료된 뒤 이전 워커의 완료를 어떻게 거절할까요?
  • 복사 결과 검증에 건수·해시·업무 불변식은 어떻게 함께 쓰일까요?

득점·감점 포인트는 학습용 자기 점검 기준이며, 특정 회사의 실제 채점표가 아닙니다.
