01

구두 답변

정의를 외우기보다, 원리와 조건을 연결해 설명해 보세요.

온디맨드 마이그레이션은 실제로 접속한 사용자의 데이터부터 전환해 전체 일괄 작업을 줄일 수 있지만, 로그인·첫 요청 경로에 복사 지연과 실패를 넣습니다. 상태를 not_started → copying → verifying → complete와 needs_repair처럼 내구성 있게 저장하고, lease를 가진 한 작업자만 진행하게 하겠습니다. 완료 플래그 하나로는 부분 복사와 오래된 워커를 구분할 수 없습니다.

작업 ID, 원본 버전, 단계별 checkpoint와 대상 upsert 키를 저장해 재시도를 멱등적으로 만듭니다. 관련 데이터·권한·라우팅·건수/해시·업무 불변식 검증까지 통과한 뒤 complete로 바꿉니다. 복사 중 원본 쓰기를 잠시 보류할 수 있으면 cutover가 단순해지고, 쓰기를 허용하면 변경 추적·dual write·소유권 전환과 충돌 처리가 필요합니다. 오래 기다리는 사용자 요청에는 무한 대기 대신 진행 중·재시도 가능한 응답을 줍니다.

동시 접속, 단계 중단, lease(작업을 일정 시간만 소유하는 임대권) 만료 뒤 늦은 완료, 자격 변경, 미접속 사용자를 각각 시험합니다. lease가 만료된 옛 워커의 완료를 그대로 받으면 새 워커의 복사 결과를 덮을 수 있으므로 세대 번호를 함께 검사합니다. 완료 후 읽기 경로가 새 저장소를 일관되게 가리키고, 실패 시 원본으로 안전하게 되돌리거나 repair queue로 보낼 수 있어야 합니다. 온디맨드만으로 레거시를 영원히 남기지 않도록 미접속 사용자 일괄 이관·보관·삭제 종료 계획도 둡니다.

02

득점 포인트

이해가 드러나는 지점을 확인해 보세요.

  • 완료 플래그를 상태 머신·lease·checkpoint로 확장한다.
  • 원본 쓰기 허용 여부에 따른 cutover 복잡성을 설명한다.
  • 검증·repair·미접속 사용자 종료 계획을 포함한다.
03

감점 포인트

놓치기 쉬운 조건과 오해를 짚어 보세요.

  • 복사가 끝나는 즉시 관련 데이터·권한·라우팅 검증 없이 완료 처리한다.
  • 접속마다 처음부터 복사해 중복 부하를 만든다.
  • 미접속 사용자를 영원히 레거시에 남겨도 된다고 말한다.
04

더 파고들 거리

하나 더 질문하며 이해의 범위를 넓혀 보세요.

  • lease 만료 뒤 이전 워커가 보낸 완료를 어떤 generation/version 검사로 거절할까요?
  • 마이그레이션 중 자격 변경 요청은 원본·대상 중 어느 권위 경로에서 처리할까요?
  • 건수·해시·업무 불변식을 대용량 복사 검증에 어떤 순서로 결합할까요?

득점·감점 포인트는 학습용 자기 점검 기준이며, 특정 회사의 실제 채점표가 아닙니다.
