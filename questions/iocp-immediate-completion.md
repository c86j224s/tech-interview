# WSARecv가 즉시 성공해서 버퍼를 정리했는데 IOCP 완료 패킷이 다시 왔습니다. 왜 이중 처리가 생기며 어떤 경로가 정리를 맡아야 하나요?

## 구두 답변

일반적인 IOCP 연계 중첩 I/O에서는 즉시 성공해도 완료 패킷이 큐에 들어올 수 있으므로 반환값에서 성공했다고 바로 정리하면 안 됩니다. 다만 성공 시 완료 통지를 생략하는 모드나 이벤트의 설정 등 예외가 있어, API와 핸들 설정의 계약을 함께 확인해야 합니다.

여기서는 IOCP에 연결된 소켓을 사용하고 성공 완료 통지를 생략하는 설정은 켜지 않았다고 가정합니다. 즉시 성공은 작업이 빨리 끝났다는 뜻이지 완료 큐에 결과가 오지 않는다는 뜻이 아닙니다. 아래는 제출 결과별 책임을 보여 주는 의사 코드입니다.

```text
제출 전에 작업과 버퍼의 수명을 확보
ret = WSARecv(..., ov)
if ret == 0:
    완료 큐 경로가 결과를 처리하도록 둠
else:
    error = WSAGetLastError()
    if error == WSA_IO_PENDING:
        제출은 성공했으므로 완료 큐 경로를 기다림
    else:
        제출 실패 경로에서 작업을 정리
```

완료 워커가 제출 함수 반환 전에 실행될 수도 있습니다. 따라서 제출 뒤에야 참조를 확보하거나, 이미 정리됐을 수 있는 작업의 상태를 덮어쓰는 코드는 피해야 합니다.

저는 제출 결과를 즉시 성공, 정상적인 pending, 제출 실패로 나누겠습니다. Winsock이라면 WSA_IO_PENDING은 요청이 비동기로 진행된다는 뜻이지 작업 실패가 아닙니다. 즉시 성공 경로와 완료 큐 경로에서 모두 같은 버퍼를 반환하면 이중 정리가 생길 수 있습니다. 통지 생략을 사용한다면 어떤 성공은 제출한 스레드가 처리하고 어떤 것은 완료 큐가 처리하는지 명확히 나눠야 합니다.

통지 생략은 완료 큐 비용을 줄일 수 있지만 분기와 검증 부담을 늘립니다. 처음에는 한 완료 경로로 수명 관리를 단순하게 만들고, 측정된 비용이 클 때 최적화하겠습니다. 테스트는 항상 pending이 되는 환경만 쓰지 않고 즉시 성공과 즉시 실패도 강제로 확인합니다. 중요한 것은 성공 반환 자체가 아니라 각 작업의 결과 전달과 정리가 정확히 한 번 이루어지는지입니다.

## 득점 포인트

- **기본 동작과 예외를 구분한다.** 완료 생략 설정을 함께 본다.
- **pending을 실패와 구분한다.** 제출 결과별 처리 책임을 정한다.
- **단일 정리 책임을 유지한다.** 이중 완료와 해제를 검증한다.

## 감점 포인트

- **즉시 성공이면 완료 패킷이 절대 없다고 말한다.** 기본 통지 규칙을 놓친다.
- **pending을 일반 실패로 취급한다.** 유효한 미완료 작업을 정리할 수 있다.
- **최적화 설정을 모든 핸들에 무조건 적용한다.** API 지원과 완료 계약이 다르다.
