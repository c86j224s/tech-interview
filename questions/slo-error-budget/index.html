01

구두 답변

정의를 외우기보다, 원리와 조건을 연결해 설명해 보세요.

SLO는 사용자가 기대하는 서비스 품질을 측정 가능한 기준으로 정한 목표입니다. 서버 프로세스가 살아 있는 비율만이 아니라 유효한 요청이 올바른 결과를 정해진 시간 안에 받는지를 볼 수 있습니다. 먼저 어떤 사용자 흐름을 성공으로 볼지 정의해야 합니다.

로그인 API가 HTTP 200을 반환해도 토큰이 잘못돼 다음 요청을 못 하면 사용자에게는 실패입니다. 반대로 잘못된 비밀번호를 거절한 것은 정상 보안 동작일 수 있습니다. 저는 성공·실패의 분류와 측정 위치를 정하고, 외부 의존성 실패를 누구의 품질 지표에 포함할지도 명확히 하겠습니다. 평균 지연보다 기준 시간 안에 끝난 요청 비율이 적합한 경우도 많습니다.

오류 예산은 목표에서 허용한 실패의 양을 운영 결정에 연결하는 수단입니다. 빠르게 소진되고 있다면 기능 배포를 늦추고 안정화에 집중할 근거가 됩니다. 단순한 처벌 지표로 쓰면 실패를 숨기게 될 수 있어 사용자 영향 중심으로 해석해야 합니다. 경보는 짧은 순간의 잡음보다 여러 시간 구간에서 예산이 얼마나 빨리 소진되는지 보겠습니다. 목표를 높이는 것에는 비용이 있으므로 업무 중요도와 실제 사용자 기대에 맞춰 정하겠습니다.

02

득점 포인트

이해가 드러나는 지점을 확인해 보세요.

  • 사용자 성공을 정의한다. 프로세스 생존·상태 코드만 보지 않는다.
  • 측정 계약을 명확히 한다. 실패 분류와 시간 경계를 정한다.
  • 운영 행동으로 연결한다. 예산 소진을 배포·안정화 결정에 쓴다.
03

감점 포인트

놓치기 쉬운 조건과 오해를 짚어 보세요.

  • 모든 오류 응답을 서비스 실패로 센다. 정상 거절일 수 있다.
  • 무조건 가장 높은 가용성을 목표로 한다. 비용과 요구를 봐야 한다.
  • 월말 수치만 확인한다. 빠른 예산 소진을 놓칠 수 있다.
04

더 파고들 거리

하나 더 질문하며 이해의 범위를 넓혀 보세요.

  • 다중 윈도우 burn-rate 경보는 순간 잡음과 지속 장애를 어떻게 구분할까요?
  • 트래픽이 적은 기능의 SLO는 어떤 측정 한계가 있나요?
  • 종속 서비스의 목표를 조합해 사용자 흐름의 목표를 어떻게 정할까요?

득점·감점 포인트는 학습용 자기 점검 기준이며, 특정 회사의 실제 채점표가 아닙니다.
