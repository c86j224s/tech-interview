# TLS 핸드셰이크가 성공해도 의도한 서버를 신뢰한다고 말하려면 어떤 인증서 검증과 API 인가가 필요한가요?

## 구두 답변

**여기서는 일반적인 HTTPS처럼 인증서 기반 서버 인증을 사용하는 TLS 연결을 전제로 합니다.** TLS는 통신 기밀성과 무결성을 제공하지만, 암호화됐다는 사실만으로 의도한 서버와 연결됐다는 뜻은 아닙니다. TLS 1.3에는 사전 공유키인 PSK로 서버를 인증해 Certificate 메시지를 보내지 않는 방식도 있습니다. 이것은 인증이 없는 것이 아니라 인증서 대신 다른 자격으로 인증하는 경우이므로, 모든 TLS가 매번 인증서를 검증한다고 일반화하지 않겠습니다. 클라이언트는 신뢰할 수 있는 루트까지 인증서 체인이 이어지는지, 접속한 호스트 이름이 SAN 등의 대상 이름과 맞는지, 유효 기간·키 용도·서명 알고리즘을 확인해야 합니다. 이 검사를 끄면 공격자와도 암호화된 연결을 만들 수 있습니다.

인증서 오류가 나면 검증을 끄지 않고 실제 접속 이름, 서버가 보낸 체인, 중간 인증서 누락, 클라이언트 trust store, 시스템 시계를 확인하겠습니다. 사설 CA를 사용한다면 신뢰 루트 배포와 교체 기간을 별도로 설계합니다. 인증서가 서버 신원을 확인해 주더라도 그 서버가 특정 사용자나 API 작업을 수행할 권한이 있다는 뜻은 아니므로, TLS 뒤에서 사용자 인증·서비스 인가를 계속 적용해야 합니다.

교체는 만료 전에 새 인증서를 모든 진입 경로에 배포하고, 새로운 인증서 기반 핸드셰이크에서 일부 인스턴스나 로드밸런서가 여전히 옛 인증서를 제공하는지 확인합니다. 기존 연결이나 TLS 1.3의 PSK 기반 세션 재개는 새 인증서를 다시 제시하지 않을 수 있으므로 별도로 확인해야 합니다. 특히 키 유출 대응이라면 인증서 교체만으로 기존 연결과 재개 자격까지 즉시 회수됐다고 판단하지 않고, 연결·세션 티켓의 만료 및 무효화 정책을 적용하겠습니다. mTLS를 쓴다면 클라이언트 인증서가 서비스 신원을 증명하는 것과 최종 사용자의 위임 권한을 구분해야 합니다. 고정(pin)은 특정 키만 허용해 일부 공격을 줄일 수 있지만 정상 교체와 복구를 어렵게 만들 수 있습니다.

테스트는 정상 체인, 이름 불일치, 만료, 중간 CA 누락, 신뢰 루트 교체, 잘못된 용도를 넣어 올바른 연결만 통과하는지 확인합니다.

## 득점 포인트

- 암호화와 서버 신원 인증을 구분한다.
- 체인·호스트 이름·기간·용도 검증과 오류 진단을 설명한다.
- TLS 인증과 API 권한, 교체 운영을 분리한다.
- 인증서 기반 인증이라는 전제를 명시하고, PSK 인증·기존 연결·세션 재개를 새 인증서 검증과 구분한다.

## 감점 포인트

- TLS가 연결되면 누구와 연결됐든 안전하다고 말한다.
- 인증서 오류를 검증 비활성화로 해결한다.
- 인증서 검증이 API 업무 권한까지 보장한다고 말한다.
- 모든 TLS가 Certificate 메시지를 교환한다고 말하거나, 인증서 교체만으로 기존 연결과 세션 재개가 모두 무효화됐다고 단정한다.
