# TLS로 연결됐으면 상대 서버를 신뢰해도 되나요?

## 구두 답변

암호화된 연결이라는 사실만으로 의도한 서버인지 확인된 것은 아닙니다. 인증서 체인이 신뢰하는 발급자로 이어지는지, 연결하려는 호스트 이름과 맞는지, 유효 기간과 용도가 맞는지 검증해야 합니다. 그 검사를 끄면 중간의 다른 상대와도 암호화해서 통신할 수 있습니다.

운영 중 인증서 오류가 생겼다고 검증을 비활성화하는 방식은 피하겠습니다. 먼저 실제 연결 이름과 인증서의 대상 이름을 비교하고, 중간 인증서가 누락됐는지와 클라이언트의 신뢰 저장소·시계를 확인하겠습니다. 서버가 보낸 인증서를 받아들인다는 것과 업무상 권한을 허용하는 것도 별개이므로, TLS 뒤의 API 인가는 그대로 필요합니다.

인증서 교체는 만료 전에 자동화하고 새 인증서가 모든 진입 경로에서 제공되는지 확인하겠습니다. 일부 서버만 교체되면 요청마다 성공과 실패가 섞일 수 있습니다. 사설 인증 기관을 쓴다면 신뢰 루트 교체 시 구·신 루트가 겹치는 기간도 설계해야 합니다. 테스트에서는 정상 인증서뿐 아니라 이름 불일치·만료·잘못된 체인을 넣어 거절되는지 확인하겠습니다. 연결이 된다는 것보다 잘못된 상대를 제대로 거절하는지가 보안 검증의 핵심입니다.

## 득점 포인트

- **암호화와 상대 인증을 구분한다.** 체인·이름·기간 검증을 설명한다.
- **오류 원인을 진단한다.** 검증 해제 대신 신뢰·이름·배포 상태를 본다.
- **교체와 거절 테스트를 포함한다.** 부분 배포와 만료를 점검한다.

## 감점 포인트

- **TLS면 누구와 연결됐든 안전하다고 말한다.** 올바른 상대 확인이 필요하다.
- **인증서 오류를 우회해 해결한다.** 상대 인증을 잃을 수 있다.
- **인증서가 API 권한도 보장한다고 말한다.** 업무 인가는 별도다.
