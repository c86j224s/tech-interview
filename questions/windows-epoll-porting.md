# Windows IOCP 서버를 Linux epoll로 이식할 때 완료 통지와 준비 통지의 차이를 연결 상태 머신에 어떻게 반영하나요?

## 구두 답변

IOCP는 제출한 비동기 I/O 작업이 완료됐다는 결과와 바이트 수를 받는 완료 중심 모델입니다. epoll은 소켓에서 지금 읽기·쓰기를 시도할 수 있다는 준비 상태를 알려 주므로, 이벤트를 받은 뒤 애플리케이션이 논블로킹 `read`·`write`를 직접 수행해야 합니다. 따라서 API 이름을 바꾸는 것만으로는 버퍼 소유권과 재시도 시점이 보존되지 않습니다.

IOCP에서는 수신 버퍼를 커널 작업에 제출하고 완료된 범위를 처리한 뒤 다음 작업을 제출할 수 있습니다. epoll의 edge-triggered 모드에서는 이벤트를 받은 동안 `EAGAIN`이 나올 때까지 읽어야 하며, 처리 예산 때문에 중간에 멈췄다면 다시 읽도록 상태를 유지해야 합니다. 쓰기도 부분 전송 뒤 남은 바이트와 writable 감시 등록을 관리합니다. 취소는 IOCP의 이미 제출된 작업 완료와 epoll 감시 제거가 같은 의미가 아니므로, 이미 실행 중인 콜백과 연결 수명을 별도로 정리합니다.

상위 계층에는 `bytes received`, `send progress`, `peer closed`, `protocol error` 같은 의미 있는 이벤트를 제공하고, 하위 어댑터가 준비·완료 모델 차이를 숨기되 버퍼 소유와 재진입·취소 계약은 명시하겠습니다. 공통 인터페이스가 특정 OS API의 세부 형태를 그대로 닮으면 이식성이 아니라 한쪽 모델에 맞춘 래퍼가 됩니다.

두 구현에서 부분 읽기·부분 쓰기·EOF·`EAGAIN`·연결 종료·재진입·취소 경합을 같은 계약 테스트로 실행하겠습니다. 성능 이전에 이벤트 의미와 객체 수명을 동일하게 보장하는지가 핵심입니다.

## 득점 포인트

- 완료 통지와 준비 통지의 실제 I/O 위치를 구분한다.
- 부분 처리·재스케줄링·취소와 버퍼 수명을 재설계한다.
- OS별 구현을 공통 의미 계약으로 검증한다.

## 감점 포인트

- API 호출 이름만 일대일로 치환한다.
- 감시를 제거하면 이미 실행 중인 콜백도 절대 없다고 가정한다.
- 공통 추상화에서 부분 처리·소유권 계약을 숨긴다.
