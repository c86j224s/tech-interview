# TCP 흐름 제어와 혼잡 제어가 각각 수신자와 네트워크 경로를 보호하는 방식은 무엇이며 어떤 지표로 구분하나요?

## 구두 답변

흐름 제어는 수신 호스트가 애플리케이션과 버퍼로 감당할 수 있는 양보다 많이 보내지 않도록 하는 기능입니다. 수신 버퍼가 차고 애플리케이션이 데이터를 늦게 읽으면 수신 윈도우가 줄어 송신자가 더 보내지 못합니다. 혼잡 제어는 네트워크 경로의 공유 큐와 링크가 감당할 수 있는 전송률을 추정해, 손실·RTT 증가 같은 신호에 따라 혼잡 윈도우를 조절합니다.

수신 애플리케이션이 느린 경우 송신 서버 스레드를 늘려도 수신 윈도우가 늘지 않습니다. 수신 버퍼 점유, 애플리케이션 소비 지연, 송신 측 큐를 확인해 소비 경로를 개선하거나 상위 생산을 제한해야 합니다. 반대로 패킷 손실과 RTT 증가가 함께 나타나면 경로 혼잡, 링크 대역폭, 중간 큐를 살펴야 하며 수신 애플리케이션만 최적화해서는 해결되지 않습니다.

실제 전송량은 수신 윈도우와 혼잡 윈도우, 애플리케이션의 송신 가능 데이터 중 더 제한적인 조건에 영향을 받습니다. 소켓 버퍼를 무작정 키우면 짧은 버스트는 흡수하지만 긴 큐와 bufferbloat로 지연이 커질 수 있습니다. 따라서 수신 윈도우·혼잡 윈도우·재전송·RTT·애플리케이션 큐를 같은 시간축에서 측정하겠습니다.

테스트는 수신자를 의도적으로 느리게 하는 경우와 네트워크 손실·지연을 주는 경우를 분리합니다. 원인에 따라 소비자 처리, 애플리케이션 백프레셔, 전송률, 경로 설정을 다르게 조정해야 합니다.

## 득점 포인트

- 수신자 용량과 네트워크 경로 용량을 구분한다.
- 윈도우·RTT·재전송·애플리케이션 큐를 원인에 연결한다.
- 버퍼 증설의 처리량 이점과 큐 지연 비용을 설명한다.

## 감점 포인트

- 흐름 제어가 네트워크 혼잡까지 모두 해결한다고 말한다.
- 소켓 버퍼를 키우면 항상 빨라진다고 말한다.
- 모든 손실을 서버 애플리케이션 처리 부족으로 본다.

## 더 파고들 거리

- TCP 흐름 제어 외에 애플리케이션 백프레셔가 필요한 이유는 무엇인가요?
