# 직렬화 격리를 켠 뒤 일부 트랜잭션이 실패합니다. 쿼리 하나만 다시 실행하면 되나요?

## 구두 답변

직렬화 실패는 실행 이력 전체를 그대로 확정할 수 없다는 신호일 수 있어 보통 트랜잭션 전체를 새로 시작해야 합니다. 마지막 UPDATE만 반복하면 이미 읽은 낡은 값과 분기를 재사용합니다.

### 동작 원리와 전제

잔량을 읽고 가격·한도를 계산한 뒤 쓰는 거래에서 충돌이 나면 새 트랜잭션으로 최신 상태를 읽고 계산을 다시 합니다. 오류 코드로 직렬화 실패·데드락·고유 위반·연결 단절을 구분합니다. 연결 단절은 커밋 여부가 불확실할 수 있어 단순 재시도와 다릅니다.

### 선택과 실패 처리

재시도 횟수와 전체 deadline을 제한하고 지터를 둡니다. 트랜잭션 안에서 이미 호출한 외부 결제는 DB 롤백에 포함되지 않으므로 멱등 키나 outbox로 분리합니다. 반복해서 충돌하면 격리를 낮추기 전에 핫키와 읽기·쓰기 범위를 줄일지 봅니다.

### 구체적인 사례와 검증

처음에는 재고 1을 읽어 판매 가능하다고 판단했지만 다른 거래가 먼저 성공했다면 재시도 시 재고는 0일 수 있습니다. 이전 계산 결과를 그대로 저장하는 재시도는 새로운 상태에 맞지 않습니다. 재시도 함수는 transaction 생성부터 읽기·계산·쓰기·커밋까지 감싸고, 시도 밖에 유지할 논리 요청 ID와 시도 안에서 새로 읽을 값을 구분합니다. 한도를 넘으면 실패 사유와 재시도 가능성을 사용자에게 전달합니다. 시도별 로그에는 같은 요청 ID와 다른 시도 번호를 남겨 운영자가 한 사용자의 요청을 여러 주문으로 오해하지 않게 합니다. 영원히 충돌하는 핫키는 순차 실행이나 예약 모델로 바꿀지 검토합니다.

동시 부하에서 처음 시도와 최종 성공률, 재시도 횟수, 잠금·지연을 측정합니다. 재시도 때문에 유효한 요청이 무기한 굶지 않게 하며, 사용자가 보는 결과는 시도별 성공이 아니라 하나의 논리 거래 결과로 연결합니다.

## 득점 포인트

- 핵심 구분: 직렬화 실패는 실행 이력 전체를 그대로 확정할 수 없다는 신호일 수 있어 보통 트랜잭션 전체를 새로 시작해야 합니다.
- 선택 조건: 재시도 횟수와 전체 deadline을 제한하고 지터를 둡니다.
- 검증 기준: 동시 부하에서 처음 시도와 최종 성공률, 재시도 횟수, 잠금·지연을 측정합니다.
