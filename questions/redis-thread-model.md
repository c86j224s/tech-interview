# Redis가 싱글 스레드라고 할 때 명령 실행과 네트워크·백그라운드 작업의 범위를 어떻게 구분하나요?

## 구두 답변

Redis가 싱글 스레드라는 말은 보통 클라이언트 명령을 주 실행 경로에서 순차적으로 처리한다는 뜻입니다. 네트워크 I/O의 일부, lazy freeing, RDB/AOF 같은 백그라운드 작업까지 모든 일이 단 하나의 스레드에서만 일어난다는 뜻은 아닙니다. 세부 범위는 Redis 버전과 설정에서 달라질 수 있으므로, 병목을 말할 때 실제 주 실행 경로를 확인해야 합니다.

긴 명령, 큰 컬렉션 순회, 큰 키 삭제, 긴 Lua 스크립트는 CPU 평균이 낮아도 주 실행 경로를 오래 차지할 수 있습니다. 그러면 다른 클라이언트의 짧은 `GET`도 같은 큐에서 기다립니다. 연결 수를 늘리는 것은 실행 경로의 한 명령이 차지한 시간을 줄이지 못합니다. 저는 slow log와 latency 이벤트, 명령별 호출 수·실행 시간, 큰 키 크기, 네트워크 대기를 따로 측정하겠습니다.

명령 하나가 중간에 다른 명령에 끼어들지 않는다는 것은 여러 명령으로 구성한 업무 전체가 원자적이라는 뜻이 아닙니다. `GET` 후 애플리케이션 판단 후 `SET` 사이에는 다른 클라이언트가 변경할 수 있습니다. 조건부 명령, `WATCH`+`MULTI/EXEC`, 짧은 Lua를 선택할 수 있지만, 긴 스크립트는 오히려 모든 명령을 지연시킵니다.

따라서 해결은 단순히 스레드를 늘리는 것이 아니라 큰 작업을 분할하고, 자료구조를 재설계하며, 원자성이 필요한 범위를 짧게 유지하는 것입니다. I/O 스레드가 네트워크 처리 비용을 줄여도 명령 실행 비용까지 병렬화한다고 가정하지 않겠습니다.

## 득점 포인트

- 주 명령 경로와 보조 작업의 범위를 구분한다.
- 긴 명령이 전체 클라이언트 지연으로 전파되는 이유를 설명한다.
- 명령 원자성과 여러 명령 업무의 원자성을 나눈다.

## 감점 포인트

- Redis의 모든 작업이 한 스레드에서만 실행된다고 단정한다.
- 클라이언트 수를 늘리면 명령 실행 병목도 자동으로 해결된다고 말한다.
- 여러 명령은 명령별 순차성 때문에 자동 원자적이라고 말한다.

## 더 파고들 거리

- I/O 스레드가 줄이는 네트워크 비용과 줄이지 못하는 명령 비용은 무엇인가요?
- 긴 스크립트를 작은 명령으로 나눌 때 잃는 원자성은 무엇인가요?
- 주 실행 지연과 네트워크 지연을 어떤 측정 시각으로 분리하나요?
