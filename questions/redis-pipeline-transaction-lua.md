# Redis 파이프라이닝, MULTI/EXEC, Lua는 무엇이 다른가요?

## 구두 답변

세 기능은 **왕복을 줄일 것인지, 명령들을 끼어듦 없이 실행할 것인지, 읽은 결과에 따라 서버 안에서 판단할 것인지**가 다릅니다. ‘재고가 남아 있을 때만 하나 차감한다’는 예제로 비교하겠습니다.

### 1. 파이프라이닝: 응답을 매번 기다리지 않고 보냅니다

파이프라이닝은 별도의 Redis 명령이 아니라, 클라이언트가 명령을 연달아 보내고 응답을 모아서 읽는 통신 방식입니다. 아래는 그 흐름을 표현한 것이며, 그대로 실행하는 코드가 아닙니다.

```text
보내기: GET stock
보내기: DECR stock
그다음 두 응답 읽기
```

왕복 대기는 줄지만, **GET의 결과를 확인하기 전에 이미 DECR를 보냈습니다.** 재고가 0이어도 감소시킵니다. 다른 클라이언트가 사이에 명령을 실행하지 못하게 묶는 보장도 없습니다. 따라서 서로 독립적인 조회들을 빠르게 보내는 데는 좋지만, 이것만으로 조건부 차감이 안전해지지는 않습니다.

### 2. MULTI/EXEC: 묶은 명령 사이에 다른 클라이언트가 끼어들지 못합니다

```text
MULTI
GET stock
DECR stock
EXEC
```

`MULTI` 다음 명령들은 실행 대기열에 들어가고 `EXEC`에서 실행됩니다. 이 실행 중에는 다른 클라이언트의 명령이 중간에 끼어들지 않습니다. 하지만 **클라이언트는 EXEC 전에 GET 결과를 받아서 다음 명령을 선택할 수 없습니다.** 위 예제는 여전히 재고가 0이어도 감소시킵니다.

클라이언트에서 값을 보고 판단하려면 `WATCH`를 함께 사용할 수 있습니다.

```text
WATCH stock
GET stock                 ← 여기서 실제 값을 읽고 클라이언트가 판단
값이 0보다 크면:
    MULTI
    DECR stock
    EXEC                  ← 감시한 키가 변경됐다면 실행하지 않음
그렇지 않으면:
    UNWATCH
```

이것도 제어 흐름을 보여 주는 예입니다. 같은 연결에서 수행하며, `EXEC`가 충돌로 중단됐다면 다시 읽고 판단해야 합니다. 다른 요청이 먼저 재고를 줄였는데 예전 판단만 재사용해서는 안 됩니다.

### 3. Lua: Redis 안에서 값을 읽고 판단해 변경합니다

아래 스크립트는 `stock` 키가 **존재하는 작은 비음수 정수 재고**이고, `KEYS[1]`로 전달된다는 예제입니다.

```lua
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock > 0 then
    redis.call('DECR', KEYS[1])
    return 1
end
return 0
```

Redis가 읽기·판단·변경을 하나의 스크립트 안에서 수행하므로 그사이에 다른 클라이언트가 재고를 바꾸지 못합니다. 재고가 없으면 0, 하나 차감했으면 1을 반환합니다. 운영 코드에서는 키 누락이나 잘못된 타입·값도 정의한 정책으로 처리해야 합니다.

| 방식 | 줄이거나 보장하는 것 | 위 예제에서 주의할 점 |
|---|---|---|
| 파이프라이닝 | 명령별 왕복 대기 감소 | 조회 결과를 보기 전에 차감을 보냄 |
| MULTI/EXEC | 묶인 명령 실행 중 다른 명령의 끼어듦 방지 | 결과를 받아 조건 분기하는 기능은 아님 |
| WATCH + MULTI/EXEC | 클라이언트 판단 이후 감시 키의 변경 감지 | 충돌 시 다시 읽고 판단해야 함 |
| Lua | 서버 안에서 읽기·분기·변경 수행 | 긴 스크립트는 다른 요청을 지연시킴 |

저라면 독립적인 다건 요청은 제한된 파이프라인으로 보내고, 이 예제처럼 짧은 조건부 변경은 원자적인 기본 명령으로 표현할 수 있는지 먼저 본 뒤 필요하면 Lua를 쓰겠습니다.

단, **끼어듦이 없다는 것과 오류 시 롤백은 다릅니다.** `EXEC` 실행 중 특정 명령이 실패해도 앞서 성공한 변경이 자동으로 취소되지 않습니다. Lua도 앞선 쓰기 이후 실행 오류가 나면 그 쓰기가 남을 수 있습니다. 필요한 값과 타입을 쓰기 전에 확인하고, 스크립트는 짧게 유지해야 합니다. 성공 응답을 잃고 다시 실행하는 경우의 중복 차감은 별도의 멱등성 문제입니다.

## 득점 포인트

- **같은 재고 사례로 기능의 차이를 설명한다.** 파이프라인과 단순 MULTI/EXEC 모두 그 자체로 ‘재고가 있을 때만 차감’이라는 분기를 만들지 못함을 짚는다.
- **WATCH와 Lua의 판단 위치를 구분한다.** 클라이언트의 재검증·재시도와 서버 내부의 읽기·분기를 비교한다.
- **비간섭 실행과 롤백을 구분한다.** 실행 중 오류에 앞선 쓰기가 남을 수 있고, Lua 실행 시간이 다른 요청에 영향을 준다고 설명한다.

## 감점 포인트

- **“파이프라인으로 묶으면 원자적으로 실행된다”고 말한다.** 통신 비용을 줄이는 것과 다른 클라이언트의 명령을 배제하는 것은 별개다.
- **“MULTI 안에서 GET 결과를 받아 다음 명령을 결정한다”고 말한다.** 명령이 대기열에 들어가므로 클라이언트는 EXEC 전에 해당 결과를 얻지 못한다. WATCH를 사용하는 예에서는 읽기와 판단이 MULTI보다 앞에 있다.
- **“트랜잭션이나 Lua에서 오류가 나면 앞선 변경도 전부 롤백된다”고 말한다.** 실행 중 오류의 처리 계약은 일반적인 관계형 DB 트랜잭션의 롤백과 다르다.
