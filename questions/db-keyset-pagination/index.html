01

구두 답변

정의를 외우기보다, 원리와 조건을 연결해 설명해 보세요.

OFFSET으로 앞의 행을 건너뛰는 방식이라면 뒤 페이지일수록 많은 행을 읽고 버릴 수 있습니다. 저는 실제 읽은 행 수와 정렬 비용을 확인하겠습니다. 반환은 20개여도 수십만 행을 지나야 한다면 페이지 크기보다 접근 방식이 문제입니다.

순서대로 더 보기를 제공하는 화면이라면 마지막으로 읽은 정렬 키 다음부터 찾는 키셋 페이지네이션을 선택하겠습니다. 주문 시각과 주문 ID를 함께 정렬 키로 두면 같은 시각의 주문도 순서를 정할 수 있습니다. 커서에는 마지막 시각과 ID를 담고 그 뒤 구간을 인덱스로 탐색합니다. 시각만 비교하면 같은 시각의 행을 빠뜨릴 수 있어 유일한 보조 키가 필요합니다.

대신 임의의 300번째 페이지로 바로 이동하거나 정확한 전체 페이지 수를 보여 주는 요구는 구현 방식이 달라집니다. 데이터가 중간에 삽입·수정되는 동안 어떤 목록 일관성을 기대하는지도 정해야 합니다. 저는 대량 목록의 연속 탐색은 커서를 쓰고, 작은 관리 목록의 페이지 번호 요구는 비용을 확인해 별도로 허용하겠습니다. 테스트에서는 같은 정렬 값, 새 행 삽입, 정렬 키 변경을 섞어 누락과 중복이 계약 범위 안인지 확인하겠습니다.

02

득점 포인트

이해가 드러나는 지점을 확인해 보세요.

  • 버리는 읽기 비용을 설명한다. OFFSET과 반환 건수를 구분한다.
  • 안정적인 순서를 만든다. 유일한 보조 키를 커서에 포함한다.
  • 제품 요구와 비용을 비교한다. 임의 페이지와 연속 탐색을 구분한다.
03

감점 포인트

놓치기 쉬운 조건과 오해를 짚어 보세요.

  • 인덱스가 있으면 OFFSET 비용은 일정하다고 말한다. 건너뛸 구간을 읽을 수 있다.
  • 시각만 커서로 쓰면 충분하다고 말한다. 같은 시각의 행이 있다.
  • 커서는 모든 동시 변경에서 완벽한 스냅샷이라고 말한다. 변경되는 정렬 키와 삭제를 봐야 한다.
04

더 파고들 거리

하나 더 질문하며 이해의 범위를 넓혀 보세요.

  • 정렬 방향이 섞인 복합 키의 다음 페이지 조건은 어떻게 만들까요?
  • 커서 변조를 막으면서 필터와 정렬 조건을 어떻게 묶을까요?
  • 전체 건수를 매번 세지 않고 사용자에게 목록 규모를 어떻게 제공할까요?

득점·감점 포인트는 학습용 자기 점검 기준이며, 특정 회사의 실제 채점표가 아닙니다.
