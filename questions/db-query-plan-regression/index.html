01

구두 답변

정의를 외우기보다, 원리와 조건을 연결해 설명해 보세요.

그럴 수 있습니다. 데이터 분포와 통계, 캐시된 실행 계획, 잠금과 메모리 상황이 달라지면 같은 SQL도 다른 비용으로 실행됩니다. 저는 코드 변경이 없다는 이유로 DB 밖의 문제라고 넘기지 않겠습니다.

특정 고객의 주문 수가 급격히 많아졌는데 예전에는 적은 행을 가정한 계획이 재사용된다고 하겠습니다. 인덱스로 찾은 뒤 원본 행을 반복 조회하는 계획이 작은 고객에는 빠르지만 큰 고객에는 비쌀 수 있습니다. 실제 계획의 추정 행과 실제 행을 비교하고, 빠른 파라미터와 느린 파라미터를 나눠 재현하겠습니다. 정렬이 메모리에 안 들어 디스크로 넘치는지도 확인해야 합니다.

통계가 오래됐다면 갱신을 검토하지만, 갱신이 항상 모든 쿼리에 좋은 계획을 만든다고 보지는 않겠습니다. 재컴파일이나 계획 고정은 즉시 완화책이 될 수 있어도 컴파일 비용과 다른 파라미터의 손해를 따져야 합니다. 저는 이전 정상 계획과 현재 계획의 차이를 보존하고, 데이터 편중에 맞는 인덱스나 쿼리 분리를 검토하겠습니다. 수정 후에는 대표 파라미터 전체의 논리 읽기와 지연을 비교해 특정 사례만 빠르게 만든 것은 아닌지 확인하겠습니다.

02

득점 포인트

이해가 드러나는 지점을 확인해 보세요.

  • 변경 없는 성능 회귀 원인을 설명한다. 데이터·통계·자원 상태를 본다.
  • 추정과 실제를 비교한다. 파라미터별 계획 차이를 확인한다.
  • 완화와 근본 해결을 구분한다. 계획 고정과 구조 개선의 비용을 비교한다.
03

감점 포인트

놓치기 쉬운 조건과 오해를 짚어 보세요.

  • SQL이 같으면 성능도 같다고 말한다. 분포와 계획이 달라질 수 있다.
  • 통계를 갱신하면 무조건 해결된다고 말한다. 다른 쿼리에 영향이 있을 수 있다.
  • 빠른 파라미터 하나만 재검증한다. 편중된 데이터의 비용이 남는다.
04

더 파고들 거리

하나 더 질문하며 이해의 범위를 넓혀 보세요.

  • 계획 고정을 해제할 기준은 어떤 지표로 정할까요?
  • 메모리 grant 부족과 과다 할당은 각각 어떤 증상을 만들까요?
  • 실행 계획 이력을 수집할 때 운영 부담과 분석 범위를 어떻게 조절할까요?

득점·감점 포인트는 학습용 자기 점검 기준이며, 특정 회사의 실제 채점표가 아닙니다.
