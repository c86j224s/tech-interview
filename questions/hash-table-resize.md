# 해시 테이블의 원소가 늘면 왜 재해시가 필요하며 요청 지연에 어떤 영향을 주나요?

## 구두 답변

버킷에 비해 원소가 많아지면 충돌과 탐색 길이가 늘기 때문에 저장 공간을 확장할 수 있습니다. 버킷 수가 바뀌면 같은 해시값도 들어갈 위치가 달라질 수 있어 기존 원소를 다시 배치해야 합니다. 이것이 재해시입니다.

평소 한 번의 삽입은 짧아도 임계값을 넘는 삽입에서 전체 재배치가 발생하면 지연이 튈 수 있습니다. 새 버킷과 옛 버킷을 동시에 보유하는 동안 메모리 피크도 커질 수 있습니다. 저는 예상 원소 수가 알려져 있으면 미리 용량을 확보하고, 무작위 부하만 아니라 확장 직전과 직후를 측정하겠습니다.

점진적 재해시는 여러 연산에 이동을 나눠 개별 지연을 낮추지만 두 테이블에서 조회하고 동시 변경을 처리하는 복잡성이 생깁니다. 모든 라이브러리가 이 방식을 쓰는 것은 아닙니다. 반복자와 원소 참조의 유효성도 구현 계약을 확인해야 합니다. 목표는 평균 조회 속도뿐 아니라 확장 중 누락·중복이 없고 최대 지연과 메모리가 예산 안에 있는지입니다.

## 득점 포인트

- 버킷 수와 위치 계산의 관계를 설명한다.
- 재배치의 지연·메모리 피크를 구분한다.
- 점진적 방식의 복잡성과 무효화 계약을 확인한다.

## 감점 포인트

- 크기만 늘리면 기존 위치는 항상 그대로라고 말한다.
- 분할 상환 비용이면 개별 지연도 일정하다고 말한다.
- 모든 언어의 iterator가 재해시 후 유효하다고 말한다.

## 더 파고들 거리

- 점진적 이동 중 같은 키가 갱신되면 어느 테이블을 바꿀까요?
- 부하율 상한을 낮추면 어떤 메모리 비용이 생길까요?
- 동시 해시 테이블에서 확장 상태를 독자에게 어떻게 공개할까요?
