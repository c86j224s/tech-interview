01

구두 답변

정의를 외우기보다, 원리와 조건을 연결해 설명해 보세요.

상태 값이 있다는 것과 올바른 전이만 허용한다는 것은 다릅니다. enum으로 대기·진행·완료를 정의해도 여러 요청이 동시에 값을 바꾸면 완료를 다시 진행으로 되돌리거나 같은 효과를 두 번 반영할 수 있습니다. 저는 각 상태에서 어떤 요청이 허용되고 누가 전이를 확정하는지 정하겠습니다.

결제 승인과 취소가 동시에 들어온다면 마지막 저장이 이긴다는 규칙으로 처리하면 안 됩니다. 현재 상태나 버전을 조건으로 갱신하고, 실패한 요청은 최신 상태를 읽어 이미 완료인지 충돌인지 판단해야 합니다. 외부 호출이 필요하면 호출 의도와 결과를 구분해 저장하고, 응답 유실 뒤 같은 작업 ID로 결과를 다시 확인할 수 있게 하겠습니다.

상태가 너무 많으면 구현이 어려워질 수 있지만, 실제로 서로 다른 복구 행동이 필요한 상황을 한 상태로 합치면 더 위험합니다. 예를 들어 미실행과 결과 불확실은 재시도 정책이 다를 수 있습니다. 저는 정상 전이뿐 아니라 금지된 전이를 테스트하고, 오래 멈춘 상태의 나이와 원인을 관찰하겠습니다. 운영자가 수동으로 값을 바꾸는 도구도 같은 전이 규칙과 감사 기록을 따라야 합니다. 상태 머신은 그림보다 실제 저장 조건과 복구 경로에서 완성됩니다.

02

득점 포인트

이해가 드러나는 지점을 확인해 보세요.

  • 값과 전이 규칙을 구분한다. 동시 변경과 금지 전이를 설명한다.
  • 조건부 갱신과 작업 ID를 쓴다. 재시도·불확정 결과를 다룬다.
  • 운영 복구도 같은 규칙에 둔다. 장기 정체와 수동 변경을 추적한다.
03

감점 포인트

놓치기 쉬운 조건과 오해를 짚어 보세요.

  • enum을 만들면 상태가 안전하다고 말한다. 전이 검증이 필요하다.
  • 마지막 쓰기가 이기면 된다고 말한다. 업무 순서와 효과를 깨뜨릴 수 있다.
  • 수동 운영은 예외로 직접 갱신한다. 불변식과 감사가 사라진다.
04

더 파고들 거리

하나 더 질문하며 이해의 범위를 넓혀 보세요.

  • 상태 전이와 이벤트 발행을 같은 원자적 경계로 묶으려면 어떻게 할까요?
  • 종료 상태가 다시 바뀔 수 있는 업무는 어떤 별도 전이를 둘까요?
  • 상태 버전과 작업 재시도 ID는 어떤 역할이 다른가요?

득점·감점 포인트는 학습용 자기 점검 기준이며, 특정 회사의 실제 채점표가 아닙니다.
