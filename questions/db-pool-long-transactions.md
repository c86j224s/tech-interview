# DB 연결 풀이 부족할 때 풀 크기보다 먼저 볼 것은 무엇인가요?

## 구두 답변

연결이 실제 쿼리를 수행하느라 바쁜지, 일을 하지 않은 채 오래 점유되는지 먼저 보겠습니다. 풀 부족은 DB 용량이 작다는 뜻일 수도 있지만, 연결을 반환하지 않거나 트랜잭션 안에서 외부 응답을 기다리는 코드 때문일 수도 있습니다.

예를 들어 연결을 얻고 데이터를 읽은 뒤 외부 API를 호출하고 마지막에 커밋한다면, 외부 서비스가 느려질 때 DB 연결과 잠금을 함께 붙잡습니다. 저는 연결 획득 대기 시간과 보유 시간, 실제 쿼리 시간을 나눠 추적하겠습니다. 쿼리는 짧은데 보유 시간이 길다면 트랜잭션 범위를 줄이고 외부 작업을 경계 밖으로 옮기겠습니다. 다만 다시 돌아왔을 때 상태가 바뀌었는지 조건부 갱신으로 확인해야 합니다.

풀을 늘리는 것은 DB에 여유가 있고 정상적인 병렬 작업이 연결을 기다리는 경우에 하겠습니다. 여러 애플리케이션 인스턴스의 풀 합계가 DB 한도를 넘지 않는지도 확인해야 합니다. 유휴 트랜잭션과 오래된 작업을 관찰하고, 취소·예외 경로에서 연결이 반환되는지 테스트하겠습니다. 목표는 대기 숫자를 숨기는 것이 아니라 제한된 연결이 실제 업무에 쓰이고, 완료된 요청이 자원을 남기지 않는 상태를 만드는 것입니다.

## 득점 포인트

- **대기·보유·실행 시간을 나눈다.** 연결 부족의 원인을 구분한다.
- **트랜잭션 범위를 조정한다.** 외부 호출 제거 후 재검증을 설명한다.
- **전체 연결 예산을 확인한다.** 인스턴스 합계와 예외 반환을 본다.

## 감점 포인트

- **풀 부족이면 즉시 크기만 늘린다.** DB 포화와 누수가 악화될 수 있다.
- **외부 호출은 DB 부하와 무관하다고 말한다.** 연결과 잠금을 보유할 수 있다.
- **타임아웃이면 연결도 자동 정리된다고 말한다.** 드라이버와 코드 경로를 확인해야 한다.

## 더 파고들 거리

- 연결을 빌린 채 사용자 응답을 스트리밍하면 어떤 한계가 생길까요?
- 드라이버 취소 후 연결을 재사용해도 되는 시점은 어떻게 확인할까요?
- 유휴 트랜잭션 제한을 적용하면 애플리케이션은 어떤 오류를 처리해야 할까요?
