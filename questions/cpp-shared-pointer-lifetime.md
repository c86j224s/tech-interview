# C++ 비동기 콜백에 shared_ptr를 복사해 넘겼습니다. 객체 수명과 여러 스레드의 필드 수정이 모두 안전해지나요?

## 구두 답변

shared_ptr는 소유자 수를 관리해 마지막 소유자가 사라질 때 객체를 정리하도록 돕습니다. 하지만 객체 내부 데이터의 동시 접근까지 보호하지는 않습니다. 저는 참조 카운트의 안전성, 포인터 변수의 접근, 객체 내용의 접근을 구분하겠습니다.

예를 들어 두 콜백이 서로 다른 shared_ptr 복사본으로 같은 객체를 소유하면 마지막 복사본이 사라질 때까지 객체 수명은 유지됩니다. 하지만 둘이 동시에 객체의 일반 정수 count를 증가시키면 데이터 레이스가 될 수 있습니다. 참조 수를 안전하게 갱신하는 것과 대상 객체의 필드를 안전하게 바꾸는 것은 다릅니다.

서로 다른 shared_ptr 인스턴스가 같은 객체를 소유하며 각자 복사·파괴되는 것과, 같은 shared_ptr 변수 하나를 여러 스레드가 동시에 바꾸는 것은 다릅니다. 후자는 적절한 동기화나 원자적 shared_ptr가 필요합니다. 객체의 필드를 함께 수정한다면 그 필드도 락이나 소유권 규칙으로 보호해야 합니다. shared_ptr를 복사해 콜백에 넣으면 콜백 동안의 수명은 유지되지만, 상태가 유효한 업무 단계인지는 별도로 확인해야 합니다.

저는 소유권이 한곳이면 unique_ptr를 우선하고, 실제로 여러 비동기 작업이 수명을 공유해야 할 때 shared_ptr를 쓰겠습니다. 서로를 강하게 참조하면 순환 때문에 해제되지 않을 수 있어 관찰자 관계에는 weak_ptr를 사용할 수 있습니다. 마지막 참조가 어느 스레드에서 사라지는지도 중요합니다. 무거운 소멸자가 이벤트 루프에서 실행되면 지연이 생길 수 있으므로, 수명 추적과 해제 시점의 지연을 함께 확인하겠습니다.

## 득점 포인트

- **세 가지 안전성을 구분한다.** 제어 블록·포인터 변수·대상 객체를 따로 설명한다.
- **실제 소유 관계에 맞춘다.** 단독 소유와 공유·관찰 관계를 구별한다.
- **파괴 위치까지 본다.** 비동기 콜백과 마지막 참조의 실행 환경을 확인한다.

## 감점 포인트

- **참조 카운트가 원자적이니 객체도 안전하다고 말한다.** 데이터 레이스는 남는다.
- **순환 참조도 자동 해제된다고 말한다.** 강한 참조 고리는 끊어야 한다.
- **shared_ptr를 쓰면 논리적 종료도 안전하다고 말한다.** 살아 있는 객체가 종료된 상태일 수 있다.
