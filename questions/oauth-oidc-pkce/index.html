01

구두 답변

정의를 외우기보다, 원리와 조건을 연결해 설명해 보세요.

PKCE는 인증 코드를 받은 요청자가 처음 흐름을 시작한 클라이언트와 연결되는지 확인하는 장치이고, state는 돌아온 응답을 내가 시작한 요청과 묶는 데 사용합니다. 서로 역할이 달라 하나가 있다고 다른 검증을 생략하면 안 됩니다. OAuth 자체의 권한 위임과 OIDC의 신원 확인도 구분해야 합니다.

클라이언트는 예측하기 어려운 verifier를 만들고 그로부터 만든 challenge를 처음 요청에 보냅니다. 코드를 토큰으로 바꿀 때 verifier를 제출해 연결을 증명합니다. 코드를 중간에서 얻은 쪽이 verifier 없이 교환하기 어렵게 하는 것입니다. state는 세션에 묶어 보관하고 콜백에서 정확히 비교해, 다른 흐름의 응답을 내 로그인으로 받아들이지 않게 하겠습니다.

OIDC로 로그인한다면 ID 토큰의 발급자·대상·서명·만료와 필요한 nonce도 확인해야 합니다. 리다이렉트 주소는 사전에 정한 값으로 엄격하게 제한하고 코드와 verifier를 로그에 남기지 않겠습니다. 모바일·SPA처럼 클라이언트 비밀을 안전하게 보관하기 어려운 환경에서 공개 클라이언트에 비밀값을 숨겨 둔다는 가정도 하지 않겠습니다. 검증은 로그인 성공보다 잘못된 state, 재사용 코드, 다른 대상 토큰을 거절하는지 중심으로 하겠습니다.

02

득점 포인트

이해가 드러나는 지점을 확인해 보세요.

  • PKCE와 요청 연결 검증을 구분한다. 코드 교환과 콜백 매칭을 설명한다.
  • OAuth와 OIDC 역할을 구분한다. 위임 토큰과 로그인 신원을 혼동하지 않는다.
  • 거절 경로를 테스트한다. 리다이렉트·대상·재사용을 확인한다.
03

감점 포인트

놓치기 쉬운 조건과 오해를 짚어 보세요.

  • PKCE가 모든 CSRF 검사를 대체한다고 말한다. 흐름과 구현에 맞는 요청 연결 검증이 필요하다.
  • access token이면 신원 확인이 끝났다고 말한다. 토큰의 용도와 계약을 봐야 한다.
  • 앱에 넣은 client secret은 안전하다고 말한다. 공개 클라이언트에서 비밀 보관을 가정할 수 없다.
04

더 파고들 거리

  • nonce와 state는 검증 대상과 보관 위치에서 어떻게 다를까요?
  • 여러 로그인 공급자를 지원할 때 발급자 혼동을 어떻게 막을까요?
  • 콜백을 받은 기기와 로그인 시작 기기가 다르면 어떤 세션 연결이 필요할까요?
