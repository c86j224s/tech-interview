01

구두 답변

정의를 외우기보다, 원리와 조건을 연결해 설명해 보세요.

요청마다 고루틴을 만드는 것 자체는 자연스러운 패턴이지만 가볍다는 것과 동시 작업 수가 무제한이어도 된다는 것은 다릅니다. Go 런타임은 G인 고루틴을 M인 OS 스레드와 P인 실행 자원에 스케줄링합니다. GOMAXPROCS는 Go 코드를 동시에 실행할 P의 수이지 고루틴이나 전체 OS 스레드 수의 상한은 아닙니다.

채널이나 netpoller가 지원하는 네트워크 I/O에서 대기하면 보통 고루틴을 파킹해 스레드를 다른 작업에 사용할 수 있습니다. 반면 블로킹 시스템 호출이나 cgo는 OS 스레드를 점유할 수 있습니다. 고루틴 자체도 스택과 스케줄링 비용이 있고, 버퍼나 연결을 참조하면 그 메모리도 유지됩니다. 많은 살아 있는 스택과 객체는 GC 스캔 비용에도 영향을 줍니다.

외부 API가 느려져 응답 시간이 늘면 도착률이 같아도 in-flight 작업이 증가합니다. 안정된 구간에서는 리틀의 법칙 L = λW로 이 관계를 생각할 수 있습니다. 따라서 세마포어나 작업자 풀로 실행 수를 제한하되, 고루틴을 먼저 무제한 생성한 뒤 세마포어 앞에서 기다리게 하면 대기 고루틴은 계속 쌓입니다. 입구에서 동시성 permit을 얻거나 대기열을 제한하고, 넘치는 부하는 거절하거나 상위로 백프레셔를 전달해야 합니다.

수명 관리도 중요합니다. 호출자가 사라졌는데 작업자가 채널 전송에 막히면 CPU를 쓰지 않아도 누수입니다. context 취소는 강제 종료가 아니므로 채널 대기와 하위 호출이 실제로 취소에 반응해야 합니다. 구조화된 동시성처럼 부모가 자식 작업의 종료를 책임지고, errgroup 같은 도구로 실패·취소·join을 묶는 것이 도움이 됩니다. 다만 취소 신호만 보내고 종료를 확인하지 않으면 자원 정리는 보장되지 않습니다.

운영에서는 고루틴 수만 보지 않고 pprof의 goroutine·block·mutex 프로파일과 runtime trace로 대기 위치를 구분하겠습니다. 힙과 스택 메모리, GC CPU, 연결 풀 대기까지 함께 보고, 부하를 내렸을 때 고루틴 수가 회복되는지도 확인합니다. 스케줄러의 효율이 아니라 작업 수명과 허용 동시성이 시스템의 상한을 결정합니다.

02

득점 포인트

이해가 드러나는 지점을 확인해 보세요.

  • G·M·P와 제한의 의미를 구분한다. GOMAXPROCS를 고루틴 수나 OS 스레드 수 제한으로 오해하지 않는다.
  • 지연·동시성·메모리의 관계를 설명한다. in-flight 증가를 리틀의 법칙과 보유 자원, GC 비용에 연결한다.
  • 대기열까지 포함한 진입 제어를 제시한다. 작업자 수만 제한하지 않고 permit 획득 시점과 과부하 정책을 정한다.
  • 수명 관리와 진단을 연결한다. 협력적 취소·join과 프로파일별 관측 범위를 구분해 누수와 정상 적체를 판단한다.
03

감점 포인트

놓치기 쉬운 조건과 오해를 짚어 보세요.

  • “GOMAXPROCS를 줄이면 고루틴 누수가 제한된다”고 말한다. 실행 병렬성과 고루틴 생성·대기는 다른 축이다.
  • “GC가 블로킹된 고루틴을 정리한다”고 말한다. 대기 중 실행 흐름과 그 스택이 참조하는 객체에는 종료 경로가 필요하다.
  • “context 취소나 errgroup 사용만으로 모든 자식 작업이 끝난다”고 말한다. 작업이 취소를 확인하고 실제 종료할 수 있어야 한다.
  • “세마포어를 고루틴 안에 두면 메모리 사용량도 제한된다”고 말한다. 실행 permit 대기자가 무한히 증가하는 경로는 여전히 남는다.
04

더 파고들 거리

하나 더 질문하며 이해의 범위를 넓혀 보세요.

  • 블록 프로파일과 고루틴 덤프는 이미 끝난 대기와 현재 멈춘 대기를 관찰하는 데 어떤 차이가 있을까요?
  • 부모 context가 취소돼도 반드시 완료해야 하는 작업은 요청 수명에서 어떻게 분리하고 누가 복구를 책임져야 할까요?
  • cgo 비중이 큰 서버에서 OS 스레드 증가와 GOMAXPROCS 조정을 어떻게 해석해야 할까요?
  • bounded queue의 상한을 정할 때 데드라인, 서비스 시간 분포, 메모리 예산을 어떻게 결합할까요?
