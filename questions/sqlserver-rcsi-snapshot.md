# SQL Server에서 RCSI와 SNAPSHOT 격리는 반복 읽기의 시점과 쓰기 충돌을 어떻게 다르게 만들나요?

## 구두 답변

RCSI(Read Committed Snapshot Isolation)는 데이터베이스 옵션을 켠 뒤 `READ COMMITTED` 읽기를 잠금 대신 행 버전으로 처리하는 방식입니다. 일반적으로 각 문장이 시작될 때의 커밋된 버전을 읽으므로, 같은 트랜잭션에서 두 SELECT를 실행하는 사이 커밋이 보일 수 있습니다. SNAPSHOT 격리는 트랜잭션이 시작한 스냅샷을 기준으로 읽기 때문에 한 트랜잭션 안의 반복 읽기 기준이 더 오래 유지됩니다.

따라서 단순 조회에서 읽기와 쓰기의 블로킹을 줄이고 문장 단위로 일관된 결과를 얻는 목적이면 RCSI가 적합할 수 있습니다. 여러 조회를 조합한 보고서가 모두 같은 기준 시점이어야 한다면 SNAPSHOT 또는 더 강한 설계가 필요합니다. 이름만 보고 판단하지 않고 트랜잭션 시작 시점과 첫 접근, 실제 SQL Server 옵션을 확인하겠습니다.

두 방식 모두 버전 저장 공간과 오래 열린 트랜잭션의 정리 지연을 만듭니다. SNAPSHOT에서 읽은 행을 다른 트랜잭션이 먼저 수정하면 갱신을 수행하는 시점이나 처리 과정에서 업데이트 충돌이 감지되어 트랜잭션이 실패할 수 있으므로, 애플리케이션 재시도가 필요합니다. 반면 여러 행의 불변식이나 쓰기 편향을 스냅샷이 자동으로 직렬화해 주는 것은 아니므로, 조건부 갱신·공통 잠금 행·SERIALIZABLE 등 별도 보호가 필요합니다.

두 세션에서 첫 SELECT, 중간 UPDATE, 두 번째 SELECT, UPDATE 커밋 순서를 맞춰 RCSI와 SNAPSHOT의 결과를 비교하겠습니다. 버전 저장소 사용량, 충돌·재시도율, 오래 열린 트랜잭션도 함께 관찰해야 합니다.

## 득점 포인트

- 문장 단위 RCSI와 트랜잭션 단위 SNAPSHOT을 구분한다.
- 블로킹 감소와 반복 보고서 일관성의 요구를 나눈다.
- 버전 비용·업데이트 충돌·쓰기 편향을 함께 다룬다.

## 감점 포인트

- RCSI면 트랜잭션 전체가 항상 같은 시점이라고 말한다.
- SNAPSHOT이 모든 직렬화 이상을 막는다고 말한다.
- 버전 읽기가 아무 비용 없이 블로킹을 없앤다고 말한다.
