# Kafka 파티션이 3개인데 같은 그룹의 소비자를 5개로 늘렸습니다. 왜 일부 소비자는 일을 하지 않으며 언제 확장이 도움이 되나요?

## 구두 답변

일반적인 Kafka consumer group에서는 한 시점에 한 파티션을 같은 그룹의 한 소비자가 소유합니다. 따라서 파티션이 3개이면 소비자 5개 중 최대 3개만 파티션을 받아 실제 소비하고, 나머지 2개는 유휴 상태가 됩니다. 다른 group은 같은 레코드를 독립적으로 읽으므로 group 내부 작업 분배와 여러 서비스의 fan-out을 혼동하면 안 됩니다.

파티션 수가 충분해도 키 해시 편중으로 한 파티션만 바쁘거나, 그 파티션의 레코드 처리 비용이 클 수 있습니다. 전체 lag만 보지 말고 파티션별 lag, 처리율, 가장 오래된 레코드의 나이를 확인하겠습니다. 소비자 내부에서 한 파티션의 워커를 여러 개로 늘리면 CPU 병렬성은 얻지만 완료 순서가 뒤섞입니다. offset은 완료된 연속 구간까지만 커밋해야 하며, 뒤 레코드가 먼저 끝났다고 그 위치를 바로 커밋하면 앞의 미완료 레코드를 건너뛸 수 있습니다.

소비자를 늘리기 전에 파티션 분포와 하위 DB(소비 결과를 저장하는 데이터베이스)의 처리 여유, 소유권을 다시 나누는 리밸런싱 비용을 측정하겠습니다. 소비자 수만 늘려 DB가 먼저 포화되면 lag가 더 커지는 실패가 생깁니다. 재할당 중에는 중복 처리가 생길 수 있으므로 외부 효과의 멱등성이 필요합니다. 키 편중, 소비자 추가·제거, 느린 처리와 재시작을 시험해 파티션별 지연과 중복·누락이 허용 범위에 있는지 검증합니다.

## 득점 포인트

- 파티션 수가 group 내부 병렬성의 상한임을 숫자로 설명한다.
- 키 편중과 전체 lag의 한계를 연결한다.
- 내부 워커 병렬화에서 연속 완료 offset 규칙을 제시한다.

## 감점 포인트

- 소비자 수만큼 항상 처리량이 증가한다고 말한다.
- 다른 consumer group이 메시지를 서로 나눠 가진다고 말한다.
- 뒤에서 끝난 레코드의 offset을 바로 커밋해 앞의 작업을 건너뛴다.

## 더 파고들 거리

- 파티션 내 병렬 처리를 허용하면서 연속 완료 위치를 어떤 자료구조로 추적할까요?
- 핫키를 분할할 수 없을 때 batch 크기와 작업의 분할 방식을 어떻게 바꿀까요?
- pause와 group 탈퇴는 처리 중 작업의 소유권에서 어떻게 다른가요?
