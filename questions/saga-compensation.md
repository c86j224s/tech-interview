# 여러 서비스의 변경을 하나의 업무로 묶을 때 롤백은 어떻게 하나요?

## 구두 답변

각 서비스가 자기 DB에 이미 커밋했다면 로컬 트랜잭션처럼 전부 되돌릴 수는 없습니다. 완료한 단계의 효과를 업무적으로 상쇄하는 보상 작업이 필요할 수 있습니다. 이런 여러 단계와 보상을 관리하는 방식이 saga입니다. 보상은 과거를 지우는 것이 아니라 새로운 업무 변경이라는 점이 중요합니다.

주문에서 재고를 예약하고 결제를 승인한 뒤 배송 생성에 실패했다고 하겠습니다. 재고 예약을 해제하고 결제를 취소할 수 있지만, 그사이에 사용자에게 알림이 갔거나 취소 수수료가 생겼다면 처음부터 없던 일과 같지는 않습니다. 저는 각 단계가 재시도 가능한지, 취소 가능한지, 취소할 수 없으면 어떤 상태로 운영자가 확인할지를 먼저 정하겠습니다.

진행 상태는 내구성 있게 저장하고 단계와 보상에 멱등성 키를 두겠습니다. 보상 요청도 실패하거나 응답이 유실될 수 있어 반복해도 안전해야 합니다. 단순히 예외를 잡고 역순 함수를 호출하는 것으로 끝내지 않겠습니다. 사용자에게는 처리 중·취소 중처럼 실제 중간 상태를 보여 주고, 오래 멈춘 업무를 탐지하겠습니다. 검증에서는 단계별 중단과 보상 실패를 주입해 재시작 후 계속 진행하거나 대사할 수 있는지 확인하겠습니다.

## 득점 포인트

- **보상과 DB 롤백을 구분한다.** 외부에 보인 효과는 사라지지 않을 수 있다.
- **단계별 복구 계약을 정한다.** 재시도·취소·수동 확인을 구분한다.
- **진행 상태와 멱등성을 저장한다.** 재시작과 보상 실패를 처리한다.

## 감점 포인트

- **saga는 분산 ACID와 같다고 말한다.** 중간 상태가 관찰될 수 있다.
- **보상은 항상 성공한다고 가정한다.** 실패와 재시도가 필요하다.
- **메모리의 호출 스택만으로 진행을 추적한다.** 재시작하면 상태를 잃는다.
