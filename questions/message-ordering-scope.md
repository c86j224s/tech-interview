# 메시지 브로커가 순서를 보장하면 업무 처리 순서도 보장되나요?

## 구두 답변

브로커가 보장하는 순서의 범위와 애플리케이션이 실행하는 순서를 구분해야 합니다. 보통 특정 파티션이나 키 안에서의 전달 순서이지 모든 메시지의 전역 순서는 아닙니다. 순서대로 받은 뒤 여러 워커에 넘기면 완료 순서는 다시 달라질 수 있습니다.

계정 상태 변경 이벤트라면 같은 계정 키를 같은 순서 경로로 보내고 소비자에서도 그 키의 적용을 직렬화하겠습니다. 첫 이벤트가 실패해 재시도되는 동안 두 번째를 먼저 적용해도 되는지도 정해야 합니다. 최신 버전의 전체 상태를 덮어쓰는 이벤트와 증분으로 잔액을 더하는 이벤트는 순서 역전의 영향이 다릅니다. 버전으로 오래된 상태를 거절할 수 있어도 중간 증분을 건너뛰어서는 안 되는 경우가 있습니다.

전체 순서를 보장하려고 모두 한 파티션에 넣으면 병렬성과 장애 격리가 줄어듭니다. 저는 실제로 함께 순서가 필요한 업무 키를 기준으로 나누겠습니다. 키를 바꾸거나 파티션을 늘리는 중에는 이전 경로와 새 경로의 순서가 이어지는지도 확인해야 합니다. 테스트는 소비자 재시작과 재시도, 느린 첫 메시지를 섞어 최종 상태뿐 아니라 금지된 중간 상태가 생기지 않는지 보겠습니다.

## 득점 포인트

- **순서의 범위를 명확히 한다.** 파티션·키·수신·적용 순서를 구분한다.
- **이벤트 의미를 고려한다.** 전체 상태와 증분의 역전 처리 차이를 설명한다.
- **병렬성 비용을 비교한다.** 필요한 키만 직렬화한다.

## 감점 포인트

- **브로커 FIFO면 워커 완료도 FIFO라고 말한다.** 실행 병렬성이 순서를 바꾼다.
- **버전이 높으면 중간 증분을 버려도 된다고 말한다.** 계산 결과가 틀릴 수 있다.
- **전역 한 줄로 만들면 비용이 없다고 말한다.** 처리량과 장애 범위가 커진다.
