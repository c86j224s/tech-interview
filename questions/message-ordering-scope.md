# 메시지 브로커가 같은 partition의 전달 순서를 보장해도 여러 워커의 업무 완료 순서가 달라지는 이유는 무엇인가요?

## 구두 답변

브로커가 보장하는 순서는 보통 특정 partition 또는 키가 배치된 흐름의 전달 순서입니다. 그것은 모든 topic의 전역 FIFO도 아니고, 소비자가 외부 시스템에 효과를 적용한 완료 순서도 아닙니다. 소비자가 1번을 받은 뒤 1번을 느린 워커에 넘기고 2번을 빠른 워커에 넘기면 브로커 전달은 순서였어도 완료와 DB(업무 상태를 저장하는 데이터베이스) 반영은 2번이 먼저 될 수 있습니다. 잔액을 먼저 더하고 나중에 빼는 이벤트라면 최종 값이 같아 보여도 중간에 허용되지 않은 잔액이 노출될 수 있습니다.

계정 잔액 변경처럼 같은 키의 순서가 필수라면 키를 같은 partition으로 보내고 소비자에서도 그 키의 적용을 직렬화하겠습니다. 첫 이벤트가 실패해 재시도되는 동안 둘째 이벤트를 먼저 적용해도 되는지 업무 의미를 확인해야 합니다. 전체 상태를 담은 version 8 이벤트는 version 7을 거절할 수 있지만, `+10` 증분 이벤트는 중간 하나를 버리면 최종 잔액이 틀립니다.

모든 메시지를 한 partition에 넣으면 순서는 단순해지지만 처리량과 장애 격리가 나빠집니다. 필요한 업무 키만 직렬화하고, 순서가 깨진 이벤트는 보류 큐·시간 상한·재동기화 정책으로 처리하겠습니다. 파티션 변경·재시도·느린 첫 메시지를 시험해 최종 상태뿐 아니라 금지된 중간 상태, 중복과 외부 커밋 순서까지 검증하겠습니다.

## 득점 포인트

- 전달·워커 완료·외부 적용 순서의 범위를 분리한다.
- 전체 상태와 증분 이벤트의 역전 영향을 대비한다.
- 필요한 키만 직렬화하고 병렬성 비용을 명시한다.

## 감점 포인트

- 브로커 FIFO가 워커 완료 FIFO까지 보장한다고 말한다.
- version이 높으면 어떤 증분 이벤트도 버려도 된다고 말한다.
- 전체를 한 partition으로 만들면 처리량·장애 비용이 없다고 말한다.

## 더 파고들 거리

- 순서가 깨진 이벤트를 보류할 때 메모리·시간 상한과 재동기화는 어떻게 정할까요?
- 파티션 수 변경 중 키별 순서를 이어 가는 전환 절차는 무엇인가요?
- 외부 쓰기 완료와 broker offset 커밋을 어떤 원자성·멱등성으로 조정할까요?
