# DB 요청이 몰려 실행 대기 시간이 길어집니다. 동시에 실행할 작업 수와 기다리게 할 요청 수를 어떻게 제한하나요?

## 구두 답변

먼저 하위 시스템이 안정적으로 처리하는 양과 요청이 기다릴 수 있는 시간을 보겠습니다. 동시 실행 수는 자원을 얼마나 함께 쓰게 할지이고, 대기열 크기는 넘치는 작업을 얼마나 보관할지입니다. 둘을 크게 잡는다고 처리 능력이 늘지는 않습니다. 오히려 실패할 요청을 오래 붙잡을 수 있습니다.

실행 제한이 20이면 최대 20개가 DB 작업을 진행하고, 대기열 상한이 100이면 추가 요청 100개까지 보관하는 식입니다. 이 숫자는 예시일 뿐 권장 설정이 아닙니다. 대기열을 1,000개로 늘려도 DB가 빨라지지는 않고, 요청이 보유한 메모리와 기다린 시간만 늘 수 있습니다.

DB 요청을 예로 들면 부하를 올리면서 쿼리 시간과 연결 대기 시간을 나눠 측정하겠습니다. 처리량은 더 늘지 않는데 대기와 p99만 커지는 구간보다 낮게 실행 수를 잡는 것이 출발점입니다. DB 연결 수가 상한의 단서일 수는 있어도, 다른 서비스가 같은 DB를 쓰고 있으므로 연결 수 그대로를 최적값으로 보지는 않겠습니다. 긴 작업과 짧은 작업이 섞이면 긴 작업이 모두 차지하지 못하도록 풀을 분리하는 것도 방법입니다.

대기열은 요청의 남은 데드라인과 메모리 예산 안에서 정하겠습니다. 이미 기다리는 작업만으로도 제한 시간을 소진할 것 같다면 새 요청을 즉시 거절하는 편이 유효 처리량에 낫습니다. 재시도 가능한 오류와 적절한 간격을 안내하고, 생산자가 멈출 수 있는 내부 파이프라인은 상위로 대기를 전달하겠습니다. 마지막으로 평상시뿐 아니라 하위 장애와 회복을 테스트해, 큐가 비워지는 시간과 성공 요청 수를 확인하겠습니다.

## 득점 포인트

- 실행 상한과 저장 상한을 처리량·p99로 구분한다.
- 데드라인·메모리 예산으로 대기와 거절을 선택한다.
- 긴 작업 분리와 장애 회복을 검증한다.

## 감점 포인트

- 큐가 크면 처리량이 늘어난다고 말한다.
- DB 연결 수가 곧 최적 동시성이라고 단정한다.
- 과부하에서 거절이 항상 나쁘다고 말한다.
