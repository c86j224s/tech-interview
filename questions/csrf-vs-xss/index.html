01

구두 답변

정의를 외우기보다, 원리와 조건을 연결해 설명해 보세요.

CSRF는 사용자의 브라우저가 자동으로 보내는 인증 정보를 이용해 의도하지 않은 요청을 보내게 하는 문제이고, XSS는 신뢰한 페이지 안에서 공격자 스크립트가 실행되는 문제입니다. 둘은 공격 경계가 다르므로 쿠키 옵션 하나로 모두 해결되지는 않습니다.

쿠키 기반 상태 변경 API라면 SameSite 설정과 CSRF 토큰, Origin 검증 같은 방법으로 외부 사이트에서 유도한 요청을 제한하겠습니다. 읽기용 GET에 상태 변경을 넣지 않는 것도 중요합니다. HttpOnly는 스크립트가 쿠키 값을 직접 읽는 것을 막지만, 같은 페이지에서 실행된 XSS가 사용자의 권한으로 요청하는 것까지 막지는 못합니다.

XSS에는 출력 위치에 맞는 인코딩과 안전한 DOM API를 사용하고, 신뢰하지 않는 HTML을 그대로 넣지 않겠습니다. HTML을 허용해야 한다면 검증된 정화 도구와 제한된 정책을 사용하겠습니다. CSP는 추가 방어지만 입력·출력 처리의 대체재는 아닙니다. 테스트에서는 실제 상태 변경 요청이 외부 출처에서 거절되는지와 문자열이 HTML·속성·스크립트 문맥에서 어떻게 렌더링되는지 확인하겠습니다. 인증 수단을 바꿨다고 두 위험이 자동으로 사라지는 것은 아닙니다.

02

득점 포인트

이해가 드러나는 지점을 확인해 보세요.

  • 신뢰 경계를 구분한다. 자동 자격 전송과 페이지 내 코드 실행을 나눈다.
  • 쿠키 옵션의 한계를 설명한다. HttpOnly와 SameSite 역할을 구분한다.
  • 문맥별 방어를 제시한다. 토큰·출처 검증과 안전한 출력 처리를 나눈다.
03

감점 포인트

놓치기 쉬운 조건과 오해를 짚어 보세요.

  • HttpOnly면 XSS가 무해하다고 말한다. 권한 있는 요청을 실행할 수 있다.
  • CSP만 설정하면 안전하다고 말한다. 안전한 렌더링도 필요하다.
  • GET으로 상태를 바꿔도 문제없다고 말한다. 요청 유도와 캐시 등 계약 문제가 생긴다.
04

더 파고들 거리

하나 더 질문하며 이해의 범위를 넓혀 보세요.

  • SameSite 설정이 외부 로그인 콜백과 충돌할 때 어떻게 설계할까요?
  • 허용된 HTML에서 링크와 스타일도 제한해야 하는 이유는 무엇인가요?
  • 토큰을 브라우저 저장소에 둘 때 CSRF와 XSS의 위험은 어떻게 이동할까요?
