# ARC를 사용하는 Swift 객체가 해제되지 않습니다. 강한 순환 참조와 `weak`, `unowned`의 차이를 어떻게 진단하고 고치나요?

## 구두 답변

ARC(Automatic Reference Counting)는 객체를 가리키는 강한 참조의 수를 세어 더 이상 강한 참조가 없을 때 객체를 해제합니다. 두 객체가 서로를 강하게 가리키거나, 객체가 자신을 캡처하는 탈출 클로저를 보관하면 외부에서 사용을 끝내도 참조 수가 0이 되지 않는 강한 순환 참조가 생깁니다. 이 경우 단순히 화면을 닫거나 변수를 nil로 만드는 것만으로는 해제가 일어나지 않으므로, 메모리 그래프와 deinit 로그로 누가 누구를 붙잡는지 확인해야 합니다.

`weak` 참조는 소유권을 늘리지 않는 옵셔널 참조입니다. 대상의 마지막 강한 참조가 사라지면 ARC가 weak 참조를 자동으로 nil로 바꾸므로, 대상이 먼저 사라질 수 있는 관찰자나 클로저 캡처에 적합합니다. 예를 들어 뷰 컨트롤러가 오래 사는 서비스의 콜백을 받는다면 `[weak self]`로 화면을 붙잡지 않게 하고, 콜백 시점에 self가 존재할 때만 UI를 갱신합니다. 대신 대상이 사라진 뒤에는 콜백이 아무 일도 하지 않을 수 있다는 동작을 받아들여야 합니다.

일반적인 비옵셔널 `unowned`도 소유권을 늘리지 않고 접근합니다. 옵셔널 unowned 표현도 가능하지만 weak처럼 대상 해제 시 자동으로 nil이 되는 것은 아닙니다. 그래서 대상이 먼저 해제된 뒤 접근하면 nil이 되는 것이 아니라 런타임 오류가 납니다. 소유자보다 오래 살 수 없다는 관계가 설계상 확실할 때만 사용해야 합니다. 예를 들어 자식이 부모를 unowned로 참조한다면, 자식이 그 참조를 사용하는 동안 부모가 반드시 살아 있다는 수명 보장이 있을 때만 가능합니다. 비동기 작업·캐시·지연된 콜백처럼 실행 시점을 통제하기 어려운 곳에서 단지 강한 순환을 없애려고 `unowned`를 쓰면 해제 문제를 충돌 문제로 바꾸게 됩니다.

순환을 고치는 방법은 무조건 모든 self를 weak로 바꾸는 것이 아닙니다. 소유 관계라면 강한 참조를 유지하고, 역방향 링크나 관찰 관계라면 weak로 표현하며, 클로저가 작업 완료 후 폐기되는지 또는 서비스보다 짧게 사는지 확인합니다. 약한 캡처로 바꾼 뒤에도 작업이 취소되었을 때 콜백이 남아 있는지, 객체가 사라져 필요한 정리가 누락되지 않는지 테스트해야 합니다.

## 득점 포인트

- ARC의 강한 참조 수와 서로를 강하게 가리킬 때 해제가 막히는 인과를 설명한다.
- 대상이 먼저 사라질 수 있는 관계에는 nil이 되는 `weak`를 선택하고 그 결과를 처리한다.
- 수명 선행 보장이 실제 계약일 때만 `unowned`를 쓰며, 위반 시 충돌한다는 비용을 말한다.

## 감점 포인트

- ARC가 순환 참조도 자동으로 알아서 끊는다고 설명한다.
- `weak`와 `unowned`가 모두 nil로 바뀐다고 말해 `unowned` 접근 충돌을 놓친다.
- 모든 클로저에서 `weak self`를 쓰면 안전하다고 하고 작업 취소와 필요한 정리를 확인하지 않는다.

## 더 파고들 거리

- 서비스가 클로저를 보관하고 뷰 컨트롤러가 서비스를 보관하는 구조에서 캡처 그래프를 그려 보세요.
- weak 캡처 때문에 작업 완료 처리가 사라질 때 취소 핸들러와 명시적 소유자를 어떻게 둘지 비교해 보세요.
- 메모리 그래프 디버거와 `deinit` 로그로 순환 참조의 원인을 재현하고 확인해 보세요.
