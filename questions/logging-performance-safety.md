# 로그를 많이 남기면 장애 분석에 항상 유리한가요?

## 구두 답변

필요한 맥락이 있는 로그는 도움이 되지만 양을 늘리는 것만으로 분석이 쉬워지지는 않습니다. 동기 로그 쓰기가 요청을 막거나 저장 비용이 커질 수 있고, 토큰과 개인정보가 섞이면 보안 위험도 생깁니다. 저는 어떤 질문에 답하려고 남기는지부터 정하겠습니다.

결제 재시도를 분석하려면 요청 ID, 업무 ID, 시도 번호, 결과 상태가 중요합니다. 전체 요청 본문을 매번 출력하는 것보다 구조화된 필드로 남기면 검색하기 쉽고 민감정보도 줄일 수 있습니다. 오류 스택은 필요한 지점에서 한 번 충분한 맥락으로 남기고, 모든 계층이 같은 오류를 중복 출력하지 않게 하겠습니다.

비동기 로그 큐를 쓰면 요청 지연을 줄일 수 있지만 큐가 가득 찼을 때 대기할지 버릴지 정책이 필요합니다. 감사상 반드시 필요한 기록은 일반 디버그 로그와 같은 유실 정책에 두면 안 됩니다. 저는 부하가 커질 때 로그 저장소가 느려지는 상황을 재현해 요청 지연과 유실량을 확인하겠습니다. 보관 기간과 접근 권한, 마스킹도 함께 관리합니다. 장애 때 쓸 수 있고 시스템을 더 아프게 하지 않는 기록이 좋은 로그입니다.

## 득점 포인트

- **분석 목적에 맞는 필드를 고른다.** ID·상태·시도를 구조화한다.
- **유실 정책을 구분한다.** 감사 기록과 일반 로그의 요구를 나눈다.
- **로그 자체의 장애를 테스트한다.** 큐·지연·보안을 확인한다.

## 감점 포인트

- **전체 본문을 남기면 안전하다고 말한다.** 비밀과 개인정보가 유출될 수 있다.
- **비동기 로그는 비용이 없다고 말한다.** 큐 적체와 유실이 있다.
- **모든 로그를 같은 보관 정책에 둔다.** 법적·보안·운영 요구가 다르다.

## 더 파고들 거리

- 장애 중 로그 폭주를 제한하면서 최초 원인과 빈도를 어떻게 보존할까요?
- 감사 이벤트를 내구성 있게 남기려면 업무 트랜잭션과 어떻게 연결할까요?
- 상관 ID가 외부 입력일 때 길이와 형식을 왜 제한해야 할까요?
