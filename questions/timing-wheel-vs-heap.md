# 수십만 개 타이머를 관리할 때 최소 힙과 타이밍 휠을 정밀도·취소·만료 집중으로 어떻게 비교하나요?

## 구두 답변

최소 힙은 가장 이른 만료 시각을 루트에서 얻기 쉽고 타이머 간격이 넓거나 정밀한 순서가 필요할 때 유연합니다. 삽입·삭제는 일반적으로 `O(log n)`이며, 취소된 항목을 즉시 힙에서 제거할지 지연 삭제할지에 따라 비용과 메모리가 달라집니다. 타이밍 휠은 시간을 버킷으로 나누고 현재 위치를 이동하며 만료를 처리해 대량 타이머에서 관리 비용을 줄일 수 있지만, 버킷 해상도와 긴 만료를 다음 회전으로 넘기는 규칙이 필요합니다.

세션 만료가 초 단위이고 수 밀리초의 오차를 허용한다면 휠이 적합할 수 있습니다. 정확한 재전송이나 짧은 deadline처럼 다음 시각의 정밀도가 중요하면 힙이나 계층형 휠을 비교합니다. 타이머 개수만 벤치마크하지 않고 등록률·취소률·동일 시각 만료 집중·긴 타이머 분포를 재현해야 합니다.

자료구조가 만료를 찾는 비용을 줄여도 만료 콜백이 한 번에 수십만 개 실행되면 이벤트 루프가 막힙니다. 만료 감지와 실제 콜백 실행을 나누고 tick별 실행 예산, 작업 큐 상한, 부하 시 지연 정책을 둡니다. 취소 상태를 원자적으로 읽는 것만으로 콜백 실행을 막을 수는 없습니다. 워커가 ‘취소 안 됨’을 읽고 멈춘 사이 다른 스레드가 취소하고 반환하면, 워커는 다시 실행되며 콜백을 호출할 수 있습니다.

저는 **취소와 실행권 획득을 하나의 상태 전이로 경쟁**시키겠습니다. 다음은 일회성 타이머 한 세대를 설명하는 의사코드입니다. CAS는 현재 상태가 예상 값과 같을 때만 새 값으로 바꾸는 원자 연산입니다.

```text
초기 상태: Pending
취소 요청: CAS(Pending → Cancelled)가 성공하면 취소 성공
만료 워커: CAS(Pending → Running)가 성공한 워커만 콜백 실행
           콜백 종료 후 Done으로 정리
```

취소가 먼저 성공하면 실행권을 얻을 수 없으므로 콜백이 실행되지 않습니다. 반대로 워커가 먼저 실행권을 얻었다면 콜백 본문을 아직 시작하지 않았어도 취소는 ‘너무 늦음’으로 처리합니다. **이 계약은 ‘취소 함수가 반환하면 무조건 콜백이 없다’가 아니라, ‘취소 전이가 성공한 경우 미실행을 보장한다’는 뜻**입니다. 반환 후 실행 중인 콜백까지 없어야 하는 API라면 별도의 완료 대기가 필요하며, 콜백이 자기 자신을 기다려 교착하지 않도록 해야 합니다. 타이머 객체를 재사용한다면 세대 번호와 상태를 같은 동기화 규칙으로 검사하고, 관련 참조가 끝나기 전에 메모리를 반환하지 않겠습니다.

경과 시간은 단조 시계를 사용하고, 프로세스가 오래 멈췄다가 돌아온 경우 만료를 모두 즉시 실행할지 합쳐 처리할지 정합니다. 검증은 등록·취소·시간 점프·만료 폭주에서 지연, 메모리, 콜백 중복을 확인하겠습니다.

## 득점 포인트

- 정밀도·삽입·삭제 비용으로 힙과 휠을 비교한다.
- 취소와 실행권 획득을 같은 락 또는 CAS 상태 전이로 보호하고, 취소 성공과 이미 실행권을 얻은 상태의 계약을 구분한다.
- 동시 만료를 찾는 비용과 콜백 실행 예산을 분리한다.
- 단조 시계와 중단 후 만료 정책을 명시한다.

## 감점 포인트

- 타이밍 휠이면 모든 연산이 항상 상수 시간이라고 단정한다.
- 타이머 개수만으로 성능을 판단한다.
- 취소 플래그를 원자적으로 읽기만 하면 이후 콜백이 실행되지 않는다고 말한다. 확인과 실행 사이에 취소가 완료될 수 있으므로 실행권 획득과 경쟁시켜야 한다.
- 벽시계로 경과 시간을 재어 시각 조정 영향을 무시한다.

## 더 파고들 거리

- 계층형 타이밍 휠은 긴 만료를 어느 버킷에 보관하나요?
- 취소와 실행이 경합할 때 정확히 한 번의 콜백을 어떻게 정의하나요?
- 같은 시각에 몰린 재시도 타이머를 어떻게 분산하나요?
