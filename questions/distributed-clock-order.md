# 두 서버의 이벤트를 timestamp로 정렬했더니 나중에 일어난 변경이 먼저 보입니다. 서버 시각만으로 변경 적용 순서를 정해도 되나요?

## 구두 답변

여러 서버의 벽시계는 완전히 같지 않고 조정 과정에서 흐름이 달라질 수 있어, 시각만으로 인과관계를 판단하면 위험합니다. 늦게 일어난 이벤트의 타임스탬프가 더 작거나 같은 값이 생길 수 있습니다. 저는 사람이 보는 발생 시각과 변경 적용 순서를 정하는 값을 구분하겠습니다.

벽시계는 ‘몇 시 몇 분’처럼 현실 시각을 나타내는 시계이고, 단조 시계는 경과 시간을 재는 동안 뒤로 가지 않도록 제공되는 시계입니다. 서로 다른 서버의 벽시계에는 오차가 있을 수 있고, 단조 시계의 값도 서버끼리 직접 비교하는 전역 순서 번호는 아닙니다. 같은 계정의 변경 순서가 필요하면 저장하는 권위 지점에서 부여한 버전을 쓰는 편이 명확합니다.

같은 계정의 변경 순서라면 권위 있는 저장 지점에서 증가하는 버전을 부여하는 편이 명확합니다. 서로 다른 서버가 독립 변경하는 데이터라면 하나의 시각으로 덮어쓰기 전에 충돌을 어떻게 해석할지 정해야 합니다. 마지막 쓰기 우선 정책은 단순하지만 실제로 중요한 변경을 잃을 수 있습니다. 논리 시계는 인과관계 표현에 도움을 주지만 어떤 충돌을 병합할지는 업무 규칙이 필요합니다.

타임아웃이나 경과 시간은 벽시계 대신 단조 시계를 쓰겠습니다. 시간이 동기화되며 뒤로 움직여도 대기 시간이 늘거나 음수가 되는 것을 피하기 위해서입니다. 로그에는 사람이 비교할 시각과 요청·작업 ID, 버전을 같이 남겨 추적하겠습니다. 테스트는 시계 오차와 동시 변경을 재현해 순서 판단이 시각의 우연에 의존하지 않는지 확인하겠습니다. 시계 동기화를 잘 운영하는 것과 정합성의 유일한 근거로 삼는 것은 다른 선택입니다.

## 득점 포인트

- **표시 시각과 변경 적용 순서를 구분한다.** 시계 오차와 인과관계를 설명한다.
- **순서 부여 지점을 정한다.** 키별 버전과 충돌 정책을 사용한다.
- **경과 시간에 단조 시계를 쓴다.** 시간 조정의 영향을 피한다.

## 감점 포인트

- **NTP를 쓰면 서버 시각이 완전히 같다고 말한다.** 오차와 조정은 남는다.
- **최신 timestamp면 항상 올바른 상태라고 말한다.** 중요한 변경을 잃을 수 있다.
- **논리 시계가 모든 충돌을 자동 해결한다고 말한다.** 데이터 병합 규칙이 필요하다.
