# 에이전트가 링크와 인용을 붙였지만 결론이 원문과 다릅니다. 근거 있는 답변인지 무엇을 검증하나요?

## 구두 답변

인용 링크가 존재하는 것과 그 자료가 해당 주장을 뒷받침하는 것은 다릅니다. 답변의 주요 주장을 나누고 각 주장에 연결된 원문 구간·문서 버전·적용 조건을 확인하겠습니다. 모델이 자료를 읽었다는 표시보다 원문에서 어떤 사실을 얻었고 어디부터 해석인지 드러나야 합니다. 이를 근거에 연결된 생성, 즉 grounding의 관점에서 평가합니다.

### 주장과 근거를 일대일로 대조합니다

공식 문서가 '기능은 실험적이며 일부 클라이언트만 지원한다'고 했는데 답변이 '모든 에이전트의 표준 기능이다'라고 하면 링크가 맞아도 주장은 틀립니다. 버전·지원 범위·필수와 선택 기능의 차이를 보존해야 합니다. 수치도 모집단·실험 조건·날짜를 함께 읽고, 특정 벤치마크 결과를 일반적인 운영 성공률로 바꾸지 않습니다. 원문에 없는 인과관계를 여러 관찰의 단순 동시 발생에서 추론했다면 추정으로 표시합니다.

검색 도구가 제목과 짧은 요약만 반환했다면 그것만으로 본문의 세부 계약까지 확인했다고 보고하지 않습니다. 중요한 주장은 원문 해당 구간을 추가로 읽고, 읽지 못한 자료는 확인 한계를 밝힙니다. 서로 다른 문서가 같은 원문을 재인용하면 독립된 증거로 중복 계산하지 않습니다. 업데이트된 문서의 URL이 같아도 내용이 바뀔 수 있으므로 확인 날짜와 고정 버전 링크를 보존합니다.

### 없는 근거를 억지로 채우지 않습니다

근거를 찾지 못했을 때 미확인 상태를 허용해야 합니다. 인용 필드를 필수로 만들었다고 자료가 생기지는 않으며, 모델이 그럴듯한 URL·문서 ID를 만들 수 있습니다. 존재 검사는 코드로 수행하고, 주장과 구간의 관계는 규칙·모델 평가·사람 검토를 조합합니다. 모델 채점기도 원문을 잘못 해석할 수 있어 중요한 계약은 전문가 표본 검토로 보정합니다.

답변 평가에서는 인용의 정확성뿐 아니라 주요 주장 중 근거가 연결된 비율과 불필요한 인용을 구분합니다. 링크 열 개를 붙이고 가장 중요한 한 문장을 뒷받침하지 못하면 충분하지 않습니다. 삭제된 문서·접근 불가 자료·서로 다른 버전을 포함한 시험으로 실패 처리를 확인합니다. 실제 행동이 이어지는 에이전트라면 근거 있는 설명과 실행 권한도 별개입니다. 문서에 권장된 조치가 있다고 사용자가 그 변경을 승인한 것은 아니므로, 인용 검증 뒤에도 행동 승인 경계를 유지하겠습니다.

### 실행 사례로 확인합니다

숫자 비교에서는 단위와 분모를 명시합니다. '성공률 90%'가 전체 요청인지 도구가 정상 응답한 요청만인지에 따라 의미가 달라집니다. 두 자료가 다른 예산과 시도 수를 사용했다면 수치를 나란히 놓아 모델 우열을 확정하지 않습니다. 한 문장이 원문 두 곳의 조합에서 도출됐다면 직접 인용과 계산·해석을 구분하고 필요한 중간 과정을 설명합니다. 자동 검증기는 링크 상태와 문서 ID 존재를 쉽게 확인할 수 있지만 논리적 뒷받침은 더 어려우므로 중요한 주장만 골라 심층 검토할 수 있습니다. 답변 전체의 모든 단어에 인용을 붙이는 것보다 결정에 영향을 주는 핵심 주장을 정확히 연결하는 것이 우선입니다.

## 득점 포인트

- 링크 존재와 주장 뒷받침·주요 주장 커버리지를 나눠 확인한다.
- 원문 구간·버전·조건과 추정을 보존한다.
- 미확인 상태와 채점기의 한계를 허용한다.

## 감점 포인트

- 공식 링크를 붙이면 모든 결론이 사실이라고 한다.
- 검색 요약만 보고 원문 전체를 확인했다고 보고한다.
- 문서의 권장 행동을 사용자의 실행 승인으로 취급한다.
