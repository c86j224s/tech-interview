01

구두 답변

정의를 외우기보다, 원리와 조건을 연결해 설명해 보세요.

먼저 포트부터 닫으면 미완료 작업의 결과를 정상적으로 정리하는 경로를 잃을 수 있습니다. 저는 새 연결과 새 제출을 막고, 연결별 작업을 취소하거나 완료까지 기다린 뒤 워커를 종료하는 순서를 기본으로 하겠습니다. 포트 핸들 해제는 그 뒤의 자원 정리 단계입니다.

완료 포트는 결과를 전달하는 통로이고 워커는 그 통로에서 결과를 받아 자원을 정리하는 실행 흐름입니다. 통로부터 없애면 아직 끝나는 중인 작업을 정리하기 어렵습니다. 새 제출 차단 → 미완료 I/O 종료와 결과 회수 → 워커 종료 → 포트 정리라는 의존 순서를 먼저 세워야 합니다.

워커를 깨우기 위해 PostQueuedCompletionStatus로 종료 패킷을 넣을 수 있지만, 종료 패킷을 받았다는 이유만으로 아직 남은 작업을 버려서는 안 됩니다. 종료 조건을 전역 제출 차단과 미완료 작업 수에 연결하고, 사용자 패킷과 I/O 완료를 구분하는 규약을 두겠습니다. 워커 수만큼 패킷을 넣는 방식도 실제 소비와 종료 구조에 맞는지 검증해야 합니다.

완료를 처리하는 도중 다른 작업을 새로 제출하는 경로가 있다면 종료 상태에서 막혀야 합니다. 그렇지 않으면 drain이 끝나지 않습니다. 종료 제한 시간이 있어도 조기 메모리 해제를 안전한 취소로 착각하지 않겠습니다. 테스트는 유휴 워커, 수신 대기, 송신 진행, 취소 경합 상태에서 종료해 남은 작업과 핸들을 확인합니다. 핵심은 스레드가 끝났다는 것보다 종료 후 접근 가능한 컨텍스트가 더 이상 없는지입니다.

02

득점 포인트

이해가 드러나는 지점을 확인해 보세요.

  • 의존성 순서로 종료한다. 유입·제출·완료·워커·포트를 나눈다.
  • 종료 신호와 drain 조건을 구분한다. 사용자 패킷만으로 완료를 선언하지 않는다.
  • 재제출 경로를 막는다. 종료 상태의 새 작업을 통제한다.
03

감점 포인트

놓치기 쉬운 조건과 오해를 짚어 보세요.

  • 포트를 닫으면 모든 작업이 정리된다고 말한다. 수명과 완료 처리가 남는다.
  • 종료 패킷을 받으면 무조건 즉시 반환한다. 미완료 작업이 있을 수 있다.
  • 시간 초과면 버퍼를 강제 해제한다. 접근 경합을 만들 수 있다.
04

더 파고들 거리

하나 더 질문하며 이해의 범위를 넓혀 보세요.

  • 종료 중 오류 로깅이 다른 워커나 풀에 의존하면 어떤 순환이 생길까요?
  • GQCS 타임아웃과 종료 패킷 중 어느 방식으로 제어 루프를 만들까요?
  • 전역 작업 수와 연결별 작업 수를 어떻게 일관되게 집계할까요?

득점·감점 포인트는 학습용 자기 점검 기준이며, 특정 회사의 실제 채점표가 아닙니다.
