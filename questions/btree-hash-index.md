# 같은 값 찾기와 기간 조회가 모두 필요한 컬럼에 B+tree와 해시 인덱스 중 무엇을 선택하나요?

## 구두 답변

B+tree 인덱스는 키를 정렬된 경로로 유지하고 리프 노드가 인접한 키를 연결하거나 순서대로 탐색할 수 있게 합니다. 그래서 `id = 10` 같은 동등 검색뿐 아니라 `created_at >= 시작 AND created_at < 끝` 같은 범위 검색, 정렬된 결과의 일부, 값의 앞부분을 이용하는 조건에 활용할 수 있습니다. 인덱스에서 시작 위치를 찾은 뒤 필요한 범위만 연속으로 읽을 수 있다는 점이 핵심입니다.

해시 인덱스는 키에서 해시값을 계산해 버킷을 찾는 구조라 동등 비교에 맞습니다. 같은 해시가 나오는 충돌은 별도 비교로 확인해야 하므로 이상적인 경우에도 무조건 한 번에 끝난다고 말할 수 없고, 해시값에는 원래 키의 순서 정보가 없습니다. 따라서 `값이 특정 범위에 있다`, `앞으로 시작한다`, `ORDER BY`처럼 순서가 필요한 질의에는 일반적으로 적합하지 않습니다. 해시 인덱스가 모든 DBMS와 모든 저장 엔진에서 같은 범위로 제공되는 것도 아니므로 제품의 구현 계약을 확인해야 합니다.

결정할 때는 연산 종류만 보지 말고 실제 선택도와 반환량도 봅니다. 동등 검색이라도 거의 모든 행을 반환하면 인덱스에서 행을 하나씩 찾아가는 비용보다 테이블 스캔이 나을 수 있습니다. 반대로 범위가 좁고 정렬까지 제거할 수 있으면 B+tree가 유리합니다. 인덱스는 읽기만 빠르게 하는 것이 아니라 삽입·삭제·키 변경 때 유지 비용과 저장 공간을 추가하므로, 실행 계획과 실제 읽은 행 수를 확인해야 합니다.

실무에서는 기본 선택으로 B+tree를 검토하고, 범위나 순서가 전혀 필요 없으며 엔진이 해시의 이점을 분명히 보이는 좁은 동등 조회에서만 해시를 선택하겠습니다. 인덱스를 추가한 뒤 대표 데이터 분포와 쓰기 부하에서 계획이 안정적인지 검증하고, 특정 제품의 ‘O(1)’ 설명을 전체 질의 비용의 보장으로 오해하지 않겠습니다.

## 득점 포인트

- B+tree의 정렬·범위 스캔과 해시의 동등 비교 특화를 구분한다.
- 해시 충돌과 순서 정보 부재 때문에 범위·정렬 질의에 불리함을 설명한다.
- 선택도·반환량·쓰기 유지 비용을 실행 계획과 함께 판단한다.

## 감점 포인트

- 해시 조회가 이론상 O(1)이므로 모든 SQL 조건에서 B+tree보다 빠르다고 말한다.
- B+tree 인덱스가 있으면 항상 테이블 전체 스캔을 피한다고 단정한다.
- 인덱스 추가의 저장 공간과 쓰기 유지 비용을 성능 판단에서 제외한다.

## 더 파고들 거리

- 범위 조건과 ORDER BY가 함께 있는 질의에서 B+tree의 시작점과 스캔 구간을 그려 보세요.
- 해시 충돌이 많은 경우 검색 비용과 버킷 재구성 비용이 어떻게 변하는지 확인해 보세요.
- 사용 중인 DBMS가 해시 인덱스를 어떤 저장 엔진·연산·제약으로 지원하는지 공식 문서에서 찾아보세요.
