# CPU가 낮은데 요청이 느리면 어떻게 프로파일링하나요?

## 구두 답변

CPU가 낮다는 것은 계산을 많이 하지 않는다는 단서이지 여유 있게 처리한다는 뜻은 아닙니다. 락이나 연결 풀, 디스크, 외부 응답을 기다리느라 일을 못 할 수 있습니다. CPU 프로파일만 보면 이런 대기 시간이 잘 드러나지 않을 수 있어 실행 중 시간과 기다린 시간을 나눠 보겠습니다.

예를 들어 전체 코어 평균은 낮아도 단일 이벤트 루프 하나만 포화될 수 있습니다. 코어별 사용률과 이벤트 루프 지연을 확인해야 합니다. 여러 워커가 같은 락을 기다리는 상황이라면 락 소유자의 스택과 보유 시간을 보고, 외부 호출을 락 안에서 하는지 확인하겠습니다. DB 연결 대기라면 실제 쿼리 시간과 풀 보유 시간을 분리해야 합니다.

저는 요청 추적으로 느린 구간을 좁힌 뒤 off-CPU나 블록 프로파일, 스레드 덤프로 대기 원인을 찾겠습니다. 도구에 따라 현재 대기와 완료된 대기를 다르게 보여 준다는 점도 확인합니다. 원인을 찾은 뒤 스레드를 더 주는 대신 해당 공유 경계나 외부 지연을 줄이는 실험을 하겠습니다. 수정 전후 동일 부하에서 사용자 지연과 대기 분포가 줄어야 성공입니다. CPU 수치만 높아지거나 낮아진 것으로 판단하지 않겠습니다.

## 득점 포인트

- **낮은 CPU와 여유를 구분한다.** 대기와 단일 코어 포화를 본다.
- **관측 도구를 원인에 맞춘다.** 추적·블록·스택을 조합한다.
- **동일 부하의 지연으로 검증한다.** 자원 숫자만 목표로 삼지 않는다.

## 감점 포인트

- **CPU가 낮으니 서버는 정상이라고 말한다.** 막힌 작업이 있을 수 있다.
- **CPU 프로파일만으로 모든 지연을 찾는다.** 대기 시간을 놓칠 수 있다.
- **무조건 워커를 추가한다.** 공유 병목을 악화시킬 수 있다.

## 더 파고들 거리

- 락 소유자가 실제로 일하는 시간과 스케줄링되지 못한 시간을 어떻게 구분할까요?
- 샘플링 프로파일의 짧은 실행 누락은 어떤 해석 오류를 만들까요?
- 평균 코어 사용률이 단일 스레드 병목을 숨기는 경우를 어떻게 검출할까요?
