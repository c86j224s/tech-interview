# API의 평균 요청률과 순간 버스트를 제한할 때 고정 윈도우와 토큰 버킷을 어떻게 선택하나요?

## 구두 답변

고정 윈도우는 예를 들어 1분마다 카운터를 초기화해 구간당 최대 요청 수를 제한하는 단순한 방식입니다. 그러나 12:00:59에 한도만큼 보내고 12:01:00에 다시 한도만큼 보내면 실제 2초 안에 두 구간의 요청이 몰릴 수 있습니다. 토큰 버킷은 일정 속도로 토큰을 채우고 버킷 크기만큼 쌓아 두므로, 장기 평균은 제한하면서 허용한 크기의 짧은 버스트를 수용합니다.

따라서 사용자가 순간적으로 여러 API를 호출해도 되는 일반 업무 API에는 토큰 버킷이 더 자연스러울 수 있고, 엄격한 시간 구간 사용량이나 과금 정산에는 슬라이딩 윈도우나 고정 구간 집계가 더 설명하기 쉬울 수 있습니다. 요청마다 비용이 다르면 요청 수가 아니라 비용만큼 토큰을 차감해야 합니다. 동시성 제한이 필요한 작업은 속도 제한만으로 충분하지 않아 별도의 동시 실행 상한도 둡니다.

분산 환경에서는 사용자·IP·테넌트·API 키 중 어떤 키를 기준으로 할지 정하고, 모든 인스턴스가 한도를 공유해야 하는지 결정합니다. 공유 저장소는 전역 정확도를 높이지만 매 요청의 왕복과 저장소 장애를 추가합니다. 로컬 예산을 인스턴스별로 나누면 지연은 줄지만 인스턴스 수와 재배치에 따라 총 허용량이 변할 수 있습니다. 로그인 남용처럼 보안상 엄격해야 하는 제한과 일반 사용자의 과금 한도는 장애 시 fail-open/fail-closed 정책도 다를 수 있습니다.

거절 응답에는 재시도 시점이나 `Retry-After`를 넣고, 클라이언트가 지수 백오프를 사용하게 하겠습니다. 테스트는 윈도우 경계, 버스트, 키 편중, 인스턴스 증감, 저장소 장애에서 실제 허용량과 재시도 폭주를 확인합니다.

## 득점 포인트

- 평균률·버스트·동시성이라는 서로 다른 제한을 구분한다.
- 집계 키와 분산 정확도의 비용을 함께 비교한다.
- 거절 응답과 장애 시 정책까지 구체화한다.

## 감점 포인트

- 고정 윈도우가 모든 짧은 구간을 균일하게 제한한다고 말한다.
- 인스턴스별 한도가 전역 한도와 같다고 말한다.
- 요청을 거절하기만 하면 재시도 폭주도 해결된다고 말한다.

## 더 파고들 거리

- 요청별 비용이 다를 때 토큰을 어떻게 차감하나요?
- 제한 저장소 장애 시 fail-open과 fail-closed를 어떤 API별 기준으로 고르나요?
- 공유 IP 환경에서 로그인 제한의 오탐을 어떻게 줄이나요?
