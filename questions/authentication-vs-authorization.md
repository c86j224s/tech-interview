# 인증과 인가는 어떻게 다르고, 로그인한 사용자에게도 인가 검사가 필요한 이유는 무엇인가요?

## 구두 답변

인증은 요청한 사람이 누구인지 확인하는 것이고, 인가는 그 사람이 지금 이 자원에 이 작업을 해도 되는지 판단하는 것입니다. **로그인이 됐다는 것은 신원을 확인했다는 뜻이지, 모든 데이터에 접근해도 된다는 뜻은 아닙니다.**

예를 들어 로그인한 사용자가 주문 조회 API에 다른 사람의 주문 ID를 넣었다고 하겠습니다. 서버가 토큰만 확인하고 주문을 반환하면 로그인은 정상이어도 정보가 노출됩니다. 이런 객체 단위 접근 제어 누락을 BOLA라고 합니다. 저는 요청 주체는 검증된 인증 정보에서 가져오고, 주문의 소유자와 소속 테넌트, 조회 권한이 일치하는지 서버에서 확인하겠습니다. 사용자 ID를 요청 본문에서 받아 그대로 믿지는 않겠습니다.

권한을 관리할 때는 역할로 큰 범위를 나누고, 실제 자원에서는 소유권과 상태를 추가로 검사하는 방식부터 보겠습니다. 예를 들어 담당자는 주문을 수정할 수 있어도 자기 조직의 주문이어야 하고, 이미 정산된 주문은 수정할 수 없을 수 있습니다. 역할 기반 접근 제어인 RBAC만으로 끝내지 않고 이런 속성 기반 조건을 함께 사용하는 것입니다. 게이트웨이에서 역할을 확인하더라도 주문 상태를 아는 서비스의 검사까지 생략하지는 않겠습니다.

권한이 바뀐 뒤 언제부터 막을지도 정해야 합니다. JWT 안에 권한이 들어 있고 서명이 유효하더라도, 발급 후 관리자 권한을 회수했을 수 있습니다. 저는 민감도가 낮고 짧은 지연을 허용하는 조회라면 토큰 만료까지의 지연을 명시할 수 있다고 보겠습니다. 반면 관리자 삭제처럼 즉시 회수가 중요한 작업은 현재 세션이나 권한 상태를 다시 확인하겠습니다. 조회 비용과 해당 서비스에 대한 의존성이 생기지만, 그 작업에서는 안전성을 우선하는 것입니다.

테스트도 정상 사용자에게 허용되는지만 보지 않겠습니다. 같은 역할의 다른 사용자, 다른 테넌트, 권한 회수 직후의 요청을 보내서 실제로 거절되는지 확인하겠습니다. **인증 성공 여부뿐 아니라 누구의 어떤 자원을 어떤 시점의 권한으로 판단했는지**가 남아야 합니다. 그래야 문제가 생겼을 때 정책이 잘못됐는지, 검사가 빠졌는지 구분할 수 있습니다.

## 득점 포인트

- **인증과 자원별 인가를 구분한다.** 다른 사용자의 주문을 조회하는 사례로 신원 확인만으로 부족한 이유를 설명한다.
- **역할과 자원 조건을 함께 적용한다.** 테넌트·소유자·주문 상태를 어디에서 검사할지 정한다.
- **권한 회수 요구에 따라 방식을 선택한다.** 만료까지 허용할 지연과 현재 상태 재조회 비용을 작업별로 비교한다.
- **거절 사례로 검증한다.** 교차 사용자·테넌트·회수 직후의 요청과 판단 근거 기록을 확인한다.

## 감점 포인트

- **“서명이 유효한 토큰이면 모든 권한도 최신이다”라고 말한다.** 발급 이후의 권한 회수가 반영되지 않을 수 있다.
- **“관리자 역할만 확인하면 충분하다”고 말한다.** 조직 범위와 자원 상태 같은 제약은 별도로 필요할 수 있다.
- **“게이트웨이가 검사하므로 내부 서비스는 믿어도 된다”고 말한다.** 우회 경로와 자원별 조건을 집행할 경계가 필요하다.
- **“클라이언트가 보낸 사용자 ID로 권한을 확인한다”고 말한다.** 요청 주체의 신원은 조작 가능한 입력이 아닌 검증된 인증 정보에서 얻어야 한다.

## 더 파고들 거리

- 권한 검사 뒤 실제 변경 전에 소유권이나 상태가 바뀌는 TOCTOU 문제는 어떻게 막을까요?
- 정책 결정과 집행을 PDP·PEP로 분리하면 지연·장애·정책 배포 책임은 어떻게 달라질까요?
- 사용자 대신 호출하는 서비스가 자기 권한을 잘못 사용하지 않도록 위임 범위를 어떻게 표현할까요?
- 장시간 작업 중 권한이 회수되면 시작 시점 권한을 인정할지 실행 중 다시 검사할지 어떻게 결정할까요?
