# 인증과 인가는 어떻게 다르고, 로그인한 사용자에게도 인가 검사가 필요한 이유는 무엇인가요?

## 구두 답변

인증은 요청한 주체가 누구인지 확인하는 과정이고, 인가는 그 주체가 특정 자원에 특정 작업을 해도 되는지 판단하는 과정입니다. 로그인에 성공했다는 것은 신원을 확인했다는 뜻이지, 서비스의 모든 데이터에 접근할 권한을 얻었다는 뜻은 아닙니다.

예를 들어 로그인한 사용자가 주문 조회 API에 주문 ID를 보낸다고 하겠습니다. 서버가 세션이나 토큰의 유효성만 확인하고 해당 주문을 반환하면, 다른 사람의 주문 ID를 보낸 경우에도 정보가 노출될 수 있습니다. 요청자가 그 주문의 소유자인지, 해당 조직의 담당자인지, 관리 권한이 있는지 같은 자원 단위의 조건을 추가로 확인해야 합니다.

인가 판단에는 주체, 자원, 행동, 필요한 환경 조건이 들어갑니다. 같은 문서라도 읽기와 삭제 권한이 다를 수 있고, 같은 사용자라도 조직이나 테넌트에 따라 권한이 달라질 수 있습니다. 역할 기반 접근 제어는 역할에 권한을 묶어 관리하기 편하고, 속성 기반 접근 제어는 소유자나 조직, 자원 상태 같은 조건을 세밀하게 표현할 수 있습니다. 실제로는 둘을 함께 쓰는 경우도 많습니다.

검사는 서버의 신뢰할 수 있는 경로에서 수행해야 합니다. 화면에서 버튼을 숨기거나 클라이언트가 보낸 사용자 ID를 믿는 것으로는 충분하지 않습니다. 요청자의 신원은 검증된 인증 정보에서 가져오고, 자원과 작업에 필요한 권한을 확인해야 합니다. 원칙적으로 명시적으로 허용된 경우만 통과시키는 편이 안전합니다.

권한 변경의 반영 시점도 중요합니다. 토큰이나 캐시에 권한을 오래 담아 두면 이미 회수한 권한이 계속 사용될 수 있습니다. 작업의 민감도에 따라 만료 시간, 현재 권한 재확인, 세션 폐기 같은 방식을 정해야 합니다. 결국 인증은 인가 판단의 입력을 제공하는 과정이며, 실제 접근 가능 여부는 자원과 행동별로 별도로 결정해야 합니다.

## 득점 포인트

- **신원 확인과 권한 판단을 구분한다.** 로그인 성공만으로 모든 작업이 허용되는 것은 아니라고 설명한다.
- **자원 단위의 검사를 구체적으로 설명한다.** API 접근 가능 여부뿐 아니라 소유자와 테넌트, 작업 종류까지 고려한다.
- **신뢰 경계를 명확히 한다.** 클라이언트 입력 대신 검증된 인증 정보에서 요청 주체를 식별한다.
- **권한의 수명까지 고려한다.** 권한 회수와 토큰·캐시의 만료 사이에 생기는 지연을 설명한다.

## 감점 포인트

- **“유효한 토큰이 있으면 인가도 끝났다”고 말한다.** 토큰 검증 이후에도 대상 자원과 행동에 필요한 권한을 확인해야 한다.
- **“클라이언트에서 버튼을 숨기면 접근을 막을 수 있다”고 말한다.** UI와 별개로 서버에서 모든 보호된 요청을 검증해야 한다.
- **“요청 본문의 사용자 ID를 기준으로 권한을 확인하면 된다”고 말한다.** 요청자가 임의로 바꿀 수 있는 값은 신원의 근거가 될 수 없다.
- **“관리자 역할만 확인하면 충분하다”고 일반화한다.** 테넌트 경계, 위임 범위, 자원별 제한을 별도로 확인해야 할 수 있다.

## 더 파고들 거리

- API 게이트웨이의 인증 검사와 개별 서비스의 인가 검사는 어떤 책임으로 나누는 것이 좋을까요?
- 권한을 즉시 회수해야 한다면 자체 포함 토큰과 서버 측 세션은 어떤 차이가 있을까요?
- 권한 검사 이후 실제 변경 전에 자원의 소유자나 상태가 바뀌면 어떻게 처리해야 할까요?
- 사용자 대신 동작하는 서비스가 자신의 권한과 사용자의 권한을 혼동하지 않게 하려면 어떻게 설계해야 할까요?
