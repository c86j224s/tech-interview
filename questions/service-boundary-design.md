# 주문·결제·재고 테이블을 각각 서비스로 나누자는 제안이 나왔습니다. 어떤 변경은 함께 확정해야 하는지와 데이터 소유권을 기준으로 경계를 어떻게 검토하나요?

## 구두 답변

서비스 경계는 기능이나 테이블을 같은 개수로 쪼개는 문제가 아니라, 어떤 업무 규칙과 데이터를 한 팀이 책임지고 어떤 변경을 독립적으로 배포할지 정하는 문제입니다. 함께 지켜야 하는 불변식이 자주 같은 트랜잭션으로 바뀐다면 같은 경계에 두는 편이 단순합니다. 반대로 별도 보안 권한, 운영 책임, 확장 패턴이 명확하면 분리의 이점이 생깁니다.

예를 들어 계정의 신원 정보와 인증 자격은 책임이 다를 수 있지만, 로그인마다 계정 서비스의 여러 작은 API를 순서대로 호출해야 한다면 지연과 장애 의존성이 커집니다. 다른 서비스가 상대 DB를 직접 읽지 않도록 API나 이벤트로 공개 계약을 만들되, 그 계약 때문에 한 요청의 처리가 여러 저장소를 동시에 바꿔야 한다면 saga·비동기 일관성·보상 비용까지 포함해 판단합니다.

초기에는 모듈 경계를 먼저 강하게 만들고, 실제 변경 빈도·부하·팀 소유권·장애 전파를 관찰한 뒤 프로세스 분리를 늦출 수 있습니다. 반대로 결제 자격처럼 격리된 권한이나 별도 규제 책임이 필요한 영역은 운영 요구 때문에 일찍 분리할 수 있습니다. 서비스 수와 독립 배포 가능성만으로 좋은 경계를 판정하지 않겠습니다.

검증 지표는 호출 왕복 수, 공동 변경 비율, 분산 트랜잭션·보상 수, 장애 전파 범위, 배포 때 함께 건드리는 코드입니다. 분리 뒤 이 지표가 악화되고 소유권이 불명확해지면 서비스를 다시 합치는 것도 합리적인 선택입니다.

## 득점 포인트

- 불변식과 데이터 소유권을 경계의 출발점으로 둔다.
- 분리의 통신·분산 변경·장애 전파 비용을 설명한다.
- 모듈에서 서비스로 점진적으로 분리하고 되돌릴 지표를 제시한다.

## 감점 포인트

- 기능이나 테이블마다 하나의 서비스를 만든다.
- 조직 이름이 곧 데이터 소유권이라고 말한다.
- 독립 배포만 가능하면 좋은 경계라고 판단한다.

## 더 파고들 거리

- 데이터 소유권을 이전할 때 직접 DB 조회를 어떤 API·이벤트로 바꾸나요?
- 공유 라이브러리가 배포 독립성을 깨는 조건은 무엇인가요?
- 서비스를 다시 합치는 것을 고려할 운영 신호는 무엇인가요?
