# 마이크로서비스의 경계는 어떤 기준으로 나누나요?

## 구두 답변

저는 테이블이나 기능 개수보다 함께 바뀌어야 하는 규칙과 독립적으로 소유할 책임을 보겠습니다. 서비스로 나누면 배포와 확장을 독립시킬 수 있지만, 같은 업무를 위해 계속 왕복하고 여러 저장소를 함께 바꿔야 한다면 분리 비용이 더 클 수 있습니다.

계정과 인증을 나누는 경우 계정의 신원 속성 관리와 자격 검증은 서로 다른 책임일 수 있습니다. 하지만 인증 요청마다 계정 서비스의 여러 작은 API를 순서대로 호출해야 한다면 지연과 장애 의존성이 커집니다. 저는 어떤 불변식을 같은 트랜잭션에 두어야 하는지, 상대의 데이터를 어떤 계약으로 읽어도 되는지 정하겠습니다. 조직 이름이 바뀌었다는 이유만으로 데이터 소유권까지 바로 쪼개지는 것은 아닙니다.

불확실한 초기 단계에는 모듈 경계를 먼저 명확히 두고, 실제 변경 빈도와 부하·장애 요구가 확인되면 서비스로 분리할 수 있습니다. 반대로 별도 보안 권한과 운영 책임이 필요한 경계는 일찍 분리할 이유가 있습니다. 판단은 배포 독립성뿐 아니라 호출 수, 동시 변경 비율, 장애 전파 범위로 검증하겠습니다. 작은 서비스가 많다는 것보다 한 서비스를 바꿀 때 다른 서비스를 얼마나 덜 건드릴 수 있는지가 중요합니다.

## 득점 포인트

- **불변식과 소유권으로 나눈다.** 테이블 수와 서비스 수를 동일시하지 않는다.
- **분리의 통신 비용을 설명한다.** 왕복·분산 변경·장애 의존성을 본다.
- **점진적인 경계 검증을 제안한다.** 모듈과 서비스 분리를 구분한다.

## 감점 포인트

- **기능마다 하나의 서비스를 만든다.** 과도한 분산 비용이 생긴다.
- **조직 경계가 곧 데이터 경계라고 말한다.** 업무 불변식이 다를 수 있다.
- **독립 배포만 가능하면 좋은 경계라고 말한다.** 실제 공동 변경과 호출 의존성을 봐야 한다.

## 더 파고들 거리

- 데이터 소유권을 바꿀 때 직접 DB 조회를 어떤 API나 이벤트로 대체할까요?
- 공유 라이브러리가 서비스들의 배포 독립성을 해치는 경우는 무엇인가요?
- 서비스를 다시 합치는 것이 합리적인 신호는 무엇일까요?
