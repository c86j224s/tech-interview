# 여러 프로세스가 같은 파일에 주문을 저장할 때 생기는 문제를 DBMS는 어떤 책임으로 해결하나요?

## 구두 답변

파일에 직접 저장하는 방식과 DBMS의 차이는 단순히 저장 위치가 아니라, 여러 요청이 데이터를 다루는 책임을 어디에서 맡느냐에 있습니다. 여러 프로세스가 같은 파일을 읽고 각자 수정한 뒤 덮어쓰면 마지막 쓰기가 앞선 변경을 잃게 만들 수 있습니다. 한 프로세스가 쓰는 중 다른 프로세스가 부분적으로 읽으면 손상된 형식을 볼 수도 있고, 주문과 결제처럼 여러 파일을 함께 바꾸는 작업이 중간에 멈추면 일부만 반영됩니다. 파일 잠금과 임시 파일 교체로 일부 문제를 줄일 수 있지만, 잠금 규칙과 복구 코드를 모든 애플리케이션이 일관되게 지켜야 합니다.

DBMS도 내부적으로 파일을 사용하지만, 그 위에 동시 실행을 조정하는 트랜잭션과 잠금 또는 버전 관리, 장애 뒤 복구를 위한 로그, 기본키·외래키·고유값 같은 제약, 조건에 맞는 행을 찾는 질의 처리 기능을 제공합니다. 애플리케이션은 “재고가 남아 있을 때만 차감한다” 같은 규칙을 트랜잭션과 제약으로 데이터 저장 계층에 맡길 수 있고, 여러 요청의 실행 순서가 달라도 정해진 일관성 경계를 얻습니다. 인덱스와 질의 최적화기는 데이터를 전부 직접 순회하지 않도록 실행 방법도 선택합니다.

다만 DBMS가 모든 업무 규칙을 자동으로 알아내는 것은 아닙니다. 어떤 범위에서 이름이 유일한지, 주문과 결제의 원자적 경계가 어디인지는 스키마와 트랜잭션을 설계해야 합니다. 또한 단일 프로세스의 설정 파일이나 한 번 쓰고 읽는 대용량 파일처럼 동시 갱신과 복잡한 질의가 없는 경우에는 파일이 더 단순하고 저렴할 수 있습니다. 반대로 여러 요청이 같은 데이터를 수정하거나 부분 실패 복구와 검색 조건이 중요해지면 파일 잠금을 계속 확장하기보다 DBMS에 책임을 모으는 편이 안전합니다.

## 득점 포인트

- 동시 파일 갱신의 lost update와 부분 반영 문제를 DBMS의 트랜잭션 책임과 연결한다.
- DBMS가 파일을 대체하는 것이 아니라 제약·복구·질의 처리 계층을 추가한다는 점을 구분한다.
- 동시 갱신과 질의 요구가 없는 경우에는 파일이 적합할 수 있다는 선택 기준을 제시한다.

## 감점 포인트

- 파일 하나를 원자적으로 교체하면 여러 파일에 걸친 작업도 원자적이라고 단정한다.
- DBMS를 사용하면 기본키나 업무 불변식이 설계 없이 자동으로 보장된다고 말한다.
- 파일은 항상 느리고 DBMS는 항상 빠르다고 저장 형식만으로 성능을 단정한다.

## 더 파고들 거리

- 파일 잠금만으로 여러 프로세스의 트랜잭션과 장애 복구를 구현할 때 필요한 로그·복구 절차를 비교해 보세요.
- DBMS의 격리 수준이 동시 읽기와 쓰기의 관찰 결과를 어떻게 바꾸는지 설명해 보세요.
- 단일 파일 저장소에서 DBMS로 이전할 때 중복 쓰기와 검증을 이용해 중단 없이 전환하는 방법을 생각해 보세요.
