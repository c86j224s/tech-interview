# SQS 메시지를 처리하는 동안 visibility timeout이 지나 다른 워커도 같은 메시지를 받았습니다. 기존 작업은 중단되며 중복 반영과 메시지 삭제는 어떻게 처리하나요?

## 구두 답변

SQS에서 메시지를 수신하면 visibility timeout 동안 다른 소비자에게 그 메시지가 보이지 않도록 숨깁니다. 이것은 첫 소비자의 코드를 중단하거나 처리 결과를 저장하는 DB의 행을 배타적으로 잠그는 기능이 아닙니다. 워커가 계속 실행 중이어도 시간이 지나면 메시지가 다시 전달될 수 있으므로, 중복 소비를 정상적인 가능성으로 설계해야 합니다.

처리 시간의 p99와 장애 복구 목표를 보고 기본 timeout을 정하고, 긴 작업은 heartbeat 방식으로 visibility를 연장합니다. 연장 요청 자체가 실패할 수 있으므로 연장만 믿지 않습니다. 처리 결과를 저장하는 DB에 결과를 내구적으로 반영한 뒤 메시지를 삭제하고, 삭제 응답이 유실돼 같은 메시지가 다시 오더라도 요청 ID나 이벤트 ID로 같은 효과를 한 번만 적용하게 합니다. 수신 시도의 `receipt handle`은 삭제에 쓰는 임시 식별자이지 원래 작업의 고유 ID가 아닙니다.

Standard 큐는 순서와 중복이 강하게 보장되지 않고, FIFO도 지정된 범위의 순서·중복 제거 계약이지 외부 DB 효과의 정확히 한 번 실행을 보장하는 것은 아닙니다. 반복 실패 메시지는 DLQ로 보내고 원인과 원래 작업 ID를 보존해야 안전하게 재처리할 수 있습니다. timeout을 너무 길게 잡으면 워커가 죽었을 때 재전달이 늦어지고, 너무 짧으면 정상 작업과 경쟁하는 중복이 늘어납니다.

테스트는 처리 시간 초과, 연장 실패, DB 커밋 직후 삭제 응답 유실, 워커 중단, FIFO message group 핫키를 재현해 중복 효과와 복구 시간을 확인하겠습니다.

## 득점 포인트

- 메시지 숨김과 워커 실행·DB 잠금을 구분한다.
- 처리→내구 반영→삭제 순서와 멱등성을 설명한다.
- 큐 종류·receipt handle·DLQ의 범위를 구분한다.

## 감점 포인트

- timeout이 끝나면 실행 중 워커가 자동 중단된다고 말한다.
- FIFO면 외부 DB 효과도 자동으로 한 번이라고 말한다.
- 처리 결과 반영보다 메시지 삭제를 먼저 한다.

## 더 파고들 거리

- visibility timeout을 너무 길게 잡을 때 장애 복구가 늦어지는 이유는 무엇인가요?
- FIFO message group이 핫키 병목이 되는 조건은 무엇인가요?
- DLQ 재주입 시 원래 순서를 보존해야 하는 작업을 어떻게 처리하나요?
