# Kubernetes의 일부 컨테이너는 OOMKilled로 재시작하고 다른 컨테이너는 살아 있지만 느립니다. 메모리 종료와 CPU 제한을 어떻게 구분하나요?

## 구두 답변

OOMKilled는 메모리 한도나 압력과 관련해 프로세스가 종료된 상황을 조사할 단서이고, CPU throttling은 CPU 제한 때문에 실행 시간을 못 받는 현상입니다. 둘 다 지연·오류를 만들 수 있지만 메모리를 늘리는 것과 CPU 정책을 바꾸는 것은 다른 대응입니다.

OOMKilled는 메모리 부족이나 제한으로 프로세스가 종료됐는지 조사할 단서입니다. CPU throttling은 실행 시간을 제한받는 현상이라 프로세스는 살아 있어도 요청이 늦어질 수 있습니다. 컨테이너에 설정한 자원 상한인 limit와 실제 사용·제한 지표를 비교해 두 원인을 나눠야 합니다.

재시작이 증가하면 종료 사유와 이벤트, 한도 근처의 메모리 피크를 먼저 보겠습니다. 평균은 낮아도 큰 요청이나 GC·백그라운드 저장 때 순간적으로 넘을 수 있습니다. CPU가 한도 근처에서 제한되면 살아 있는 프로세스가 응답만 늦어질 수 있어 throttled 시간과 애플리케이션 대기를 비교해야 합니다.

저는 OOM에 무조건 재시작 횟수만 늘리지 않고 실제 생존 데이터와 동시 요청 메모리를 줄일 수 있는지 보겠습니다. throttling이라면 limit·request와 노드 경쟁을 확인해 조정하되 공유 환경의 격리 정책을 무시하지 않겠습니다. 테스트는 메모리 피크와 CPU 지속 부하를 분리합니다. 자원 숫자 변경의 성공은 재시작 감소뿐 아니라 정상 지연과 노드 전체 안정성으로 검증해야 합니다.

## 득점 포인트

- 종료와 실행 지연을 구분한다.
- 평균 외 피크·제한 시간을 관측한다.
- 컨테이너와 노드 전체 영향을 함께 본다.

## 감점 포인트

- 재시작은 모두 코드 크래시라고 말한다.
- CPU 한도 초과도 항상 프로세스를 죽인다고 말한다.
- limit를 없애는 것이 모든 환경의 정답이라고 말한다.
