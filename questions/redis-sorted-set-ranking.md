# Redis sorted set 랭킹에서 동점 정렬, 점수 정밀도, 중복 갱신을 어떻게 안정적으로 처리하나요?

## 구두 답변

Redis sorted set은 멤버별 점수로 정렬하고 점수가 같으면 멤버의 바이트 순서를 사용합니다. 따라서 ‘먼저 달성한 사용자 우선’ 같은 서비스 규칙은 삽입 순서에 맡기지 말고 별도의 결정적 비교 키로 표현해야 합니다. 점수에 시각과 보조 순위를 한 부동소수점 값으로 합치려면 정밀도 범위를 먼저 계산하고, 재전달되는 이벤트는 `ZINCRBY`만으로 처리하지 않겠습니다.

### 중복 갱신과 확정 집계를 보호합니다

같은 점수의 A와 B가 sorted set에 들어갔다고 해서 먼저 들어간 A가 자동으로 앞선다고 할 수 없습니다. 조회 방향에 따라 점수 순서가 뒤집히고, 동점자 사이에서는 멤버의 바이트 사전식 순서가 적용됩니다. 가입 시각·달성 시각·사용자 ID가 필요한 랭킹이라면 `(점수 내림차순, 달성 시각 오름차순, 사용자 ID)` 같은 전체 정렬 규칙을 서비스 계약으로 정합니다. 이를 **결정적 타이브레이커**(deterministic tie-breaker)라고 부릅니다.

점수와 시각을 하나의 큰 실수에 이어 붙이는 방식은 간단해 보여도 Redis가 표현 가능한 정밀도와 최대 정수 범위를 넘을 수 있습니다. 점수가 커질수록 작은 시각 차이가 같은 값으로 반올림되면 동점 규칙이 무너집니다. 최대 점수, 타임스탬프 범위, 구별해야 하는 최소 간격을 계산해 실제 저장·조회 결과를 확인하겠습니다. 범위가 안전한 정수 인코딩을 쓰거나 점수와 보조 키를 별도 구조에서 관리하는 대안도 있습니다.

### 중복 이벤트와 확정 버전을 보호합니다

`ZINCRBY`는 같은 이벤트를 두 번 받으면 두 번 더합니다. 네트워크 재시도나 소비자 재전달이 있으면 점수가 부풀 수 있으므로 이벤트 ID 처리 원장을 두고 점수 변경과 원장 기록을 원자적으로 묶거나, 이벤트 버전이 더 최신일 때만 절대 점수를 반영하겠습니다. Redis 한 곳에서 원자 스크립트를 사용해도 외부 DB와의 변경까지 자동으로 하나의 트랜잭션이 되는 것은 아닙니다.

화면은 현재 sorted set을 읽어도 되지만 보상은 변하는 자료구조를 직접 기준으로 삼지 말고 마감 집계 버전을 봉인한 뒤 계산합니다. 테스트는 대규모 동점, 최대 점수, 정밀도 경계, 중복·지연 이벤트, 오름차순·내림차순 조회를 포함합니다. 화면 순서와 지급 대상이 같은 비교 규칙을 사용하는지 독립 계산으로 확인하고, 갱신 지연과 메모리도 측정하겠습니다.

동점 규칙을 score에 합칠지 member에 인코딩할지는 범위 질의와 표시 API로 결정하겠습니다. 안전한 정수 범위를 넘는 합성 score는 작은 시간 차이를 같은 값으로 만들 수 있습니다. score를 실제 점수로 유지하고 동점 키를 별도 인덱스로 두면 조회는 명확하지만 갱신 일관성과 병합 비용이 늘어납니다.

이벤트 원장을 Redis에만 두면 만료·복제·장애 복구에서 중복 방지 기록이 사라질 수 있습니다. 보상처럼 되돌릴 수 없는 변경은 내구성 있는 원장과 확정 버전을 기준으로 하고 Redis는 표시용으로 제한하겠습니다. 정밀도 경계·중복 재전달·역방향 조회·외부 DB와의 원자성 경계를 독립 테스트합니다.

score 인코딩을 선택할 때는 음수 점수와 조회 방향도 함께 계산해야 합니다. 달성 시각을 뒤집어 저장하면 역순 조회에서 원하는 순서가 나올 수 있지만, 변환 경계를 잘못 잡으면 오래된 사용자가 앞서는 반례가 생깁니다. 이벤트 ID 원장 기록과 점수 갱신은 같은 원자적 경계에서 함께 수행해야 중간 실패의 중복·누락을 막을 수 있습니다. Redis를 빠른 현재 상태로 쓰고 내구성 원장을 권위 데이터로 둔다면 재구축 절차가 필요하며, 재구축 중 화면이 어느 세대를 읽는지도 응답 메타데이터로 드러내겠습니다.

역순 랭킹에서 높은 점수가 먼저이고 동점이면 달성 시각이 빠른 사용자가 먼저라면 두 정렬 방향이 다릅니다. member를 시각 오름차순 그대로 넣으면 역순 조회에서 늦은 시각이 앞설 수 있습니다. 고정 폭과 범위가 있는 역변환 키를 쓰거나 동점 그룹을 별도 정렬해야 하며, 최대 시각·동일 시각·ID 동률을 포함해 비교자를 시험하겠습니다.

## 득점 포인트

- Redis의 기본 동점 순서와 서비스가 요구하는 결정적 타이브레이커를 구분한다.
- 부동소수점 정밀도·범위·인코딩 검증을 랭킹 정확성과 연결한다.
- 증분 갱신 중복 방지와 마감 집계 버전의 필요성을 설명한다.

## 감점 포인트

- 같은 점수에서 삽입 순서가 자동 보장된다고 말한다.
- 임의의 큰 정수를 score에 넣어도 항상 정확하다고 단정한다.
- `ZINCRBY` 재시도가 멱등적이라고 말한다.
