01

구두 답변

정의를 외우기보다, 원리와 조건을 연결해 설명해 보세요.

일부는 줄지만 모든 선두 지연이 없어지는 것은 아닙니다. HTTP/2는 한 연결에서 여러 스트림의 프레임을 섞어 보낼 수 있어, HTTP/1.1 파이프라이닝의 응답 순서 제약을 줄입니다. 하지만 아래에는 순서 있는 TCP 바이트 스트림이 있어서 패킷 손실의 영향은 여러 스트림에 걸칠 수 있습니다.

예를 들어 뒤쪽 패킷이 도착해도 앞쪽 바이트가 빠졌다면 TCP는 그 구간이 채워질 때까지 애플리케이션에 순서대로 전달하지 못합니다. 서로 다른 HTTP/2 요청의 데이터도 같은 연결에 실려 있다면 함께 지연될 수 있습니다. 저는 느린 요청 하나 때문인지 패킷 손실과 재전송 때문인지 나눠 보겠습니다. 서버 핸들러 지연만 줄여도 해결되지 않는 이유입니다.

HTTP/3의 QUIC은 스트림별 전달을 분리해 이런 전송 계층의 영향 일부를 줄이지만, 연결의 혼잡 제어나 공통 자원 한계는 여전히 공유됩니다. 따라서 새 프로토콜이면 무조건 빨라진다고 보지 않겠습니다. 손실이 있는 실제 경로에서 작은 요청과 큰 응답을 섞어 응답 분포를 비교하고, 서버 CPU와 네트워크 지원 환경도 확인하겠습니다. 프로토콜 다중화와 애플리케이션의 작업 큐 공정성은 별개라서 서버 내부의 긴 작업이 짧은 작업을 막는지도 함께 봐야 합니다.

02

득점 포인트

이해가 드러나는 지점을 확인해 보세요.

  • 계층별 선두 지연을 구분한다. 응답 순서와 TCP 전달 순서를 나눈다.
  • 손실의 실행 과정을 설명한다. 빠진 바이트가 여러 스트림 전달에 영향을 줌을 짚는다.
  • 프로토콜 비교 조건을 정한다. 실제 손실·워크로드·CPU를 함께 본다.
03

감점 포인트

놓치기 쉬운 조건과 오해를 짚어 보세요.

  • HTTP/2에는 선두 지연이 전혀 없다고 말한다. TCP 계층의 제약이 남는다.
  • QUIC은 모든 스트림이 완전히 독립이라고 말한다. 공통 혼잡·자원 제한은 남는다.
  • 프로토콜 교체로 내부 작업 큐도 해결된다고 말한다. 서버 실행 경로는 별도다.
04

더 파고들 거리

하나 더 질문하며 이해의 범위를 넓혀 보세요.

  • 스트림별 흐름 제어와 연결별 흐름 제어는 어떻게 상호작용할까요?
  • 큰 다운로드와 짧은 RPC를 같은 연결에 섞을 때 공정성을 어떻게 측정할까요?
  • QUIC 연결 이동과 재연결은 어떤 차이가 있나요?
