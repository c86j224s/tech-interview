# AcceptEx로 연결 수락을 미리 요청했습니다. 클라이언트는 연결됐는데 왜 완료가 늦을 수 있고, 완료 뒤 소켓은 어떻게 초기화하나요?

## 구두 답변

AcceptEx는 미리 준비한 소켓과 버퍼로 연결 수락을 중첩 I/O로 요청할 수 있는 Winsock 확장입니다. 워커가 연결마다 블로킹 accept를 하는 대신 여러 수락을 미리 걸어 두고 완료로 처리할 수 있습니다. 주소 정보와 선택적인 초기 데이터 수신도 함께 다루므로 버퍼 형식과 완료 조건을 확인해야 합니다.

AcceptEx는 Windows에서 새 연결 수락을 비동기로 제출하는 함수입니다. accept용 소켓과 결과 버퍼를 애플리케이션이 준비합니다. 여기서 초기 수신 길이는 연결 직후 함께 기다릴 데이터 양과 관련됩니다. 연결만 하고 말을 보내지 않는 클라이언트는 이 조건 때문에 수락 완료를 늦출 수 있습니다.

특히 초기 수신 길이를 0보다 크게 요청하면 연결만 됐다고 바로 완료되지 않고 데이터 도착을 기다릴 수 있습니다. 저는 빠른 연결 수락이 목적이라면 이 설정을 명확히 선택하겠습니다. 완료 후에는 SO_UPDATE_ACCEPT_CONTEXT로 수락 소켓의 문맥을 갱신하고, 주소 버퍼는 전용 해석 함수를 사용해 읽겠습니다. 수락한 소켓의 IOCP 연결과 이후 수신 제출도 별도로 준비해야 합니다.

미리 걸어 둔 수락 수가 부족하면 순간 접속 폭주를 처리하지 못할 수 있지만, 무조건 늘리면 소켓과 버퍼를 더 보유합니다. 완료 후 다음 수락을 보충하는 경로와 실패 시 정리를 확인하겠습니다. 테스트는 연결만 하고 데이터를 보내지 않는 클라이언트, 빠른 종료, 수락 소켓 초기화 실패를 포함합니다. 수락 완료는 애플리케이션의 사용자 인증 완료가 아니므로 이후 핸드셰이크와 시간 제한도 필요합니다.

## 득점 포인트

- **미리 제출하는 수락을 설명한다.** 소켓·버퍼 준비가 필요함을 짚는다.
- **초기 수신 조건을 구분한다.** 연결 완료와 데이터 대기의 차이를 말한다.
- **완료 뒤 초기화를 확인한다.** 문맥 갱신과 다음 수락 보충을 포함한다.

## 감점 포인트

- **연결만 되면 항상 바로 완료된다고 말한다.** 수신 길이 설정의 영향이 있다.
- **주소 버퍼를 임의 포인터 계산으로 읽는다.** API의 형식 계약을 따라야 한다.
- **수락 소켓이 자동으로 모든 설정을 상속한다고 말한다.** 필요한 초기화를 확인해야 한다.
