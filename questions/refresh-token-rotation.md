# 갱신 토큰을 매번 교체하면 탈취를 어떻게 발견하나요?

## 구두 답변

한 번 사용한 갱신 토큰을 다시 쓰지 못하게 하면, 이전 토큰이 재사용됐을 때 정상 흐름 밖의 사용을 의심할 수 있습니다. 새 접근 토큰을 발급할 때 갱신 토큰도 새것으로 바꾸고 이전 것은 사용 완료로 기록하는 방식입니다. 다만 재사용이 항상 공격이라는 뜻은 아니어서 동시 요청과 응답 유실도 다뤄야 합니다.

예를 들어 모바일 앱이 갱신 요청을 보냈고 서버는 교체했지만 응답이 끊겼다고 하겠습니다. 앱이 이전 토큰으로 재시도하면 이미 사용한 토큰처럼 보입니다. 저는 단순히 매번 전체 계정을 잠그기보다 동일 요청의 짧은 재시도를 어떻게 식별할지 정하겠습니다. 제한된 재시도 결과 재사용이나 클라이언트의 갱신 직렬화가 도움이 될 수 있지만, 무제한 유예는 탈취 탐지 효과를 약하게 만듭니다.

토큰 교체는 원자적으로 처리해 동시 요청이 여러 유효 후속 토큰을 만들지 못하게 해야 합니다. 확실한 비정상 재사용에는 해당 토큰 계열을 회수하고 재인증을 요구할 수 있습니다. 토큰 원문 대신 안전한 검증용 값을 보관하고, 기기별 세션과 사용자 전체 차단 범위를 나누겠습니다. 테스트에서는 동시 갱신, 응답 유실, 오래된 토큰 재사용을 재현해 사용자 불편과 탐지 정책을 함께 검증하겠습니다.

## 득점 포인트

- **회전의 탐지 원리를 설명한다.** 이전 토큰 재사용을 추적한다.
- **정상 경쟁을 고려한다.** 동시 갱신과 응답 유실을 구분한다.
- **원자성과 회수 범위를 정한다.** 토큰 계열과 기기 세션을 다룬다.

## 감점 포인트

- **재사용은 무조건 공격이라고 단정한다.** 정상 재시도도 가능하다.
- **오래된 토큰을 계속 허용한다.** 회전의 탐지 효과가 사라진다.
- **토큰을 로그로 남겨 분석한다.** 재사용 가능한 비밀이 유출될 수 있다.

## 더 파고들 거리

- 여러 탭이나 기기가 동시에 갱신할 때 클라이언트와 서버 책임은 어떻게 나눌까요?
- 토큰 계열 회수가 이미 발급한 접근 토큰에도 즉시 적용되려면 무엇이 필요할까요?
- 재시도 허용 창의 길이를 어떤 근거로 정할까요?
