# Redis에 사용자별 속성 목록을 저장하려 합니다. 문자열·해시·집합 중 필요한 연산에 맞는 자료형을 고르고 실제 메모리와 갱신 비용은 어떻게 확인하나요?

## 구두 답변

Redis 자료형 선택은 어떤 명령이 가능한지만의 문제가 아닙니다. 원소 수, 값 길이, 갱신 패턴, 읽어 오는 바이트 양, 메모리 표현을 함께 봅니다. 전체 값을 문자열이나 JSON으로 저장하면 한 번에 읽기 쉬울 수 있지만 작은 필드 하나를 바꿔도 큰 값을 다시 쓰게 됩니다. 해시는 부분 갱신에 유리할 수 있고, 순위 조회에는 sorted set, 존재 여부에는 set이 더 직접적입니다.

해시나 sorted set은 작은 크기와 값 길이에서 조밀한 내부 인코딩을 사용할 수 있지만, 임계값을 넘으면 다른 표현으로 전환돼 메모리와 지연 특성이 달라질 수 있습니다. 임계값은 Redis 버전·설정에 따라 달라지므로 운영 환경에서 `MEMORY USAGE`, 샘플 명령 지연, 실제 응답 크기를 측정하겠습니다. 자료형 이름만 보고 원소당 비용을 고정하지 않겠습니다.

예를 들어 사용자 프로필에서 자주 바뀌는 필드만 부분 갱신해야 하면 해시를 선택하되, 필드 메타데이터와 TTL 관리 단위가 늘어나는 비용을 감수합니다. 랭킹은 sorted set이 자연스럽지만 동점 규칙과 부동소수점 정밀도는 별도로 설계해야 합니다. 클라이언트가 값을 압축해 바이트 문자열로 저장하면 압축·해제 CPU는 주로 클라이언트에 들고 Redis는 압축된 바이트를 저장·전달합니다. 반대로 Redis 모듈이나 서버 측 처리로 압축한다면 Redis CPU 비용도 측정해야 하며, 어느 경우든 부분 갱신이 어려워질 수 있습니다.

테스트는 작은 샘플이 아니라 예상 원소 수·최대 값 길이·임계값 직전과 직후, 실제 갱신 비율에서 메모리, p99 지연, 복제·백업 부하를 비교합니다. 운영 후 성장했을 때도 비용이 예측 가능한 표현을 선택하겠습니다.

## 득점 포인트

- 연산·데이터 분포·인코딩 전환을 함께 본다.
- 부분 갱신의 이점과 키·필드 메타데이터 비용을 비교한다.
- 실제 상한 근처의 메모리·지연을 측정한다.

## 감점 포인트

- 자료형 이름만으로 원소당 비용이 고정된다고 말한다.
- 모든 값을 JSON 문자열로 저장하는 것이 항상 최적이라고 말한다.
- 작은 데이터 측정만으로 운영 비용을 확정한다.

## 더 파고들 거리

- 해시를 여러 키로 쪼갤 때 TTL과 원자성은 어떻게 달라지나요?
- 인코딩 전환 전후의 p99 갱신 지연을 어떻게 측정하나요?
- 압축이 네트워크와 Redis CPU에 만드는 교환은 무엇인가요?
