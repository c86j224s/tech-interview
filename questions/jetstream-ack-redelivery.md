# JetStream 메시지 처리 중 AckWait가 지났거나 ACK가 유실돼 같은 메시지가 다시 왔습니다. 원래 작업과 중복 반영은 어떻게 처리하나요?

## 구두 답변

ACK가 필요한 consumer에서는 제한 시간 안에 확인되지 않은 메시지를 다시 전달할 수 있습니다. AckWait는 작업이 반드시 끝나는 최대 시간이 아니라 재전달 판단의 기준입니다. 원래 작업이 아직 실행 중인데 시간이 지나면 같은 이벤트가 다른 실행 흐름에서 다시 처리될 수 있습니다.

JetStream에서 stream은 발행된 메시지를 저장하는 로그이고 consumer는 전달·확인 상태를 관리하는 리소스입니다. 여기서 소비 ACK는 앱이 받은 메시지를 처리했다고 서버에 알리는 확인입니다. 예를 들어 DB 반영 → 앱의 ACK 전송 → ACK 전달 유실 순서라면 DB 효과는 남아 있어도 서버는 재전달할 수 있습니다. 이 경우 같은 이벤트 ID에 대한 처리 기록과 DB 변경을 하나의 트랜잭션으로 묶어 두 번째 효과를 막을 수 있습니다.

저는 실제 처리 시간 분포에 맞게 대기와 재시도 정책을 정하고, 긴 처리에서 진행 중 신호를 사용할 수 있는지 확인하겠습니다. 하지만 진행 신호도 외부 효과의 원자성을 만들지는 않으므로 이벤트 ID로 목적지 변경을 보호해야 합니다. 실패를 명시하는 NAK와 더 이상 재전달하지 않도록 하는 처리의 의미도 구분해야 합니다.

consumer의 미확인 수 상한은 메모리와 동시 처리량을 제한하는 데 중요합니다. 실패 메시지를 끝없이 반복하면 다른 작업이 밀릴 수 있어 최대 전달 횟수와 운영 알림·복구 절차를 둡니다. 자동으로 원하는 DLQ에 이동한다고 가정하지 않고 실제 정책을 구현·검증하겠습니다. 테스트는 처리 시간이 AckWait를 넘는 경우와 ACK 응답 유실을 확인해 중복 효과가 없는지 보겠습니다.

## 득점 포인트

- 재전달 타이머와 실제 작업 수명을 구분한다.
- 진행 신호와 메시지 처리의 멱등성을 분리한다.
- 미확인 상한과 독성 메시지 처리를 정한다.

## 감점 포인트

- AckWait가 지나면 원래 워커가 중단된다고 말한다.
- 진행 ACK면 외부 효과가 정확히 한 번이라고 말한다.
- 최대 전달 횟수 후 자동 DLQ를 가정한다.
