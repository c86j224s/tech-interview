# C++에서 바이트 버퍼를 구조체 포인터로 캐스팅해 읽으려 합니다. 크기만 맞으면 안전한가요?

## 구두 답변

크기 외에 정렬·객체 수명·타입 접근 규칙·표현 형식이 맞아야 합니다. 임의 바이트를 reinterpret_cast했다고 해당 타입 객체가 항상 생성되는 것은 아니며 잘못된 접근은 undefined behavior가 될 수 있습니다.

### 동작 원리와 전제

네트워크 패킷은 padding·endianness·필드 크기가 로컬 struct와 다를 수 있습니다. 명시적인 바이트 파싱과 범위 검사를 사용하고 trivially copyable 타입의 memcpy·bit_cast 같은 수단도 적용 조건을 확인합니다. 포인터 값 자체를 외부 입력에서 복원하지 않습니다.

### 선택과 실패 처리

packed 구조체는 정렬 비용·플랫폼 의존을 만들 수 있고 aliasing 규칙을 모두 해결하지 않습니다. 객체 풀에서 메모리를 재사용하면 이전 객체의 포인터 수명과 새 객체 생성 경계도 관리해야 합니다.

### 구체적인 사례와 검증

네트워크의 4바이트 길이 필드를 host uint32_t로 포인터 캐스팅하면 주소가 정렬되지 않았거나 byte order가 다를 수 있습니다. 바이트를 명시적으로 읽고 변환한 뒤 최대 길이와 남은 입력을 검사하는 방식이 더 명확합니다. 메모리 풀의 같은 주소에 새 객체를 생성할 때도 이전 객체의 소멸과 새 수명 시작을 지켜야 합니다. 타입의 객체 표현을 복사할 수 있는 조건과 그 값이 도메인상 유효한지는 별개입니다. bool·enum·포인터처럼 임의 비트가 정상 값이 아닐 수 있는 타입을 외부 데이터로 직접 복원하지 않습니다. 컴파일러 최적화가 강해질 때만 드러나는 UB도 언어 계약을 근거로 제거해야 합니다.

다른 아키텍처·정렬되지 않은 입력·잘린 데이터·잘못된 enum을 시험합니다. sanitizer가 모든 UB를 발견하지는 않으므로 언어 계약을 근거로 설계합니다. 빠른 캐스팅보다 표현과 수명의 명시적인 변환이 이식성과 안전성에 유리합니다.

## 득점 포인트

- 핵심 구분: 크기 외에 정렬·객체 수명·타입 접근 규칙·표현 형식이 맞아야 합니다.
- 선택 조건: packed 구조체는 정렬 비용·플랫폼 의존을 만들 수 있고 aliasing 규칙을 모두 해결하지 않습니다.
- 검증 기준: 다른 아키텍처·정렬되지 않은 입력·잘린 데이터·잘못된 enum을 시험합니다.

## 감점 포인트

- 바이트 수가 같으면 임의 버퍼를 struct 포인터로 읽어도 안전하다고 한다.
