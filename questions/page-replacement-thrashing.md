# 프로세스들이 페이지를 계속 밀어내고 다시 읽으며 느려집니다. 페이지 교체 정책과 작업 집합을 어떻게 보나요?

## 구두 답변

프로그램이 당장 필요로 하는 페이지 집합이 실제로 확보한 메모리보다 크면, 내보낸 페이지를 금방 다시 읽는 일이 반복될 수 있습니다. 이런 스래싱에서는 디스크와 페이지 관리에 시간을 쓰느라 유용한 작업이 잘 진행되지 않습니다. 단순히 더 많은 프로세스를 실행하는 것이 처리량을 낮출 수도 있습니다.

FIFO는 오래 들어온 페이지부터, LRU는 최근 사용되지 않은 페이지부터 교체한다는 모델입니다. 정확한 LRU는 매 접근 추적 비용이 있어 OS는 접근 비트 등을 이용한 근사 정책을 쓰기도 합니다. 미래 접근을 아는 최적 교체는 비교 기준이지 일반 실행에서 그대로 구현할 수는 없습니다.

저는 페이지 폴트와 저장 대기, 프로세스별 작업 집합과 동시 실행 수를 보겠습니다. 정책만 바꾸기보다 동시성을 줄이거나 캐시·메모리 접근 패턴을 바꿔 활성 데이터가 메모리에 남게 하는 것이 효과적일 수 있습니다. FIFO에서는 프레임을 늘려도 폴트가 늘어나는 특정 참조열이 가능하므로 모든 정책에 같은 직관을 적용하지 않겠습니다. 테스트는 실제 참조 패턴과 회복 상태를 함께 확인합니다.

## 득점 포인트

- 작업 집합과 반복 재읽기의 관계를 설명한다.
- 교체 정책과 구현 비용을 구분한다.
- 동시성·접근 패턴을 해결책에 포함한다.

## 감점 포인트

- 메모리 부족은 스케줄러를 더 돌리면 해결된다고 말한다.
- 미래 최적 교체를 실제로 항상 구현할 수 있다고 말한다.
- 프레임 증가가 모든 정책에서 폴트 감소를 보장한다고 말한다.

- 작업 집합을 측정할 시간 창은 어떻게 고를까요?
