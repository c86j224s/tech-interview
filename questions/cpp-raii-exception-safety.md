# C++에서 락과 파일을 RAII 객체로 관리합니다. 작업 도중 예외가 나면 자원 해제와 업무 상태 복구가 모두 보장되나요?

## 구두 답변

RAII는 객체 수명에 맞춰 자원을 해제하도록 돕지만, 업무 상태가 원래대로 복구된다는 뜻은 아닙니다. 파일 핸들을 닫는 것과 계좌 이체를 되돌리는 것은 다릅니다. 저는 자원이 새지 않는지와 중간 변경이 일관된 상태로 남는지를 따로 확인하겠습니다.

RAII는 자원을 객체의 생성·소멸에 묶는 관용구입니다. 예를 들어 lock_guard는 스코프를 벗어나면 락을 해제합니다. 하지만 락 안에서 잔액을 차감한 뒤 다른 연산이 실패했다면, 락이 풀리는 것만으로 차감한 잔액이 돌아오지는 않습니다. 무엇을 자동 정리하는지와 무엇을 되돌려야 하는지를 분리해야 합니다.

예를 들어 컨테이너에 새 값을 넣는 도중 메모리 할당이 실패할 수 있습니다. 락은 자동으로 풀려도 원래 데이터를 먼저 지웠다면 값이 사라질 수 있습니다. 실패해도 유효한 상태를 유지하는 기본 보장과, 실패 시 관찰 가능한 상태가 변하지 않는 강한 보장을 구분해야 합니다. 강한 보장이 필요하면 임시 객체에서 새 상태를 완성한 뒤 실패하지 않는 교체 연산으로 반영하겠습니다. 대신 복사와 추가 메모리 비용이 생깁니다.

소멸자에서 실패할 수 있는 외부 저장까지 마무리하려고 하지는 않겠습니다. 소멸 과정에서 다시 예외를 던지면 종료로 이어질 수 있고 호출자가 복구하기도 어렵습니다. 실패 결과가 중요한 작업은 명시적인 완료 함수에서 확인하고, 소멸자는 남은 자원의 안전한 정리에 집중시키겠습니다. 테스트에서는 할당이나 복사 중간에 실패를 주입해 누수뿐 아니라 원래 상태와 불변식이 유지되는지 확인하겠습니다.

## 득점 포인트

- **자원과 업무 상태를 구분한다.** 자동 해제가 롤백을 의미하지 않음을 설명한다.
- **필요한 예외 보장을 선택한다.** 임시 상태와 최종 반영의 비용을 비교한다.
- **실패 주입으로 확인한다.** 중간 실패에서 불변식과 누수를 함께 검사한다.

## 감점 포인트

- **RAII면 모든 예외가 안전하다고 말한다.** 부분 변경은 남을 수 있다.
- **소멸자에서 복구 가능한 오류를 모두 던진다.** 종료와 오류 처리 어려움이 생길 수 있다.
- **무조건 복사해 강한 보장을 주자고 한다.** 자원과 성능 요구를 함께 봐야 한다.

## 더 파고들 거리

- 외부 자원 변경은 강한 예외 보장으로 어떻게 다룰 수 있을까요?
- 여러 객체의 불변식을 하나의 커밋 단계로 묶으려면 어떻게 설계할까요?
