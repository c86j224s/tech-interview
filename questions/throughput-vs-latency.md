# 처리량과 응답 시간은 어떻게 다르며, 평균 응답 시간만으로 성능을 판단해도 되나요?

## 구두 답변

처리량은 단위 시간에 완료한 작업 수이고, 응답 시간은 개별 요청의 시작부터 결과까지 걸린 시간입니다. 특히 **서비스 시간과 큐 대기 시간을 분리**해야 합니다. CPU에서 계산하는 시간은 그대로여도 연결 풀이나 실행 큐에서 기다리는 시간이 늘면 사용자가 보는 지연은 악화됩니다.

안정적인 시스템에서는 리틀의 법칙으로 평균 진행 중 요청 수 L, 처리량 λ, 평균 응답 시간 W가 `L = λW`로 연결됩니다. 다만 같은 측정 경계와 안정 상태에서의 평균 관계이지 p99를 대입하는 공식은 아닙니다. 이용률이 포화에 가까워지면 도착·처리 시간의 변동성 때문에 대기열이 커질 수 있어, 처리량은 정체되는데 꼬리 지연은 급격히 증가합니다. 동시성을 높인다고 용량이 계속 늘지는 않습니다.

평균은 긴 꼬리를 숨기므로 p95·p99와 오류·타임아웃을 함께 봐야 합니다. p99는 최대값이 아니고, 여러 서버의 p99를 평균 내도 전체 p99가 되지 않습니다. 분포를 합칠 수 있는 히스토그램 등이 필요합니다. 여러 하위 호출을 기다리는 fan-out 요청은 느린 하나에 묶일 수 있어, 개별 서비스의 작은 꼬리 지연도 전체 사용자 요청에서 증폭됩니다.

부하 생성 모델도 중요합니다. 응답을 받아야 다음 요청을 보내는 closed-loop는 서버가 느려질 때 도착 부하도 줄어듭니다. 실제로는 요청이 계속 도착하는 서비스를 이 방식으로만 측정하면 **coordinated omission**으로 정체 구간의 지연을 과소평가할 수 있습니다. open-loop 부하도 생성기 자체가 포화되지 않았는지, 예정된 발송 시각에서 얼마나 늦어졌는지 확인해야 합니다.

저는 동일한 요청 분포와 캐시 조건에서 도착률을 단계적으로 높이고, **SLO를 만족하는 성공 처리량, 즉 유효 처리량(goodput)**을 보겠습니다. 빠르게 실패한 요청으로 평균이 좋아지는 착시를 피하고, CPU·GC·락·연결 풀·큐 대기를 추적해 병목을 찾겠습니다. 최대 TPS보다 지연과 오류 목표를 지키면서 과부하에서도 무너지지 않는 운영 용량이 중요합니다.

## 득점 포인트

- **대기와 실행을 분리한다.** 리틀의 법칙을 평균·안정 상태·동일 측정 경계라는 조건과 함께 설명한다.
- **분포와 fan-out의 영향을 설명한다.** 백분위수의 집계 한계와 느린 하위 호출이 전체 요청에 미치는 영향을 짚는다.
- **측정 도구의 왜곡을 점검한다.** open-loop·closed-loop와 coordinated omission을 실제 트래픽 모델에 연결한다.
- **SLO 기반 용량을 판단한다.** 성공률·데드라인·goodput을 함께 보고 과부하 시 대기열과 실패 정책을 평가한다.

## 감점 포인트

- **“처리량은 지연의 역수이며 p99에도 같은 식을 쓴다”고 말한다.** 동시성과 측정 경계를 무시하고 평균 관계를 백분위수에 잘못 적용한 설명이다.
- **“서버별 p99의 평균이 서비스 전체 p99다”라고 말한다.** 분위수는 원래 요청 분포를 보존하지 않으므로 그렇게 합성할 수 없다.
- **“응답이 늦어도 부하 도구의 목표 동시 사용자 수가 같으면 비교가 공정하다”고 말한다.** 실제 도착률과 대기 모델이 달라질 수 있다.
- **“오류를 포함한 평균 지연이 줄면 성능 개선이다”라고 판단한다.** 빠른 거절과 타임아웃 표본 누락으로 지연이 좋아 보일 수 있다.

## 더 파고들 거리

- coordinated omission을 피하는 측정에서는 요청의 예정 발송 시각과 실제 발송 시각을 어떻게 다뤄야 할까요?
- 히스토그램 버킷 경계와 샘플 수가 p99 추정 오차에 어떤 영향을 주며, 낮은 트래픽에서는 어떻게 보고해야 할까요?
- hedged request로 꼬리 지연을 줄일 때 중복 작업과 하위 시스템 부하 증가는 어떻게 제한할까요?
- 부하 차단이 오류율을 높이더라도 goodput과 복구 시간을 개선하는 조건은 무엇일까요?
