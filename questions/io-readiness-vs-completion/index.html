01

구두 답변

정의를 외우기보다, 원리와 조건을 연결해 설명해 보세요.

준비 통지는 I/O를 시도할 수 있는 상태를, 완료 통지는 제출한 I/O 작업의 결과를 알립니다. 설계 패턴으로는 각각 Reactor와 Proactor에 연결됩니다. 핵심은 운영체제 이름이 아니라 I/O 수행과 버퍼 소유권을 누가 어느 시점에 책임지는지입니다.

epoll 기반 Reactor에서는 준비 이벤트를 받은 애플리케이션이 논블로킹 소켓을 읽습니다. 이벤트는 상태에 대한 힌트이므로 실제 반환값에서 데이터, EOF, 오류, EAGAIN을 구분해야 합니다. 에지 트리거라면 보통 EAGAIN까지 drain합니다. 공정성을 위해 읽기 예산을 정해 중간에 멈춘다면 새 에지만 기다리지 말고 애플리케이션의 실행 대기열에 다시 올려야 합니다. 그렇지 않으면 커널 버퍼에 데이터가 남아도 처리가 멈출 수 있습니다.

IOCP와 중첩 I/O를 쓰는 Proactor 구조에서는 수신 버퍼와 OVERLAPPED를 준비해 작업을 제출하고 완료 바이트 수와 오류를 처리합니다. 연결 종료나 취소 요청의 반환은 버퍼를 해제해도 된다는 뜻이 아닙니다. 미완료 작업이 모두 정리될 때까지 작업 컨텍스트와 연결 객체의 수명을 유지해야 합니다. 즉시 성공이나 완료 통지 생략 설정처럼 API별 완료 규칙도 확인해야 합니다.

완료 큐를 여러 워커가 소비한다고 같은 연결의 상태 변경이 자동으로 직렬화되지는 않습니다. 완료 패킷의 큐 순서와 애플리케이션 처리 완료 순서도 다릅니다. 연결별 직렬 실행기, 제한된 in-flight 작업, 명시적인 상태 머신 중 적합한 방식으로 버퍼 재사용과 종료 경합을 통제해야 합니다.

성능에서는 통지 방식보다 시스템 호출·완료 배치 크기, 워커 경합, 연결별 공정성과 큐 적체가 병목일 수 있습니다. 이벤트 루프 지연, 완료 큐 대기, in-flight I/O 수와 버퍼 사용량을 측정하고, 느린 연결과 취소·종료 경합을 테스트하겠습니다. 준비 통지는 재시도 상태, 완료 통지는 제출 작업의 수명과 소유권이 특히 중요합니다.

02

득점 포인트

이해가 드러나는 지점을 확인해 보세요.

  • Reactor·Proactor를 책임 분담으로 설명한다. 알림 이름만 나열하지 않고 실제 I/O 수행과 결과 처리 시점을 구분한다.
  • 에지 트리거의 진행성과 공정성을 함께 다룬다. drain을 중단할 경우 자체 재스케줄링이 필요한 이유를 설명한다.
  • 완료와 객체 수명을 연결한다. 취소·즉시 성공·연결 종료 경로에서도 작업별 소유권과 해제 시점을 추적한다.
  • 완료 순서와 상태 변경 순서를 구분한다. 여러 워커가 처리하는 연결의 재진입과 직렬화 정책을 설명한다.
03

감점 포인트

놓치기 쉬운 조건과 오해를 짚어 보세요.

  • “준비 이벤트가 왔으니 원하는 길이만큼 읽을 수 있다”고 말한다. 준비 상태는 메시지 완성이나 데이터 독점권을 보장하지 않는다.
  • “에지 트리거에서 일부만 읽고 다음 이벤트를 기다리면 된다”고 말한다. 새 에지가 생기지 않으면 남은 데이터가 정체될 수 있다.
  • “CancelIoEx가 반환되면 OVERLAPPED를 해제한다”고 말한다. 취소 요청과 실제 작업 완료 사이의 수명 계약을 위반할 수 있다.
  • “완료 큐가 FIFO면 같은 연결의 콜백도 순서대로 끝난다”고 말한다. 큐에서 꺼낸 순서와 여러 실행 흐름의 처리 순서는 별개다.
04

더 파고들 거리

하나 더 질문하며 이해의 범위를 넓혀 보세요.

  • EPOLLONESHOT의 재무장과 연결별 실행 소유권을 결합할 때 어떤 이벤트 유실 경로를 점검해야 할까요?
  • IOCP에서 즉시 완료와 비동기 완료의 통지 정책이 다르면 이중 완료 처리를 어떻게 방지할까요?
  • 취소와 정상 완료가 경합할 때 참조 카운트나 generation ID로 어떤 문제를 막을 수 있을까요?
  • io_uring을 도입해도 없어지지 않는 버퍼 수명·백프레셔·애플리케이션 순서 보장 문제는 무엇일까요?
