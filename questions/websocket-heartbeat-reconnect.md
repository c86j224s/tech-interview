# WebSocket 하트비트로 연결 생존을 확인하고 재연결 뒤 누락·중복 메시지를 복구하려면 어떤 상태를 저장해야 하나요?

## 구두 답변

TCP나 WebSocket 소켓이 아직 닫히지 않았다는 것과 상대 애플리케이션이 정상적으로 처리하고 있다는 것은 다릅니다. 경로 단절이나 서버 정지 뒤에도 한동안 로컬 연결은 열린 것처럼 보일 수 있으므로, ping/pong 또는 애플리케이션 heartbeat의 응답 시각으로 일정 범위의 생존을 추정합니다. 너무 짧은 timeout은 일시적인 지연을 장애로 오판하고 재연결 폭주를 만들 수 있습니다.

heartbeat 간격은 중간 프록시의 유휴 종료, 원하는 장애 감지 시간, 정상 지연 분포로 정합니다. 재연결은 지수 백오프·무작위 지연·최대 시도 간격을 사용하고, 서버 재시작 뒤 모든 클라이언트가 동시에 인증·상태 복구를 요청하지 않게 제한합니다. heartbeat가 정상이어도 실제 요청의 응답이 느릴 수 있으므로 전송·처리·DB 대기를 별도 측정하겠습니다.

누락 복구는 애플리케이션 메시지 기록이 필요합니다. 중요한 이벤트에 순서 번호나 커서를 붙이고 클라이언트가 마지막으로 적용·확인한 위치를 서버에 보내면, 재연결 뒤 그 다음부터 재전달할 수 있습니다. 확인 응답 유실로 이미 적용한 이벤트를 다시 받을 수 있으므로 이벤트 ID와 버전으로 적용을 멱등화합니다. 보관 기간을 넘겼다면 최신 스냅샷을 먼저 받고 그 이후 커서부터 재개하는 규칙을 둡니다.

테스트는 메시지 적용 직후 ACK 유실, 반열림 연결, 서버 재시작, 장기 오프라인, 커서 만료를 재현합니다. 재연결 성공률이 아니라 누락 없이 복구되고 중복 효과가 남지 않는지를 성공 기준으로 삼겠습니다.

## 득점 포인트

- 소켓 상태와 애플리케이션 생존·처리를 구분한다.
- heartbeat·백오프·재접속 부하 제한을 구체화한다.
- 커서 재개·스냅샷 대체·멱등 적용을 함께 설계한다.

## 감점 포인트

- 연결이 열려 있으면 상대 애플리케이션이 정상이라고 말한다.
- 재연결하면 메시지가 자동으로 복구된다고 말한다.
- 확인 응답 유실 뒤 재전달이 중복되지 않는다고 말한다.

## 더 파고들 거리

- 오래 오프라인인 클라이언트의 이벤트 보관·스냅샷 기준은 무엇인가요?
- heartbeat는 정상인데 실제 요청의 응답만 느릴 때 어느 구간을 추가 측정하나요?
- 여러 기기에서 같은 세션 커서와 소유권을 어떻게 나누나요?
