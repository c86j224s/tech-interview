# WebSocket 연결이 살아 있는지와 재연결 후 누락은 어떻게 확인하나요?

## 구두 답변

소켓이 아직 닫히지 않았다는 것과 상대 애플리케이션이 정상적으로 응답한다는 것은 다릅니다. 네트워크가 끊겨도 한동안 연결 상태가 유지될 수 있습니다. 저는 하트비트로 응답을 확인하되, 너무 짧은 시간에 실패를 확정해 불필요한 재연결 폭주를 만들지 않겠습니다.

하트비트 간격은 중간 장치의 유휴 종료와 원하는 장애 감지 시간을 기준으로 정하겠습니다. 응답 지연 분포를 보고 일시적인 멈춤을 허용할 여유를 두며, 재연결에는 무작위 지연과 상한을 넣겠습니다. 서버 전체가 재시작한 뒤 모든 클라이언트가 동시에 접속하면 인증과 상태 복구가 함께 몰릴 수 있기 때문입니다.

재연결에 성공했다고 이전 메시지가 모두 처리된 것도 아닙니다. 중요한 이벤트라면 순서 번호나 커서로 마지막 확인 위치를 기록하고 그 이후부터 다시 받게 하겠습니다. 재전달은 중복될 수 있으므로 적용도 멱등적으로 해야 합니다. 보관 기간을 넘어 복구할 수 없다면 최신 스냅샷을 받고 새 커서부터 시작하는 규칙이 필요합니다. 테스트는 연결 성공만 보지 않고, 메시지 적용 직후 확인 응답이 유실된 경우와 서버 재시작 후 복구까지 확인하겠습니다.

## 득점 포인트

- **연결과 업무 생존을 구분한다.** 하트비트의 감지 범위를 설명한다.
- **재접속 부하를 제한한다.** 지연·분산·상한을 둔다.
- **누락 복구와 중복 방지를 묶는다.** 커서 재개와 스냅샷 대체 경로를 정한다.

## 감점 포인트

- **연결이 열려 있으면 상대가 정상이라고 말한다.** 반열림과 앱 정체가 가능하다.
- **재연결하면 메시지도 자동 복구된다고 말한다.** 애플리케이션 기록이 필요하다.
- **재전송은 중복되지 않는다고 말한다.** 확인 유실로 다시 받을 수 있다.

## 더 파고들 거리

- 클라이언트가 오래 오프라인이면 이벤트 보관과 스냅샷 정책을 어떻게 정할까요?
- 하트비트가 정상인데 업무 응답만 늦을 때 어떤 경로를 따로 측정할까요?
- 여러 기기에서 같은 세션을 복구할 때 커서와 소유권은 어떻게 나눌까요?
