# Redis WAIT가 복제 확인을 반환한 뒤에도 장애 전환에서 쓰기 보존을 단정할 수 없는 이유는 무엇인가요?

## 구두 답변

`WAIT`는 현재 연결에서 앞서 수행한 쓰기가 지정한 수의 replica에 복제됐다고 확인될 때까지 기다립니다. 이는 primary 하나만 성공한 경우보다 장애 시 최신 값이 남을 가능성을 높이지만, 복제 ACK 자체가 모든 장애 조합에서 강한 일관성이나 디스크 내구성을 보장하지는 않습니다. 어떤 replica가 실제로 승격되는지, 각 노드가 디스크에 어떻게 동기화되는지는 별도의 조건입니다.

예를 들어 ACK를 보낸 replica들이 함께 고장 나고 ACK를 보내지 않은 다른 replica가 승격되면 쓰기가 사라질 수 있습니다. `WAIT` 타임아웃은 원래 쓰기가 취소됐다는 뜻도 아닙니다. primary에는 이미 반영됐지만 충분한 replica 확인을 못 받은 상태일 수 있으므로, 증분 쓰기를 무조건 재전송하면 중복 효과가 생깁니다.

저는 요구를 최근 유실 가능성 감소와 엄격한 보존으로 나눕니다. 디스크에 기록된 replica 수까지 확인해야 한다면 지원 버전의 `WAITAOF`와 지속성 설정을 검토하되, 그것도 전체 장애 도메인과 승격 정책을 대신하지 않는지 시험하겠습니다. 데이터를 변경하는 요청에는 요청 ID나 최종 상태 조회를 붙여 타임아웃 뒤 결과를 확인합니다.

테스트는 복제 확인 전·후 primary 중단, ACK replica 중단, 다른 replica 승격, 타임아웃 뒤 재시도를 재현합니다. 성공 여부는 `WAIT`를 호출했다는 사실이 아니라 각 실패에서 어떤 값이 남고 재시도가 중복되지 않는지로 판단하겠습니다.

## 득점 포인트

- 복제 ACK·디스크 기록·승격 선택을 별도 보장으로 구분한다.
- 타임아웃을 불확정 결과로 다뤄 중복 재시도를 막는다.
- 장애 도메인과 요청 처리의 멱등성까지 포함해 검증한다.

## 감점 포인트

- `WAIT` 성공이면 모든 장애에서 무손실이라고 말한다.
- `WAIT` 실패가 primary의 원래 쓰기를 롤백한다고 말한다.
- 타임아웃 뒤 증분 쓰기를 새로 보내도 안전하다고 말한다.

## 더 파고들 거리

- `WAITAOF`와 `WAIT`는 확인하는 내구 지점이 어떻게 다른가요?
- 복제 지연 제한은 가용성과 유실 가능성에 어떤 교환을 만드나요?
- 확인 replica 수와 장애 도메인 배치를 어떻게 함께 정하나요?
