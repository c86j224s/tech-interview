# I/O 준비 통지와 완료 통지는 무엇이 다르며, 서버 코드는 어떻게 달라지나요?

## 구두 답변

준비 통지는 지금 I/O를 시도하면 진행할 수 있는 상태라는 알림이고, 완료 통지는 미리 요청한 I/O 작업의 결과가 나왔다는 알림입니다. 핵심 차이는 통지를 받은 뒤 애플리케이션이 실제 읽기나 쓰기를 수행하는지, 아니면 이미 요청한 작업의 결과를 처리하는지에 있습니다.

대표적인 준비 통지 방식인 epoll에서는 소켓을 등록하고 읽기 가능 같은 이벤트를 기다립니다. 이벤트가 오면 애플리케이션이 논블로킹 소켓에 `recv()`를 호출해서 데이터를 가져옵니다. 알림이 왔다는 이유만으로 원하는 크기의 데이터가 모두 준비됐다고 볼 수는 없습니다. 다른 실행 흐름이 먼저 데이터를 소비했을 수도 있으므로 실제 호출 결과를 확인해야 합니다. 읽기 가능 상태가 데이터 도착이 아니라 연결 종료를 의미할 수도 있습니다.

에지 트리거 방식을 사용한다면 보통 더 읽을 수 없다는 `EAGAIN` 등의 결과가 나올 때까지 읽습니다. 일부만 읽고 다음 알림만 기다리면, 남은 데이터에 대해 기대한 새 이벤트가 오지 않아 처리가 멈출 수 있기 때문입니다. 한 연결이 실행 시간을 독점하지 않도록 처리량을 제한한다면, 남은 작업을 다시 실행할 별도 스케줄링 규칙도 필요합니다.

완료 통지 방식의 예로는 IOCP와 중첩 I/O를 함께 사용하는 구조가 있습니다. 애플리케이션이 버퍼와 작업 정보를 준비해 수신을 요청하고, 완료 결과에서 전송 바이트 수나 오류를 확인합니다. 이때 작업이 끝나기 전에 해당 버퍼나 작업 정보를 해제하거나 잘못 재사용하면 안 됩니다. 취소를 요청한 경우에도 실제 완료를 확인하기 전까지 수명 관리가 필요합니다.

두 방식 모두 적은 수의 실행 흐름으로 여러 연결을 다루는 구조를 만들 수 있습니다. 준비 통지는 I/O 시도와 재시도 상태 관리가 중요하고, 완료 통지는 제출한 작업과 버퍼의 수명 관리가 중요합니다. 어느 쪽이든 한 번의 통지가 완전한 애플리케이션 메시지 하나를 의미하지는 않으므로, 메시지를 조립하는 처리는 별도로 필요합니다.

## 득점 포인트

- **통지가 나타내는 대상을 구분한다.** 소켓의 준비 상태와 제출한 작업의 완료 결과를 비교한다.
- **통지 이후에도 결과 확인이 필요함을 설명한다.** 부분 처리, 연결 종료, 오류를 정상적인 상태 전이로 다룬다.
- **방식별로 다른 책임을 짚는다.** 준비 통지에서는 논블로킹 재시도, 완료 통지에서는 작업과 버퍼의 수명 관리가 중요하다고 설명한다.
- **전송 단위와 메시지 단위를 구분한다.** 완료 통지를 받더라도 애플리케이션 메시지 전체가 도착했다는 뜻은 아니라고 설명한다.

## 감점 포인트

- **“epoll 이벤트가 오면 데이터가 사용자 버퍼에 이미 들어 있다”고 말한다.** 일반적인 준비 통지에서는 애플리케이션이 읽기 호출을 해야 한다.
- **“읽기 가능 이벤트는 반드시 읽을 데이터가 있다는 뜻이다”라고 말한다.** 연결 종료나 상태 변화도 실제 반환값으로 확인해야 한다.
- **“IOCP는 연결마다 전용 스레드를 만드는 방식이다”라고 설명한다.** 완료 큐를 여러 작업자가 처리하는 구조를 구성할 수 있다.
- **“I/O 취소 함수가 반환되면 버퍼를 즉시 해제해도 된다”고 단정한다.** 취소 요청과 실제 작업 완료를 구분하고 API의 수명 규칙을 따라야 한다.
