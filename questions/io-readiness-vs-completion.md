# I/O 준비 통지와 완료 통지는 무엇이 다르며, 서버 코드는 어떻게 달라지나요?

## 구두 답변

준비 통지는 지금 읽거나 써 볼 수 있다는 알림이고, 완료 통지는 앞서 요청한 읽기나 쓰기의 결과가 나왔다는 알림입니다. 보통 준비 통지를 이용하는 구조를 Reactor, 완료 통지를 이용하는 구조를 Proactor라고 부릅니다. 차이는 이름보다 **알림을 받은 다음 실제 I/O를 할지, 이미 수행된 I/O의 결과를 처리할지**에 있습니다.

epoll에서는 읽기 가능 이벤트를 받고 나서 애플리케이션이 소켓을 읽습니다. 그런데 알림이 왔다고 원하는 양을 다 읽을 수 있는 것은 아닙니다. 일부만 있을 수도 있고 연결이 끝났을 수도 있어 반환값을 확인해야 합니다. 특히 에지 트리거에서는 보통 더 읽을 것이 없다는 EAGAIN이 나올 때까지 읽습니다. 일부만 읽고 새 이벤트를 기다리면 남은 데이터에 대해 새 알림이 오지 않아 처리가 멈출 수 있기 때문입니다.

그렇다고 한 연결만 끝없이 읽으면 다른 연결이 밀립니다. 저는 연결별로 한 번에 처리할 양을 제한하되, 데이터가 남아 있는 상태로 멈췄다면 그 연결을 자체 실행 대기열에 다시 넣겠습니다. 이렇게 해야 처리 누락을 막으면서 다른 연결에도 실행 기회를 줄 수 있습니다.

IOCP와 중첩 I/O에서는 버퍼와 작업 정보를 준비해 먼저 수신을 요청하고 완료된 바이트 수나 오류를 받습니다. 이쪽에서 특히 신경 쓸 것은 수명입니다. 사용자가 연결을 끊었다고 연결 객체와 버퍼를 바로 해제하면, 아직 끝나지 않은 I/O가 그 메모리를 사용하고 있을 수 있습니다. 저는 새 I/O 제출을 막고 미완료 작업의 수를 추적해서, 실제 완료가 확인된 뒤 마지막 참조를 정리하겠습니다. 취소 요청을 보낸 것만으로 완료됐다고 처리하지는 않겠습니다.

두 구조 모두 워커를 늘리는 것만으로 안전해지지 않습니다. 여러 워커가 같은 연결을 동시에 처리한다면 연결별 상태 변경을 직렬화해야 합니다. 검증할 때는 빠른 정상 통신만 보지 않고, 데이터가 계속 들어오는 연결과 종료·취소가 겹치는 연결을 섞어 보겠습니다. **준비 통지에서는 남은 작업을 놓치지 않는지, 완료 통지에서는 아직 사용 중인 자원을 먼저 정리하지 않는지**를 중심으로 보겠습니다.

## 득점 포인트

- **통지 후 애플리케이션의 책임을 설명한다.** 직접 I/O를 시도하는 단계와 완료 결과를 처리하는 단계를 구분한다.
- **진행성과 공정성을 함께 해결한다.** 에지 트리거에서 처리 예산을 소진하면 자체 재스케줄링해야 하는 이유를 말한다.
- **종료 순서를 구체적으로 정한다.** 새 제출 차단, 미완료 작업 추적, 완료 후 자원 해제를 연결한다.
- **검증할 경합 상황을 제시한다.** 다중 워커, 지속적인 입력, 취소·종료 경쟁으로 정상 경로 밖의 오류를 확인한다.

## 감점 포인트

- **“epoll 이벤트가 오면 사용자 버퍼에 데이터가 들어 있다”고 말한다.** 준비 통지를 받은 뒤 읽기 호출을 해야 한다.
- **“에지 트리거는 일부만 읽고 기다려도 다시 알려 준다”고 말한다.** 남은 데이터를 스스로 재처리하지 않으면 정체될 수 있다.
- **“취소 함수가 반환되면 I/O 버퍼를 해제한다”고 말한다.** 취소 요청과 실제 완료는 다를 수 있다.
- **“완료 이벤트가 순서대로 나오면 워커 처리도 순서대로 끝난다”고 말한다.** 여러 실행 흐름의 처리 순서는 별도로 보장해야 한다.

## 더 파고들 거리

- IOCP에서 즉시 성공과 나중 완료가 서로 다른 통지 규칙을 가질 때 이중 처리를 어떻게 막을까요?
- EPOLLONESHOT으로 연결 소유권을 넘길 때 언제 재무장해야 이벤트를 놓치지 않을까요?
- 취소와 정상 완료가 동시에 도착할 때 버퍼 반환을 정확히 한 번 수행하려면 어떤 상태가 필요할까요?
- io_uring에서도 남는 버퍼 수명과 백프레셔 문제는 무엇일까요?
