# 검색용 데이터에 정확한 ID 조회와 본문 검색이 함께 있습니다. Elasticsearch의 mapping과 shard 수를 어떻게 정해야 하나요?

## 구두 답변

shard는 검색과 저장을 나누는 단위지만 많이 만든다고 항상 빠르지는 않습니다. 각 shard의 메타데이터·세그먼트·검색 fan-out 비용이 생깁니다. mapping은 필드를 어떤 형태로 색인하고 정렬·집계할지 결정하므로 실제 쿼리 요구와 맞아야 합니다.

mapping은 필드를 어떻게 색인할지 정하는 스키마입니다. 본문을 단어로 분석하는 text와 ID 문자열을 정확한 값으로 다루는 keyword는 용도가 다릅니다. shard는 인덱스를 나눈 검색·저장 단위입니다. 필드 표현이 잘못된 문제를 shard 수만 늘려 해결할 수는 없습니다.

정확한 계정 ID 비교에 분석된 text 필드를 쓰면 기대와 다른 토큰 검색이 될 수 있습니다. 저는 전문 검색용 text와 정확 비교·정렬·집계용 keyword를 구분하겠습니다. 동적으로 임의 필드가 계속 생기는 데이터는 mapping 폭증을 만들 수 있어 스키마를 제한해야 합니다.

shard 수는 예상 데이터 크기와 병렬성뿐 아니라 복구·재배치 시간을 보고 정하겠습니다. 작은 shard가 너무 많으면 운영 비용이 커지고, 너무 큰 shard는 이동과 복구가 오래 걸립니다. 테스트는 실제 쿼리와 집계, 필드 분포를 재현해 heap·검색 지연·복구 시간을 비교합니다. 인덱스 구조를 잘못 정한 뒤 서버만 늘리는 것보다 질의와 데이터 표현을 함께 설계하는 것이 먼저입니다.

## 득점 포인트

- shard 병렬성과 관리 비용을 비교한다.
- text와 keyword의 의미를 구분한다.
- mapping 성장과 복구 시간을 확인한다.

## 감점 포인트

- shard는 많을수록 무조건 좋다고 말한다.
- 모든 문자열을 같은 분석 필드로 처리한다.
- 동적 필드 증가를 제한하지 않는다.

## 더 파고들 거리
