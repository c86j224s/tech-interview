# 타임아웃과 작업 취소는 어떻게 다르며 어디까지 전파해야 하나요?

## 구두 답변

타임아웃은 결과를 기다리는 쪽이 정해진 시간을 넘겼다는 뜻이고, 취소는 더 이상 작업이 필요 없다는 의사를 실행하는 쪽에 전달하는 것입니다. 대기를 끝냈다고 실제 작업도 끝나는 것은 아닙니다. 그래서 요청 수명과 작업 수명을 따로 추적해야 합니다.

웹 요청이 취소됐는데 DB 쿼리와 하위 RPC가 계속 실행되면 이미 쓸모없어진 작업이 자원을 차지합니다. 저는 요청이 끝나는 데드라인을 하위 호출에 전달하고, 각 단계가 남은 시간 안에서만 기다리도록 하겠습니다. 단계마다 원래 타임아웃을 새로 주면 전체 요청 시간이 계속 늘 수 있습니다. 취소를 받으면 새 작업을 만들지 않고, 대기 중인 채널이나 I/O에서 빠져나와 보유 자원을 정리해야 합니다.

다만 취소할 수 없는 순간도 있습니다. DB가 이미 커밋했거나 외부 결제가 완료됐다면 취소 신호가 그 효과를 되돌리지는 않습니다. 저는 실행 전 취소, 실행 중 취소, 커밋 뒤 취소를 상태로 나누고, 마지막 경우에는 결과 확인이나 보상이 필요한지 업무 계약으로 정하겠습니다. 반드시 완료해야 할 작업은 요청 고루틴에 매달지 않고 내구성 있는 작업 큐로 넘기는 편이 낫습니다. 검증은 호출자에게 오류가 돌아왔는지만이 아니라 하위 작업과 연결이 실제로 정리되는지까지 확인하겠습니다.

## 득점 포인트

- **대기 종료와 실행 종료를 구분한다.** 취소 전달만으로 끝났다고 보지 않는다.
- **전체 시간 예산을 전파한다.** 단계마다 시간을 다시 시작하지 않는다.
- **커밋 이후의 의미를 정한다.** 취소와 롤백·보상은 다름을 설명한다.

## 감점 포인트

- **타임아웃이면 하위 작업도 멈춘다고 말한다.** 호출 대상이 취소에 반응해야 한다.
- **모든 취소를 실패로 되돌리면 된다고 말한다.** 이미 반영된 외부 효과가 있을 수 있다.
- **취소 함수 반환만 확인한다.** 실제 종료와 자원 반환을 검증해야 한다.

## 더 파고들 거리

- 부모 요청과 무관하게 완료할 작업에는 어떤 내구성과 소유권이 필요할까요?
- 취소와 정상 완료가 경합할 때 결과를 한 번만 전달하려면 어떻게 할까요?
- 하위 서비스가 데드라인을 지원하지 않으면 자원 고갈을 어떻게 제한할까요?
