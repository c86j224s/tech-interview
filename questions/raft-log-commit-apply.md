# Raft에서 로그가 복제된 뒤 커밋되고 상태 머신에 적용되는 각 시점은 어떻게 다르며 클라이언트 응답은 어디에 묶어야 하나요?

## 구두 답변

Raft의 로그는 팔로워 디스크에 저장된 시점, 클러스터가 그 엔트리를 커밋한 시점, 각 노드의 상태 머신이 명령을 적용한 시점을 나누어 이해해야 합니다. 팔로워 한 대가 저장했다는 것만으로는 리더 교체 뒤에도 유지될 기록이라고 확정할 수 없습니다. 커밋은 현재 리더가 정한 규칙에 따라 과반이 보유하고 이후 리더도 보존해야 하는 위치가 된 상태이며, 적용은 그 확정된 명령을 순서대로 업무 상태에 반영하는 단계입니다.

리더는 일반적으로 현재 term의 엔트리가 과반에 복제된 것을 이용해 커밋 인덱스를 전진시킵니다. 이전 term의 엔트리를 복제 수만으로 직접 커밋한다고 단순화하면 안 됩니다. 현재 term의 엔트리가 커밋되면서 그 앞의 연속된 로그가 함께 확정되는 것과, 과거 term 엔트리 자체를 직접 확정하는 것은 구분해야 합니다.

클라이언트 응답의 의미도 계약으로 정합니다. 커밋 성공만 기다리면 일부 조회 경로에서는 아직 적용되지 않은 값을 볼 수 있고, 외부 부수 효과까지 자동으로 한 번만 실행되는 것도 아닙니다. 상태 머신 적용은 재시작과 재전달을 고려해 결정적이고 멱등적으로 만들며, 요청 ID와 결과를 저장해 응답 직전 리더가 죽어도 재시도에서 같은 업무 결과를 찾게 하겠습니다. 외부 결제나 알림은 합의 로그의 순서와 별도의 전달·중복 방지 경계로 다뤄야 합니다.

검증은 복제 직후, 커밋 직후, 적용 직후 각각 프로세스를 중단하고 재시작합니다. 커밋 인덱스와 적용 인덱스의 차이, 클라이언트 재시도 결과, 외부 효과의 중복 여부를 따로 확인하겠습니다.

## 득점 포인트

- 복제 저장·커밋·상태 머신 적용을 시간 순서로 분리한다.
- 현재 term 커밋 규칙과 앞선 로그의 간접 확정을 구분한다.
- 클라이언트 결과와 외부 효과의 멱등성을 합의 로그와 별도로 설계한다.

## 감점 포인트

- 복제된 모든 로그가 즉시 절대 변경되지 않는다고 말한다.
- 모든 term의 엔트리를 복제 수만으로 직접 커밋한다고 말한다.
- 커밋된 명령은 외부 부수 효과도 자동으로 한 번만 실행된다고 말한다.

## 더 파고들 거리

- 응답 직전 리더가 죽었을 때 요청 ID로 결과를 어떻게 조회하나요?
- 상태 머신을 결정적으로 만들어야 하는 이유는 무엇인가요?
- 적용이 느린 팔로워에서 읽기를 허용할 조건은 무엇인가요?
