# 레거시 시스템의 사용자 요청과 데이터 소유권을 점진적으로 새 시스템으로 옮길 때 strangler 방식의 안전 조건은 무엇인가요?

## 구두 답변

strangler 방식은 기존 시스템을 한 번에 끄지 않고, 진입 라우터나 모듈 경계에서 기능·사용자 집단을 조금씩 새 시스템으로 전환하는 방법입니다. 기존 외부 계약을 유지하거나 호환 계층을 두고, 새 경로의 결과·오류·지연을 관찰하면서 전환 범위를 늘립니다. 먼저 읽기처럼 부수 효과가 작은 기능을 옮기고 쓰기는 권위 있는 소유자를 명확히 하는 것이 일반적으로 안전합니다.

예를 들어 계정 조회의 5%를 새 서비스로 보내 결과 차이를 비교할 수 있지만, 두 시스템이 동시에 계정 상태를 권위 있게 수정하면 부분 성공과 충돌이 생깁니다. 이중 쓰기를 한다면 어느 시스템이 원본인지, 실패를 어떻게 재처리할지, 순서를 어떻게 맞출지 명시해야 하며 단순히 두 곳에 호출하는 것으로 일관성이 생기지 않습니다. shadow traffic도 실제 결제·메일 같은 부수 효과가 실행되지 않도록 읽기 전용 또는 시뮬레이션 경로로 보내야 합니다.

전환 확대 기준은 오류율·p99·데이터 차이·남은 레거시 호출입니다. 라우팅을 되돌릴 때 새 시스템이 만든 데이터가 레거시 형식으로 표현되지 않을 수 있으므로, 호환 가능한 저장 형식과 역방향 읽기·보정 절차를 먼저 준비해야 합니다. 최종 제거에는 사용 경로가 없다는 증거, 보관·복구 요구, 운영자 도구 종료까지 포함합니다.

테스트는 사용자 단위·기능 단위 전환, 전환 중 장애, 쓰기 재시도, 양방향 데이터 차이, 롤백을 포함합니다. 구축 완료가 아니라 권위 소유권과 레거시 의존성이 실제로 사라졌을 때 전환 완료로 판단하겠습니다.

## 득점 포인트

- 작은 전환 단위와 외부 계약·관측을 유지한다.
- 읽기 비교와 권위 있는 이중 쓰기를 구분한다.
- 데이터 호환·롤백·레거시 제거 조건을 함께 계획한다.

## 감점 포인트

- 라우팅만 되돌리면 항상 원래 상태로 복귀한다고 말한다.
- 두 시스템에 동시에 쓰면 자동으로 안전하다고 말한다.
- 새 시스템 구축 완료를 마이그레이션 완료로 본다.

## 더 파고들 거리

- 사용자 단위 전환과 기능 단위 전환의 실패 범위는 어떻게 다른가요?
- 병행 운영 중 정책 차이를 어떤 비교 지표로 추적하나요?
