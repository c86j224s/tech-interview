# 로드밸런서 헬스 체크가 성공한 서버가 실제 요청을 실패할 수 있고, 배포 중 기존 연결도 실패할 수 있는 이유는 무엇인가요?

## 구두 답변

헬스 체크 성공은 정해진 시점에 정해진 경로가 성공했다는 의미이지 다음 실제 요청의 성공을 보장하지 않습니다. 프로세스가 살아 있는지 확인하는 liveness와 새 요청을 받을 준비가 됐는지 확인하는 readiness를 나눕니다. 예를 들어 프로세스가 응답해도 DB 연결 풀이 모두 고갈됐다면 실제 주문 요청은 실패할 수 있으므로, DB·큐 같은 의존성을 어디까지 검사할지 정해야 합니다. 외부 의존성을 모두 포함하면 공통 장애가 모든 서버를 동시에 제외할 수 있고, 너무 얕으면 실제 요청 처리의 장애를 놓칩니다.

종료할 서버는 먼저 readiness를 실패시켜 새 연결 유입을 막고, 로드밸런서와 endpoint에 상태가 전파될 시간을 둡니다. 이미 유지 중인 TCP·HTTP/2·스트리밍 연결은 헬스 체크 변화만으로 즉시 다른 서버로 이동하지 않으므로 `preStop`(종료 직전 실행할 정리 단계), connection draining(새 요청을 막고 기존 요청을 끝내는 과정), termination grace period(강제 종료 전 대기 시간), 클라이언트 재시도를 함께 설계합니다. 이 순서를 생략하면 체크는 실패했는데 기존 연결이 종료되어 배포 중 오류가 생깁니다. 드레이닝 중 긴 요청이 끝나지 않으면 무한 대기하지 않고 취소·재개·재시도 계약을 적용합니다.

테스트는 체크 경로 성공과 실제 DB 장애, readiness 전파 지연, 짧은 요청과 장기 스트리밍, 종료 제한 시간 초과를 분리해 재현합니다. 지표는 체크 응답만이 아니라 배포 중 오류율·재시도 폭증·완료율·연결 종료 결과를 봅니다. 헬스 체크를 깊게 만드는 것이 항상 안전한 것이 아니라, 기능별 격리와 종료 순서가 함께 맞아야 합니다.

## 득점 포인트

- liveness·readiness·실제 요청 성공의 검사 범위를 구분한다.
- 헬스 상태 전파와 기존 연결의 독립성을 드레이닝 순서로 설명한다.
- 실제 요청 오류와 스트리밍 종료를 검증 기준에 넣는다.

## 감점 포인트

- 헬스 체크 성공이면 모든 실제 요청도 성공한다고 말한다.
- 체크를 실패시키자마자 프로세스를 종료해도 안전하다고 말한다.
- 모든 외부 장애를 서버 생존 실패로 처리한다.

## 더 파고들 거리

- 긴 스트리밍 연결은 일반 요청과 다른 drain·재개 계약을 어떻게 갖나요?
- flapping readiness가 트래픽을 출렁이게 할 때 어떤 hysteresis를 둘까요?
- 종료 제한 시간을 넘긴 요청을 재시도할 때 중복 효과를 어떻게 막을까요?
