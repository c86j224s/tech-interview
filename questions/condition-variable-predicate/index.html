01

구두 답변

정의를 외우기보다, 원리와 조건을 연결해 설명해 보세요.

알림을 받은 스레드가 큐를 다시 확인하기 전에, 다른 스레드가 먼저 작업을 가져갈 수 있기 때문입니다. 따라서 깨어났다는 사실만 믿고 작업을 꺼내지 말고, 큐가 비어 있는지 다시 검사해야 합니다.

여기서 생산자는 큐에 작업을 넣는 스레드이고, 소비자는 작업을 꺼내 처리하는 스레드입니다. 소비자는 할 일이 없을 때 큐를 계속 확인하며 CPU를 쓰는 대신 **조건 변수(condition variable)**를 이용해 잠들어 기다릴 수 있습니다. 생산자는 작업을 넣은 뒤 알림을 보내 소비자를 깨웁니다. 다만 이 알림이 특정 작업을 그 소비자에게 예약해 주는 것은 아닙니다.

C++에서 소비자가 아래처럼 작성됐다고 하겠습니다. queue는 여러 소비자가 공유하는 정수 작업 큐, mutex는 그 큐의 접근을 보호하는 뮤텍스, cv는 대기와 알림에 쓰는 조건 변수입니다. 모든 스레드가 큐를 같은 뮤텍스로 보호하더라도 빈 큐를 if로 한 번만 확인하는 아래 코드는 안전하지 않습니다.

std::unique_lock<std::mutex> lock(mutex);
if (queue.empty()) {
    cv.wait(lock);
}
int job = queue.front(); // 깨어났어도 비어 있을 수 있습니다.
queue.pop();

wait는 뮤텍스를 놓고 대기에 들어가며, 반환하기 전에는 뮤텍스를 다시 획득합니다. 하지만 깨어난 스레드가 그 뮤텍스를 바로 얻는다는 보장은 없습니다. 다음 실행 순서가 가능합니다.

순서 실행 흐름 큐 상태
1 소비자 A가 빈 큐를 보고 wait 비어 있음
2 생산자가 작업 하나를 넣고 A에게 알림 작업 1개
3 A가 락을 다시 얻기 전에 소비자 B가 들어와 작업을 꺼냄 비어 있음
4 A가 락을 얻고 wait에서 반환 여전히 비어 있음

A는 알림을 받았지만 작업을 소유한 것은 아닙니다. if는 이미 검사한 조건을 다시 보지 않으므로 빈 큐에 front()를 호출하게 됩니다. 또 조건 변수는 알림 없이 깨어나는 **허위 깨움(spurious wakeup)**도 허용합니다. 둘 다 처리하려면 깨어날 때마다 조건을 다시 확인해야 합니다.

std::unique_lock<std::mutex> lock(mutex);
while (queue.empty()) {
    cv.wait(lock);
}
int job = queue.front();
queue.pop();

이제 A가 락을 얻었는데 작업이 없다면 다시 기다립니다. 조건 검사부터 작업을 꺼내는 부분까지 락을 유지하므로, 검사 직후 다른 소비자가 작업을 가져가는 것도 막습니다.

C++에서는 조건을 받는 wait를 사용하면 반복 검사를 더 간결하게 표현할 수 있습니다. 아래는 종료가 시작되면 남은 작업을 처리하고, 큐까지 비었을 때 소비자 함수를 끝내는 정책의 예입니다.

std::unique_lock<std::mutex> lock(mutex);
cv.wait(lock, [&] { return stopping || !queue.empty(); });
if (queue.empty()) {
    return; // 여기서는 stopping이 true인 상태입니다.
}
int job = queue.front();
queue.pop();
lock.unlock();
process(job); // 긴 처리는 큐의 락 밖에서 실행합니다.

생산자는 같은 뮤텍스로 큐에 작업을 넣은 뒤 알리고, 종료를 담당하는 쪽은 같은 뮤텍스로 stopping을 바꾼 뒤 기다리는 소비자들을 깨워야 합니다. 알림을 기억하는 것이 아니라, 락으로 보호한 상태를 다시 검사하는 구조라고 이해하면 됩니다.

02

득점 포인트

이해가 드러나는 지점을 확인해 보세요.

  • 알림과 자원 소유를 구분한다. 알림을 받은 A보다 B가 먼저 락을 얻어 작업을 소비할 수 있다는 순서를 설명한다.
  • wait의 잠금 계약을 설명한다. 대기하면서 락을 놓고, 반환 전에 다시 획득하며, 조건 확인과 큐 접근은 같은 락 아래에서 수행한다.
  • 종료 정책까지 구체화한다. 작업 존재와 종료 상태를 대기 조건에 넣고, 종료 시 남은 작업을 처리할지 버릴지 명시한다.
03

감점 포인트

놓치기 쉬운 조건과 오해를 짚어 보세요.

  • “허위 깨움만 없으면 if도 안전하다”고 말한다. 다른 소비자가 먼저 상태를 바꾸는 경쟁만으로도 문제가 생긴다.
  • “notify_one이 큐의 작업 하나를 그 스레드에 넘겨준다”고 말한다. 알림은 락 획득 순서나 작업 소유권을 보장하지 않는다.
  • wait 전에 락을 직접 풀고 나중에 대기한다. 조건 확인과 대기 등록 사이에 알림이 지나가는 틈을 만들 수 있다. 잠금 해제와 대기를 연결하는 조건 변수의 API를 사용해야 한다.
