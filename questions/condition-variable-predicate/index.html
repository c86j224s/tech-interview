조건 변수는 왜 if가 아니라 while로 조건을 확인하나요?

01

구두 답변

정의를 외우기보다, 원리와 조건을 연결해 설명해 보세요.

조건 변수의 알림은 원하는 조건이 지금도 참이라는 보장이 아니라, 조건을 다시 확인할 기회라고 보기 때문입니다. 알림 없이 깨어나는 허위 깨움도 가능하고, 알림을 받아 락을 다시 얻는 사이에 다른 스레드가 데이터를 먼저 가져갈 수도 있습니다. 따라서 보호된 상태를 다시 확인하면서 기다려야 합니다.

작업 큐가 비어 있으면 소비자가 기다리는 예를 들겠습니다. 생산자가 작업 하나를 넣고 소비자를 깨웠는데, 그 소비자가 락을 얻기 전에 다른 소비자가 작업을 꺼낼 수 있습니다. if로 한 번만 검사했다면 깨어난 뒤 빈 큐에서 꺼내게 됩니다. while로 큐 상태를 확인하면 작업이 없을 때 다시 기다립니다. 조건 변수의 wait가 락을 놓고 잠드는 과정을 원자적으로 연결해 주는 것도 중요합니다. 락을 별도로 풀고 나중에 기다리면 그 사이 알림을 놓칠 수 있습니다.

저는 큐의 상태를 같은 뮤텍스로 보호하고, 생산자가 상태를 바꾼 뒤 알리도록 하겠습니다. 종료 신호도 같은 조건식에 포함해 서버 종료 때 소비자가 영원히 기다리지 않게 하겠습니다. 알림 한 번으로 한 작업자를 깨울지 전부 깨울지는 실제 조건에 따라 정합니다. 모든 작업자가 다시 잠들 뿐인데 전부 깨우면 경합만 커지므로, 단일 작업 추가와 전체 종료 같은 경우를 구분하겠습니다.

02

득점 포인트

이해가 드러나는 지점을 확인해 보세요.

  • 알림과 조건을 구분한다. 깨어난 시점의 상태를 락 아래에서 다시 검사한다.
  • 경쟁 실행 순서를 설명한다. 다른 소비자가 먼저 작업을 가져갈 수 있음을 짚는다.
  • 종료 경로까지 설계한다. 작업 존재와 종료 상태를 같은 대기 조건으로 관리한다.
03

감점 포인트

놓치기 쉬운 조건과 오해를 짚어 보세요.

  • 알림 횟수를 작업 개수처럼 취급한다. 조건 변수는 상태를 저장하는 큐가 아니다.
  • 락을 풀고 따로 기다리면 된다고 말한다. 알림 유실 구간이 생길 수 있다.
  • 허위 깨움만 없으면 if가 안전하다고 말한다. 다른 소비자가 조건을 바꿀 수 있다.
04

더 파고들 거리

하나 더 질문하며 이해의 범위를 넓혀 보세요.

  • notify를 락 안과 밖에서 호출할 때 정확성과 경합은 어떻게 달라질까요?
  • 조건 변수 대신 세마포어를 쓰면 어떤 상태를 따로 관리하지 않아도 될까요?
  • 시간 제한 대기에서 반복 깨움이 전체 데드라인을 늘리지 않게 하려면 어떻게 할까요?
