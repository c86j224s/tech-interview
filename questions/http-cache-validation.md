# 개인정보가 포함된 HTTP 응답을 캐시하면서 최신 여부도 확인하려면 Cache-Control, ETag, 304를 어떻게 조합하나요?

## 구두 답변

HTTP 캐시는 응답을 저장할 수 있는지와 저장된 응답을 원본 확인 없이 재사용해도 되는지를 나누어 판단해야 합니다. `Cache-Control: max-age=60`처럼 신선도 수명을 정하면 그 기간 동안 조건을 만족하는 캐시는 원본에 다시 묻지 않고 응답할 수 있습니다. `no-cache`는 저장 금지가 아니라 재사용 전 검증을 요구하는 지시자이고, `no-store`는 요청·응답을 저장하지 말라는 지시자입니다. `private`는 공유 캐시가 저장하지 못하게 하지만 개인 브라우저 캐시까지 금지하거나 콘텐츠를 암호화하지는 않습니다.

검증에는 응답의 `ETag`를 사용합니다. 캐시가 다음 요청에 `If-None-Match`를 보내면 서버는 현재 표현과 태그가 같을 때 본문 없이 `304 Not Modified`를 반환할 수 있습니다. 그러면 캐시는 기존 본문을 재사용하면서 304의 헤더로 메타데이터를 갱신합니다. 태그가 달라지면 서버는 새 본문을 200으로 보내야 합니다. ETag가 있다고 개인정보가 보호되는 것은 아니며, 태그 자체가 사용자 정보를 드러내지 않도록 불투명한 값을 사용하겠습니다.

개인 사용자 정보나 권한에 따라 다른 응답은 기본적으로 `Cache-Control: private` 또는 민감도가 높으면 `no-store`를 검토하겠습니다. 공유 캐시가 저장할 수 있는 응답이라면 `Vary`로 응답을 바꾸는 요청 헤더를 지정하고, 인증 응답을 공개 캐시가 재사용하지 않는지 확인해야 합니다. HTTPS는 전송 중 내용을 보호하지만 브라우저나 프록시가 저장한 뒤 다른 문맥에서 재사용하는 정책을 대신 정하지 않습니다.

조회가 공개 데이터이고 변경이 드물면 긴 freshness와 ETag를 조합해 요청과 본문 전송을 줄이겠습니다. 변경이 잦거나 사용자가 즉시 최신 값을 봐야 하면 짧은 수명과 조건부 검증을 선택하고, 저장·304·200 비율과 개인정보 응답의 캐시 경로를 관찰하겠습니다. 캐시를 지우는 것만으로 모든 브라우저와 중간 캐시의 사본이 즉시 사라진다고 단정하지 않겠습니다.

## 득점 포인트

- freshness와 검증 및 저장 금지 지시자를 구분한다.
- ETag·If-None-Match·304의 요청과 응답 흐름을 설명한다.
- 개인정보 캐시에서 private·no-store·HTTPS의 한계를 구체적으로 판단한다.

## 감점 포인트

- no-cache가 저장 자체를 금지한다고 말한다.
- ETag가 있으면 개인정보가 암호화된다고 말한다.
- private 응답을 공유 캐시가 자유롭게 재사용해도 된다고 말한다.
