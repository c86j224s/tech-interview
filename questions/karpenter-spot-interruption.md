# Spot 노드에 중단 통지가 왔을 때 큐 작업·게임 세션·대체 용량을 어떻게 처리해야 하나요?

## 구두 답변

Spot 중단 통지는 노드가 곧 회수될 수 있음을 알려 주어 새 작업을 멈추고 기존 작업을 정리할 기회를 줍니다. 그러나 모든 장애에 통지가 오거나 정해진 시간을 항상 확보할 수 있는 것은 아니므로, 통지 없는 즉시 종료에도 재시작·재처리 가능한 설계를 기본으로 둡니다. Karpenter의 interruption handling과 노드 drain만으로 업무 완료가 보장되지는 않습니다.

큐 소비자는 통지를 감지하면 새 메시지 수신을 중지하고, 이미 시작한 작업을 제한 시간 안에 완료한 뒤 ACK(처리 완료 확인)·커밋하고 종료합니다. 제한 시간 안에 끝나지 않은 작업은 ACK하지 않고 재전달되게 해야 작업이 사라지지 않습니다. 끝나지 않은 작업은 ACK 전에 중단해 재전달되게 하거나 checkpoint(중간 진행 위치를 저장한 기록)로 재개하고, 어느 쪽이든 외부 효과는 멱등적으로 처리합니다. 그래야 통지가 늦거나 아예 오지 않아 프로세스가 끊겨도 같은 결제가 두 번 반영되지 않습니다. 게임 세션처럼 메모리 상태가 핵심이면 짧은 시간에 전체 상태를 옮길 수 있다고 가정하지 말고 상태 복제·체크포인트·재접속 위치를 설계합니다.

대체 노드도 같은 Spot(중단될 수 있지만 저렴한 용량)이 즉시 생긴다는 보장이 없습니다. 여러 인스턴스 유형과 가용 영역(AZ)을 허용하고, 핵심 최소 용량은 on-demand(상대적으로 안정적이지만 비싼 일반 용량)나 다른 pool로 확보할지 비용 정책을 정하겠습니다. 한 유형만 고집하면 중단 뒤 대체 노드가 생기지 않는 사례가 발생합니다. 통지 있는 회수와 통지 없는 장애를 각각 시험해 drain 완료, 작업 유실·중복, 대체 노드 Ready 시간, 사용자 재접속 결과를 확인합니다.

## 득점 포인트

- 통지의 기회와 갑작스러운 장애 내구성을 분리한다.
- 큐 작업과 메모리 세션의 복구 전략을 각각 제시한다.
- 대체 용량의 가용성·비용·장애 영역을 운영 정책에 포함한다.

## 감점 포인트

- 항상 충분한 사전 통지가 온다고 말한다.
- 대체 노드가 생기면 메모리 상태가 자동 이동한다고 말한다.
- 작업 효과를 남기기 전에 ACK해 종료를 빠르게 한다.

## 더 파고들 거리

- 중단 통지 전달 경로가 고장 났을 때 감지·대체 신호를 어떻게 설계할까요?
- checkpoint 주기와 허용 가능한 유실 작업량을 어떤 식으로 연결할까요?
- on-demand와 Spot을 섞을 때 핵심 최소 용량과 비용 상한을 어떻게 계산할까요?
