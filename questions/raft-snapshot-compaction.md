# Raft 로그를 스냅샷으로 압축할 때 복구 기준과 이전 로그 삭제 순서를 어떻게 보장하나요?

## 구두 답변

Raft 스냅샷은 업무 데이터 덤프만 저장하는 파일이 아닙니다. 상태 머신이 어느 로그 인덱스와 term까지 적용한 결과인지인 `lastIncludedIndex`와 `lastIncludedTerm`을 함께 보관해야 이후 로그를 올바른 위치에서 이어 붙이고, 이미 적용한 명령을 다시 실행하지 않습니다. 현재 구성 정보나 요청 중복 방지 기록이 상태 머신의 의미를 구성한다면 그것도 같은 기준 시점에 포함해야 합니다.

쓰기와 스냅샷 생성이 동시에 일어날 때는 서로 다른 시점의 필드가 섞이지 않는 일관된 상태를 만들어야 합니다. 구현은 상태 머신을 잠깐 정지하거나 불변 스냅샷을 복사하고, 복사 완료 후 해당 위치의 로그와 파일을 내구성 있게 기록한 다음 메타데이터를 원자적으로 교체하는 순서를 택할 수 있습니다. 스냅샷이 안전하게 재시작 가능한 상태가 되기 전에 이전 로그를 삭제하면 복구 경로가 끊깁니다.

필요한 로그가 이미 삭제된 뒤처진 팔로워에게는 InstallSnapshot으로 스냅샷을 보내야 합니다. 수신자는 임시 파일에 검증하며 기록하고 체크섬·메타데이터를 확인한 뒤 원자적으로 상태를 교체해야 하며, 설치 중인 부분 상태를 읽기 경로에 노출하면 안 됩니다. 설치 뒤에는 스냅샷 인덱스 다음 로그부터 재생하고, 이전 버전의 메모리나 파일 참조가 살아 있는 동안 삭제하지 않도록 수명을 관리합니다.

주기를 짧게 하면 재시작·팔로워 복구 시간이 줄지만 복사와 I/O, 쓰기 시 복사 메모리가 커집니다. 로그 증가량, 팔로워 지연, 복구 목표를 부하 중에 측정해 정하겠습니다. 테스트는 스냅샷 생성 중 중단, 전송 중 중단, 새 로그 유입, 재시작 후 중복 요청을 포함해야 합니다.

## 득점 포인트

- 상태와 적용 인덱스·term을 한 복구 기준으로 보관한다.
- 내구화와 메타데이터 교체 뒤 로그를 삭제하는 순서를 설명한다.
- 뒤처진 팔로워의 원자적 설치와 이후 로그 재생을 다룬다.

## 감점 포인트

- 데이터 덤프만 있으면 스냅샷 이전 로그를 즉시 삭제해도 된다고 말한다.
- 스냅샷 설치 중 부분 상태를 서비스해도 된다고 말한다.
- 요청 중복 처리 기록은 스냅샷과 항상 무관하다고 말한다.

## 더 파고들 거리

- 큰 스냅샷 전송이 정상 복제를 막지 않게 어떤 예산을 둘까요?
- 복구 뒤 같은 요청이 다시 왔을 때 결과를 어떻게 보존하나요?
