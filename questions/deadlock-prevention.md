# 교착 상태는 어떤 조건에서 발생하고, 락을 사용하는 코드에서는 어떻게 예방하나요?

## 구두 답변

교착 상태는 여러 실행 흐름이 서로가 가진 자원이 해제되기를 기다리면서 더 이상 진행하지 못하는 상태입니다. 예를 들어 첫 번째 스레드가 락 A를 잡고 B를 기다리는데, 두 번째 스레드는 B를 잡고 A를 기다리면 어느 쪽도 다음 단계로 갈 수 없습니다.

일반적인 자원 모델에서는 상호 배제, 점유와 대기, 비선점, 순환 대기라는 네 조건이 함께 성립할 때 교착 상태가 가능해집니다. 한 번에 하나만 자원을 사용할 수 있고, 자원을 가진 채 다른 자원을 기다리며, 가진 자원을 외부에서 강제로 회수할 수 없고, 대기 관계가 고리를 이루는 것입니다. 다만 네 조건이 가능한 구조라는 사실만으로 매번 교착 상태가 발생한다는 뜻은 아닙니다.

락을 여러 개 사용하는 코드에서는 잠금 순서를 통일하는 방법이 실용적입니다. 모든 경로에서 A를 잡은 뒤 B를 잡도록 하면, B를 가진 채 A를 기다리는 반대 경로가 없어져 순환 대기를 끊을 수 있습니다. 동적으로 정해지는 여러 객체를 잠근다면 객체의 안정적인 키 같은 기준으로 전체 순서를 정할 수 있습니다. 이 규칙은 일부 함수가 아니라 모든 관련 경로에서 지켜져야 합니다.

락을 가진 상태에서 오래 걸리는 I/O나 외부 콜백을 호출하지 않는 것도 중요합니다. 대기 시간이 길어질 뿐 아니라, 호출한 코드가 다시 같은 락이나 다른 락을 요구해서 예상하지 못한 대기 관계를 만들 수 있기 때문입니다. 임계 구역을 줄이되, 락을 풀고 다시 잡았다면 그사이에 상태가 바뀌었는지도 확인해야 합니다.

타임아웃이나 락 획득 실패 후 재시도를 사용할 수도 있지만, 실패했을 때 이미 잡은 자원을 해제하고 변경 중이던 상태를 정리할 수 있어야 합니다. 무조건 재시도만 하면 서로 계속 양보하며 진행하지 못하는 라이브락이 생길 수 있습니다. 따라서 일관된 잠금 순서를 기본으로 하고, 취소와 복구가 가능한 경계를 함께 설계하겠습니다.

## 득점 포인트

- **교착 상태를 구체적인 대기 관계로 설명한다.** 단순히 느리거나 오래 기다리는 상태와 구분한다.
- **네 조건을 예방 방법과 연결한다.** 잠금 순서를 통일하면 순환 대기 조건을 끊을 수 있다고 설명한다.
- **규칙의 적용 범위를 고려한다.** 모든 잠금 경로와 외부 호출, 재진입 경로가 같은 규칙을 따라야 한다고 짚는다.
- **실패 후 정리까지 설명한다.** 타임아웃 이후 자원 해제, 상태 복구, 재시도 정책이 필요하다고 설명한다.

## 감점 포인트

- **“네 조건이 존재하면 항상 교착 상태다”라고 말한다.** 조건이 가능한 구조와 실제로 진행 불가능한 대기 상태가 형성된 상황을 구분해야 한다.
- **“재귀 뮤텍스를 쓰면 교착 상태가 해결된다”고 말한다.** 같은 스레드의 재획득은 허용할 수 있지만 여러 스레드 사이의 순환 대기는 해결하지 못한다.
- **“타임아웃만 넣으면 안전하다”고 단정한다.** 대기 중단 이후 자원과 부분 변경을 정리하지 못하면 다른 문제가 남는다.
- **“락을 풀었다 다시 잡아도 이전에 읽은 상태는 유효하다”고 가정한다.** 다른 실행 흐름이 상태를 변경했을 가능성을 재검증해야 한다.

## 더 파고들 거리

- 교착 상태, 기아 상태, 라이브락은 관찰되는 현상과 해결 방법에서 어떻게 다를까요?
- 두 계정 사이의 이체처럼 잠금 대상이 동적으로 정해지는 작업에서는 잠금 순서를 어떻게 정할까요?
- 락을 잡은 상태에서 콜백을 호출해야 하는 API를 어떻게 재설계할 수 있을까요?
- 운영 중인 서버가 멈춘 것처럼 보일 때 스레드 덤프와 잠금 정보를 이용해 교착 상태를 어떻게 확인할까요?
