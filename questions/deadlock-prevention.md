# 교착 상태는 어떤 조건에서 발생하고, 락을 사용하는 코드에서는 어떻게 예방하나요?

## 구두 답변

교착 상태는 여러 실행 흐름이 서로 가진 자원을 기다려서 아무도 진행할 수 없는 상태입니다. 락이 잠시 붐비는 것과는 다릅니다. 첫 스레드가 A를 잡고 B를 기다리는데, 다른 스레드는 B를 잡고 A를 기다리면 락이 풀릴 일이 없는 것이죠.

이때 자원을 독점하고, 하나를 가진 채 다른 것을 기다리고, 남이 강제로 빼앗을 수 없고, 대기 관계가 고리를 이룹니다. 이것이 교착을 설명하는 네 가지 Coffman 조건입니다. 실제 코드를 고칠 때 저는 조건 이름을 나열하기보다 **어떤 대기 관계를 끊을 수 있는지** 보겠습니다.

두 계정의 잔액을 함께 바꾸는 경우라면 계정 ID가 작은 쪽부터 잠그는 식으로 순서를 통일하겠습니다. 모든 경로가 같은 순서로 잡으면 서로 반대 순서로 기다리는 고리를 만들지 않기 때문입니다. C++의 scoped_lock 같은 다중 락 획득 도구도 쓸 수 있지만, 호출 전에 이미 잡은 다른 락까지 해결해 주는 것은 아닙니다. 따라서 함수 하나뿐 아니라 그 함수를 부르는 경로도 봐야 합니다.

특히 락을 잡은 채 콜백이나 외부 요청의 완료를 기다리는 코드는 주의하겠습니다. 상대가 다시 같은 락을 필요로 하면 코드에서 바로 보이지 않는 대기 고리가 생깁니다. 가능하면 락 안에서는 필요한 상태만 읽고 외부 작업은 밖에서 하겠습니다. 대신 돌아와서 변경을 적용하기 전에는 버전이 바뀌었는지 다시 확인해야 합니다. 락을 풀었던 사이의 변경을 무시하면 교착은 줄여도 데이터가 잘못될 수 있습니다.

운영에서 멈춤이 의심된다면 시간 간격을 두고 스레드 덤프를 받아 같은 락의 소유자와 대기자가 유지되는지 확인하겠습니다. DB라면 교착 그래프로 관련 쿼리와 획득 순서를 보겠습니다. 타임아웃을 넣는 경우에도 이미 잡은 자원을 해제하고 부분 변경을 정리할 수 있어야 합니다. **기다림을 중단시키는 것과 안전하게 복구하는 것은 다르기 때문에**, 재시도까지 포함해 실제로 다시 진행되는지 확인하겠습니다.

## 득점 포인트

- **경합과 교착을 대기 관계로 구분한다.** 잠깐의 지연과 스스로 풀리지 않는 순환 대기를 구별한다.
- **잠금 순서를 사례에 적용한다.** 계정 ID 순서 같은 일관된 기준이 순환 대기를 어떻게 끊는지 설명한다.
- **락 밖으로 작업을 옮기는 비용을 설명한다.** 외부 호출을 분리한 뒤 상태 버전을 재검증해야 함을 짚는다.
- **진단과 복구를 구체화한다.** 덤프·교착 그래프로 경로를 찾고 자원 해제와 부분 변경 정리를 확인한다.

## 감점 포인트

- **“락을 오래 기다리면 교착이다”라고 말한다.** 소유자와 대기자의 의존 관계 및 실제 진행 여부를 봐야 한다.
- **“RAII를 쓰면 교착이 없다”고 말한다.** 범위 종료 시 해제는 순환 대기를 막는 보장이 아니다.
- **“외부 호출 전에 락을 풀기만 하면 된다”고 말한다.** 다시 잠근 시점에는 앞서 읽은 상태가 유효하지 않을 수 있다.
- **“타임아웃 뒤 바로 재시도한다”고 말한다.** 자원과 부분 상태를 정리하지 않으면 문제가 남거나 경쟁이 반복된다.
