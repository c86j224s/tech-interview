# 고루틴은 가볍다는데, 요청마다 계속 만들어도 괜찮나요?

## 구두 답변

고루틴이 운영체제 스레드보다 가벼운 실행 단위인 것은 맞지만, 비용이 없거나 개수를 무제한으로 늘려도 된다는 뜻은 아닙니다. 고루틴마다 스택과 런타임 관리 비용이 있고, 실행 중인 작업이 버퍼나 연결 같은 자원을 잡고 있을 수도 있습니다. 요청마다 고루틴을 만드는 방식 자체는 흔하지만, 동시에 살아 있는 작업 수와 종료 조건을 관리해야 합니다.

예를 들어 요청이 들어올 때마다 느린 외부 API를 호출하는 고루틴을 만든다고 하겠습니다. 외부 응답 시간이 길어지면 새 요청이 들어오는 동안 기존 고루틴이 끝나지 않아 개수가 쌓입니다. 도착률이 같아도 처리 시간이 늘면 진행 중인 작업 수가 증가하므로, 결국 메모리나 연결 풀 같은 다른 자원을 소진할 수 있습니다.

종료되지 않는 고루틴도 문제입니다. 결과를 받던 요청이 취소됐는데 작업 고루틴이 아무도 읽지 않는 채널로 계속 전송을 기다리는 경우가 있습니다. 이 고루틴은 CPU를 거의 사용하지 않아도 스택과 참조 중인 데이터를 계속 유지합니다. 가비지 컬렉터가 있다고 해서 이런 실행 흐름을 자동으로 종료시켜 주지는 않습니다.

그래서 고루틴을 시작할 때 누가 종료를 책임지는지, 무엇을 기다리는지, 취소됐을 때 그 대기에서 빠져나올 수 있는지 정해야 합니다. `context`를 전달하더라도 실제 코드가 취소 신호를 확인하거나 호출한 API가 취소를 지원해야 합니다. 채널 송수신도 필요한 경우 `select`에서 취소 신호를 함께 기다리도록 구성합니다.

부하가 커질 수 있는 작업은 세마포어나 제한된 작업자 풀로 동시 실행 수를 제어하겠습니다. 이때 고루틴을 무제한으로 만든 뒤 세마포어 앞에서 기다리게 하면 대기 고루틴은 계속 쌓이므로, 진입 단계의 대기열과 요청 거절 기준까지 정해야 합니다. 결국 고루틴의 가벼움보다 작업의 수명과 시스템이 감당할 수 있는 동시성을 관리하는 것이 핵심입니다.

## 득점 포인트

- **고루틴의 비용과 보유 자원을 함께 설명한다.** 스택뿐 아니라 버퍼, 연결, 참조 중인 데이터도 고려한다.
- **지연 증가가 동시 작업 수 증가로 이어짐을 설명한다.** 요청률이 일정해도 느린 의존성 때문에 작업이 누적될 수 있다고 짚는다.
- **구체적인 누수 경로를 제시한다.** 수신자가 사라진 채널 전송이나 취소되지 않는 대기를 예로 든다.
- **취소와 진입 제어를 함께 다룬다.** 실행 중인 작업 수뿐 아니라 대기 중인 작업 수와 종료 조건도 제한한다.

## 감점 포인트

- **“GC가 사용하지 않는 고루틴을 알아서 정리한다”고 말한다.** 블로킹된 고루틴은 단순한 미참조 객체와 다르며 명시적인 종료 경로가 필요하다.
- **“context를 취소하면 모든 하위 작업이 즉시 중단된다”고 말한다.** 취소는 협력적이며 코드와 호출 대상이 신호에 반응해야 한다.
- **“버퍼 채널을 쓰면 고루틴 누수가 사라진다”고 말한다.** 버퍼가 차거나 다른 대기 경로가 있으면 여전히 종료되지 않을 수 있다.
- **“작업자 수만 제한하면 대기열 크기는 상관없다”고 말한다.** 무제한 대기열도 메모리와 지연을 증가시킨다.

- CPU 중심 작업과 I/O 중심 작업은 동시 실행 수를 어떤 기준으로 다르게 정해야 할까요?
