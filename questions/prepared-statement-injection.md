# 검색어를 SQL 문자열에 이어 붙인 코드가 위험합니다. 파라미터 바인딩으로 무엇을 막고 동적 식별자는 어떻게 처리하나요?

## 구두 답변

사용자 입력을 SQL 문장의 문자열에 이어 붙이면 입력이 데이터가 아니라 SQL 문법으로 해석될 수 있습니다. 검색어에 따옴표나 조건을 넣는 것처럼 문장 구조를 닫고 다른 조건을 추가하는 입력이 들어오면, 원래 의도한 한 행 검색이 아니라 다수 행 조회나 변경으로 이어질 수 있습니다. 파라미터 바인딩은 SQL 구조를 먼저 준비하고 값은 별도의 매개변수로 전달해, 값 안의 특수 문자가 SQL 연산자로 해석되지 않게 합니다. 예를 들어 문장은 `SELECT ... WHERE username = ?`처럼 고정하고 `?`에 사용자 이름을 바인딩합니다.

준비된 문장은 반복 실행에서 파싱·계획 비용을 줄일 수도 있지만, 보안의 핵심은 성능이 아니라 코드와 값의 분리입니다. 바인딩은 문자열·숫자·날짜의 타입 처리도 드라이버에 맡길 수 있어 수동 인용보다 안전합니다. 그래도 테이블명, 컬럼명, 정렬 방향처럼 SQL 구조에 들어가는 식별자는 일반적인 값 파라미터로 바인딩할 수 없습니다. `ORDER BY ?`가 컬럼 선택으로 동작한다고 기대하면 안 됩니다.

동적 식별자가 필요하면 허용 목록으로 애플리케이션의 논리 이름을 실제 컬럼명에 매핑하고, 허용되지 않은 값은 거부해야 합니다. 정렬 방향도 `asc`와 `desc`만 별도로 검사합니다. 식별자 인용 함수가 있는 드라이버라면 검증된 식별자에 한해 사용할 수 있지만, 사용자 입력 전체를 그대로 인용하는 방식에 의존하지 않겠습니다. `LIKE` 검색에서는 파라미터 바인딩을 하더라도 `%`와 `_`가 와일드카드라는 별도 의미가 있으므로, 문자 그대로 찾을지 패턴 검색을 허용할지 정하고 필요하면 이스케이프 규칙과 `ESCAPE` 절을 적용해야 합니다.

파라미터 바인딩만으로 권한 검사가 생기는 것도 아닙니다. 조회한 행이 현재 사용자의 테넌트에 속하는지, 변경 권한이 있는지는 별도 조건과 인가 정책으로 확인해야 합니다. 따라서 값은 바인딩하고 구조는 허용 목록으로 통제하며, 로그와 오류 응답에 원문 입력이나 민감한 SQL을 노출하지 않는 구성을 기본으로 삼겠습니다.

## 득점 포인트

- SQL 구조와 사용자 값을 분리하는 파라미터 바인딩의 보안 효과를 설명한다.
- 컬럼명·정렬 방향 같은 동적 식별자는 값 바인딩 대상이 아니며 허용 목록이 필요함을 짚는다.
- LIKE 와일드카드와 인가 검사가 별도의 문제라는 조건을 덧붙인다.

## 감점 포인트

- 문자열에서 따옴표만 올바르게 이스케이프하면 모든 SQL Injection이 해결된다고 말한다.
- Prepared Statement를 쓰면 테이블명과 컬럼명도 자동으로 안전하게 바인딩된다고 단정한다.
- SQL Injection 방어가 행 소유권과 권한 검사를 대신한다고 설명한다.

## 더 파고들 거리

- 사용하는 드라이버가 서버 측 준비와 클라이언트 측 에뮬레이션을 어떻게 구분하는지 확인해 보세요.
- 허용 목록 기반 정렬과 LIKE 이스케이프를 언어별 API로 구현해 보세요.
- 파라미터화된 오류 로그에서 공격 분석에 필요한 정보와 민감정보 비노출을 어떻게 균형 잡을지 정해 보세요.
