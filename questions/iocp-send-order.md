# 여러 스레드가 같은 소켓에 메시지를 WSASend로 보냅니다. 제출 순서와 완료 순서가 다를 때 메시지와 버퍼를 어떻게 관리하나요?

## 구두 답변

애플리케이션의 메시지 순서, 소켓에 제출하는 바이트 순서, 완료 처리 순서를 구분해야 합니다. TCP는 스트림의 바이트 순서를 전달하지만 서로 다른 스레드가 여러 번 나눠 보낸 논리 메시지를 자동으로 하나씩 묶어 주지는 않습니다. 완료 통지도 애플리케이션의 메시지 처리 순서와 같다고 가정하지 않겠습니다.

예를 들어 메시지 A의 헤더와 본문을 서로 다른 호출로 보내는 사이에 메시지 B의 쓰기가 끼면, 받는 쪽은 A 헤더 다음에 B 데이터를 읽을 수 있습니다. TCP가 바이트 순서를 지켜도 잘못 섞어 제출한 애플리케이션 프레임을 고쳐 주지는 않습니다. 연결별로 완성된 프레임을 큐에 넣고 제출 책임을 한곳에 두는 이유입니다.

저는 연결별 송신 큐에 완성된 프레임을 넣고 한 소유자가 제출 순서를 관리하도록 하겠습니다. 여러 미완료 송신을 허용한다면 각 버퍼의 수명과 제출 순서에 대한 Winsock 계약을 확인하고, 완료가 다른 순서로 처리돼도 큐 상태가 깨지지 않게 해야 합니다. 처음에는 제한된 in-flight 송신으로 단순하게 구현하고 실제 병목이 확인될 때만 병렬 제출을 늘리겠습니다.

완료 바이트 수와 오류도 확인하고, 실패한 연결에 남은 메시지를 어떻게 처리할지 정해야 합니다. 상대가 느리면 송신 큐가 계속 커지므로 상한을 두고 메시지의 성격에 따라 생산을 늦추거나 연결을 종료할 수 있습니다. 테스트는 다중 생산자와 큰 프레임, 연결 종료가 겹치는 경우를 재현합니다. 중요한 것은 완료를 많이 받는 것이 아니라 상대가 해석하는 메시지 순서와 자원 수명이 맞는지입니다.

## 득점 포인트

- **세 가지 순서를 나눈다.** 메시지·제출·완료를 구별한다.
- **연결별 소유권을 둔다.** 다중 생산자와 버퍼 수명을 관리한다.
- **병렬화 조건을 측정한다.** in-flight 수와 대기열 상한을 정한다.

## 감점 포인트

- **스레드 안전 API면 논리 메시지도 원자적이라고 말한다.** 호출 간 조각이 섞일 수 있다.
- **완료 순서가 제출 순서와 항상 같다고 말한다.** 처리 스케줄링을 구분해야 한다.
- **느린 상대에는 버퍼만 늘린다.** 메모리 고갈과 지연이 커진다.

## 더 파고들 거리

- scatter/gather 버퍼를 사용할 때 배열과 실제 데이터의 수명은 어떻게 다를까요?
- 송신 완료를 받은 뒤에도 상대 애플리케이션의 처리 확인 응답이 필요한 이유는 무엇인가요?
- 연결 재접속 때 미확인 메시지를 어떤 ID로 재전달할까요?
