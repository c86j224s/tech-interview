# Elasticsearch가 문서 저장 성공을 반환했는데 바로 실행한 검색에는 문서가 없습니다. 왜 지연되며 즉시 확인이 필요한 화면은 어떻게 만드나요?

## 구두 답변

색인 요청 성공과 검색에 보이는 시점은 다를 수 있습니다. Elasticsearch는 보통 refresh를 통해 새 데이터를 검색 가능한 세그먼트 상태로 노출하는 near real-time 구조입니다. 따라서 쓰기 응답을 받자마자 검색 결과에 반드시 나타난다고 가정하지 않겠습니다.

refresh는 최근 색인 변경을 검색하는 쪽에서 볼 수 있게 여는 단계입니다. near real-time은 검색 가시성에 짧은 지연이 있을 수 있다는 의미입니다. 사용자에게 저장 직후 검색 결과를 보여 줘야 한다면 해당 요청에서 refresh를 기다리는 옵션을 검토하되, 모든 쓰기에 강제 refresh를 넣는 것과 비용이 다릅니다.

사용자가 저장 직후 같은 문서를 확인해야 한다면 ID 기반 조회와 검색의 가시성 계약을 구분하거나 필요한 요청에 refresh 대기를 사용할 수 있습니다. 매 쓰기마다 강제 refresh를 하면 작은 세그먼트와 추가 비용이 늘어 색인·검색 성능에 영향을 줄 수 있습니다. 저는 어떤 화면에서 즉시 가시성이 필요한지 먼저 정하겠습니다.

refresh는 내구성을 위해 디스크에 모든 상태를 안전하게 기록하는 flush와 같은 의미가 아닙니다. 복제와 쓰기 확인도 별도로 봐야 합니다. 테스트는 색인 ACK 이후 검색 노출까지의 지연을 측정하고 대량 입력에서 refresh 정책 변경의 처리량·세그먼트 비용을 비교하겠습니다. 저장 성공, 검색 가시성, 장애 복구를 각각 다른 계약으로 다루는 것이 중요합니다.

## 득점 포인트

- 색인 ACK와 검색 가시성을 구분한다.
- 필요한 요청에만 대기 비용을 적용한다.
- refresh와 내구 기록을 혼동하지 않는다.

## 감점 포인트

- 색인 성공이면 모든 검색이 즉시 최신이라고 말한다.
- 매 문서 강제 refresh는 비용 없다고 말한다.
- refresh가 모든 디스크 내구성을 보장한다고 말한다.

## 더 파고들 거리

- refresh=wait_for와 즉시 강제 refresh는 어떤 차이가 있나요?
- 대량 색인 중 refresh 주기를 조정하면 어떤 사용자 지연을 받아들여야 하나요?
- ID 기반 get과 검색 API의 가시성은 어떻게 검증할까요?
