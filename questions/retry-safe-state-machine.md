# 업무 상태를 enum으로 저장하는 것만으로 동시 전이·재시도·불확정 외부 결과를 안전하게 만들 수 없는 이유는 무엇인가요?

## 구두 답변

`PENDING`, `RUNNING`, `DONE` 같은 enum은 현재 상태를 표현할 뿐, 어떤 요청이 어떤 조건에서 다음 상태로 갈 수 있는지까지 보장하지 않습니다. 두 요청이 동시에 `PENDING`을 읽고 각각 결제 승인이나 작업 실행을 시작하면, 마지막 저장이 이기는 방식으로는 중복 효과와 잘못된 역전이가 생길 수 있습니다. 상태 모델에는 허용 전이, 전이의 주체, 버전, 작업 ID를 함께 둬야 합니다.

예를 들어 `UPDATE orders SET state='CANCELLED', version=version+1 WHERE id=? AND state='PENDING' AND version=?`처럼 읽었을 때의 상태와 버전을 조건으로 갱신하면 한 요청만 전이에 성공합니다. 영향받은 행이 0이면 최신 상태를 다시 읽어 이미 완료됐는지, 다른 요청과 충돌했는지, 재시도 가능한지 판단합니다. 결제 승인과 취소가 동시에 들어올 때 단순히 마지막 시간을 기준으로 덮어쓰지 말고 업무 우선순위와 종료 상태 규칙을 정하겠습니다.

외부 호출은 `미실행`, `처리 중`, `성공`, `실패`, `결과 불확실`을 구분해야 할 수 있습니다. 결과 불확실은 재시도해도 되는 상태와 확인·대사가 필요한 상태가 다릅니다. 작업 의도와 외부 요청 ID를 저장하고, 응답 유실 뒤 같은 ID로 결과를 조회하거나 보상 흐름으로 넘기겠습니다. 운영자 도구도 직접 enum을 바꾸지 않고 동일한 전이 조건과 감사 기록을 사용해야 합니다.

검증은 정상 전이뿐 아니라 금지 전이, 동시 승인·취소, 워커 중단, 오래 멈춘 상태, 수동 복구를 재현합니다. 상태 수를 줄이는 것보다 서로 다른 복구 행동을 안전하게 구분하는 것이 우선입니다.

## 득점 포인트

- 상태 값과 허용 전이·버전·작업 ID를 구분한다.
- 조건부 갱신으로 동시 전이를 하나만 성공시키는 방법을 제시한다.
- 외부 결과 불확실 상태와 운영 복구를 모델에 포함한다.

## 감점 포인트

- enum을 만들면 상태 전이가 자동으로 안전하다고 말한다.
- 마지막 저장이 이기면 업무 순서도 안전하다고 말한다.
- 운영자가 불변식을 우회해 상태 값을 직접 바꿔도 된다고 말한다.

## 더 파고들 거리

- 상태 전이와 이벤트 발행을 어떤 원자적 경계로 연결하나요?
- 종료 상태를 다시 열어야 하는 업무는 어떤 별도 전이를 두나요?
- 상태 버전과 멱등 작업 ID의 역할은 어떻게 다른가요?
