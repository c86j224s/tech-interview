# 사용자별 지연을 보고 싶어 메트릭 라벨에 사용자 ID를 넣었습니다. 어떤 문제가 생기고 개별 요청은 어떻게 분석하나요?

## 구두 답변

라벨 조합마다 별도 time series가 만들어지는 시스템에서는 사용자 ID·주문 ID·원문 URL처럼 값이 계속 늘어나는 label이 카디널리티를 폭발시킬 수 있습니다. 서비스·경로·상태·오류 종류 같은 저카디널리티 라벨에 `user_id`를 곱하면 사용자 수와 다른 라벨 조합만큼 시계열이 만들어져 수집기 메모리, remote write, 인덱스와 대시보드 조회 비용이 증가합니다. 자유로운 오류 메시지는 같은 문제를 더 키웁니다.

요청 지연은 `service`, 템플릿화한 route, method, status class로 집계하고, 개별 사용자의 원인은 구조화 로그나 trace로 연결하겠습니다. 예를 들어 `/users/123/orders`를 `/users/{id}/orders`로 정규화하고, trace exemplar로 일부 메트릭 샘플에서 사건 분석으로 이동할 수 있습니다. 개인정보·식별자 노출은 비용 문제와 별도로 보안·보관 문제이므로 원문을 무조건 남기지 않습니다.

테넌트별 SLO(서비스 품질 목표)가 꼭 필요하면 상위 테넌트 집합, 별도 집계 시스템, 제한된 샘플링과 예산을 사용합니다. label을 모두 없애면 원인 분류가 사라지므로 질문에 필요한 구분은 남기되 조합 수의 상한과 신규 series(새로 만들어지는 시계열) 생성률을 배포 전 추정·배포 후 관찰하겠습니다. 히스토그램 bucket(지연 구간의 칸) 수도 라벨 조합마다 곱해진다는 점을 포함해 비용을 계산합니다. 개별 요청을 보고 싶다면 exemplar(메트릭 표본을 trace로 연결하는 참조)를 제한적으로 사용하겠습니다. 예를 들어 지연이 목표를 넘은 일부 요청만 trace로 연결하면 전체 사용자 ID를 시계열 라벨로 저장하지 않고도 원인을 따라갈 수 있습니다.

## 득점 포인트

- 라벨 조합 곱으로 시계열이 증가하는 원리를 설명한다.
- 메트릭·로그·trace의 개별 분석 역할을 분리한다.
- 정규화·상한·exemplar·개인정보를 함께 다룬다.

## 감점 포인트

- 라벨은 많을수록 관측성이 좋아진다고 말한다.
- 동적 URL과 자유 오류 문자열을 그대로 라벨로 사용한다.
- 모든 라벨을 삭제하면 카디널리티 문제가 완전히 해결된다고 말한다.

## 더 파고들 거리

- 히스토그램 bucket 수와 label 조합 수가 series 비용에 어떻게 곱해지나요?
- exemplar로 trace를 연결할 때 모든 요청이 아니라 어떤 샘플을 남길까요?
- 테넌트별 SLO를 제한된 집계와 별도 저장소로 관찰하려면 어떤 기준이 필요할까요?
