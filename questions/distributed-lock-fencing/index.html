분산 락에 만료 시간이 있으면 동시에 실행되는 일을 막을 수 있나요?

01

구두 답변

정의를 외우기보다, 원리와 조건을 연결해 설명해 보세요.

락 만료는 죽은 작업자가 자원을 영원히 잡는 문제를 줄이지만, 만료된 작업자가 다시 실행되는 것까지 막지는 않습니다. 긴 정지나 네트워크 지연 뒤 원래 작업자가 돌아오면 새 락 소유자와 동시에 쓰기를 할 수 있습니다. 락 서비스에서 소유권이 하나라는 것과 실제 저장소의 쓰기가 하나라는 것은 다릅니다.

예를 들어 첫 워커가 락을 얻고 파일 생성 작업 중 멈췄다고 하겠습니다. 락이 만료돼 두 번째 워커가 새 결과를 저장한 뒤, 첫 워커가 예전 결과를 덮을 수 있습니다. 이때 락을 얻을 때마다 증가하는 펜싱 토큰을 주고 저장하는 쪽이 이전 토큰의 쓰기를 거절하면 낡은 작업자를 막을 수 있습니다. 토큰을 워커가 확인하는 것만으로는 부족하고 실제 변경을 집행하는 계층이 검증해야 합니다.

저는 DB의 조건부 갱신이나 고유 제약으로 직접 보호할 수 있는 업무라면 분산 락을 먼저 추가하지 않겠습니다. 외부 시스템이 토큰 검증을 지원하지 않으면 락만으로 얻는 보장의 한계를 명시하고 중복 방지나 대사 경로를 설계해야 합니다. 테스트에서는 정상 동시 요청뿐 아니라 락 만료 뒤 멈췄던 워커를 재개시켜 보겠습니다. 갱신 주기를 늘려 문제를 숨기기보다 오래된 소유자가 돌아와도 데이터가 깨지지 않는지가 중요합니다.

02

득점 포인트

이해가 드러나는 지점을 확인해 보세요.

  • lease와 실제 실행을 구분한다. 만료된 워커가 살아날 수 있음을 설명한다.
  • 집행 지점의 펜싱을 설명한다. 저장 계층에서 낡은 토큰을 거절한다.
  • 단순한 대안을 비교한다. DB 조건부 변경과 락의 한계를 판단한다.
03

감점 포인트

놓치기 쉬운 조건과 오해를 짚어 보세요.

  • 만료되면 기존 워커가 자동 중단된다고 말한다. 프로세스 실행은 별개다.
  • 워커만 토큰을 확인하면 충분하다고 말한다. 확인 뒤 지연될 수 있다.
  • 타임아웃을 길게 하면 정확성이 해결된다고 말한다. 임의의 중단 가능성은 남는다.
04

더 파고들 거리

하나 더 질문하며 이해의 범위를 넓혀 보세요.

  • 펜싱 토큰이 재시작 후에도 단조 증가해야 하는 이유는 무엇인가요?
  • 여러 저장소에 쓰는 업무에서 토큰 검증 범위는 어떻게 정할까요?
  • 락 해제 시 다른 워커의 락을 지우지 않으려면 무엇을 비교해야 할까요?

득점·감점 포인트는 학습용 자기 점검 기준이며, 특정 회사의 실제 채점표가 아닙니다.
