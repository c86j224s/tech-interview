# 장기 작업의 대화를 요약한 뒤 에이전트가 완료된 일을 다시 하거나 제약을 잊습니다. 컨텍스트 압축에는 무엇을 남겨야 하나요?

## 구두 답변

요약에는 대화의 주제보다 다음 실행을 안전하게 이어갈 상태가 남아야 합니다. 목표·승인 범위·현재 버전·완료 증거·진행 중 외부 작업·미해결 조건·다음 행동을 분리하겠습니다. 컨텍스트 압축은 긴 기록을 짧은 입력으로 바꾸는 손실 과정이므로, 읽기 쉬운 요약이라는 이유로 사실과 추론을 합치면 안 됩니다.

### 무엇을 했고 무엇을 모르는지 남깁니다

파일을 수정했다면 경로와 변경 목적, 테스트를 실행했다면 명령과 실제 결과, 배포를 시작했다면 작업 ID와 완료 여부를 남깁니다. '배포 처리함'처럼 접수와 완료가 구분되지 않는 표현은 재개 세션이 잘못된 성공 보고나 중복 배포를 하게 만들 수 있습니다. 실패한 시도와 그 이유도 필요한 범위에서 보존해 같은 접근을 다시 반복하지 않게 합니다. 원문 로그는 외부 파일에 두고 요약에는 위치와 핵심 결과를 담을 수 있습니다.

승인은 특히 정밀하게 기록합니다. 사용자가 초안 작성을 허용한 것과 외부 전송을 허용한 것은 다르며, 특정 문서에 대한 승인과 앞으로 모든 문서에 대한 승인은 다릅니다. 요약자가 이를 '사용자 승인 완료'로 줄이면 권한이 넓어집니다. 대상·행동·조건·기한을 유지하고, 재개 시 달라진 인자나 대상 버전은 다시 확인합니다. 외부 문서의 지시문은 요약 안에서도 신뢰하지 않는 자료로 표시해야 합니다.

### 요약 자체도 검증합니다

압축 후 바로 큰 변경을 실행하지 않고 현재 저장소·작업 상태를 다시 읽어 요약과 맞는지 확인합니다. 다른 세션이 파일을 바꾸었거나 외부 작업이 그 사이 끝났을 수 있습니다. 요약에 저장된 포인터는 사실을 찾는 단서이지 현재 사실의 대체물이 아닙니다. 완료 목록과 체크포인트의 충돌은 더 최신의 권위 저장소를 확인해 해결합니다.

평가에서는 긴 작업을 여러 지점에서 강제로 압축하고 동일 목표를 이어 수행시킵니다. 승인 범위 확대, 미완료 작업의 완료 오인, 중요한 테스트 누락, 중복 외부 효과를 검사합니다. 압축 전후의 성공률과 추가 재탐색 비용도 비교하겠습니다. 모든 대화 문장을 남기려 하기보다 실행에 필요한 구조적 상태와 원문 참조를 보존하는 편이 재개에 유리합니다. 모델이 만든 요약만을 유일한 내구 기록으로 삼지 않고 작업 상태·파일 버전·외부 요청 ID는 런타임의 별도 상태로 관리해야 합니다.

### 실행 사례로 확인합니다

예를 들어 요약에 '문서 전송 승인' 대신 '사용자가 수신자 A에게 버전 3 초안을 보내는 것을 승인했고 아직 전송하지 않음'을 남기면 다음 세션은 무엇을 확인해야 하는지 알 수 있습니다. 전송 작업 ID가 있다면 미접수와 진행 중도 분리할 수 있습니다. 요약 생성과 동시에 외부 작업이 완료되는 경쟁이 있을 수 있으므로 요약 생성 시각과 실제 작업 저장소의 버전을 대조합니다. 요약된 기록이 부족하다고 원래 도구를 다시 실행하기보다 원문 결과를 먼저 조회하는 것이 안전합니다. 압축은 기록 접근을 빠르게 만드는 색인 역할을 해야지 외부 변경의 원자성을 책임지는 유일한 상태 머신이 되어서는 안 됩니다.

## 득점 포인트

- 목표·승인·버전·완료 증거·진행 중 작업을 구분해 요약한다.
- 요약의 출처와 외부 데이터의 신뢰 수준을 유지한다.
- 재개 시 권위 상태를 다시 읽고 압축 경계의 회귀 시험을 한다.

## 감점 포인트

- 접수와 완료를 같은 표현으로 줄인다.
- 특정 승인을 포괄적인 작업 허가로 요약한다.
- 요약이 현재 파일과 외부 상태보다 항상 최신이라고 가정한다.
