# 가끔만 발생하는 동시성 버그를 어떻게 재현하나요?

## 구두 답변

반복 실행만으로 우연히 재현되기를 기다리기보다, 문제가 생기는 읽기·쓰기 사이의 순서를 의도적으로 만들겠습니다. 동시성 오류는 연산 자체보다 두 연산이 만나는 구간에 있는 경우가 많습니다. 어떤 불변식이 깨졌는지 먼저 적는 것이 출발점입니다.

두 요청이 같은 재고를 읽고 차감하는 버그라면 두 스레드가 읽기를 끝낸 지점에서 배리어로 기다리게 한 뒤 함께 쓰도록 하겠습니다. 타임아웃 테스트도 실제 시간을 길게 기다리기보다 주입한 시계와 제어 가능한 완료 신호를 사용할 수 있습니다. 임의의 sleep은 환경이 바뀌면 순서를 보장하지 못해 테스트가 불안정해지기 쉽습니다.

레이스 탐지기는 메모리 접근 오류를 찾는 데 도움이 되지만, 모두 원자적 연산인 코드의 잘못된 업무 순서까지 전부 잡지는 못합니다. 저는 결과의 불변식과 금지된 상태 전이를 검증하고, 오류가 난 실행 순서와 랜덤 시드를 남기겠습니다. 결정적 테스트로 핵심 경로를 재현한 뒤 스트레스 테스트로 더 넓은 조합을 탐색하겠습니다. 테스트 통과를 모든 실행 순서의 증명으로 보지는 않되, 발견한 실패를 다시 놓치지 않는 회귀 테스트로 만드는 것이 중요합니다.

## 득점 포인트

- **실행 순서를 제어한다.** 배리어·시계·완료 신호를 사용한다.
- **논리 오류와 데이터 레이스를 구분한다.** 불변식을 직접 검사한다.
- **재현 정보를 남긴다.** 순서와 시드를 회귀 테스트로 만든다.

## 감점 포인트

- **sleep을 길게 넣으면 순서가 보장된다고 말한다.** 스케줄링에 따라 달라진다.
- **레이스 탐지기 통과면 모든 동시성이 안전하다고 말한다.** 논리적 경쟁은 남는다.
- **수천 번 통과를 완전한 증명으로 본다.** 실행 공간 일부만 탐색한다.

## 더 파고들 거리

- 선형화 가능한 자료구조를 이력 기반으로 검증하려면 무엇을 기록할까요?
- 실패 주입 위치를 너무 많이 노출하지 않고 테스트 가능하게 설계하려면 어떻게 할까요?
- 분산 테스트에서 네트워크 분할과 노드 정지를 어떻게 구분해 주입할까요?
