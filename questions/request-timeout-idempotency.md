# 요청이 타임아웃됐을 때 그대로 재시도해도 되나요?

## 구두 답변

타임아웃은 실패 확정이 아니라 **결과를 알 수 없는 상태, 즉 ambiguous outcome**일 수 있습니다. 서버가 실행하지 않았을 수도, 커밋한 뒤 응답만 유실됐을 수도 있습니다. 따라서 재시도 가능 여부는 네트워크 오류 종류만이 아니라 같은 논리 작업이 두 번 실행됐을 때의 효과로 판단해야 합니다.

멱등성은 반복 적용해도 의도한 상태 변화가 한 번 적용했을 때와 같은 성질입니다. 단순 상태 설정은 자연스럽게 멱등적일 수 있지만 잔액 차감이나 주문 생성은 요청 식별이 필요합니다. 클라이언트가 같은 작업의 재시도에 **동일한 idempotency key**를 보내고, 서버는 사용자·작업 범위와 요청 내용의 해시까지 묶어 잘못된 키 재사용을 거절할 수 있습니다.

핵심은 check-then-act 경쟁과 크래시 구간입니다. 키가 없음을 조회한 뒤 실행하는 구조는 동시에 두 요청이 통과합니다. 하나의 DB 안에서 끝나는 작업이라면 고유 제약으로 키를 선점하고 **멱등성 기록, 업무 변경, 결과 기록을 같은 트랜잭션으로 커밋**하는 방법이 있습니다. 먼저 처리 중 상태만 별도 커밋한다면 워커가 죽었을 때 영구 처리 중으로 남지 않게 소유권과 복구 절차가 필요합니다.

외부 결제나 메시지 발행은 로컬 DB 트랜잭션에 포함되지 않습니다. outbox는 업무 커밋과 발행 의도를 묶지만 전달은 중복될 수 있으므로 소비자의 inbox나 멱등 처리가 필요합니다. 외부 시스템이 지원하면 동일 작업 키를 전달하고, 그렇지 않으면 상태 조회와 대사·보상 절차가 필요합니다. **한 계층의 exactly-once라는 표현을 전체 업무 효과의 보장으로 확대하면 안 됩니다.**

재시도는 전체 데드라인 안에서 retry budget을 두고 exponential backoff와 jitter를 적용하겠습니다. 여러 계층이 독립 재시도하면 호출 수가 곱으로 늘 수 있어 책임 계층을 정해야 합니다. 커밋 직후 응답 유실, 동시 중복, 프로세스 종료를 주입해 효과가 한 번만 반영되는지 검증하고, 중복 적중률·장기 처리 중 요청·재시도 증폭을 관찰하겠습니다.

## 득점 포인트

- **불확정 결과를 정확히 다룬다.** 타임아웃을 업무 미실행으로 간주하지 않고 상태 확인과 중복 효과 방지를 연결한다.
- **원자적 경계를 구체적으로 정한다.** 키 등록·업무 변경·결과 기록과 크래시 시 복구 범위를 설명한다.
- **외부 효과의 한계를 인정한다.** outbox·inbox·외부 멱등성·대사가 각각 어떤 실패 구간을 처리하는지 구분한다.
- **정확성과 부하를 함께 검증한다.** 장애 주입으로 중복 효과를 점검하고 데드라인·retry budget·jitter로 증폭을 제한한다.

## 감점 포인트

- **“키를 Redis에 저장했으니 DB 변경도 정확히 한 번이다”라고 말한다.** 서로 다른 저장소 사이의 원자성 공백과 기록 유실을 해결해야 한다.
- **“outbox는 메시지를 정확히 한 번 전달한다”고 말한다.** 발행 성공 후 상태 기록 전에 죽으면 재전달될 수 있다.
- **“재시도할 때 새 키를 발급한다”고 말한다.** 서버가 같은 논리적 작업임을 식별할 수 없어진다.
- **“백오프만 넣으면 무제한 재시도해도 안전하다”고 말한다.** 총 시도량·시간 예산과 다층 재시도 증폭을 제한해야 한다.

## 더 파고들 거리

- 멱등성 기록의 보관 기간보다 늦게 도착한 재시도를 거절하려면 요청 만료와 API 계약을 어떻게 정할까요?
- 처리 중 레코드의 lease가 만료된 뒤 원래 워커가 돌아오면 fencing 없이 안전하게 재처리할 수 있을까요?
- 외부 API가 멱등성 키와 상태 조회를 모두 지원하지 않는다면 어떤 수준까지 보장할 수 있을까요?
- 취소된 요청이 이미 커밋됐다면 취소 응답과 보상 트랜잭션의 의미를 어떻게 구분해야 할까요?
