# TCP로 메시지를 두 번 보내면 받는 쪽에서도 두 번에 나눠 읽게 되나요?

## 구두 답변

아닙니다. TCP는 메시지 단위가 아니라 순서가 있는 바이트 스트림을 제공합니다. 보내는 쪽에서 `send()`를 두 번 호출했다는 경계가 받는 쪽의 `recv()` 호출에 그대로 전달되지는 않습니다.

예를 들어 논리적으로 100바이트짜리 메시지 두 개를 모두 보냈다고 하겠습니다. 받는 쪽은 두 메시지를 합친 200바이트를 한 번에 읽을 수도 있고, 첫 메시지의 일부인 60바이트만 먼저 읽을 수도 있습니다. 수신 버퍼 크기와 데이터 도착 시점 등에 따라 읽히는 크기가 달라집니다. 바이트 순서가 유지된다는 보장과 애플리케이션 메시지 경계가 유지된다는 보장은 다른 것입니다.

그래서 애플리케이션 프로토콜에서 메시지의 시작과 끝을 구분하는 규칙, 즉 프레이밍을 정해야 합니다. 고정 길이 메시지를 사용하거나, 구분자를 넣거나, 헤더에 본문 길이를 기록하는 방식이 있습니다. 길이 헤더를 사용한다면 수신 데이터를 버퍼에 쌓아 두고, 먼저 헤더가 완성됐는지 확인합니다. 헤더에서 길이를 읽은 뒤에는 그만큼의 본문이 모였는지 확인하고, 완성된 메시지만 처리합니다.

한 번 읽은 데이터에 메시지가 여러 개 들어 있다면 완성된 메시지를 반복해서 꺼내야 합니다. 반대로 마지막 메시지가 일부만 도착했다면 그 데이터는 버리지 않고 다음 수신까지 보관해야 합니다. 길이 필드도 그대로 믿으면 안 됩니다. 최대 메시지 크기를 제한하고, 헤더와 본문 길이를 계산할 때 정수 범위를 넘지 않는지 확인해야 합니다.

송신 쪽에서도 `send()`의 반환값을 확인해야 합니다. 호출이 요청한 데이터의 일부만 받아들일 수 있으므로 남은 부분을 이어서 보내야 합니다. 또 송신 성공은 보통 로컬 네트워크 스택이 데이터를 받아들였다는 뜻이지, 상대 애플리케이션이 메시지를 처리했다는 뜻은 아닙니다. 결국 TCP의 전송 보장 위에 메시지 경계와 처리 확인을 애플리케이션이 별도로 설계해야 합니다.

## 득점 포인트

- **바이트 순서와 메시지 경계를 구분한다.** TCP가 송신 호출 단위를 수신 호출 단위로 보존하지 않는다고 설명한다.
- **부분 수신과 여러 메시지의 동시 수신을 모두 다룬다.** 수신 버퍼에 데이터를 누적하고 완성된 메시지만 반복해서 꺼내는 처리 방식을 설명한다.
- **프레이밍 규칙을 구체적으로 제시한다.** 고정 길이, 구분자, 길이 헤더의 예를 들고 헤더 자체도 나뉘어 도착할 수 있음을 고려한다.
- **송신 완료의 의미를 구분한다.** 부분 송신을 처리해야 하며, 로컬 송신 성공이 상대 애플리케이션의 처리 성공은 아니라고 설명한다.

## 감점 포인트

- **“TCP는 신뢰성이 있으므로 메시지가 잘리거나 합쳐지지 않는다”고 말한다.** 신뢰성 있는 바이트 전달과 애플리케이션 메시지 경계 보존을 혼동한 설명이다.
- **“수신 버퍼를 충분히 크게 잡으면 해결된다”고 말한다.** 큰 버퍼도 데이터가 한 번에 모두 도착하도록 보장하지 않는다.
- **“`TCP_NODELAY`를 켜면 송신한 단위대로 받는다”고 설명한다.** Nagle 알고리즘 설정은 작은 데이터의 전송 시점에 영향을 주지만 메시지 경계를 만들어 주지는 않는다.
- **“길이 헤더에 적힌 크기만큼 바로 메모리를 할당하면 된다”고 말한다.** 길이 검증과 상한이 없으면 비정상 입력으로 과도한 메모리를 사용하거나 크기 계산이 잘못될 수 있다.

- 메시지 중간에서 연결이 끊기거나 상대가 본문을 아주 천천히 보낼 때, 버퍼와 타임아웃을 어떻게 관리해야 할까요?
