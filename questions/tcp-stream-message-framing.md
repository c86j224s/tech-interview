# TCP로 메시지를 두 번 보내면 받는 쪽에서도 두 번에 나눠 읽게 되나요?

## 구두 답변

아닙니다. TCP는 순서가 있는 바이트 스트림을 전달하지, 보내는 쪽의 메시지 경계를 전달하지는 않습니다. 100바이트짜리 메시지를 두 번 보냈어도 받는 쪽에서는 200바이트를 한 번에 읽거나, 처음 60바이트만 먼저 읽을 수 있습니다. **바이트 순서가 유지되는 것과 메시지가 한 덩어리로 읽히는 것은 다른 보장**입니다.

그래서 애플리케이션에서 메시지 경계를 정해야 합니다. 예를 들어 앞부분에 본문 길이를 넣는 프로토콜이라면, 수신 데이터를 모으면서 먼저 헤더가 다 왔는지 확인하겠습니다. 헤더에서 길이를 읽고 그만큼 본문이 모였을 때만 메시지를 처리합니다. 한 번에 여러 메시지가 왔다면 완성된 것을 계속 꺼내고, 마지막 조각은 다음 수신까지 보관합니다. 이런 파서는 헤더를 기다리는 상태와 본문을 기다리는 상태를 가진 증분 상태 머신으로 만들 수 있습니다.

여기서는 길이 필드를 그대로 믿으면 안 됩니다. 최대 메시지 크기를 넘으면 거절하고, 헤더 길이와 더할 때 정수 범위를 넘지 않는지 확인하겠습니다. 크기 자체는 정상이지만 본문을 아주 천천히 보내는 연결도 있으므로, 버퍼 상한과 메시지 완성 제한 시간을 함께 두겠습니다. 버퍼를 키우는 것만으로 해결하면 연결이 늘 때 메모리가 먼저 고갈될 수 있습니다.

송신도 마찬가지입니다. send가 일부만 받아들였다면 남은 위치를 기억했다가 이어서 보내야 합니다. 여러 작업이 같은 소켓에 메시지를 나눠 쓰면 조각이 섞일 수 있어 연결별 송신 큐로 순서를 관리하겠습니다. 상대가 느려서 큐가 쌓인다면 생산을 늦추거나 요청을 제한해야 합니다. 데이터를 버려도 되는지, 연결을 종료해도 되는지는 그 프로토콜의 계약에 따라 정하겠습니다.

테스트에서는 같은 메시지들을 매번 다른 위치에서 잘라 넣어도 결과가 같은지 확인하겠습니다. 헤더 중간이나 본문 중간에서 연결이 끊기는 경우도 포함합니다. 마지막으로 send 성공이나 TCP ACK는 상대 애플리케이션의 요청 처리 완료를 뜻하지 않습니다. **주문 저장 같은 작업이 끝났는지는 별도 응답으로 확인해야 한다는 점**까지 구분하겠습니다.

## 득점 포인트

- **순서와 경계를 구분한다.** 송신 횟수와 수신 횟수가 달라도 올바르게 동작해야 한다고 설명한다.
- **부분 입력을 처리하는 절차를 말한다.** 헤더·본문 누적과 완성 프레임 추출, 남은 조각 보관을 연결한다.
- **자원 제한의 이유와 행동을 설명한다.** 비정상 길이와 느린 연결에 대해 거절·시간 제한·백프레셔를 구분한다.
- **테스트할 불변식을 제시한다.** 같은 바이트 스트림은 분할 방식과 관계없이 같은 메시지로 해석돼야 함을 짚는다.

## 감점 포인트

- **“TCP가 신뢰성이 있으니 메시지가 나뉘지 않는다”고 말한다.** 신뢰성 있는 바이트 전달은 메시지 경계 보존이 아니다.
- **“TCP_NODELAY로 메시지 단위를 맞춘다”고 말한다.** 작은 데이터의 전송 시점과 프레이밍은 별개다.
- **“큰 버퍼와 한 번의 recv로 처리하면 된다”고 말한다.** 데이터 도착 시점과 EOF에 따라 일부만 읽힐 수 있다.
- **“ACK를 받았으니 요청 처리도 완료됐다”고 말한다.** 상대 TCP의 수신 확인은 애플리케이션 처리나 DB 커밋을 보장하지 않는다.

## 더 파고들 거리

- 링 버퍼나 scatter/gather I/O로 복사를 줄이면 파싱 결과와 수신 버퍼의 수명을 어떻게 관리해야 할까요?
- 구분자 방식과 길이 헤더 방식은 잘못된 입력 이후 복구와 바이너리 데이터 처리에서 어떻게 다를까요?
- 느린 수신자에게 보낼 데이터가 계속 쌓일 때 메시지 중요도에 따라 폐기 정책을 어떻게 나눌까요?
- 응답을 받기 전에 연결이 끊어졌다면 작업의 중복 실행 없이 어떻게 재시도할까요?
