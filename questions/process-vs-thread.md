# 프로세스와 스레드는 어떻게 다르고, 서버에서는 어떤 기준으로 선택하나요?

## 구두 답변

프로세스는 주소 공간과 자원을 나누는 경계이고, 스레드는 그 안에서 실행되는 흐름입니다. 같은 프로세스의 스레드는 힙과 전역 데이터를 공유하지만, 각자 스택과 레지스터 상태를 갖습니다. 서버에서는 어느 쪽이 더 가벼운지보다 **무엇을 함께 쓰고, 하나가 실패했을 때 어디까지 영향을 허용할지**를 먼저 보겠습니다.

예를 들어 여러 요청이 큰 메모리 캐시를 자주 읽고 수정한다면 스레드가 편리합니다. 프로세스 간 통신, 즉 IPC로 데이터를 주고받지 않고 바로 접근할 수 있기 때문입니다. 대신 갱신에는 동기화가 필요하고, 잘못된 포인터 접근 하나가 프로세스 전체를 손상시킬 수 있습니다. 개별 스택이 있다는 것도 접근을 격리한다는 뜻은 아니어서, 잘못 공유된 포인터로 다른 스레드의 스택을 건드릴 수 있습니다.

반대로 외부 라이브러리를 실행하는 작업자가 가끔 크래시하고, 그때 다른 요청은 계속 처리해야 한다면 프로세스로 나누겠습니다. 감독 프로세스가 실패한 작업자만 다시 띄우도록 만드는 식입니다. 다만 작업이 중간에 죽으면 이미 반영한 결과가 있는지 확인해야 하므로, 재시작만이 아니라 작업 재할당과 중복 처리 정책도 필요합니다. 메모리 오류를 격리하는 것과 업무를 안전하게 복구하는 것은 별개입니다.

성능 비교에서도 스레드가 무조건 유리하지는 않습니다. 여러 스레드가 각자 다른 카운터를 변경해도 같은 캐시 라인에 있으면 거짓 공유, 즉 false sharing 때문에 코어 사이에서 캐시를 계속 주고받을 수 있습니다. 스레드를 늘렸는데 처리량이 떨어진다면 락 대기부터 보고, 경합이 낮다면 캐시 미스와 데이터 배치를 확인하겠습니다. 프로세스 쪽은 IPC와 중복 캐시의 메모리 비용을 함께 재야 합니다.

결국 공유 상태가 많고 장애 범위를 감당할 수 있으면 스레드, 독립적인 실패와 재시작이 중요하면 프로세스를 우선 선택하겠습니다. 필요하면 여러 작업자 프로세스 안에 스레드 풀을 둘 수도 있습니다. **실제 요청 부하에서의 비용과 작업자를 강제로 종료했을 때의 복구 결과**를 보고 최종적으로 정하겠습니다.

## 득점 포인트

- **공유와 격리를 요구사항에 연결한다.** 메모리 캐시 공유와 작업자 크래시 격리에 각각 어떤 구조가 맞는지 설명한다.
- **재시작과 업무 복구를 구분한다.** 프로세스를 다시 띄우는 것만으로 중복·부분 처리 문제가 해결되지 않는다고 짚는다.
- **성능 문제의 확인 순서를 제시한다.** 스레드 확장 실패 시 락 경합과 캐시 비용을 구분해 조사한다.
- **선택을 실제 검증으로 마무리한다.** IPC·메모리 비용과 강제 종료 시 영향을 함께 비교한다.

## 감점 포인트

- **“스레드별 스택은 다른 스레드가 접근할 수 없다”고 말한다.** 스택의 논리적 소유와 주소 공간 격리를 혼동한 설명이다.
- **“프로세스가 죽으면 재시작만 하면 된다”고 말한다.** 진행 중 업무의 부분 반영과 재처리 정책이 필요하다.
- **“스레드는 통신 비용이 없다”고 말한다.** 동기화와 캐시 일관성에 따른 비용이 발생할 수 있다.
- **“프로세스로 나누면 자원 고갈도 막는다”고 말한다.** 별도 제한 없이 호스트나 공통 DB의 자원을 함께 고갈시킬 수 있다.
