# 공유 캐시를 빠르게 사용하는 서버와 실패한 작업자를 격리해야 하는 서버에서 프로세스와 스레드는 어떤 기준으로 선택하나요?

## 구두 답변

프로세스는 별도 주소 공간과 자원 경계를 제공하고, 스레드는 같은 프로세스 안에서 실행 흐름을 나눕니다. 같은 프로세스의 스레드는 힙·전역 데이터를 공유하지만 각자 stack·register 상태를 가지며, stack이 따로 있다는 사실은 주소 공간 격리를 뜻하지 않습니다. 선택 기준은 “무엇을 공유할지”와 “한 작업의 실패가 어디까지 영향을 줘도 되는지”입니다.

큰 메모리 캐시를 여러 요청 처리 흐름이 함께 사용하고 짧은 공유 연산을 수행한다면 스레드가 IPC와 캐시 복제를 줄여 편리할 수 있습니다. 대신 모든 접근이 같은 동기화 규칙을 따라야 하고, 잘못된 포인터나 데이터 경합이 프로세스 전체를 손상시킬 수 있습니다. 스레드를 늘려도 lock 경합(같은 잠금을 기다리는 시간)·false sharing(서로 다른 값을 바꾸지만 같은 캐시 묶음을 주고받는 현상)·캐시 일관성 비용이 생깁니다. 따라서 스레드 수가 많아졌다는 사실보다 공유 카운터와 잠금 대기 시간이 줄었는지를 측정하겠습니다.

신뢰하기 어려운 외부 라이브러리나 크래시가 요청 처리 전체를 중단시키면 안 되는 작업은 worker process로 격리하고 감독자가 재시작·재할당합니다. 그러나 재시작만으로 부분 반영·중복 반영이 사라지지 않으므로 작업 ID·멱등성·복구 상태가 필요합니다. 실제 부하에서 IPC(서로 다른 프로세스가 데이터를 주고받는 통신)·중복 메모리·스레드 경합을 재고, worker 강제 종료 뒤의 작업 결과와 자원 한계를 함께 검증해 선택하겠습니다. 프로세스를 나눠도 공통 DB나 호스트 메모리를 함께 고갈시키면 장애 격리가 완성되지 않습니다.

## 득점 포인트

- 공유 효율과 장애 격리를 선택 축으로 삼는다.
- 스레드 stack과 주소 공간 보호를 구분하고 동기화·false sharing을 넣는다.
- 프로세스 재시작과 작업 복구를 분리한다.

## 감점 포인트

- 스레드별 stack은 다른 스레드가 절대 접근할 수 없다고 말한다.
- 프로세스가 죽으면 재시작만으로 진행 중 작업이 안전해진다고 말한다.
- 스레드는 통신 비용이 전혀 없거나 프로세스 분리가 자원 고갈을 자동 방지한다고 말한다.

## 더 파고들 거리

- 공유 메모리의 lock owner가 죽었을 때 잠금 복구와 데이터 불변식 복구는 어떻게 다른가요?
- 프로세스 전환에서 주소 변환 캐시와 CPU cache 비용을 어떻게 측정할까요?
- false sharing과 실제 데이터 경합을 하드웨어 성능 카운터로 어떻게 구분할까요?
