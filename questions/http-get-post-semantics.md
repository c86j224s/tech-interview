# 검색과 등록 API의 HTTP 메서드를 정하려 합니다. GET과 POST의 의미는 어떻게 다르며, 민감한 값을 POST 본문에 넣는 것만으로 보호할 수 있나요?

## 구두 답변

GET과 POST의 선택은 본문 크기나 비밀번호 노출 여부만으로 정하지 않고, 서버 상태에 미치는 의미와 재시도·캐시 계약으로 판단해야 합니다. GET은 리소스 표현을 조회하는 안전한 메서드이며 멱등적입니다. 안전하다는 말은 서버에 로그나 통계가 전혀 남지 않는다는 뜻이 아니라, 요청을 반복해도 애플리케이션의 의도된 상태 변경이 없어야 한다는 뜻입니다. POST는 대상 리소스가 본문을 처리하도록 요청하는 메서드라서 등록·명령 실행처럼 상태를 만들거나 바꾸는 작업에 알맞습니다.

GET의 질의 값은 보통 URL에 들어가므로 브라우저 기록, 접근 로그, 분석 도구, Referer 같은 경로에 남기 쉽고 길이와 인코딩 제약도 있습니다. 반대로 POST 본문은 URL보다 덜 노출될 수 있지만 비밀이 되는 것은 아닙니다. HTTPS가 없으면 네트워크에서 본문을 볼 수 있고, 서버 로그나 클라이언트 디버거에도 남을 수 있으므로 인증서·전송 암호화·로그 마스킹이 별도로 필요합니다.

GET 응답은 URL을 기준으로 캐시되기 쉬워서 조회에 사용하면 성능과 오프라인 재사용의 이점을 얻을 수 있습니다. 그렇지만 캐시 가능 여부와 실제 재사용은 Cache-Control, Vary, 인증정보 같은 조건으로 결정되며 POST라고 자동으로 안전하거나 GET이라고 항상 캐시되는 것은 아닙니다. 상태 변경을 GET에 넣으면 링크 미리보기·크롤러·재시도·캐시가 의도치 않게 작업을 실행할 수 있습니다.

따라서 조회는 GET, 생성·명령은 POST로 두고, 상태 변경 요청에는 CSRF 방어와 적절한 인증을 적용하겠습니다. 네트워크 오류 뒤 재시도할 수 있는 POST라면 idempotency key와 중복 처리 규칙을 함께 설계하겠습니다.

## 득점 포인트

- safe와 idempotent를 상태 변경 금지 및 반복 결과의 의미로 구분한다.
- POST 본문이 HTTPS 없이 비밀을 보장하지 않는다고 설명한다.
- 메서드 의미와 캐시·재시도 계약을 함께 선택한다.

## 감점 포인트

- POST 본문이면 암호화되어 안전하다고 단정한다.
- GET은 길이만 작으면 상태 변경에도 써도 된다고 말한다.
- GET은 항상 캐시되고 POST는 절대 캐시되지 않는다고 말한다.
