# 구두 면접 질답 스타일

## 목적과 주제 선정

스스로 CS 지식을 공부하고, 알고 있던 내용을 다시 떠올리며, 구두 기술 면접을 연습하기 위한 콘텐츠입니다. 향후 정적 웹 페이지로 공개할 가능성을 고려합니다.

경력과 경험은 질문의 범위와 깊이를 고르는 데만 사용합니다. 공개 콘텐츠는 경력 맥락을 숨긴 일반적인 기술 질문과 답변으로 작성합니다. 회사명, 프로젝트명, 내부 구조, 실제 성과 수치, 개인의 담당 역할이나 경력 원문은 포함하지 않습니다. 단순히 고유명사를 익명화하는 것이 아니라, 해당 경험 없이도 독립적으로 이해할 수 있는 기술 질문으로 재구성합니다.

일반적인 가상 사례는 사용할 수 있지만 실제 경험처럼 표현하지 않습니다. 개인 경험을 답변에 연결하는 항목은 두지 않습니다.

## 질문 하나의 구성

### 카테고리

질문의 중심 주제를 표시합니다. 동시성, 운영체제, 네트워크, 데이터베이스, 분산 시스템, 언어·런타임, 설계, 성능 등을 후보로 삼되 최종 분류 체계는 예시를 다듬은 뒤 정합니다.

### 질문

면접관이 실제로 말할 법한 자연스러운 한두 문장으로 작성합니다. 한 질문에 여러 개념을 지나치게 몰아넣지 않습니다. 특정 경력이나 프로젝트를 전제하지 않습니다.

### 구두 답변

소리 내어 말했을 때 약 1~3분이 되는 분량으로 작성합니다. 시간은 낭독 속도에 따라 달라지므로 실제로 읽으며 조정합니다.

불릿이 아닌 자연스러운 문단으로 작성합니다. 질문에 대한 결론부터 말하고, 이유와 동작 원리를 설명한 뒤 필요한 경우 일반적인 예시와 선택 기준, 한계를 덧붙입니다. 정의만 나열하거나 모든 관련 지식을 담으려 하지 않습니다. 모든 답변을 똑같은 문장 틀에 억지로 맞추지도 않습니다.

면접 자리에서 말할 수 있는 정중한 구어체를 사용합니다. 짧게 말하기 위해 정확성에 필요한 전제나 조건을 생략하지 않습니다.

15년차 개발자의 기술적 판단이 드러나는 깊이를 기준으로 합니다. 자연스러운 구어체를 전문 용어를 제거하는 방식으로 해석하지 않습니다. 핵심 기술 용어는 정확하게 사용하고, 필요하면 한국어 설명과 원문을 첫 등장에 함께 적습니다. 단, 용어 개수 자체를 깊이의 척도로 삼지 않습니다.

질문에 직접 답한 뒤 핵심 메커니즘 한두 가지를 파고듭니다. 그 보장이 성립하는 조건, 실패할 수 있는 실행 순서, 대안의 트레이드오프와 선택 기준을 설명합니다. 주제에 맞는 경우 어떤 로그·프로파일·지표·테스트로 판단을 검증할지도 답변 안에 담습니다. 이를 똑같은 문장 틀로 반복하거나, 모든 심화 내용을 한 답변에 몰아넣지는 않습니다.

깊이를 높이기 위해 답변을 긴 강의로 늘리지 않습니다. 1~3분 안에서 핵심 인과관계를 전달하고, 더 넓은 논점은 ‘더 파고들 거리’로 분리합니다. 분량 안내는 목표이며 낭독 실측으로 확인한 시간이 아닙니다. 공개 콘텐츠에는 개인의 연차나 경력 사례를 서술하지 않고 판단의 깊이로 숙련도를 드러냅니다.

### 득점 포인트

불릿으로 작성합니다. 답변에서 이해를 드러내는 핵심 구분, 원리, 조건, 판단 기준을 구체적으로 짚습니다. 용어를 언급했는지보다 메커니즘과 실패 조건, 트레이드오프, 진단 근거를 연결했는지 평가합니다. 단순한 키워드 목록이나 추상적인 칭찬으로 작성하지 않습니다.

### 감점 포인트

불릿으로 작성합니다. 흔한 오개념, 잘못된 인과관계, 조건 없는 단정 등을 구체적으로 짚습니다. 무엇이 잘못됐는지와 필요한 조건 또는 올바른 구분을 함께 설명합니다. 심화 내용을 전부 언급하지 않았다는 이유만으로 감점 항목을 만들지 않습니다.

득점·감점 포인트는 학습과 자기 점검을 위한 기준이며, 특정 회사의 실제 면접 채점표가 아닙니다.

### 더 파고들 거리

불릿으로 작성합니다. 기본 답변에서 이어지는 꼬리 질문, 심화 학습 질문, 검증해 볼 상황을 제시합니다. 단순한 주제명보다 무엇을 더 설명하거나 비교해야 하는지 드러나는 질문으로 작성합니다.

이 단계에서는 심화 질문마다 긴 답변을 붙이지 않습니다. 나중에 독립된 질답으로 작성된 항목은 연관 질문으로 연결할 수 있습니다. 연관 질문 탐색 기능은 유지하되 아직 존재하지 않는 항목에 링크를 만들지 않습니다.

## 파일 저장 형식

작성한 문항은 대화에만 남기지 않고 `questions/` 폴더에 문항 하나당 Markdown 파일 하나로 저장합니다. 카테고리별로 폴더를 나누지 않고 파일의 메타데이터로 분류합니다. 파일명은 내용을 설명하는 영문 소문자와 하이픈으로 작성합니다.

파일 맨 위에는 다음과 같은 YAML 프런트매터를 넣습니다. 목록, 검색, 카테고리 필터와 연관 질문 연결에 사용할 구조화된 정보입니다.

```yaml
---
id: async-api-and-blocking
title: "비동기 API를 사용하면 호출한 스레드는 블로킹되지 않나요?"
category: 동시성
tags:
  - 비동기
  - 블로킹
  - 스레드
  - 이벤트 루프
  - future
related: []
---
```

- `id`는 문항의 고유 식별자이며 파일명에서 `.md`를 뺀 값과 일치시킵니다. 제목이나 분류가 바뀌더라도 식별자는 유지합니다.
- `title`은 화면과 검색 결과에 표시할 질문 전문입니다. 본문의 최상위 제목과 동일하게 작성합니다.
- `category`는 질문의 중심이 되는 대분류 하나입니다.
- `tags`는 개념, 기술, 언어 등 세부 주제를 나타내는 문자열 목록입니다. 기존 태그를 먼저 확인해 같은 뜻의 태그가 중복되지 않도록 합니다.
- `related`는 연관 문항의 `id` 목록입니다. 실제로 저장된 문항만 연결하고, 아직 연결할 문항이 없다면 빈 목록으로 둡니다.

본문은 질문을 최상위 제목으로 적고, `구두 답변`, `득점 포인트`, `감점 포인트`, `더 파고들 거리`를 순서대로 두 번째 수준 제목으로 작성합니다. 구두 답변은 문단으로, 나머지 세 부분은 불릿으로 작성합니다. 질문 데이터만 수집할 수 있도록 `questions/`에는 문항 파일만 두고 작성 지침은 `docs/`에 둡니다.

## 인덱스와 중복 질문 확인

루트의 `question-index.json`에 전체 문항을 JSON 배열로 기록합니다. 각 항목에는 `id`와 `question` 두 필드만 넣고 `id` 오름차순으로 정렬합니다. `question`은 문항 파일의 `title` 및 최상위 제목과 정확히 일치시킵니다. 답변, 카테고리, 태그는 문항 파일에서 관리하며 인덱스에 복제하지 않습니다.

새 문항을 작성하기 전에 인덱스 전체를 확인합니다. 같은 ID나 같은 질문뿐 아니라, 표현만 다르고 묻는 핵심과 답변 범위가 같은 문항도 중복 후보로 봅니다. 후보가 있으면 해당 문항의 본문까지 읽고, 기존 문항을 보완할지 별도 질문으로 구분할지 판단합니다. 같은 기술을 다루더라도 확인하는 개념이나 판단 기준이 다르면 별도 문항으로 작성할 수 있습니다.

문항을 추가하거나 삭제할 때, 또는 질문 제목을 수정할 때는 인덱스도 같은 작업에서 갱신합니다. 저장을 마친 뒤 ID와 질문의 중복 여부, `questions/*.md`와 인덱스의 일대일 대응, 질문 제목의 일치를 확인합니다. 인덱스 자체가 의미상 중복을 자동으로 판별하지는 않으므로 작성 전 내용 비교를 생략하지 않습니다.

## 진행 순서와 확인 기준

첫 비동기·블로킹 예시의 스타일에 동의한 상태입니다. 이 예시를 기준으로 다른 주제에서도 말투, 분량, 기술적 깊이가 잘 맞는지 확인합니다. 작성한 문항은 위 형식으로 바로 저장하며, 대량 확장과 사이트 구현은 별도 요청을 받은 뒤 진행합니다.

예시 검토에서는 답변이 질문에 바로 답하는지, 1~3분 안에 자연스럽게 설명할 수 있는지, 기술적으로 정확한지, 개인 경력 맥락 없이 이해되는지 확인합니다. 득점·감점 포인트가 자기 점검에 도움이 되는지, 더 파고들 거리가 다음 학습으로 이어지는지도 살펴봅니다.

정적 사이트는 `questions/`와 인덱스를 읽어 빌드하며, 콘텐츠 검증을 통과해야 페이지를 생성합니다. 문항 수정 후 `npm run build`와 `npm test`로 검증합니다. 사이트 실행과 배포 절차는 README를 따릅니다. 경력 원본은 저장소나 공개 배포물에 포함하지 않습니다.
